## 1. 职责边界（契约 §1）

```
小程序 ──→ CloudBase 云函数 community ──→ 本服务(code/bridge/api.py) ──→ PostgreSQL
   微信身份/问卷/选择                     服务端到服务端，Bearer 令牌      只本机回环
```

**前端不直连 PostgreSQL，也不持有数据库密码。** 本服务只监听 `127.0.0.1`，
所有端点（除健康检查）都要 Bearer 令牌。CloudBase 是原始答案与授权事件的事实来源；
本库是标准化分析与匹配结果的来源——**禁止两边同时不受约束地覆盖同一原始答案**。

## 2. 交换包摄入的八条规则

`code/bridge/exchange.py` 把这八条做成可测试的硬规则：

| 规则 | 内容 | 违反时的返回 |
|---|---|---|
| **R1** | 交换包不得含身份标识（memberKey/openid/appid/手机号/证件号/密钥…），**任意层级深度扫描** | `INVALID_ARGUMENT`，整包拒绝 |
| **R2** | `sourceSystem + personId` 唯一绑定本库随机 `person_id`，后者不含任何微信标识 | — |
| **R3** | 同一 `(来源, 事件号)` 重复投递：载荷一致 → 返回原结果；不一致 → `CONFLICT` | 幂等 |
| **R4** | `aggregateVersion` 不得倒退，迟到包直接拒绝 | `CONFLICT` |
| **R5** | 墓碑优先：已删除的人的迟到事件一律拒绝 | `PROFILE_DELETING` |
| **R6** | 撤回 `personal_analysis` 后不得再写入分析产物 | `CONSENT_REQUIRED` |
| **R7** | `skillClaims` 落库为 `verify_status=V1`、`evidence_id=NULL`、**不写置信概率** | 库层 CHECK 强制 |
| **R8** | 事实一律先原样写入 `answer`；只有 `crosswalk` 登记了映射的才投影到规范表；未映射的**计数上报**，绝不静默丢弃 | — |

R1 与 R8 是这轮最值得强调的两条：

- **R1 是"整包拒绝"而不是"丢弃字段后继续"**。丢弃字段会让对方以为投递成功，
  而实际上身份关联已经丢失。拒绝才能让对方修正。
- **R8 是不臆造映射**。契约 §7 明确"源码示例中的 D2/D3、F02、V1/V2/V3 等编码并未提供
  完整字典，因此本包没有臆造映射"。我们的做法一致：`crosswalk` 表默认是空的，
  未映射时自述技能进通用 `assertion` 表并计入 `unmappedSkillClaims` 上报，
  等对方的正式字典到位后再逐条审阅（`review_status`：pending → reviewed → rejected）。

## 3. 幂等与按人串行（契约 §7.1）

- **幂等键 = (来源, 对方事件号)**。这里踩过一个坑：最初把对方的 `eventId` 当全局主键，
  结果两个来源复用同一编号时被 `ON CONFLICT DO NOTHING` **静默吞掉**——
  表现为"事件没入账但身份版本已推进"，是最难查的一类错误。
- **按人按版本升序交付**。消费时取该人该方向**最小**的未交付版本，
  让新事件等待旧事件，而不是反过来越过它。同批次内同一人只处理一条。
- **租约 + 退避 + 死信**：`lease_until` 到期可被其他消费者接管（不能靠 status 永久锁死）；
  失败按退避重试，超过 5 次进 `dead` 并保留 `last_error`。

## 4. 撤回与删除（契约 §5、§8）

| 动作 | 效果 |
|---|---|
| `personal_analysis=false` | 人才状态置 `restricted`；`getMyTalentMatches` 返回 `CONSENT_REQUIRED`，**不再返回任何派生画像** |
| 停用成员 | 可撤回、可删除；**不得新授予** |
| `requestTalentDeletion` | 受理后置 `deleting`，阻断新分析与同步；**受理 ≠ 完成** |
| 删除完成 | 必须有 `downstream_confirmed=true`，否则 `completedAt` 保持 null（不能先显示完成再等下游） |
| 墓碑 | 删除后，`deleted_through_version` 以下的所有迟到写入被 `guard_tombstone` 触发器拦住 |

## 5. 岗位投影与匹配（契约 §7.2）

**岗位投影**（`projection.export_jobs`）：

- 要求拆成 `must / preferred / unclear` 三态 + `requirementLogic`（AND/OR）；
  映射不到概念的要求进 `unclear`，**不臆断**
- `salary` 带 `currency / period / basis / sourceRef`，`basis` 区分
  `employer_disclosed`（本库来自 JD 原文）与 `not_disclosed`
- 只返回 `open` 且未过截止日的岗位；带 `sourceVersion` 供下游校验
- 分页基于 `(recordedAt, jobId)` 游标，**每页硬上限 20**

**匹配结果**：

- 分 `met / gap / unknown` 三态。**`unknown` 不是不合格**：
  要求没映射到概念（`requirement_not_mapped_to_concept`）、
  或该人没有有效观测窗口（`no_observation_window`）都归入 `unknown`。
  这条直接落实了我们既有的观测期纪律——**"没记录"不等于"不具备"**。
- 带 `coverage / profileVersion / jobSourceVersion / ruleVersion`，
  下游据此判断解释是否对应当前事实；过期版本必须丢弃或重算
- `rankingScore` 是排序分，**不是录用概率**

## 6. API 端点

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/v1/health` | 健康检查（免令牌） |
| POST | `/v1/exchange` | 摄入交换包（幂等） |
| GET | `/v1/jobs?limit=&cursor=&family=` | 岗位投影 |
| GET | `/v1/persons/{personId}/matches?sourceSystem=` | 匹配结果（需分析授权） |
| POST | `/v1/persons/{personId}/consent` | 授权/撤回 |
| POST | `/v1/persons/{personId}/deletion` | 发起删除 |
| GET | `/v1/persons/{personId}/deletion/{requestId}` | 删除状态 |
| POST | `/v1/outbox/drain` | 消费待投递事件（服务身份） |

统一外壳 `{ok, data}` / `{ok:false, code, message}`；错误码沿用契约新增的定义。

启动：
```powershell
$env:MEDTALENT_BRIDGE_TOKEN = "<强随机串>"     # 不设则随机生成并打印（仅开发）
python code\bridge\api.py --port 8097
```

## 7. 这轮抓到的 4 个问题（都是真库才暴露）

| # | 问题 | 教训 |
|---|---|---|
| 1 | `sync_event.event_id` 用对方事件号当**全局主键** → 跨来源复用被静默吞掉 | **对方系统的 id 一律不当全局主键**；本地生成稳定 id + `UNIQUE(来源, 外部id)` |
| 2 | `crosswalk.crosswalk_id` 固定值 → 跨轮次 PK 冲突被 `DO NOTHING` 吞掉 | 同上 |
| 3 | `talent_deletion_request.request_id` 当全局主键 → 同上（契约本来就写的是 personId+requestId 唯一） | 同上 |
| 4 | `sync_event` 唯一约束漏了 `direction` → 入向与出向的同版本同类型事件互相顶掉 | 唯一约束要覆盖**全部**区分维度 |

另外修正了两个 outbox 逻辑错误：`claim` 取的是**最大**待处理版本（应按升序取最小）；
`consent_change` 未校验「不得携带画像载荷」。

> 这四个问题全属同一类：**把外部系统的标识符当成自己系统的主键**。
> 契约里两处都明说了唯一性是"某范围内"的（personId+requestId、按其系统内唯一），
> 实现时必须落成对应的局部唯一约束。
