# 15 · 视觉与交互设计评审（数据密集型界面）

- 评审对象：`code/demo/portal.py` 直出的只读数据门户（端口 8082，21 个页面）
- 评审方式：把服务起在 **8085**（不占用 8082/8083），用 Chrome 无头逐页截图（1600×1200），逐张看图判断；改完再逐页重截对比
- 约束：**零 JS、零 CDN**，全部交互靠原生 HTML（`<details>`、GET 表单、`position:sticky`）；图表是服务端内联 SVG；只改 `code/demo/portal.py`
- 改动范围：`CSS` 常量（约 150 行 → 约 180 行）+ 约 25 行 markup（`page()` 外壳、`render_rows()`、6 处调用点）

> 一句话结论：**信息架构和密度基本是对的，坏在三个具体的地方**——一个真实的布局故障（按钮被撑成一列）、详情页丢失位置指示、以及三处不达 WCAG AA 的灰阶文字。这三类都改掉了。

## 1. 依据

以下 5 条是本轮所有判断的标尺。每条都给出处；**"我读到了什么"一栏只写实际读到的内容**，读不到正文的列在第 1.6 节。

### 1.1 数据墨水比（data-ink）与 chartjunk

> 一像素的墨水如果只用来重复信息或装饰，就该删掉；图上的每一点非数据墨水都要有理由。

出处：Edward Tufte, *The Visual Display of Quantitative Information*（<https://www.edwardtufte.com/tufte/books_vdqi>）；讨论见 VisGuides <https://visguides.org/t/data-ink-ratio-principle-how-to-use-it/72>。

**落在本项目**：KPI 卡片里那行 11px 的浅灰说明（"共有 17 个视图""88 个触发器"）是**信息**不是装饰，所以不该删——但它用了对比度只有 3.04:1 的 `#8c959f`，等于把墨水淡到看不清，是最坏的组合（既不省墨水，又没读到）。反过来，`/talent` 里那一整块约 200px 高的空白按钮容器，才是真正的 chartjunk：它不承载任何信息。

### 1.2 先总览、再缩放过滤、最后按需细节

> "Overview first, zoom and filter, then details-on-demand." —— Shneiderman 的 Visual Information Seeking Mantra

出处：B. Shneiderman, *The Eyes Have It: A Task by Data Type Taxonomy for Information Visualizations*, 1996（<https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf>，PDF 本工具抓不到正文，见 1.6）。

**落在本项目**：门户的"总览 → 表详情 → 实体页"三级跳就是这个结构，方向是对的；**但缺了"你现在在哪一层"的指示**——13 个顶级导航项表达不了层级，`/talent/per_mock_0001` 这种页面上没有任何面包屑，且一个导航项都不高亮。这是本轮最值得修的一处。

### 1.3 表格设计：可比较、可扫描、表头带 scope、数字右对齐

出处：GOV.UK Design System · Table（<https://design-system.service.gov.uk/components/table/>）。我读到的原文要点：

- "Use the table component to make information easier to compare and scan for users."（表格的职责是**比较与扫描**）
- "Use the `<caption>` element to describe a table in the same way you would use a heading."（表要像标题一样被描述）
- "Use the `scope` attribute to help users of assistive technology distinguish between row and column headers."（表头要带 `scope`）
- macro 选项里有 `format`："Specify format of a cell. Currently we only use **'numeric'**."（数字单元格是一种格式，不是普通文本）
- "Never use the table component to layout content on a page."（表格不能拿来排版）

**落在本项目**：结果表由 `render_rows()` 统一产出，改前是 `<table><tr><th>…` —— **没有 `<thead>`、没有 `scope`**，辅助技术无从判断某一列是什么；数字列靠调用方传 `n_right`，而 `/tree` 的时点对比表没传，于是"节点数/岗位数"按左对齐排。

### 1.4 对比度：正文 4.5:1（中文同标准），图表等非文本 3:1

出处：W3C WAI, *Understanding SC 1.4.3 Contrast (Minimum)*（<https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html>）。我读到的原文要点：

- "The visual presentation of text … has a contrast ratio of at least **4.5:1**"；"Large-scale text … at least **3:1**"。
- 大字的定义里**明确包含 CJK**："with at least 18 point or 14 point bold or font size that would yield equivalent size for **Chinese, Japanese and Korean (CJK)** fonts"。
- 计算比例"should not be rounded (e.g. 4.499:1 would not meet the 4.5:1 threshold)"。
- 图表这类信息另有 SC 1.4.11（Non-Text Contrast，3:1）。

**落在本项目**：`#8c959f` 在 `#fff` 上是 **3.04:1**，只够"大字/非文本"线；它却被用在 11px 的 KPI 说明行与 11.5px 的分组头上。`#b1b8bf`（NULL 占位）是 **2.00:1**，正文里连大字线都不到。

### 1.5 中文排版：中西医混排的行距/字距是需要显式决定的问题

出处：W3C《中文排版需求》(clreq)（<https://www.w3.org/TR/clreq/>）；其中"中西文混排时的行距"专门开了一个议题 <https://github.com/w3c/clreq/issues/731>。

（我只从检索结果确认了该议题存在，未读到规范正文，见 1.6。）

**落在本项目**：正文 `font:14px/1.6`、表格 `13px`、行高 1.6，对中文是够的；真正的问题不在行高，而在**表格里中文列不换行**（`.tablewin{white-space:nowrap}`）。这是有意的取舍——"一行一条记录"才能横向比较，宽表靠横向滚动 + 表头吸顶 + 首列吸左来读。本轮保留了这个取舍，只把**吸顶那条被浏览器吃掉的表头下边框**补回来（见 3.6）。

## 2. 逐页审查发现（按严重度排序）

严重度定义：**S1** = 直接妨碍完成任务或页面明显坏掉；**S2** = 读得下去但持续消耗注意力/不符合无障碍底线；**S3** = 观感与一致性问题。

### S1-1 `/talent`：预设字段按钮被撑成一列，筛选卡片凭空高 200px

- 现象：`筛选/应用`、`重置` 被挤到一张约 630×260px 的空白框**底部**，中间全是空白；`精简 推荐 教育 能力 成果 匹配 全部` 七个按钮竖着排（截图 [`before-talent.png`](screenshots/before-talent.png)，空白框在 y≈530–670 之间）。
- 原因：那 7 个按钮放在 `<div style="flex:1 1 auto;text-align:right">` 里，命中全局规则 `button{width:100%}`，于是每个按钮各占一整行；外层 `.row{align-items:flex-end}` 又把两个主按钮压到这一行的底部。
- 为什么是问题：**这不是"按钮太窄"，是把整屏高度浪费掉了**。改前 1200px 高的视口里，人才库里**一行人才记录都看不到**——打开"人才库"第一眼看到的是空白和按钮。

### S1-2 详情页全部丢失位置指示（6 个路由）

- 现象：`/t/<表>`、`/e/<表>`、`/talent/<id>`、`/occupation/<id>`、`/match`、`/analyze/<id>` 上，**13 个导航项没有一个高亮**，也没有面包屑（截图 [`before-table.png`](screenshots/before-table.png) 顶部导航条是全灰的）。
- 原因：`page()` 用 `title == 导航标签` 判断高亮，而这些页面的 h1 是 `job_posting`、`per_mock_0001`、`医学科学联络官`、`匹配 · 按人才`。
- 为什么是问题：13 个顶级导航本身就是重载的，唯一的"我在哪"信号就是那根蓝色下划线；它一消失，用户只能靠浏览器回退键。这正是 §1.2 里"总览→细节"结构的断点。

### S2-1 `/occupation/<id>`、`/talent/<id>`、`/e/<表>`：字段表是单列，宽屏右半页全空

- 现象：`字段`/`基本信息` 用 `200px + 1fr` 的 key→value 单列铺满整宽，值都很短（`active`、`F02`、`1.0.0`），右半边几百像素全空。`/occupation/OCC-F02-01-01` 有 **25 个字段 = 25 行**，`/talent/per_mock_0001` 有 17 个字段。
- 为什么是问题：一屏本可以放下的信息被推到屏外（`能力要求`、`观测窗口` 两张表改前都在首屏之下），用户要多滚一轮才看到"这页真正要看的东西"。

### S2-2 三处文字不达 WCAG AA 对比度

| 位置 | 字号 | 改前 | 比例 | 结论 |
| --- | --- | --- | --- | --- |
| `.metric .d`（KPI 说明行，如"共有 17 个视图"） | 11px | `#8c959f` on `#fff` | **3.04:1** | 低于正文线 4.5:1 |
| `.colgroup`（字段分组头，如"基本信息/教育/经历"） | 11.5px | `#8c959f` on `#fff` | **3.04:1** | 同上 |
| `.nul`（NULL 占位） | 13px | `#b1b8bf` on `#fff` | **2.00:1** | 连大字线 3:1 都不到 |

- 为什么是问题：这条最"隐形"——页面不至于坏，但对低视力用户等于没有。而且 `.metric .d` 承载的是**口径说明**（"88 个触发器"），恰恰是这个门户最想让人读到的东西（§1.1）。

### S2-3 空状态没有样式，看起来像页面坏了

- 现象：`/match` 的 `缺口 → 补充路径`、`当前：`、`各岗位族的匹配构成` 三块，改前是孤零零一行 `<p class="muted">没有识别到缺口。</p>`，卡片下半截全白（[`before-match.png`](screenshots/before-match.png)）。
- 为什么是问题：库里 0 行是**事实**，甚至是结论（`gap_analysis` 表本来就没填）。用"一片空白"表达事实，读者第一反应是"是不是没加载出来"。

### S2-4 结果表没有 `<thead>` / `scope`，表头下边框被 collapse 吃掉

- 现象：`render_rows()` 输出 `<table><tr><th>…`。实测（`screenshots/before-sticky-header.png`）：滚动容器内表头**能吸顶**（这点改前就是好的），但表头与数据行之间**那条分界线只剩 1px 残线**——`border-collapse:collapse` 下 sticky 表头的边框会被吃掉。
- 为什么是问题：吸顶能用不代表没毛病：分界线缺失让"表头"和"第一行数据"粘在一起；没有 `scope` 则屏幕阅读器读不出列含义（§1.3）。

### S2-5 `/tree` 时点对比表：数字列没有右对齐

- 现象："节点数 / 岗位数"两列左对齐（[`before-tree.png`](screenshots/before-tree.png) 的时点对比卡片）。
- 为什么是问题：`render_rows()` 明明有 `n_right` 参数（右对齐 + `tabular-nums`），调用处没传。数字左对齐时位数参差，比大小要靠眼睛逐位对（§1.3 的 numeric 格式）。

### S3-1 导航 13 项 + 品牌，窄屏折两行

- 现象：1600px 一行放得下；940px 折成两行，第二行是"血缘 SQL 开发者模式"（[`after-schema.png`](screenshots/after-schema.png) 顶部）。折行后导航吃掉约 70px。
- 为什么是问题：13 项已经接近上限，且分成"看数据 / 查结构 / 分析 / 治理 / 运维"几组，但视觉上没有任何分组线索，全靠标签猜。

### S3-2 「开发者模式」混在只读导航里

- 现象：`/dev` 是**可写**的另一个进程（8083），却和只读导航项长得一模一样，只是排在最后。
- 为什么是问题：门户的第一前提是"只读"（`portal_test` 有整节 T8 在验证它），导航条却把可写入口平铺在最右边，导语与结构自相矛盾。

### S3-3 KPI 卡片 6–8 个一排、全部同权重、粒度混杂

- 现象：`/occupations` 一排 6 张卡："151 在库节点 / 17 岗位族 / 690 结构化 JD / 2,970 要求条目 / 58 当前能力权重 / 40 能力概念"；`/` 上一排 8 张；`/viz` 一排 4 张里既有"451,058 数据行"也有"16 已注册度量"（16 个度量 vs 45 万行并列）。
- 为什么是问题：粒度不同（行数/条目数/版本数/图表数）却完全同权重，读者无法从视觉上判断"这页先看哪个数"。这是典型的"KPI 墙"。

### S3-4 `/analyze` 索引页密度过高

- 现象：每条分析 = 标题 + 说明 + 一整块深色 `<pre>` SQL（一行 150 字符截断），一屏只放得下 1.5 条（[`before-viz.png`](screenshots/before-viz.png) 之外的 `/analyze` 截图）。
- 为什么是问题：索引页的职责是"挑一条去跑"，SQL 是细节（属 §1.2 的 details-on-demand），却占了最大视觉权重。

### S3-5 `/viz` 16 个面板竖排一列，约 10 屏

- 现象：16 张图各占一张卡，纵向排开。
- 判断：**这一条我认为现状是对的**，不该改。横向条形图的类别标签（`job_competency_weight` 这类 20+ 字符的英文标识）在 1600px 下才勉强放得下，改 2 列会把标签压到 ~400px 而截断（§1.5）。图的坐标轴字号 10.5–12px、轴标签用 `#656d76`（5.25:1，达标），空数据有明确空状态（`viz_test` 断言 7 种图的空状态）。**保持竖排。**

### S3-6 长机器串占据首屏宽度、同一取值刷屏

- 现象：`/t/job_posting` 首屏前三列是 `job_id` / `source_id` / `ingest_run_id` 这类机器串；`/occupations` 的"能力域"列与"外码"列几乎每行都是重复的 `待核验` / `无对应`。
- 判断：这是**数据本身**的形态，不是样式问题；本轮没动（见 §4.7）。记下来是因为它直接抬高了眼动成本，如果要改，应该从"默认列顺序/默认隐藏低信息量列"入手，属于产品决策。

### S3-7 颜色语义：状态色与分类色共用同一批色相

- 现象：`charts.py` 里 `green/amber/red` 表示"达标 / 接近 / 不达标"（语义色），而分类调色板是 `blue/green/amber/purple/teal`（类别色）——**同一个绿色既表示"通过"也表示"第 2 个类别"**；`/tree` 树上的蓝/黄/青小标签没有图例。
- 为什么是问题：颜色一旦兼职两种语义，读者就不能再信任颜色。本轮**没改**（需要一张色板规范 + 逐图核对，超出"低风险"范围，见 §4.8）。

## 3. 已实施改进

每条都：**现象 → 改法 → 证据 → 实测结果**。改动全部在 `code/demo/portal.py`（`CSS` 常量 + `page()` / `render_rows()` + 6 处调用点）。

### 3.1 修好预设按钮行（S1-1）

- 改法：新增 `.btnrow{display:flex;gap:6px;flex-wrap:wrap;justify-content:flex-end}` + `.btnrow button{width:auto;padding:7px 12px}`；把那一行的容器从内联 `text-align:right` 换成 `class="btnrow"`。全局 `button{width:100%}` 保留（表单里的整宽按钮是有意的）。
- 证据：[`before-talent.png`](screenshots/before-talent.png) → [`after-talent.png`](screenshots/after-talent.png)
- 实测：那 7 个按钮从竖排 260px 高变成右对齐一行；筛选卡片缩短约 200px，**改前首屏看不到任何一行人才数据，改后能看到「人才清单」表头与前 4 行**。

### 3.2 面包屑 + 正确高亮 + 无障碍属性（S1-2）

- 改法：`page()` 新增 `here=`（当前顶级栏目）与 `crumbs=`（祖先链）两个参数；导航项按 `here or title` 高亮，并加 `aria-current="page"`、`<nav aria-label="主导航">`。调用点：表详情 → `here="表与视图"` + 面包屑「表与视图」；实体页 → + 「表名」；人才页 → 「人才库」；职业页 → 「职业库」；分析详情 → 「分析」；`/match` → `here="匹配"`。
- 证据：[`before-table.png`](screenshots/before-table.png) → [`after-table.png`](screenshots/after-table.png)；[`before-talentdetail.png`](screenshots/before-talentdetail.png) → [`after-talentdetail.png`](screenshots/after-talentdetail.png)；[`before-match.png`](screenshots/before-match.png) → [`after-match.png`](screenshots/after-match.png)（「匹配」下划线回来了）
- 实测：`/t/job_posting` 顶部出现「表与视图 › job_posting」且导航「表与视图」高亮；`/talent/per_mock_0001` 顶部出现「人才库」。

### 3.3 字段表宽屏双列（S2-1）

- 改法：`@media(min-width:1180px){.kv{grid-template-columns:190px minmax(0,1fr) 190px minmax(0,1fr)}}`。因为 `.kv` 的子元素本来就是"标签 / 值"交替，4 列网格自动变成"两对一行"，**不用改 markup**；窄屏仍退回单列。`.kv>div:nth-child(odd)` 的标签底色规则天然继续生效。
- 证据：[`before-occupation.png`](screenshots/before-occupation.png) → [`after-occupation.png`](screenshots/after-occupation.png)；[`before-talentdetail.png`](screenshots/before-talentdetail.png) → [`after-talentdetail.png`](screenshots/after-talentdetail.png)
- 实测：职业详情 25 个字段从 25 行变 14 行，`能力要求` 与 `子节点` 两张卡从屏外提到首屏内；人才档案 17 个字段变 9 行，`观测窗口` 表进入首屏。**信息一个没少，滚动少一半。**

### 3.4 对比度达标（S2-2）

| 位置 | 改前 | 改后 | 比例变化 |
| --- | --- | --- | --- |
| `.metric .d` | `#8c959f` | `#656d76`（字号 11 → 11.5px） | 3.04:1 → **5.25:1** |
| `.colgroup` | `#8c959f` | `#59636e` | 3.04:1 → **6.11:1** |
| `.nul` | `#b1b8bf` | `#6e7781` | 2.00:1 → **4.55:1** |

比例由本地按 WCAG 相对亮度公式计算（`lum()` + `(L1+0.05)/(L2+0.05)`），未四舍五入放宽。

顺手补了键盘焦点：`:focus-visible{outline:2px solid #1f6feb;outline-offset:1px}`（WCAG 2.4.7，改前只有浏览器那圈在浅灰底上几乎看不见的细描边）。

### 3.5 空状态统一成虚线框（S2-3）

## 4. 建议但未做（及理由）

### 4.1 导航从 13 项收敛/分组
会改动 21 个页面的入口结构、影响现有文档与测试断言，属于产品决策；零 JS 下"更多"只能靠 `<details>`，在深色导航条里做折叠菜单的可用性存疑（`<details>` 的展开面板定位在 sticky 导航里很难做稳）。**建议单独立项**，不要塞进视觉评审。

### 4.2 KPI 卡片分级（主指标大卡 + 次指标小卡）
需要逐页回答"这页的主指标是哪一个"——`/occupations` 的 6 个数字（节点/岗位族/JD/要求条目/权重版本/能力概念）没有天然的主次，`/` 与 `/viz` 同理。这是内容决策，不是样式决策；在没定的情况下强行分级只会换成另一种误导。本轮只做了 §3.8 的页头带。

### 4.3 `/viz` 16 面板改双列
见 §S3-5：横向条形图的类别标签是长英文标识，压到 ~400px 必然截断，**风险大于收益，明确建议不做**。

### 4.4 `/analyze` 的 SQL 默认折叠
把 `<pre>` 收进 `<details>` 确实能降低索引页密度，但"每张图/每个数字都能给出它执行的 SQL"是这个门户的卖点之一，默认折叠会削弱它；而且测试断言页面上存在 SQL 文本，折叠后仍在内文里、但要逐条验证，收益不明确。

### 4.5 表格斑马纹、行高再压缩
与现有 `tr:hover` 是两种行背景机制，叠加后噪声反而变大；而且 `.tablewin` 的吸左首列有独立的背景色，斑马纹必须同步改 `td:first-child` 才不会露馅。收益/风险比不划算，**没做**。

### 4.6 `/sql` 的「执行」按钮仍是整宽
它和门户其它紧凑按钮不一致，但"textarea + 整宽主按钮"是常见表单形态，改成小按钮不一定更好——改了是中性偏好、不改是中性偏好，**故意不动**。

### 4.7 `n_right` 只补了 `/tree` 一处
`render_rows` 的 `n_right` 是按中文列名匹配的，而各页列名是 SQL 里动态生成的（如"排名 / 年份 / 占比 / 样本"）。要逐处人工判断"这列到底是不是量"，批量套用会把"年份""排名"也右对齐。本轮只做确定性最高的 `/tree`。

### 4.8 状态色与分类色分离
需要一张色板规范（状态色：g/a/r 三档语义固定；类别色：改用同明度的蓝紫青系且与状态色不重叠）+ 逐图核对 `charts.py` 的 6 处 `colors=` 调用。这已经越出"低风险"边界（会动到 `charts.py` 的绘图语义），**留作下一轮**。

### 4.9 修掉 `#8c959f` 作为图表分类色
`charts.py` 的 `PALETTE["gray"]` = `#8c959f` 用于散点/分类填充，3.04:1 恰好压在非文本 3:1 门槛上、没有余量。它现在**达标**，所以没动；若做 §4.8 的色板规范应一并处理。

### 4.10 表格默认列顺序（长机器串前置）
见 §S3-6。属产品决策（哪些列默认隐藏），且会牵动 CSV 导出与测试断言。

### 5.1 一次真实出现过的红灯（必须记录）

第一次跑 `portal_test` 时是 **PASS 121 / FAIL 1**：

```text
  [FAIL] 遍历 96 个对象的页面后 change_log 未增长（434649 → 434908）
```

原因**不是我的改动**（我只改了 CSS 与 markup，门户全程只发 GET、且 SQL 走只读事务），而是**并发写入**：同一时间另一个会话在重放 `schema/sql/013_dimensions.sql`，该迁移按项目约定每次执行都往 `change_log` 追加审计行。我查了 `change_log` 的最近记录确认：

```text
actor='013_dimensions.sql'  object_name='dimension+code_table+code_value+field_catalog'
actor='postgres'（触发器）  object_type='field_catalog' … （写入时刻 2026-09-27 21:01:45）
```

T8 断言的正是"遍历页面前后 change_log 不增长"，它撞上了这次迁移的 +259 行。迁移跑完后重跑即 **PASS 122 / FAIL 0**（上面 §5 的输出就是这次的结果）。

### 5.2 数据快照不是同一时刻的

`before-*` 与 `after-*` 截图之间，**库里的行数变了**（`450,531 → 451,058` 数据行、`78 → 79` 基础表），因为并发会话在加数据。所以对比图里 KPI 数字的差异**不能当作我的改动的效果**，能对比的是版式（高度、对齐、颜色、位置）。这一点我选择写明而不是让读者自己发现。

## 6. 没做好的 / 已知问题

1. **`/viz`、`/analyze`、`/quality`、`/lineage`、`/search`、`/dev` 这几页我只做了"前后对照"级别的检查**：它们共享全局样式（页头带、对比度、表格语义、焦点环），全局改动在这几页生效已核对，但**没有对它们做逐条的页面级审查**（例如 `/lineage` 的层级图、`/search` 的 7 个结果块）。任务点名的 14 个页面是逐张看过的。
2. **`/quality` 的"岗位侧数据质量门"表**用一张 3 列表格表达"指标 / 值 / 目标"，值与目标被拉到卡片两端，中间几百像素空白——同一页上面那张"结构完整性不变量"表却是紧凑的。**同类元素不一致，我没改**（需要改 markup，且我判断收益不足以承担回归风险）。
3. **对比度只覆盖了 CSS 常量里的文字色**，没有逐个 token 全量审计（例如 `.p-e` 黄 pill 里的文字、`pre` 深色块里的语法高亮色）。抽样计算的 8 组 pill/提示条都在 6:1 以上。
4. **没有做真正的移动端/窄屏审查**：只在 940px 与 1600px 两个宽度上截图。940px 下导航折两行、`.grid2` 退化为单列（已有 media query），但没有逐页看窄屏的表格横向滚动体验。
5. **没有做屏幕阅读器实测**：补 `thead`/`scope`/`aria-current`/`aria-label`/`:focus-visible` 是按规范做的，但**没有用 NVDA/讲述人真机验证朗读顺序**。
6. **`.kv` 双列是我这轮最大的一处视觉改动**：如果某个字段的值特别长（长 URL、长 JSON），双列下会换行更多。我在三个页面上核对过（职业详情/人才档案/实体页），但没穷举 96 张表的实体页。
7. **§5.1 的并发写入是环境事实，不是我能消除的**：如果在我交付后又有人重放迁移，`portal_test` 的 T8 仍可能瞬时变红。这条留给仓库主人判断是否需要把该断言改成"只统计门户触发的写入"。
