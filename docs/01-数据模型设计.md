# 01 · 医学生人才信息库 · 数据模型设计（Data Model v0.1）

> 本文件是项目的**结构主干**。所有采集、解析、分析、匹配都必须在本文定义的骨架上落位。
> 变更本文件 = 变更 schema 版本；必须同步更新 `schema/catalog/field_catalog.csv` 与 `docs/CHANGELOG-schema.md`。

---

## 0. 设计目标与五条约束

| # | 目标 | 硬约束（可验收） |
|---|---|---|
| G1 | 结构化：任何一条关于"人"或"岗"的信息，都能落到确定的字段上 | 每条记录 100% 可映射到 `field_catalog` 中的字段 ID |
| G2 | 高自由度分析：任意维度组合可查、可交叉 | 新增一个分析维度 **不需要改表结构**，只需加数据行 |
| G3 | 高扩展：真实需求出现时可加实体/字段/词表 | 加字段 ≤ 30 分钟且不破坏既有数据；加实体 ≤ 1 天 |
| G4 | 可溯源：每个值都知道从哪来、谁采的、可信度多少 | 每条事实记录携带 `source_id`+`ingest_run_id`+`confidence`+`verify_status` |
| G5 | 可分析又可交付：既服务内部研究，也服务客户报告 | 分析层（marts）与事务层解耦，报告由 marts 生成 |

**总原则：核心脊柱保持窄而稳，扩展性放到三个受控的"增长面"上（见 §5）。**
不要为了"以后可能要"而把核心表做成万能宽表——那是本项目最容易走偏的地方。

## 1. 总体分层

```
┌─────────────────────────────────────────────────────────────┐
│ L3 服务层 Serving                                           │
│   匹配引擎 / 分析查询 / 报告生成 / 对外 API                   │
├─────────────────────────────────────────────────────────────┤
│ L2 语义层 Semantic                                          │
│   概念本体、代码表、字段目录、派生特征、向量、指标(marts)      │
├─────────────────────────────────────────────────────────────┤
│ L1 规范层 Canonical（可查询、可事务、可约束）                 │
│   人才域 / 机会域 / 治理域 —— PostgreSQL 类型化表             │
├─────────────────────────────────────────────────────────────┤
│ L0 原始层 Raw（只增不改，永不删除）                           │
│   原始 JD 文本、原始简历、HTML、PDF、访谈录音转写、采集日志     │
└─────────────────────────────────────────────────────────────┘
              ↕ 贯穿四层：治理面（来源/血缘/同意/访问/变更）
```

设计意图（与生物样本库的对应关系见 `docs/02-对标借鉴清单.md`）：
- **L0 与 L1 分离**：解析器会升级、会出错。原始文本必须永远保留，使"用更好的解析器重跑一遍"成为可能（对应 UK Biobank 保留原始问卷/测量、OMOP 保留 `source_value`）。
- **L2 独立于 L1**：词表、字段目录本身是数据，不是代码常量。改词表 = 加行，不是发版。
- **L3 只读 L1/L2**：禁止在服务层直接改数。

## 2. 实体全景

### 2.1 人才域（Subject Domain）

| 实体 | 表名 | 职责 | 基数 |
|---|---|---|---|
| 人才主体 | `person` | 一个自然人的假名化主体（唯一入口） | 1 |
| 身份信息 | `person_pii` | 可识别信息，**独立加密、分级隔离** | 1:0..1 |
| 人口学 | `person_demographics` | 出生年、性别、籍贯、政治面貌等 | 1:0..1 |
| 求职偏好 | `preference` | 城市/行业/岗位族/薪酬/强度容忍/稳定性 | 1:N（可随时间变） |
| 硬约束 | `person_constraint` | 户籍、地域、脱产、体检限制（色觉等）、签证 | 1:N |
| 教育经历 | `education_record` | 学历学位、学校、专业、导师、绩点、排名 | 1:N |
| 培养/规培 | `training_record` | 规培、专培、进修、住院总、轮转、实习 | 1:N |
| 临床暴露 | `clinical_exposure` | 科室、操作/手术例数、病种、技能清单 | 1:N |
| 资格证书 | `credential` | 执业医师、规培证、GCP、执业药师、语言、计算机 | 1:N |
| 工作经历 | `employment_record` | 雇主、职位、职级、职责、业绩 | 1:N |
| 科研产出 | `research_output` | 论文/专利/基金/会议/审稿 | 1:N |
| 项目经历 | `project_record` | 国自然/横向/临床研究，角色与成果 | 1:N |
| 荣誉奖励 | `award_honor` | 奖项、荣誉、竞赛 | 1:N |
| **能力主张** | `skill_assertion` | **"此人具备某能力"的断言 + 证据 + 置信度** | 1:N（核心表） |
| 证据 | `evidence` | 证书/作品/项目/评价/测评/自述，含可核验性等级 | 1:N |
| 测评记录 | `assessment` | 工具、维度、分数、常模、时间 | 1:N |
| 叙事材料 | `narrative` | 个人陈述、访谈转写、简历原文（指向 L0） | 1:N |
| 轨迹事件 | `trajectory_event` | 关键决策点：读研/转行/跳槽/停滞 | 1:N |

### 2.2 机会域（Opportunity Domain）

| 实体 | 表名 | 职责 |
|---|---|---|
| 职业/岗位族 | `occupation` | 多层级受控职业节点（大类/中类/小类/细类） |
| 岗位招聘 | `job_posting` | 一条真实 JD 的结构化主干 |
| 岗位任务 | `job_task` | 职责条目（结构化、可映射到任务概念） |
| 岗位要求 | `job_requirement` | 硬性/软性/加分要求，映射到概念或证书 |
| 能力权重 | `job_competency_weight` | 岗位族 × 概念 → 重要性/要求等级/必需性 |
| 雇主 | `employer` | 机构：类型、行业、规模、性质、地点 |
| 转行案例 | `transition_case` | 从岗 → 到岗，桥梁能力、前置条件、真实案例 |
| 薪酬基准 | `salary_benchmark` | 岗位族×城市×学历×年限 → 分位数 |
| 招聘渠道 | `job_channel` | 渠道登记与可抓取性评估 |

### 2.3 语义域（Semantic Domain）

| 实体 | 表名 | 职责 |
|---|---|---|
| 统一概念 | `concept` | 技能/知识/能力/任务/技术/兴趣/工作风格/工作情境/价值观 |
| 概念关系 | `concept_relation` | broader/narrower/related/essential_for/substitute_of |
| 代码表 | `code_table` + `code_value` | 所有枚举值的受控来源，带生效期与废弃标记 |
| **字段目录** | `field_catalog` | **变量级数据字典（对标 UK Biobank field）** |
| 实体目录 | `entity_catalog` | 实体注册表，支持新增实体而不改核心代码 |
| 派生特征 | `derived_feature` | 可重算的派生变量 + 算法版本 + 输入哈希 |
| 指标定义 | `metric_definition` | 指标 = SQL/YAML 定义，版本化 |

### 2.4 治理域（Governance Domain）

| 实体 | 表名 | 职责 |
|---|---|---|
| 数据源登记 | `source_registry` | 名称、类型、条款/robots、频率、可信度、许可 |
| 采集批次 | `ingest_run` | 每次抓取/导入的运行记录、计数、错误 |
| 逐条血缘 | `provenance` | record_uid → 来源、批次、时间、方法、抽取器版本 |
| 同意管理 | `consent_record` | 用途、范围、时间、撤回 |
| 访问审计 | `access_log` | 谁、何时、按什么授权、访问了哪些记录 |
| 变更日志 | `change_log` | append-only 变更流水 |

### 2.5 连接/匹配域

| 实体 | 表名 | 职责 |
|---|---|---|
| 匹配运行 | `match_run` | 算法版本 + 输入快照 + 参数 |
| 匹配结果 | `match_result` | 分数、分解、命中/缺口、解释文本、排名 |
| 缺口分析 | `gap_analysis` | 缺口能力 → 补齐路径（课程/证书/项目） |

## 3. 核心表字段规范（节选，完整见 `schema/sql/001_core_schema.sql`）

### 3.1 公共字段（**所有 L1 表强制携带**）

| 字段 | 类型 | 说明 |
|---|---|---|
| `<entity>_id` | TEXT PK | 稳定 ID，规范见 §6 |
| `schema_version` | TEXT | 该记录写入时的 schema 版本，如 `1.2.0` |
| `valid_from` / `valid_to` | DATE | 事实有效期（NULL = 至今），支持历史回看 |
| `recorded_at` | TIMESTAMPTZ | 系统写入时间 |
| `source_id` | TEXT FK | 来源登记 |
| `ingest_run_id` | TEXT FK | 采集批次 |
| `extractor_version` | TEXT | 解析器/人工录入版本 |
| `confidence` | NUMERIC(3,2) | 0–1，该条记录的整体置信度 |
| `verify_status` | TEXT | `raw` / `parsed` / `human_checked` / `third_party_verified` / `disputed` |
| `quality_flags` | TEXT[] | 质量问题标记，如 `missing_unit`,`ambiguous_title` |
| `attrs` | JSONB | **扩展属性袋**，键必须在 `attribute_definition` 注册（见 §5.2） |

> 这 12 个字段是"结构化"和"可分析"的分界线。没有它们的表不允许进入 L1。

### 3.2 `skill_assertion` — 全景中最重要的一张表

```
skill_assertion_id   能力主张 ID
person_id            谁
concept_id           什么能力（指向语义域 concept）
level                0–5 等级（0 未具备 / 5 专家级，取值 CT_ABILITY_LEVEL L0–L5）
claim_type           主张类型（CT_CLAIM_TYPE：CT1 能力 / CT2 成就 / CT3 潜质）
level_basis          等级判定依据（CT_LEVEL_BASIS：LB1 自述 / LB2 测评 / LB3 证书 / LB4 产出 / LB5 上级或同行评价 / LB6 临床例数）
essentiality         对目标岗位族是必需/加分（可空，匹配时算）
evidence_id          证据外键（可空，但为空则该主张置信度上限 0.5）
confidence           综合置信度（规则见 `docs/04`，取各来源系数的最小值）
transferability      可迁移性评分 **0–4**（CT_TRANSFERABILITY X0–X4；**本项目的差异化字段**）
transfer_note        迁移说明："外科住院总的应急决策 → 项目危机处理"
first_observed_at    首次具备时间（对标 UKB first-occurrence）
last_verified_at     最近核验时间
```

设计要点：**能力不是布尔值，而是"等级 × 依据 × 置信度 × 可迁移性"的四元组**。
医学生"会做科研"和"发过一作 SCI"是同一个概念的不同证据强度——必须能区分，否则匹配不可信。

### 3.3 `job_requirement` — 岗位侧的能力需求

```
requirement_id, posting_id (或 occupation_id)
requirement_kind     hard | soft | bonus
requirement_type     education|major|experience|license|skill|knowledge|language|other
concept_id           映射到的概念（可空）
raw_text             原文片段（**必须保留**，用于回查与再解析）
min_level            要求达到的等级
essentiality         必需/优先
substitutable_by     可替代路径（JSONB：["相关项目经历","同等证书"]）
```

### 3.4 `field_catalog` — 变量级数据字典（对标 UK Biobank field）

```
field_id          稳定字段 ID，如 F_PERSON_EDU_LEVEL
entity            所属实体
title / description
data_type         string|integer|number|date|boolean|code|array|json
unit              单位（薪酬=CNY/月，时长=月）
value_range       取值域（[min,max] 或枚举 code_table_id）
code_table_id     若为枚举，指向代码表
cardinality       scalar | array
collection_method questionnaire|interview|resume_parse|jd_parse|api|derived|manual
applies_to        适用人群过滤（如仅临床岗）
related_fields    相关字段
derivation        若为派生字段：算法与输入字段
status            active | deprecated | proposed
version           字段自版本
owner             负责人
```

> **本项目的"成熟度"就体现在这张表的覆盖率。** 目标：任何真实字段 100% 在此登记，包括它的单位、取值域和来源方法。

## 4. 数据分层与访问分级（对标 UK Biobank Category 1/2/3）

| Tier | 名称 | 内容 | 获取方式 |
|---|---|---|---|
| T0 | 公开 | 职业目录、能力词表、岗位族图谱、聚合统计、数据字典 | 开放浏览/下载（获客层） |
| T1 | 注册 | 脱敏人才档案、本人匹配结果、岗位库明细 | 注册 + 用户协议 |
| T2 | 受控 | 可识别 PII、原始简历文本、批量个体级数据 | 授权 + 合规审查 + **数据不落地**（仅返回汇总） |
| T3 | 敏感 | 健康信息、证件号、家庭约束 | 单独同意 + 加密 + 最小化 + 访问审计 |

**原则：元数据公开、数据受控、个体数据不外发、分析在平台内完成、只导出汇总结果。**（UK Biobank 的 Showcase/AMS/RAP 三层正是这个结构）

## 5. 三条扩展机制（本项目"高扩展性"的全部答案）

真实需求到来时，只可能落在以下三种情况之一。**不允许出现第四种**（如临时改核心表加列）。

### 5.1 机制 A：代码表驱动 —— 适用于"多了一个枚举值"

场景：新增一个岗位族、一个技能、一个证书类型、一个城市、一个行业标签。

做法：向 `code_value` 插一行（带 `code_table_id`、生效期、父节点、定义、别名、外部映射），**不动任何表结构**。

代价：几乎为零。要求：所有枚举必须先查 `code_table`，禁止在业务表里裸写中文枚举。

### 5.2 机制 B：属性登记驱动 —— 适用于"多了一个普通字段"

场景：想给 `job_posting` 增加"是否提供住宿"；给 `person` 增加"是否独生子女"。

两步（同一事务）：
1. `attribute_definition` 插一行：`attr_key`、`entity`、`data_type`、`unit`、`code_table_id`、`required`、`status`、`version`；
2. 数据写入该表的 `attrs` JSONB，**或**写入统一值表 `field_value`（推荐用于成批涌现的扩展字段）。

**统一值表 `field_value`（对标 UK Biobank 的 `field × instance × array`）**
```
field_value(field_id, subject_type, subject_id, instance_key, array_index,
            value_text|value_num|value_date|value_code|value_codes|value_json, …)
```
- `field_id` 是跨"第几次采集"不变的**语义锚点**；`instance_key` 表示第几次采集/第几段经历，`array_index` 表示同一次内的第几个重复值。
- 该表让"给人才档案加一个新字段"变成**零 DDL** 操作：登记字段 + 写值，两行数据解决。
- 主数据（教育、工作、论文等）仍用类型化表，以保证约束、索引与查询性能；`field_value` 只承接长尾扩展字段。

**升级规则**：某扩展字段被高频查询/需要约束/需要外键时，走 "promote" 流程——提升为正式列，写入 `change_log`，`attribute_definition.status='promoted'` 并回填 `promoted_to_field`。

代价：低。要求：`attribute_definition` 是唯一入口，禁止绕过它往 `attrs` 或 `field_value` 里塞未注册的字段（由校验器强制）。

### 5.3 机制 C：主张/事实三元组驱动 —— 适用于"多了一个全新维度"

场景：要记录"此人参与过某类医患沟通培训"和"该岗位实际需要夜间值班"，而概念体系里还没有对应节点，也不确定是否会长期存在。

做法：写入 `assertion` 通用事实表：
```
assertion_id, subject_type, subject_id, predicate, object_type, object_id,
object_value(JSONB), polarity(+/-), confidence, evidence_id,
source_id, valid_from, valid_to, recorded_at
```
先以"未定型维度"存在；当它被稳定使用后，**固化**为正式实体或正式字段（promotion），并保留原断言作为历史。

代价：中（查询需要额外 join，语义较弱）。**这是探索期的缓冲区，不是长期归宿**——必须有定期"固化/清理"机制，否则会腐烂成不可分析的垃圾桶。这是本项目最需要纪律的地方。

### 5.4 三种机制的选用判据

| 需求形态 | 用哪个 | 判据 |
|---|---|---|
| 新的分类值 | A | 是某个已有维度的取值 |
| 新的标量属性 | B | 一对一、不需要独立生命周期 |
| 新的关系/新实体雏形 | C（再固化） | 涉及多方关系或尚在探索 |
| 新的稳定实体 | 正式建表 + `entity_catalog` 登记 | 有独立 ID、生命周期、多字段 |

### 5.5 三条机制的落地 API（已实现，见 `docs/09`）

机制不该只停留在设计上，必须变成"一次函数调用"。`schema/sql/008_dynamic_model.sql` 已把它们收敛为：

```sql
SELECT mt.add_dimension('person','F_PROFILE_A','基层服务意愿','[...]'::jsonb);  -- 机制 A+B：加列（含 n 个选项）
SELECT mt.register_entity('profile_survey','talent','EK2');                     -- 机制 C：加实体（连表都不用建）
SELECT mt.create_instance('person','per_001','{...}'::jsonb);                   -- 加行
SELECT mt.set_value('person','per_001','F_PROFILE_A', p_code => 'A1');          -- 写值（含选项校验）
SELECT mt.deprecate_dimension('F_PROFILE_A','改用新维度');                       -- 软删列（数据不丢）
SELECT mt.delete_instance('person','per_001');                                  -- 删行
```

实测（`ops/tests/dynamic_model_test.py`，28 项断言）：新增一个带 4 选项的维度 **12.8 ms**，
建 20 条档案 **62.6 ms**，全过程 **基础表数量 59→59、`person` 列数 16→16，DDL 次数 = 0**。

## 6. 四套全局约定

### 6.1 ID 规范
`<prefix>_<ULID>`，前缀可读、ULID 单调有序（利于时间局部性与分页）。
前缀表：`per`(person) `edu` `trn` `cre` `emp` `res` `prj` `awd` `skl`(assertion) `evd` `asm` `job` `occ` `ems`(employer) `con`(concept) `fld` `ct` `src` `run` `mat` `gap` `trc`(transition_case)。

### 6.2 版本
- 实体 schema 版本：`MAJOR.MINOR.PATCH`；破坏性 = MAJOR。
- 代码表版本：单独版本号 + 生效期，**废弃不删除**。
- 派生特征：`algo_version` + `inputs_hash`，可重算、可比对、可回滚。

### 6.3 时间
统一 `TIMESTAMPTZ`；区分三类时间：**事件时间**（`valid_from`）、**记录时间**（`recorded_at`）、**来源时间**（`published_at`/`fetch_time`）。分析必须能回答"这是当时的事实，还是今天的回溯"。

### 6.4 质量与证据分级
`verify_status` 五级 + `quality_flags` + `confidence`。**任何进入对外报告的统计，必须能按 `verify_status` 过滤。**

另设**证据分级 `evidence_grade`（A/B/C/D）**，落在 `source_registry` 与 `provenance` 上：

| 级 | 含义 | 使用规则 |
|---|---|---|
| A | 官方统计、部委规章原文 | 可作为主结论 |
| B | 平台聚合统计（须记录样本量） | 可作为主结论，须标注来源与年份 |
| C | 单条在招 JD | 仅作举例，**禁止外推** |
| D | 未证实（自媒体/转述） | **禁止进入对外报告主结论**，只作线索 |

> 这条纪律来自岗位版图调研（`research/03-...md`）的实践；写进 schema 才能在报告里持续诚实标注，而不是靠人记。

## 7. 分析友好性设计

### 7.1 星型模型（L2 产出，供 BI/分析）
- 维度：`dim_person` `dim_occupation` `dim_employer` `dim_concept` `dim_geo` `dim_time` `dim_education`
- 事实：`fact_skill_demand`（岗位需求侧能力频次×重要性）、`fact_posting`、`fact_salary`、`fact_transition`（转行流向）、`fact_capability_supply`（人才供给侧能力分布）

### 7.2 长表优先
能力、经历、证书一律**长表**（一人多行），不做 `skill_1..skill_n` 宽列。**长表 = 可加维度 = 高自由度分析**。

### 7.3 派生层可重算
所有"评分""指数""适配度"都是派生特征：不写死、记算法版本、可从 L1 重算。任何结论必须能回答"用哪版算法、基于哪些字段算出来的"。

### 7.4 分析自由度三件套（客户可直接感知的价值）
1. **字段目录**（知道有什么可查）
2. **长表 + 星型模型**（任意维度组合）
3. **派生层**（新指标 = 新脚本，不动数据）

## 8. 反模式清单（明确不做）

| 反模式 | 为什么禁止 |
|---|---|
| 万能宽表 / 一堆 `extra1..extra9` | 无法查询、无法治理、无法演进 |
| 在业务表里裸写中文枚举 | 无法聚合、无法映射外部标准 |
| 直接覆盖原始记录（UPDATE 覆盖历史） | 丧失可溯源与可重算能力 |
| 把 PII 混在业务表里 | 合规风险；一旦泄露全库沦陷 |
| 把 LLM 抽取结果直接当事实 | 幻觉污染；必须带 confidence + 抽检 + `verify_status=parsed` |
| 无 `field_catalog` 登记就加字段 | 数据字典覆盖率崩塌，半年内无人知道库里有什麼 |
| 只存结论不存证据（如只存"沟通能力强"） | 匹配不可信、报告不可辩护 |
| 试用"第四种扩展方式"（临时 ALTER TABLE） | 破坏契约，迁移成本指数上升 |

## 9. 对标校准记录（v0.2 新增，见 `schema/sql/002_ukb_patterns.sql`）

岗位与能力调研 + 成熟数据库对标（`research/01-...md`）后，对 v0.1 做了以下修正。**这些不是自选动作，是同行已验证的必要结构**：

| # | 差距 | 借鉴来源 | 落位 | 优先级 |
|---|---|---|---|---|
| 1 | `access_tier` 是标量，无法表达"能看但不能导出" | UK Biobank Cost Tier `d/o/s` 乘积式 | 新表 `access_policy(object, action, min_tier)`，`access_tier` 降为默认值 | **P0** |
| 2 | 无观测期概念，"简历没写"被误判为"不具备" | OMOP `OBSERVATION_PERIOD` | 新表 `observation_window` + 视图 `v_gap_candidates`；**匹配引擎判定缺口前必须先查窗口** | **P0** |
| 3 | 分类只是字段上的字符串标签，无层级计数 | UK Biobank Category 树 | 新表 `category_node`（含 `subtree_field_count`/`node_field_count`）+ `field_catalog.main_category_id` | **P0** |
| 4 | 新字段必须改表结构 | UK Biobank `field × instance × array` | 新表 `field_value`，扩展字段零 DDL 落数 | P1 |
| 5 | "首次具备时间"只寄生在主张行内 | UK Biobank First occurrences | 新表 `first_occurrence` | P1 |
| 6 | 词表映射无独立血缘 | OMOP `SOURCE_TO_CONCEPT_MAP` | 新表 `concept_mapping` | P1 |
| 7 | 层级查询靠递归，随规模变慢 | OMOP `CONCEPT_ANCESTOR` | 新表 `concept_ancestor` + `refresh_concept_ancestor()` | P1 |
| 8 | 字典靠人维护，不是构建产物 | UK Biobank `scdown.cgi` + Croissant | `make catalog` 导出 CSV + JSON-LD + sha256；`dataset_release` 登记发布 | P2 |
| 9 | 原文与标准码未在所有业务表成对保留 | OMOP 三件套 `source_value`/`concept_id`/`type_concept_id` | 已有 `*_raw`/归一列；补齐 provenance 作为**有词表的概念**而非布尔 flag | P2 |

**新增纪律（写进代码评审清单）**：
- 任何"此人没有 X"的结论，必须先证明 X 落在该人的观测窗口内；否则只能说"未记录"。（`docs/05-匹配与分析引擎方案.md` 强制）
- 任何对外数据集，`dataset_release.doc_codebook_uri` 为空则不允许发布（DDL 已用 CHECK 约束）。
- 访问控制在代码里只能查 `access_policy`，禁止硬编码 tier 判断。
