## 二、P0 整改详解

### P0-1 主体标识的披露控制（迁移 044）

**问题**：030 的披露控制**只按表名写死** `person`/`person_pii`，紧接着的通用规则又把
`person_id` 判成 T0。实测 29 张表的 `person_id` 是 T0，而公开剖析视图
`v_column_profile_public` 把 `top_values` 一并交出：

```
evidence.person_id          → per_real_fengtang 21 / per_real_li_tiantian 21 / per_real_yu_ying 20
employment_record.person_id → per_real_yu_ying 6 / per_real_fengtang 5 ...
award_honor.person_id       → per_real_fengtang 7 ...
```

匿名因此同时拿到**编码了姓名的真实人物 id**与**"他产出最多"的精确统计**。

**根因**：**"主体标识"是值的语义，不是表名的属性。** 写成表名白名单，换个表名保护就失效。

**修法（两层）**：
1. `is_subject_identifier(table, column)` —— 列名是 `person_id`/`subject_code`，
   **或**该列是指向 `mt.person` 的外键（从 `pg_constraint` **动态发现**）。命中即 T1。
   新增任何子表自动被覆盖，不需要记得改白名单。
2. `is_enumeration_risk(table, column)` —— 主体标识本身，**或**指向"含 person_id 的表"的
   外键（如 `skill_assertion.evidence_id → evidence`）。公开视图对命中的列**置空 top_values**。
   理由：即使某列被判 T0，**公开它的取值列表仍是另一个更强的动作** ——
   这正是 030 写下的原则"能读一列 ≠ 可以枚举它的取值"，当时只用在了"编号"上，没用在"Top-K 列表"上。

**为什么两层都要**：第 1 层靠"我们记得把新列判成 T1"；第 2 层是**出口处的兜底**，
即使将来有人误判成 T0，公开视图也不会把取值列表交出去。

**验证**：T0 的 `person_id` 从 **29 张表 → 0**；公开视图里 `person_id` 的取值行 **0 条**；
匿名对 `evidence` 表直接 `permission denied`。断言固化在 `exposure_test.py` 的【I】段
（含"公开剖析视图没有交出主体标识 Top-K"）。

### P0-2 授权自愈入口（迁移 043）

**问题**：042 为解决性能问题 `DROP` 了无参 `public_counts()`，但
`apply_role_baseline()`（031/038 定义）里仍写着 `GRANT EXECUTE ON FUNCTION mt.public_counts()`。
实测 `apply_column_grants()` 直接报 `function mt.public_counts() does not exist`。

**为什么是 P0**：它是**唯一的授权对账入口**。它一报错，任何 `column_policy` 调整都落不到
实际授权上，只能手工 GRANT —— 权限模型失去可运维性。
更糟的是**没有任何指标盯着它**，所以只在"下一次需要自愈"时才炸。

**教训（已写进 043 注释）**：**`DROP FUNCTION` 之后必须全文搜索该函数的调用点** ——
函数体里的引用不出现在 `pg_depend` 的普通依赖里，常规依赖检查拦不住。

**验证**：新增 MUST 指标 **I5.0**「授权对账入口可用 且 权限不变式成立」，
每次门禁都真的调一次 `apply_column_grants()`。

## 三、P1-7 的真相：不是代码缺陷，是我方的运行方式

审查者在跑回归时得到 17/23 通过、6 个套件失败（含备份超时、外键错误
`Key (person_id)=()`、门户 90 项失败）。

**真因**：审查进行期间，**我同时跑了会改库的测试**（exposure_test 会建/删账号、
过载压测会占满连接）。两个会写库的测试并发 → 互相污染：
- 控制台套件报出荒谬的外键错误；
- 门户套件大面积失败；
- 备份套件被拖到异常退出。

**为什么值得单独记**：**现象指向代码，真因是运行方式。** 这种假失败最费时间，
而且会让人开始不信任回归结果 —— 那比没有回归更糟。

**整改**：给 `run_all.py` 加**互斥锁**（`.tools/run_all.lock`，含 pid 与启动时间）：
- 锁存在且 pid 还活着 → **拒绝启动**，并打印占用者信息与原因；
- 锁存在但 pid 已死（上次被强杀）→ 视为陈旧，接管并提示；
- `--force` 留后门，但必须自己说出口。

## 四、P1-1 / P2 / P3 的第二轮整改（2026-10-10 下午）

### 口径统一：闸门、`/schema`、`/catalog` 必须同一个答案（P1-1，迁移 048/049）

审查者指出 `public_counts()` 公开 89 张表的精确行数。核实后发现**真正的缺陷不是"公开得多"，
而是"两套实现、两个答案"**：

- 041 给聚合闸门加了排除（`login_attempt` 被藏）；
- 但**公开的 `/schema` 页用 `meta()` 照样列出所有表的精确行数**（含 `change_log` 871,163）。

于是同一个问题有两个答案，而且**两边看起来都对** —— 最难发现的一种不一致。

**裁定（写下来，只此一份）**：
| 类别 | 行数 | 理由 |
|---|---|---|
| 数据表（`person`/`job_posting`/`credential`…） | **公开** | 需求原文"数量可以公开"；目录页的意义就是"看到数据库真实的样子" |
| 身份/会话/登录表（`app_user`/`web_session`/`login_attempt`/`login_policy`） | 不公开 | 反映"有多少账号/会话/登录尝试"，属**活动信息**而非数据规模 |
| 审计流水（`access_log`/`change_log`） | 不公开（T2+ 可见） | 同样是活动量 |

**实现**：判据唯一来源 `mt.v_count_visibility`（由 `public_count_excluded` 驱动）。
聚合闸门读它，门户的 `/schema`、`/catalog` 也读它。实测：
- 匿名 `/schema`、`/catalog`：6 张活动表显示「不公开」，`person` 仍显示 `123`；
- T3 登录后：6 张活动表的真实行数全部可见（**运维能力没被牺牲**）。

**顺带修掉我自己在 048 制造的一次"飘"**（迁移 049）：048 给等级角色授了
`v_count_visibility` 却没登记进 `public_view_registry`，而对账规则是"视图默认只给 T3"——
于是"能不能读"取决于对账有没有跑过。已登记为公开（它是策略元数据，与 `export_denied` 同类），
并断言"**两次对账后状态稳定**"。教训：**加了新视图就必须同时决定它的可见性**。

### P2-1 迁移漂移从告警改为拦截（`ops/pg.py`）
原来只打印一句警告、**退出码仍是 0**，于是"库与定义已经分叉"可以长期存在 ——
别人的库和你的库结构不同，却都显示"迁移已全部应用"。
现在：`apply` 默认 **exit 4** 并说明两条出路；`--allow-drift` 显式接受并重新登记哈希。
实测 017 的漂移已被拦截并裁定。同时新增 MUST 指标 **I5.5 已应用迁移被改过的个数**。

### P2-4 / P2-5 SQL 拼接改为驱动转义
- `code/db.py::call()`：函数名原来用 `%s` 裸拼 → 改 `psycopg.sql.Identifier`。实测可用，
  且注入式输入被当标识符（报"不存在"而非执行）。
- `portal.py` 两处 `.format(pid=...)`/`.format(fam=...)`（后者还手写 `.replace("'", "''")` 转义）
  → 改为**绑定参数**（给 `mini_analysis` 加了 `params` 支持）。
  手写转义的问题不是"这次转错了"，而是**它依赖每个调用点都记得转义**，而 `pid`/`oid` 来自 URL。

### P2-6 错误信息按身份分流
数据库原文（`permission denied for function occupation_asof`）会暴露内部表名/函数名。
但**运维者需要它**（这是刻意加的可诊断性），所以不搞一刀切：
- 已登录 → 显示原文 + **追踪号**；原文同时写 stderr 与审计日志；
- 匿名 → **只给追踪号**；「被拒绝的对象」若指向内部表名也换成中性表述。
实测匿名 `/tree`、`/quality`、`/audit`、`/t/person_pii` 全部**零内部名称泄露**。

### P2-7 缓存加锁
`_EXPORT_CACHE` 与 `meta()` 的"检查-构建"都加了锁（`ThreadingHTTPServer` 下一请求一线程，
并发首请求会各建一遍）。`meta()` 另外加了 **TTL（默认 300s）** —— 它原来是无条件永久缓存，
而开发者模式/迁移会改结构，"结构页显示的是门户启动那一刻的样子"会让目录页的卖点失效。

### P3-4 统计信息（`ANALYZE`）
实测 **50 张表从未被 ANALYZE**（`last_analyze` 与 `last_autoanalyze` 都为空）——
它们多是静态小表，永远达不到 autovacuum 的分析阈值。跑一次 `ANALYZE` 后 **50 → 0**，
并把该指标从 INFO 提为 **SHOULD（≤5）**。

### P2-3 口径分叉（已核对，无需改动）
三个比率指标的名称实际已能区分：`物理列被字段字典覆盖的比例`（I2.2）、
`列级策略里有字典/人工依据的比例`（I4.3）、`能力概念映射覆盖率`（门户/metrics）。
审查者看到的"并列会误导"主要出现在**测试断言的措辞**里，已随测试重写消除。

### 仍未做

需要停机窗口 + 数据搬迁 + 回归验证，留作独立一轮，不塞进本轮。
