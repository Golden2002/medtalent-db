## 1. 概念翻译：用户的话 → 专业能力

用户说的是三件事：**记住谁来了**（记录访问用户）、**每个人能看的字段不一样**（字段级权限）、**编号年龄可以公开、其他要限**（分级分类）。下表把它们翻译成这门学科的标准术语。

| 用户原话 | 专业术语 | 它解决什么问题 | 它**不**解决什么问题 |
|---|---|---|---|
| 「记录访问用户」 | **AuthN**（身份认证）：你是谁 | 把一次请求绑定到一个**可追责的主体**（人/角色/服务）。本库对应：会话里的 `mt.actor` + 数据库登录角色 | 不回答"你能看什么"。认证成功 ≠ 有权限（登录成功的 registered 用户仍不该看到健康字段） |
| 「记录访问用户」第二层 | **访问审计**（access audit）：谁在什么时候读了哪个字段 | 事后追责、合规举证、异常检测（例如某账号一夜读了 5000 条 T3） | 不阻止任何事。**只有审计没有拦截 = 事后才知道出事**；反之只有拦截没有审计 = 出事说不清 |
| 「每一个字段权限不同」 | **AuthZ**（授权）：你能做什么 | 把"谁能对哪个对象做哪个动作"写成**可判定、可测试**的规则 | 不解决身份伪造。若身份本身可伪造（如把等级存在客户端可改的变量里），再精细的 AuthZ 也是空的 |
| 「字段权限不同」 | **列级安全**（column-level security, CLS） | 同一张表，A 角色只能读 `person_id`，B 角色能读 `person_id, birth_year`。**数据库层面拒绝**，不依赖应用记得裁剪列 | 不解决行级问题（A 和 B 都能看到**所有人**的行）；也不防"合法列的组合再识别"（邮编+生日+性别可唯一化） |
| 「只能看本人的/某范围的记录」 | **行级安全**（RLS, row-level security） | 同表同列，不同角色看到**不同行**（本人、本机构、本城市）。PostgreSQL 原生支持，且是**默认拒绝** | 不解决列问题（`SELECT *` 仍会把敏感列带出来）；表属主/超级用户默认**绕过**（见 §5 头号事故） |
| 「给重要数据加权限」 | **数据分级分类**（classification / tiering） | 先定义"什么算重要"。本库已有：`field_catalog.access_tier` = T0/T1/T2/T3 | 分级本身**只是标签**。README 那句话说的就是这个：分级写了两年，没有一处拒绝访问 |
| 「不同的人给不同级别」 | **RBAC**（基于角色的访问控制） | 用少量**角色**（而非逐个用户）承载权限，可审计、可复用。本库对应 `mt_t0/t1/t2/t3` + `mt_portal` | 角色会爆炸（每个组合一个角色）；且角色是"静态身份"，无法表达"同一角色在 A 用途下能看、B 用途下不能看" |
| 「同一字段，不同条件」 | **ABAC**（基于属性的访问控制） | 用属性（目的、时间、地点、数据主体同意状态）做判定。Snowflake 的 masking policy 内可用 `CURRENT_ROLE()` 与自定义 entitlement 表，即 ABAC 形态 | 难枚举、难测试、策略分散后**没人能回答"这个角色到底能看到什么"**；性能与调试成本高 |
| 「只给需要的人」 | **最小权限原则**（least privilege） | 默认拒绝，按需放开。本库已据此选了正确方向：`mt_portal` **自身零表权限**，忘了 `SET ROLE` 就读不到任何数据 | 不解决"已经给多了怎么收回"。必须配合**可重放的对账**（`apply_column_grants()` 的先收回再重授） |
| 「谁能批准、谁能改策略」 | **职责分离**（SoD, separation of duties） | 定策略的人 ≠ 用数据的人 ≠ 批发布的人。Snowflake 明文支持：对象属主**无权**取消掩码策略，也看不到被掩码列 | 不解决技术性绕过（拥有超级用户的人可以两件事一起做）。SoD 是**组织控制**，必须有技术对账才成立 |
| 「知道谁同意了什么」 | **同意与用途限制**（consent / purpose limitation） | 同一份数据，`matching` 用途可用、`publishing` 用途不可用。本库已有 `consent_record.purpose` 五枚举 + `access_policy.action` | 不解决技术性最小化；同意不等于"可以随便读"，仍需字段与行级拦截配合 |
| 「本人要求删掉/拿走」 | **数据主体权利**（DSR：删除/导出/更正） | 法定义务。本库已有 `subject_request`、`consent_withdrawal_action` | 不解决"删了但备份里还有"——必须同时约束备份与派生副本（`docs/06` §6 已定义保留期） |
| 「这数据能对外吗」 | **披露控制**（disclosure control：k-匿名、小样本抑制） | 防止"合法查询组合出个体信息"。本库已有 `n ≥ 5` 抑制 | 不解决越权读取，是聚合交付面的问题，与 CLS/RLS 正交 |

**一句话总纲**（本项目自己的口径）：

> 分级（T0–T3）回答"什么算重要"；**列级 GRANT 回答"谁读得到"**；RLS 回答"读得到谁的行"；审计回答"谁读过"；同意回答"为了什么目的可以读"。五者缺一，都可以被一句话反问击穿。

## 2. PostgreSQL 原生能力与可执行 SQL（含边界与坑）

本节所有「实测」均在 16.8 上执行。**每个结论都给出可复制的 SQL。**

### 2.1 列级权限：`GRANT SELECT (col) ON t TO role`

**语义**（文档 + 实测）：`SELECT` 可授到列；`INSERT`/`UPDATE`/`REFERENCES` 同样可授到列。

**A. 明确列名可以读到；`SELECT *` 被拒绝（实测）**

```sql
BEGIN;
CREATE SCHEMA t_ac18;
CREATE TABLE t_ac18.t(id int primary key, pub text, secret text);
INSERT INTO t_ac18.t VALUES (1,'a','s1'),(2,'b','s2'),(3,'c','s3');
CREATE ROLE t_ac18_r LOGIN;
GRANT USAGE ON SCHEMA t_ac18 TO t_ac18_r;
GRANT SELECT (id, pub) ON t_ac18.t TO t_ac18_r;
SET LOCAL ROLE t_ac18_r;
SELECT id, pub FROM t_ac18.t;   -- 成功
SELECT * FROM t_ac18.t;         -- 实测：ERROR 42501 permission denied for table t
SELECT id FROM t_ac18.t;        -- 成功
ROLLBACK;
```

> 这正是本项目选它的**核心理由**：应用层哪怕写错成 `SELECT *`，**数据库也会拒绝**，而不是"把敏感列一起返回"。这满足"能被证明的受限"。

**B. 聚合：`count(*)` 不受列权限影响，`count(secret)` 被拒绝（实测）**

```
E1 显式列        -> ok
E2 SELECT *      -> FAIL 42501 permission denied for table t
E3 count(*)      -> ok          ← 不引用任何列
E4 count(secret) -> FAIL 42501
E5 sum(length(secret)) -> FAIL 42501
```

**这是本项目需求的关键契合点**：用户要「编号、年龄公开」。于是"**总人数公开**（`count(*)`）、**单列受限**"可以同时成立，不需要为统计单独开一条路。

**C. `WHERE` / `ORDER BY` 引用未授权列，同样被拒绝（实测）**

```
E6 ... WHERE secret='s1'  -> FAIL 42501
E7 ... ORDER BY secret    -> FAIL 42501
E8 ... WHERE pub='a'      -> ok
```

> 含义：列权限**不是输出过滤器**，而是"这一列你能不能碰"。所以**任何**引用（包括过滤、排序、`DISTINCT`）都需要权限。设计视图时必须把受限列早早就排除在 `SELECT` 列表之外，而不是"查出来再置 NULL"——后者需要先有权读。

**D. `pg_dump` 会把列权限一起导出（实测）**

```
$ pg_dump -s -t public.t_acltest
-- Name: COLUMN t_acltest.id; Type: ACL; Schema: public; Owner: postgres
GRANT SELECT(id) ON TABLE public.t_acltest TO t_acl_r;
-- Name: COLUMN t_acltest.pub; Type: ACL; Schema: public; Owner: postgres
GRANT SELECT(pub) ON TABLE public.t_acltest TO t_acl_r;
```

且 `--no-acl` 会**全部丢掉**（实测：加 `--no-acl` 后无任何 `GRANT` 输出）。
- 对本项目的好消息：`ops/backup/backup.py` 用的是 `pg_dump -Fc`（未加 `--no-acl`），**列权限会被备份**。
- 坑：恢复顺序是"先建表 → 再 `GRANT`"，恢复脚本中途失败会留下**已建表但未授权**的状态；对账函数必须能重跑（本项目已有 `apply_column_grants()`，这正是它的价值）。

**E. 列权限与"角色阶梯"的编译方式**

阶梯不能用字符串比大小（`'T10' < 'T2'`）。本项目已落地的做法是 `access_tier.rank` + `access_rank()`：

```sql
-- 实测存在：mt.access_tier(tier, rank, ...) 与 mt.access_rank(text)
SELECT access_rank('T3'), access_rank('T0'), access_rank('X');  -- 3, 0, 99
-- 未命中返回 -1，比 T0 还低 —— "写错的等级"是拒绝而不是放行
```

编译成授权（本项目 `apply_column_grants()` 的实质，实测角色权限递增 280 < 953 < 1016 < 1040）：

```sql
-- 最低层级为 Tn 的列 → 授予 mt_tn 及所有更高层级
GRANT SELECT (person_id, subject_code) ON mt.person TO mt_t0;
GRANT SELECT (person_id, subject_code, education_record.degree_level) ON mt.person TO mt_t1;
-- …
GRANT SELECT (full_name_enc, phone_enc, id_hash) ON mt.person_pii TO mt_t3;
```

### 2.2 行级安全（RLS）

**A. 表属主默认绕过 RLS —— 这是最容易踩的一点（实测）**

```sql
BEGIN;
CREATE SCHEMA t_ac18b;
CREATE TABLE t_ac18b.t(id int, owner_note text);
INSERT INTO t_ac18b.t VALUES (1,'x'),(2,'y');
CREATE ROLE t_ac18b_owner LOGIN NOSUPERUSER;
GRANT USAGE ON SCHEMA t_ac18b TO t_ac18b_owner;
ALTER TABLE t_ac18b.t OWNER TO t_ac18b_owner;
ALTER TABLE t_ac18b.t ENABLE ROW LEVEL SECURITY;
CREATE POLICY p_all ON t_ac18b.t FOR SELECT USING (true);
CREATE POLICY p_none ON t_ac18b.t FOR SELECT USING (false);
SET LOCAL ROLE t_ac18b_owner;
SELECT count(*) FROM t_ac18b.t;      -- 实测：2  ← 属主绕过策略
ROLLBACK;
```

**B. `FORCE ROW LEVEL SECURITY` 才让属主也受约束，且 permissive 策略是 `OR`（实测）**

```sql
BEGIN;
-- … 同上建表与属主 …
ALTER TABLE t_ac18b.t ENABLE ROW LEVEL SECURITY;
CREATE POLICY p_all  ON t_ac18b.t FOR SELECT USING (true);
CREATE POLICY p_none ON t_ac18b.t FOR SELECT USING (false);
SET LOCAL ROLE t_ac18b_owner;
SELECT count(*) FROM t_ac18b.t;      -- 实测：2  ← 仅 ENABLE 时属主绕过
RESET ROLE;
ALTER TABLE t_ac18b.t FORCE ROW LEVEL SECURITY;
SET LOCAL ROLE t_ac18b_owner;
SELECT count(*) FROM t_ac18b.t;      -- 实测：2  ← FORCE 生效后按策略算：true OR false = 2 行
RESET ROLE;
ROLLBACK;
```

> 注意 B 的第二条仍是 2，容易误读成"FORCE 没生效"。它生效了——只是 `p_all(true)` 与 `p_none(false)` 是两条 **permissive** 策略，按 `OR` 合并 = 恒真。**两条 permissive 策略永远不会互相收窄**；要收窄必须用 restrictive（见 §2.2-D）。

**C. 超级用户绕过 RLS，`FORCE` 也拦不住（实测）**

`postgres`（超级用户）读带 RLS 的表看到**全部行**，与本项目 `017` 迁移注释中的实测结论一致。

**D. 无适用策略 = 默认拒绝；permissive 与 restrictive 的合成（实测）**

```sql
BEGIN;
CREATE SCHEMA t_p4;
CREATE TABLE t_p4.t(id int, v text);
INSERT INTO t_p4.t VALUES (1,'x'),(2,'y');
CREATE ROLE t_p4_app LOGIN NOSUPERUSER;
GRANT USAGE ON SCHEMA t_p4 TO t_p4_app;
GRANT SELECT ON t_p4.t TO t_p4_app;
ALTER TABLE t_p4.t ENABLE ROW LEVEL SECURITY;

SET LOCAL ROLE t_p4_app;
SELECT count(*) FROM t_p4.t;                  -- 实测：0  ← 没有任何策略 = 默认拒绝
RESET ROLE;
CREATE POLICY p_app_select ON t_p4.t FOR SELECT TO t_p4_app USING (id = 1);
SET LOCAL ROLE t_p4_app;
SELECT count(*) FROM t_p4.t;                  -- 实测：1
RESET ROLE;
CREATE POLICY p_deny ON t_p4.t AS RESTRICTIVE FOR SELECT TO t_p4_app USING (false);
SET LOCAL ROLE t_p4_app;
SELECT count(*) FROM t_p4.t;                  -- 实测：0  ← 合成式：restrictive AND (permissive OR …)
RESET ROLE;
ROLLBACK;
```

合成规则（官方文档原文口径，已在 §0.2 核对）：

```
(所有 RESTRICTIVE 表达式 AND 起来)  AND  (所有 PERMISSIVE 表达式 OR 起来)
```

**E. 用 `current_setting` + `SET LOCAL` 传递会话身份**

```sql
-- 本项目已落地（017）：缺省值是 T0 / anonymous，而不是"最高权限"
CREATE OR REPLACE FUNCTION mt.session_actor() RETURNS text
LANGUAGE sql STABLE AS $$
  SELECT COALESCE(nullif(current_setting('mt.actor', true), ''), 'anonymous');
$$;
CREATE OR REPLACE FUNCTION mt.session_tier() RETURNS text
LANGUAGE sql STABLE AS $$
  SELECT COALESCE(nullif(current_setting('mt.tier', true), ''), 'T0');
$$;
```

调用侧（本项目门户的开发模式与 `access_test` 都在用这个形态）：

```sql
BEGIN;                                        -- 身份必须与事务同生命周期
SELECT set_config('mt.actor', 'u_1001@mini', true);
SELECT set_config('mt.tier',  'T1', true);
SET LOCAL ROLE mt_t1;                         -- 真正决定权限的是这一句
SELECT count(*) FROM mt.person;
SELECT mt.log_access('view','talent_list','T1', 123, '注册用户浏览人才库');
COMMIT;                                       -- SET LOCAL 随事务失效，连接池复用不会串身份
```

**实测的三条边界（都很关键）：**

| 现象 | 实测结果 |
|---|---|
| `current_setting('mt.actor', true)` 在参数不存在时 | 返回 `NULL`（不报错）——所以 `COALESCE` 兜底是必要的 |
| `current_setting('mt.actor')` 严格模式（第二参数省缺） | `42704 unrecognized configuration parameter` |
| **非超级用户能否自行设置 `mt.tier`** | **能**。任何角色都可以 `set_config('mt.tier','T3',true)`。**所以 GUC 里的等级不可信** |

**F. `set_config('role', …)` 的边界（实测，容易误判）**

| 场景 | 结果 |
|---|---|
| 非超级用户 `set_config('role','<不是自己成员的另一个角色>')` | **拒绝**：`permission denied to set role "..."` |
| 非超级用户 `set_config('role','postgres')` | **拒绝**：`permission denied to set role "postgres"` |
| 超级用户会话里 `SET LOCAL ROLE <任意角色>` | 可以（超级用户本来就都行） |
| 事务内 `SET LOCAL ROLE <非成员角色>`（由超级用户执行） | **实测可以**，`SET LOCAL` 的角色检查时机与普通 `SET ROLE` 不同（普通 `SET ROLE` 实测报 `permission denied`） |

> 结论：**`SET LOCAL ROLE` 让数据库成为真正的强制点**——权限由"当前角色实际持有的列 GRANT"决定，"声明"改不了它。但**任何把授权判断建立在 `mt.tier` 这类 GUC 上的设计都是可伪造的**。本项目 `017` 已经意识到这点，做了一个 `effective_tier()`（取"声明等级"与"角色实际持有权限"中较低者）；正确的用法是：**判定用角色，GUC 只用于记录与展示**。

**G. `row_security = off` 不会静默放过（实测）**

```
G7 非超级用户 set_config('row_security','off') -> 接受
G8 之后 SELECT 带 RLS 的表 -> 42501 query would be affected by row-level security policy for table "t2"
```

与官方文档一致："it does throw an error if any query's results would get filtered by a policy"。这是**防止备份静默丢行**的设计。

**H. `pg_dump` 与 RLS（实测）**

```
超级用户：        pg_dump 输出 SET row_security = off; 并包含全部行
非超级用户（无 BYPASSRLS）：pg_dump: error: query failed: ERROR: query would be affected by
                            row-level security policy for table "t_rlsdump"
```

官方文档补充：`--enable-row-security` 可以让 dump **只导出该角色有权看到的部分**（但 `COPY FROM` 恢复时**不支持** RLS，宜配合 `--inserts`）。

### 2.3 安全屏障视图与"只给视图不给基表"

**实测结论（这一节最反直觉，务必看数据）：**

```sql
-- 视图属主 = postgres（超级用户）；应用只有视图的 SELECT，基表只授了 3 列
-- v_plain / v_barrier / v_invoker 三个视图都投影了 health（受限列）

B1  基表 count(*)                       -> 2      （不需要列权限）
B2  基表 SELECT health                  -> permission denied for table person   ✅ 列权限生效
B3  plain 视图 count(*)                 -> 2
B4  plain 视图 SELECT health            -> OK，读到 'colorblind'   ❌ 绕过列权限
B5  security_invoker 视图（授权列）      -> permission denied for table person   ← 见下
B6  security_invoker 视图（受限列）      -> permission denied for table person
```

**三条硬结论：**

1. **「给视图不给基表」不是安全模式，除非视图属主本身没有该列的权限。** 视图默认以**视图属主**的权限执行（官方文档原文，§0.2 已核）。若属主是超级用户或表属主，则视图就是一把万能钥匙：`B4` 实测读到了受限列。
2. **`security_invoker = true`（PG 15+，本机 16 支持）会把权限检查换成调用者**，此时调用者必须**同时**持有视图与其基表的相应列权限。实测 `B5` 失败，因为该角色只有视图的 `SELECT`、基表也只有部分列——这恰好说明它是**严格**的，不是漏洞。要用它，就必须把基表列权限也授给该角色（于是视图退化为"语法糖"，不再提供额外保障）。
3. **`security_barrier` 的作用域是"防泄漏的函数/运算符下推"，不是"防列泄漏"。** 它让"用户附加的 `WHERE` 条件在视图自身条件之后求值"，用于防御会通过报错/耗时泄漏信息的非 `LEAKPROOF` 函数。**它完全不阻止 `SELECT health FROM v_plain`。** 实测 `EXPLAIN` 可见屏障被实现为 `Subquery Scan on v_barrier`，用户条件作为上层 `Filter`。

> **推荐用法（本项目）**：若要用视图裁剪列，就**同时**做到三件事：① 视图里**根本不投影**受限列（而不是 `CASE WHEN … THEN col ELSE NULL END`，因为那需要先有权读 `col`；`docs/06` §4.2 里的 `v_person_demographics_masked` 正是这个反例，**该写法在当前列权限模型下会直接报错**）；② 视图建在**非超级、非表属主**的角色名下，并开 `security_invoker=true`；③ 逐个视图评审，禁止 `GRANT SELECT ON ALL TABLES`。

**实测补充**：本项目 `column_policy` 只覆盖 `relkind='r'` 的**基础表**，18 个视图**全部不在策略内**（实测 `in_policy = 0`），因此当前四个等级角色**读不到任何视图**（实测：等级角色仅有 4 项视图权限，即 `access_tier`、`column_policy`、`v_column_policy_coverage` 三个元数据对象）。这是**有意的安全缺省**，也是待办。

**如何自行验证（可复制的检查步骤）：**

```powershell
# 1) 服务端是否认识这个扩展
psql -h 127.0.0.1 -p 55432 -U postgres -d medtalent -c "SELECT * FROM pg_available_extensions WHERE name='pgaudit';"
#    0 行 => 没装
# 2) 扩展文件在不在

Get-ChildItem D:\wbo-workspace\.tools\pgsql\lib -Filter "*pgaudit*"
# 3) 装它需要什么：服务端头文件 + C 编译器 + 与二进制可比的 MSVC 工具链
Test-Path D:\wbo-workspace\.tools\pgsql\include\server   # 实测：True（头文件在）

```

- 头文件目录 `include\server` **实测存在**，所以自编译在原理上可行；
- 但本机**是否具备可用的 MSVC 工具链未验证**。EDB 的 Windows 构建用 Visual C++（`version()` 实测显示 `compiled by Visual C++ build 1942`），混用 MinGW 编译的扩展**不被支持**；
- 另外 `pgaudit` 必须在 `shared_preload_libraries` 里加载，**需要重启数据库**；而本项目当前 `postgresql.conf` 只显式设了 `port` 与 `listen_addresses`（实测），**未设** `shared_preload_libraries`。

**可用的替代（不装扩展）：**

| 手段 | 能记什么 | 代价 | 本机可用性 |
|---|---|---|---|
| **自建审计表 + 函数**（本项目已做：`mt.log_access()` → `mt.access_log`） | 谁、以什么角色、读了什么对象、多少行、什么目的 | 需要应用**主动调用**；漏调就漏记 | ✅ 已落地，实测可写 |
| `log_statement = 'all'` + `log_connections` | 服务端把**每条语句**写进日志文件 | 体积大、是文本不是表、难以按字段统计 | ✅ 改配置即用（未实测） |
| `pg_stat_statements`（`share/extension` 实测有） | 按 `userid` + 查询指纹的**聚合**统计 | 只有统计，没有逐次明细；需 `shared_preload_libraries` + 重启 | 可用（未安装、未实测） |
| 触发器写 `change_log`（本项目已有 `mt.log_change()`） | **写**操作的前后镜像 | **触发器无法捕获 `SELECT`**（PG 没有 `FOR SELECT` 行触发器） | ✅ 已落地 |
| 在策略表达式里写日志（`SELECT` 策略里调 `log_access()`） | 理论上可让"读"自动留痕 | 策略表达式以调用者权限执行，需要 `INSERT` 权限；每次策略求值都可能写库，**性能与副作用都危险** | ⚠️ 不推荐，未实测 |

> **关键判断**：**PG 原生没有"读审计"能力。** 要么装扩展（pgaudit，需编译+重启），要么**把读路径收口到一个会写日志的 SECURITY DEFINER 函数/视图**，要么接受"应用层主动记日志"（可被漏调，但可用集成测试兜住——本项目 `access_test.py` A5 就是在测这件事）。

**审计表设计建议（含本项目已落地的表结构，实测）：**

```
mt.access_log(access_id bigint PK, actor text NOT NULL, actor_role text,
              action text NOT NULL, target text NOT NULL,
              access_tier mt.access_tier_t, row_count integer,
              purpose text, at timestamptz NOT NULL DEFAULT now(),
              detail jsonb NOT NULL DEFAULT '{}')
```

- `actor` = 业务身份（如小程序用户 `u_1001@mini`），`actor_role` = `current_user`（**实际生效的数据库角色**）。两者都记，才能发现"声明的身份与实权不一致"。
- `detail jsonb` 是刻意留的扩展位（`docs/06` §8 同口径）：新增字段优先入 `detail`，避免改审计表结构。
- **写时机**：建议只对**敏感级读取**（T2/T3）与**导出**强制留痕；T0/T1 的列表浏览只在"会话级"记一条（否则一次翻页写 50 行，审计表比业务表还大）。

### 2.5 角色体系：登录角色 vs 组角色

```sql
-- 组角色：NOLOGIN，只作为权限载体
CREATE ROLE mt_t0 NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;
CREATE ROLE mt_t1 NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;
CREATE ROLE mt_t2 NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;
CREATE ROLE mt_t3 NOLOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;

-- 登录角色：自身零表权限，只能"变成"等级角色
CREATE ROLE mt_portal LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;
GRANT mt_t0, mt_t1, mt_t2, mt_t3 TO mt_portal;
GRANT USAGE ON SCHEMA mt TO mt_t0, mt_t1, mt_t2, mt_t3, mt_portal;
REVOKE ALL ON SCHEMA mt FROM mt_portal;   -- 连 USAGE 都不给，最保守
```

**为什么这个形状是对的**：`mt_portal` 忘了 `SET ROLE` 时，结果是**读不到任何数据**（实测：`permission denied for table person`），而不是"读到全部"。**默认方向选错是最常见的权限事故**。

**连接池下的身份传递**：
- `SET LOCAL` 的作用域是事务，`COMMIT`/`ROLLBACK` 后自动还原 → 连接被池子复用也**不会串身份**。
- 反例：用 `SET`（非 LOCAL）传身份，一个请求异常退出后身份会**留在连接上**给下一个请求。**必须用 `SET LOCAL` 且在同一事务内完成"设身份 → 查询 → 记日志"**。
- 本项目三个进程都是每请求新建连接（`psycopg.connect` + 无池），风险更低；但设计上仍应统一用 `SET LOCAL`。
- 若将来引入 PgBouncer：**transaction 模式**下 `SET LOCAL` 安全；**session 模式**下要在归还前 `DISCARD ALL`。未实测。

### 3.5 通用数据平台

**Snowflake —— 列级安全 = 掩码策略，且强制职责分离**（实际打开 <https://docs.snowflake.com/en/user-guide/security-column-intro>）

- Column-level Security 由 **Dynamic Data Masking** 与 **External Tokenization** 两个特性构成，载体是 **masking policy**（schema 级对象），在**查询时**决定返回明文还是掩码，**不改存储**（无静态掩码）。
- 策略示例（页面原文）：
  ```sql
  CREATE MASKING POLICY employee_ssn_mask AS (val string) RETURNS string ->
    CASE WHEN CURRENT_ROLE() IN ('PAYROLL') THEN val ELSE '******' END;
  ```
- **最重要的一条（本项目应直接借鉴）**：*"Object owners do not have the privilege to unset masking policies. Object owners cannot view column data in which a masking policy applies."* —— **职责分离**：定策略的人与拥有对象的人分开，且**属主自己也被掩码**。页面明确说这是相对 **secure views** 的关键优势（secure view 没有 SoD）。
- 一策略可套用到上千列（"define a policy once and apply it to 1000s of email columns"），并按数据类型匹配。

**我们能借什么**：① "属主也被策略约束"这一条，正是本项目 `FORCE ROW LEVEL SECURITY` 的同类思想；建议在本项目也确立"**策略管理员 ≠ 表属主，且表属主读敏感列同样留痕/受限**"；② 用**标签/策略驱动**而非"每列写死"，本项目 `column_policy.source`（`field_catalog`/`access_policy`/`pattern`/`table_default`）就是"策略来源可审"的同类设计。

**借不了的代价**：Snowflake 的掩码发生在**具备该能力的引擎**内；PostgreSQL 的列级 `GRANT` 是**全有或全无**（要么读到明文，要么查询报错），**没有"返回掩码值"**这一档。要在本项目做掩码，只能靠 `CASE WHEN` 视图/函数配合 `security_invoker`，并接受 §2.3 的那些约束。**这是本项目与 Snowflake 最大的能力差**，必须写清楚以免给人错误预期。

**BigQuery —— policy tags / 行访问策略：未验证。** `cloud.google.com` 与 `docs.cloud.google.com` 在本机均 fetch 失败（`TypeError: fetch failed`）。搜索结果给出 <https://docs.cloud.google.com/bigquery/docs/column-level-security-intro> 与 <https://docs.cloud.google.com/bigquery/docs/row-level-security>，但我**没有读到正文**，故不给结论。已知（但未验证）：其思路是**用 Data Catalog/Dataplex 的分类法（taxonomy）打 policy tag，再把 tag 绑到 IAM 角色**——形态与 Snowflake 类似而更依赖目录服务。

**PostgREST —— 教科书级的"JWT → 数据库角色"映射**（实际打开 <https://docs.postgrest.org/en/latest/references/auth.html>）

页面原文结构（三条可直接照抄的设计）：
1. **三种角色**：`authenticator`（登录用，权限极小）、`anonymous`（未带令牌时切换到的角色）、`user`（每个业务角色）。原文给的 DDL 形状：
   ```sql
   CREATE ROLE authenticator LOGIN NOINHERIT NOCREATEDB NOCREATEROLE NOSUPERUSER;
   CREATE ROLE anonymous NOLOGIN;
   CREATE ROLE webuser NOLOGIN;
   ```
2. **"user impersonation" 就是 `SET ROLE`**：JWT 里的 `role` claim 决定切到哪个数据库角色；且要求 DBA 预先 `GRANT user123 TO authenticator;`。
3. **"All authorization happens in the database."** —— 认证归 PostgREST，**授权全部留给数据库**。另有 `db-pre-request` 钩子做额外校验（页面给了用 `current_setting('request.jwt.claims', true)::json->>'email'` 做封禁的示例）。

**我们能借什么**：**这正是本项目应该走的形态**。`mt_portal` = `authenticator`；`mt_t0` = `anonymous` 等价物（未登录/最低）；`mt_t1/t2/t3` = 业务角色；HTTP 层（`http.server`）只负责**把已核验的会话换成 `SET LOCAL ROLE`**，不做任何权限判断。

**借不了的代价**：PostgREST 由框架统一施加 `SET LOCAL ROLE`，而本项目的 `http.server` 是手写路由——**每一处取数都必须自己记得设角色**。这需要一条"漏设即失败"的默认值来兜底：本项目选择的是 `mt_portal` 零权限（**漏设 ⇒ 读不到**），这是正确方向。

**Hasura —— 应用层权限（反例价值）**（实际打开 <https://hasura.io/docs/2.0/auth/authorization/permissions/>）

- 权限三元组：**(table, role, operation)**；请求带 `X-Hasura-Role` 等 session variable；权限表现为**布尔表达式（行）+ 列选择**，并编译成**一条 SQL**。
- 除行/列权限外还有**聚合权限、行数上限、root field 可见性、column presets、backend-only mutations**——粒度比 PostgreSQL 原生列权限更细（例如"能 `count` 但不能 `select`"）。
- **它做对了什么**：粒度细、从一个地方集中配置、并显式处理了"聚合泄漏"（有聚合权限这一独立开关）。
- **我们能借什么**：**为聚合单独设闸**。本项目已有 `access_policy.action = export_aggregate`（实测：`F_PERSON_HEALTH_LIMITS.export_aggregate = T2`），与 Hasura 的聚合权限同构。**注意**：PostgreSQL 的 `count(*)` **恰恰不受列权限约束**（§2.1-B 实测），所以"列受限"**不自动等于**"聚合受限"——想控聚合必须在 `column_policy` 之外另设判定（本项目靠 `access_policy` 的 action 维度）。
- **借不了的代价**：Hasura 的强制点在**应用层（GraphQL 引擎）**。任何能直连数据库的人都可以绕过它。本项目既然已有数据库层能力（列 GRANT + RLS），就不该把强制点降级到应用层。

### 4.2 尚未闭合的缺口（全部实测，**都是可复现的失败**）

**缺口 1（最高优先）：审计日志写不进去 —— `access_test.py` 当前 FAIL 2 项。**

```
【A5】访问日志：读也要留痕…
  [FAIL] 记日志失败：permission denied for table access_log
  [FAIL] access_log 从 0 增到 0（真的写进去了）
结果：PASS 25 项，FAIL 2 项
```

**根因（我实测定位）**：不是 `access_log` 的表权限，而是**序列权限**。

```sql
-- 实测：mt_t1 确实有 INSERT，但序列 USAGE 为假
SELECT has_table_privilege('mt_t1','mt.access_log','INSERT');                    -- t
SELECT has_sequence_privilege('mt_t1','mt.access_log_access_id_seq','USAGE');    -- f  ← 真凶

-- 只补这一句，log_access() 立刻可用（实测 OK）
GRANT USAGE ON SEQUENCE mt.access_log_access_id_seq TO mt_t1;
```

**为什么 `019` 没修好**：`019` 的注释说「`apply_role_baseline()` **必须**一并重建，否则'收回全部'会顺手收掉这些权限（踩过一次：访问日志写不进去）」——它**只补回了 `INSERT ON access_log`，漏了同一次 `REVOKE ALL ON ALL SEQUENCES` 收掉的序列 `USAGE`**。`017` 原本是成对授权的（`GRANT INSERT ON access_log` + `GRANT USAGE ON SEQUENCE access_log_access_id_seq`，实测 017 第 377–378 行），`REVOKE` 把两条都收走了，基线函数只补回了一条。

**建议修复**（一行，且应写进 `apply_role_baseline()` 而不是手工执行）：

```sql
-- 在 apply_role_baseline() 的 FOREACH 循环内，紧跟 GRANT INSERT 之后
EXECUTE format('GRANT USAGE ON SEQUENCE mt.access_log_access_id_seq TO %I', r);
```

> **教训可以推广成规则**：**一个"重建全部授权"的函数必须重建全部。** 它的正确性不能依赖于"没人碰过其它授权"。凡是"先 REVOKE ALL 再重建"的对账函数，都要有一张**基线清单**，并且有一条断言去核对"执行前后基线权限集合相同"。`019` 已经把基线抽成 `apply_role_baseline()`，**只差把这行补进去，并加一条 `has_sequence_privilege` 的断言**。

**缺口 2（最高优先）：强制点还没接到应用层 —— 三个进程仍以 `postgres` 超级用户连接。**

实测（`Select-String` 扫全仓）：

```
code/db.py:23                 user=postgres
code/demo/portal.py:64        user=postgres      ← :8082 只读门户
code/demo/portal_dev.py:261   user=postgres      ← :8083 开发者模式
code/demo/static_site.py:34   user=postgres
code/bridge/exchange.py:46    user=postgres
code/bridge/outbox.py:38      user=postgres
code/bridge/projection.py:41  user=postgres
code/demo/app.py:34           user=postgres
ops/backup/backup.py:48       user=postgres
ops/screenshots.py:44         user=postgres
```

**这意味着：`017`–`019` 建立的列级授权，目前对任何一个正在运行的进程都没有约束力。** 一个以 `postgres` 连接的进程可以读任何列、任何行，`FORCE ROW LEVEL SECURITY` 也拦不住（§2.2-C 实测）。

**这是"标签 vs 拦截"这句话在当前时点的**真实状态**：**数据库层已经把拦截造好了，应用层还没走上去。** 修复方向明确：

| 进程 | 应使用的连接 | 会话动作 |
|---|---|---|
| `:8082` 只读门户 | `mt_portal`（LOGIN，零权限） | 解析会话 cookie → `SET LOCAL ROLE mt_t<等级>` → `log_access()` |
| `:8083` 开发者模式 | 单独的 `mt_dev`（**不要**用 `mt_portal`） | 可写，但要保留"试运行默认回滚"与写操作审计 |
| `:8081` 业务控制台 | 单独角色 | 与管理动作分离 |
| `ops/backup/backup.py` | **保持 `postgres`**（否则 RLS 会让备份**静默丢行**） | 见 §5 反模式 |
| `code/bridge/*` | 单独 `mt_bridge`，只授必要列 | 小程序侧最小权限 |

**缺口 3：视图全部不可读，且不在策略内。**

实测：18 个视图 `in_policy = 0`；四个等级角色对视图只有 3 个元数据对象的权限。`018` 的注释已明确这是**有意的收口**（"视图的授权必须逐个评审"）。需要补的是**评审流程与逐视图决策**，而不是批量 `GRANT`。

**缺口 4：`column_policy` 的字典依据只有 8%。**

实测 91.9% 的列归属来自 `pattern`/`table_default`（列名正则与"默认 T1"）。这不是 bug，是**字典没跟上**的信号——用户明确说"每一个字段权限不同"，而当前**绝大多数字段的等级是正则猜的**。`field_catalog` 有 176 个字段、T2/T3 共 18 个，与 1029 个物理列之间**缺一张映射**（`field_id` 靠 `regexp_replace(field_id,'^F_[A-Za-z0-9]+_','')` 与列名模糊比对，实测大量 T2/T3 字段落在 `person`/`person_demographics` 上，而 `person` 表**根本没有** `F_PSN_CRED_AGE_BAND`/`F_PSN_GEO_HUKOU_*` 这些列——它们不存在于任何物理列）。

**缺口 5：`X`（禁止）等级为空。** 实测 `column_policy` 中 `min_tier='X'` 有 **0 行**，但 `access_policy` 里有 4 条 `export_row = X` 的策略。说明**列级（能不能读）与动作级（能不能导出）两套策略目前没有汇合**：`column_policy` 只表达"可读性"，导出禁令仍只在 `access_policy` 里，**尚未有强制点**。

### 4.3 方案

#### 4.3.1 分级与"公开字段"的口径（不另建一套）

**唯一判定源链**（**不新增第二套分级**）：

```
mt.field_catalog.access_tier          ← 字段字典里的权威等级（176 字段，T0=53/T1=105/T2=13/T3=5）
        │  refresh_column_policy()
        ▼
mt.column_policy(table_name, column_name, min_tier, source)   ← 落到物理列（1029 列）
        │  apply_column_grants()
        ▼
GRANT SELECT (列) ON mt.表 TO mt_t<rank>                      ← 数据库层的拦截
```

`access_policy` 提供**动作维度**（`view_inline` / `export_row` / `export_aggregate` / `query` / `bulk_download`），与列级可读性**正交**：列级答"能不能碰这一列"，动作级答"能不能把它带走"。

**用户点名的"公开"字段如何落地**：`017` 的兜底正则已经照用户原话写了（实测存在）：

```sql
-- ① 公共标识：编号/主键。用户明确说过"编号可以是公开"。
IF r.column_name IN ('person_id','subject_code','job_id','occupation_id', …) THEN
  v_tier := 'T0';
-- ③ 年龄相关：用户明确说"年龄可以是公开"
ELSIF r.column_name IN ('birth_year','age','age_band') THEN
  v_tier := 'T0';
```

> ⚠ **一处需要决策的口径冲突**：`birth_year` 被兜底规则判为 **T0（公开）**，但 `field_catalog` 里 `F_PERSON_BIRTH_YEAR` 是 **T2**，且 `docs/06` §2 把"出生年份"列为 T2 受控。`refresh_column_policy()` 的覆盖规则是"字典可覆盖模式"，所以最终应以 **T2** 为准——**但用户原话明确说"年龄可以是公开"**。
>
> 建议的最小改动不是改代码，而是**改数据**：把"可公开的年龄"定义为**年龄段**（`age_band`，如 `age_band = '25-29'`）而非**出生年份**，并在 `field_catalog` 里把 `F_PERSON_CRED_AGE_BAND` 设为 T0、`F_PERSON_BIRTH_YEAR` 保持 T2。这样既满足用户"年龄可以公开"，又不让"出生年份"（准标识符，可用于再识别）外泄。**这是数据治理决策，需要 DPO 确认，我在此只指出冲突。**

#### 4.3.2 强制点在哪一层：**数据库拒绝**（不是应用层隐藏）

**立场**（沿用本项目 README 的"能被证明"纪律）：

> **强制点在 PostgreSQL 的授权系统**：列级 `GRANT`（决定能读哪些列）+ RLS（决定能读哪些行）+ 视图（决定对外形态）。
> **应用层只做两件事**：把已核验的 HTTP 会话翻译成 `SET LOCAL ROLE`；把结果渲染出来。**应用层不做权限判断**（不做"要不要显示这一列"的 if）。

**为什么必须这样，而不是"应用层过滤"**：实测给出的三条不可替代的理由——

1. **`SELECT *` 会被数据库拒绝**（§2.1-A/B）。应用层过滤要求每一处都记得裁剪；一旦有人写了 `SELECT *`，应用层方案**静默泄漏**，数据库方案**直接报错**。
2. **漏设身份 ⇒ 读不到**（实测 `mt_portal` 零权限）。默认方向是安全的：忘记设等级是"页面坏了"（立刻可见），不是"数据漏了"（不可见）。
3. **对账可重放**（实测 `apply_column_grants()` 幂等：收回 `mt_t3` 对 `occupation` 的权限 → T3 立刻读不到 → 重放 → 恢复 1040）。**权限是算出来的，不是手工攒的**，这是"能被证明"的前提。

**唯一必须留在应用层的判断**：`action`（这次访问的目的是 `view_inline` 还是 `export_row`）——因为它来自 HTTP 意图，数据库无从得知。但**它的后果必须在数据库生效**（见 4.3.5）。

#### 4.3.3 角色清单与可见等级矩阵

| 角色 | 类型 | 对应"谁" | 可读 `column_policy.min_tier` | 可读 X | 写 | 说明 |
|---|---|---|---|---|---|---|
| `mt_t0` | NOLOGIN 组 | 未登录访客 | T0 | ✗ | ✗ | 等价于 PostgREST 的 `anonymous` |
| `mt_t1` | NOLOGIN 组 | 小程序注册用户 | T0,T1 | ✗ | ✗ | 默认等级 |
| `mt_t2` | NOLOGIN 组 | 本机构员工（运营/招聘顾问） | T0,T1,T2 | ✗ | ✗ | 人口学、户籍、审计流水 |
| `mt_t3` | NOLOGIN 组 | 数据管理员 / DPO | T0,T1,T2,T3 | ✗ | ✗ | 可识别身份与健康项；**每次读取必须留痕** |
| `mt_portal` | LOGIN | `:8082` 只读门户进程 | **自身 0 权限**，必须 `SET LOCAL ROLE mt_tN` | ✗ | 仅 `INSERT` 审计 | 与 PostgREST 的 `authenticator` 同构 |
| `mt_dev`（待建） | LOGIN | `:8083` 开发者模式 | 按需，但**必须独立于 mt_portal** | ✗ | 可写 + 强制审计 | 写能力不能出现在只读进程里 |
| `mt_bridge`（待建） | LOGIN | `code/bridge/*` 小程序接入 | 只授必要列 | ✗ | 受限写 | 最小权限 |
| `postgres`（现状） | 超级用户 | 运维/备份 | **全部（绕过一切）** | ✓ | ✓ | **只能用于备份与迁移，不能给应用** |

**升级路径**（身份 → 等级）：

```
HTTP 请求
  │  ① 无 cookie / 会话无效              → mt_t0   (访客)
  │  ② 有效会话 + 已同意数据使用          → mt_t1   (注册用户)
  │  ③ 会话主体在 staff 名单（本机构员工） → mt_t2   (员工)
  │  ④ 会话主体在 dpo 名单 + 二次验证      → mt_t3   (管理员)
  ▼
SET LOCAL ROLE mt_t<N>   ← 唯一把"等级"变成"权限"的动作
```

**降级路径**（同等重要，且当前缺失）：主体撤回同意（`consent_record.revoked_at`）或 `person.status='withdrawn'` → 该人相关行不应再返回。这属于**行级**问题，见 4.3.4。

**矩阵的验收方式**（可直接写成断言，不必读代码）：

```sql
-- 对每个等级角色，列权限数必须严格递增，且 T0 只能是 T0 列
SELECT grantee, count(*) FROM information_schema.column_privileges
 WHERE table_schema='mt' AND privilege_type='SELECT' AND grantee LIKE 'mt_t%'
 GROUP BY 1 ORDER BY 1;      -- 实测：290 / 963 / 1026 / 1025（应严格递增）
```

#### 4.3.4 会话与身份传递（`http.server`，无框架）

**现状**：`code/demo/portal.py` 是纯 `BaseHTTPRequestHandler`、零 JS、零 CDN、服务端渲染；取数走 `db()` → `psycopg.connect`。**没有登录态**。

**要加的三件东西**（按最小改动排序）：

1. **会话表 + 签名 cookie**（不引入框架）：
   ```sql
   CREATE TABLE mt.web_session (
     session_id      text PRIMARY KEY,            -- 随机 32 字节 hex
     actor           text NOT NULL,               -- 业务身份，如 'u_1001@mini'
     tier            text NOT NULL REFERENCES mt.access_tier(tier),
     purpose         text,                        -- 本次会话的用途（对齐 consent_record.purpose）
     created_at      timestamptz NOT NULL DEFAULT now(),
     expires_at      timestamptz NOT NULL,
     revoked_at      timestamptz
   );
   ```
   Cookie 只存 `session_id`（`HttpOnly; SameSite=Lax; Secure`），**等级一律回库查**，绝不放 cookie 里（cookie 可被改）。会话表本身是 T2 级（`column_policy` 的 pattern 规则已覆盖：`access_log` 同类被归 T2）。

2. **每请求一个事务，身份用 `SET LOCAL`**（连接池复用的正确姿势）：
   ```python
   with psycopg.connect(PORTAL_DSN) as c:      # PORTAL_DSN: user=mt_portal
       with c.cursor() as cur:
           cur.execute("BEGIN")
           cur.execute("SELECT set_config('mt.actor', %s, true)", (actor,))
           cur.execute("SELECT set_config('mt.tier',  %s, true)", (tier,))
           cur.execute(sql.SQL("SET LOCAL ROLE {}").format(sql.Identifier("mt_" + tier.lower())))
           ...  # 取数
           cur.execute("SELECT mt.log_access(%s,%s,%s,%s,%s)", (...))
           cur.execute("COMMIT")
   ```
   > ⚠ `SET ROLE` **不接受参数占位符**（`docs/12` 已记录过同类坑：`SET LOCAL statement_timeout = %s` 报 `syntax error at or near "$1"`）。角色名来自白名单枚举、且用 `sql.Identifier` 转义。

3. **"门户只读但要有登录态"的落法**：写入会话的是**另一个进程/另一条连接**（例如 `:8083` 或一个最小登录服务），`:8082` 只读 `web_session`。这样 `:8082` 的"只读"证明（`docs/12`：遍历全部页面后 `change_log` 不增长）**依然成立**：它读会话，不写会话。

**登录态与"零 JS"的兼容**：登录页用原生 `<form method="post">` 提交，服务端 302 回原页；**不需要任何 JS**。

#### 4.3.5 审计表结构与写入时机

**表结构**：复用已落地的 `mt.access_log`（实测 10 列，见 §2.4）。**建议只新增两列**（`ALTER TABLE` 追加，不改既有列）：

```sql
ALTER TABLE mt.access_log
  ADD COLUMN IF NOT EXISTS session_id text,        -- 关联 mt.web_session
  ADD COLUMN IF NOT EXISTS declared_tier text;     -- 应用"声称"的等级（与 actor_role 实际权限对照）
```

理由：`actor_role` 记的是**实际生效角色**（实测 `log_access()` 用 `current_user`），`declared_tier` 记**应用声称的等级**。两者不一致 = 有 bug 或有人在绕过，**这是最值得告警的一类日志**。

**写多少：分级采样**（这是体积与价值的取舍）

| 访问类型 | 是否留痕 | 粒度 | 理由 |
|---|---|---|---|
| T0 列表浏览（`/talent`、`/occupations`） | **记 1 条会话级** | `(actor, action='view', target='talent_list', row_count=N)` | 一次翻页 50 行，逐行记会让审计表比业务表大 |
| T1 浏览 | 记 1 条 | 同上 | 与 T0 同 |
| **T2/T3 任意读取** | **必记**（每次） | `(actor, target='person_demographics.birth_year', row_count=1)` | 敏感级，逐次留痕是合规底线 |
| **任何 `export_*` / `bulk_download`** | **必记** | 含 `row_count`、`purpose`、`detail.cells_suppressed` | 导出是"数据离开库"的时刻 |
| `/sql` 只读控制台 | **必记**，含 `detail.query_fingerprint` | 不记全文（可能含敏感字面量），只记指纹 | 这是唯一接受任意 SQL 的入口 |
| 策略变更（`access_policy`/`column_policy` 写入） | 走 `change_log`（已有触发器） | — | 变更 ≠ 访问 |

**性能与体积代价（诚实的估算，未实测）**：一行 `access_log` 约 200–300 字节（含 jsonb 空对象）。若 T2/T3 读取按每天 1000 次计，约 0.3 MB/天 ≈ 110 MB/年；`docs/06` §6 定的保留期是**在线 24 个月 + 归档 12 个月**，量级可接受。**真正的风险不是体积，而是"记了没人看"**——建议配一条月度检查：`access_log` 中 `access_tier='T3'` 且 `purpose IS NULL` 的条数必须为 0（`docs/06` §8 已写"缺 purpose 的访问视为违规"）。

**写日志本身必须不可被篡改**：
```sql
REVOKE UPDATE, DELETE ON mt.access_log FROM PUBLIC;   -- docs/06 §11.2 已有此句
```
且**审计表自己也要有等级**：实测 `column_policy` 已把 `access_log` 全部列归 **T2**，即 `mt_t0/mt_t1` **读不到审计日志**（实测：`mt_t1` 读 `access_log` 报 `permission denied`）。这是对的：**审计数据不是"谁都能自证清白"的东西**。

#### 4.3.6 与小程序接入（`code/bridge/`）的关系

**现状（读代码 + 实测）**：
- `code/bridge/exchange.py` 有硬规则 R1：**交换包禁止出现身份标识**（`memberKey`/`openid`/`appid`/手机号/证件号/密钥…深度扫描，命中即**整包拒绝**）。本库 `person_id` 是随机 ID，不含任何微信标识（R2）。
- 小程序侧的"授权"以 `consent_change` 事件进入（R6：撤回 `personal_analysis` 后，任何新分析产物一律拒绝，返回 `CONSENT_REQUIRED`）。
- 但 `bridge/*.py` 目前同样以 `user=postgres` 连接（缺口 2）。

**映射设计**（三层，各司其职）：

| 层 | 身份形态 | 存在哪 | 本库如何映射 |
|---|---|---|---|
| 小程序登录态 | `openid` / 小程序会话 | **小程序侧**，绝不进本库 | 不映射（R1 强制） |
| 小程序用户 | 随机 `personId`（契约 §7） | 交换包字段 | → `mt.external_identity`（`sourceSystem + personId` 唯一绑定到本库 `person_id`，R2 已实现） |
| 本库访问身份 | `mt.actor`（会话字符串） | `mt.web_session.actor` + `access_log.actor` | 建议形如 `wx:<sourceSystem>:<personId>`，**仅供审计关联，不作为授权依据** |

**授权依据永远是等级角色，不是小程序身份**：小程序用户经桥接后得到的是 `mt_t1`（注册用户）——**"在小程序登录过"这件事本身不授予任何列权限**。若某个小程序用户被提升为员工，那是**本库侧的管理动作**（写 `web_session.tier`），不来自交换包。

**桥接进程的最小权限（建议 `mt_bridge`）**：

```sql
-- 只授桥接真正需要的列，而不是整表
GRANT USAGE ON SCHEMA mt TO mt_bridge;
GRANT SELECT (person_id, subject_code, source_id, status) ON mt.person TO mt_bridge;
GRANT SELECT (external_identity_id, person_id, source_system, external_id, status)
      ON mt.external_identity TO mt_bridge;
GRANT INSERT (answer_id, session_id, question_id, option_ids, ordinal, status)
      ON mt.answer TO mt_bridge;
GRANT SELECT, INSERT ON mt.external_identity TO mt_bridge;   -- 按实际需要收窄
-- 桥接不得读 person_pii / person_demographics.health_limits / person_constraint
```

> 建议在 `column_policy` 里**为桥接单独留一行说明**（而不是把它的偏好塞进全局策略）：`column_policy` 的主键是 `(table_name, column_name)`，**一个列只能有一个等级**，无法表达"bridge 角色比 mt_t1 更窄"。因此桥接的收窄必须靠**独立的 GRANT 语句 + 一条断言**（断言：`has_column_privilege('mt_bridge','mt.person_pii','full_name_enc','SELECT')` 必须为 `false`）。

#### 4.3.7 行级安全（RLS）：还没做的部分

实测：**`mt` 下启用 RLS 的表 0 张，策略 0 条。** 这是下一阶段最大的一块。

**建议的落地顺序**（每步都可独立验收）：

```sql
-- 步骤 1：先给"撤回/删除"这类最硬的场景上 RLS（person_pii 最典型）
ALTER TABLE mt.person_pii ENABLE ROW LEVEL SECURITY;
ALTER TABLE mt.person_pii FORCE  ROW LEVEL SECURITY;   -- 属主也受约束（实测必需）

-- 仅授权角色可读；且主体未撤回
CREATE POLICY p_pii_authorized ON mt.person_pii
  FOR SELECT TO mt_t3
  USING (EXISTS (SELECT 1 FROM mt.person p
                  WHERE p.person_id = person_pii.person_id
                    AND p.status = 'active'));

-- 步骤 2：把"禁止导出"做成 restrictive（实测：restrictive 用 AND 合并）
CREATE POLICY p_no_row_export ON mt.person_pii AS RESTRICTIVE
  FOR SELECT TO mt_t3
  USING (current_setting('mt.action', true) IS DISTINCT FROM 'export_row');
```

**三个必须写进代码注释的实测边界**：
1. `ENABLE` 不够，**必须 `FORCE`**（属主绕过，§2.2-A/B 实测）；
2. **超级用户连 `FORCE` 也拦不住**（§2.2-C 实测）→ 所以 RLS 的前提是**应用不再以 `postgres` 连接**（缺口 2）；
3. **同命令类型下多条 permissive 策略是 `OR`**，不会互相收窄；要收窄必须用 `AS RESTRICTIVE`（§2.2-B/D 实测）。

## 5. 反模式与事故清单

> 每条格式：**现象 → 为什么危险 → 怎么发现 → 怎么防**。标注「实测」的，我在本机验证过。

### 5.1 【最危险】以为 RLS 生效，其实表属主绕过 —— 而且这条**本项目已经踩了**

- **现象**：`ALTER TABLE t ENABLE ROW LEVEL SECURITY` 之后，属主仍然看到全部行。**实测**：属主在 `ENABLE` 后 `count(*)=2`（两条策略一真一假），`FORCE` 后仍是 2（因为 permissive 是 `OR`）。
- **为什么危险**：`ENABLE` 与 `FORCE` 只差三个字母，语义差一个数量级。更危险的是**它不会报错**——一切看起来正常，只是策略没生效。
- **怎么发现**：
  ```sql
  SELECT relname, relrowsecurity, relforcerowsecurity FROM pg_class
   WHERE relnamespace='mt'::regnamespace AND relkind='r' AND relrowsecurity;
  -- 实测当前：0 行（一张都没开）。将来开了表，必须同时核对 relforcerowsecurity
  ```
- **怎么防**：建表/建策略时**总是成对写**；把"`relrowsecurity = true` 而 `relforcerowsecurity = false`"设为一条**CI 断言**（`ops/tests/access_test.py` 里加一条即可）。

### 5.2 【最危险】给视图却不给基表，但视图属主是超级用户 —— 后门

- **现象**：应用只有视图的 `SELECT`，基表一列没授，看起来"只读视图最安全"。**实测**：`v_plain` 由 `postgres` 拥有，应用读 `SELECT health FROM v_plain` **成功**，读到 `colorblind`。
- **为什么危险**：视图默认以**视图属主**权限执行（官方文档原文）。属主是超级用户时，视图 = 万能钥匙；而"我只授了视图、没授基表"会给人**虚假的安全感**。
- **怎么发现**：
  ```sql
  SELECT viewname, viewowner FROM pg_views WHERE schemaname='mt';
  -- 任何 viewowner 是 postgres 或表属主的视图，都是潜在后门
  ```
- **怎么防**：三选一 —— ① 视图**不投影**受限列（首选）；② 视图开 `security_invoker=true` 且属主非超级，同时给调用者授必要的基表列权限（**实测 B5**：只授视图会 `permission denied`，说明它严格）；③ 视图建在专用低权角色名下。

### 5.3 【最危险】"先 REVOKE ALL 再重建"的授权对账会静默清掉别的授权

- **现象**：`apply_column_grants()` 里 `REVOKE ALL ON ALL TABLES/SEQUENCES` 之后只重建"它关心的那一部分"。**本项目已踩两次（都有实测记录）**：
  - `018` 记录：紧跟的 `REVOKE ALL ON 每张表` 把刚授好的列权限清空，`mt_t1` 列权限 **942 → 180**，被访问测试的"阶梯严格递增"断言抓住；
  - `019` 记录 + **我的实测**：`REVOKE ALL ON ALL SEQUENCES` 收掉了 `access_log_access_id_seq` 的 `USAGE`，基线函数只补回了表上的 `INSERT`，于是**审计日志至今写不进去**（`access_test` A5 FAIL 2 项，根因实测为 `has_sequence_privilege(...) = false`）。
- **为什么危险**：**这不是安全漏洞，而是"安全机制自己瘫痪"**——审计写不进去，等于整条"记录访问用户"的需求落空，而表面上一切正常。
- **怎么发现**：一条断言即可 —— **对账前后，基线权限集合必须完全相同**：
  ```sql
  SELECT has_table_privilege('mt_t1','mt.access_log','INSERT')                    AS ins,
         has_sequence_privilege('mt_t1','mt.access_log_access_id_seq','USAGE')    AS seq;
  -- 实测当前：ins = t，seq = f  ← 这一行就是 bug 的指纹
  ```
- **怎么防**：① 基线权限写成一张**清单**（本项目已有 `apply_role_baseline()`，但**清单不完整**，缺序列 `USAGE`）；② 对账函数**末尾**加一条"基线自检"，缺任何一项就 `RAISE EXCEPTION`；③ 任何"REVOKE ALL"都要能回答"我重建了它的全部吗"。

### 5.4 把等级存在客户端可改的地方（GUC / cookie / JWT 未签名）

- **现象**：判定写成 `current_setting('mt.tier') >= 'T3'`。**实测**：非超级用户**可以** `set_config('mt.tier','T3',true)`，**没有任何报错**。
- **为什么危险**：整个授权模型变成"应用不说谎就行"。一旦有一处 SQL 拼接、一次 `set_config` 的调用顺序错误，等级就是装饰。
- **怎么发现**：搜代码里有没有把 GUC 直接用于判定（而不是用于记录）；再写一个反面测试：以 `mt_t0` 身份 `set_config('mt.tier','T3')` 之后**仍然读不到** T3 列（本项目 `access_test` A6 就是这个方向）。
- **怎么防**：**判定只看角色，角色不可伪造**（实测：非超级用户 `set_config('role','postgres')` 与 `set_config('role','<非成员角色>')` 均被拒绝）。`mt.tier` 只用于写日志与展示。

### 5.5 应用仍以超级用户连接（**本项目当前的状态**）

- **现象**：数据库层把列级授权、RLS 都配好了，但进程连的是 `user=postgres`。**实测**：`postgres` 读 RLS 表看到全部行（`FORCE` 也无效），列级授权对超级用户**完全无效**。
- **为什么危险**：这是**最典型的"安全 theater"**——评审时看迁移脚本一切完美，实际跑起来一个拦截都没有。本项目的 `:8082` 门户尤其危险：它以"只读"为卖点，而**只读 ≠ 受限**；它能读**每一个字段**。
- **怎么发现**：`Select-String -Pattern "user=postgres"` 扫全仓（实测命中 10 处），逐个确认是"应用"还是"运维"。
- **怎么防**：应用一律用专用 LOGIN 角色；`postgres` 只留给 `ops/backup`、迁移与应急。并把这条写成测试：**以门户角色连接，验证它读不到 T3 列**。

### 5.6 `GRANT ALL` / `GRANT SELECT ON ALL TABLES` 泄漏

- **现象**：为图省事授 `ALL`。本项目 `018` 的注释明确记录了这个诱惑（"批 `GRANT SELECT ON ALL TABLES` 会把视图一并授出"）。
- **为什么危险**：`ALL TABLES` 包含**视图**，而视图以属主权限执行（5.2）→ 一条语句产生一个后门；且 `ALL` 对**未来新建**的表无效（是快照），于是"以为授全了"与"实际漏了"同时存在。
- **怎么发现**：`information_schema.role_table_grants` 里出现非预期的对象；或断言"没有任何角色持有表级 `SELECT`（只应有列级）"。
- **怎么防**：只授**列**、逐对象评审；用 `ALTER DEFAULT PRIVILEGES` 时**不**给 `SELECT`（默认权限只用于 `EXECUTE`/`USAGE` 这类安全项）。

### 5.7 审计表自己没有等级，或被应用角色写坏

- **现象**：`ACCESS_LOG` 谁都能读、谁都能改；或者审计表建了但没有保留期，涨到无法查询。
- **为什么危险**：审计数据本身含**敏感信息**（谁在什么时候关心哪个人的健康项）。它泄漏 = 二次伤害；它能被改 = 审计无效。
- **本项目的现状（实测，值得肯定）**：`column_policy` 已把 `access_log` 全列归 **T2**，`mt_t0/mt_t1` 读不到（实测 `permission denied`）；`REVOKE UPDATE, DELETE FROM PUBLIC` 已写在 `docs/06` §11.2。
- **怎么防**：① 审计表等级 ≥ 被审计对象的最低等级；② 写入口收口到一个函数（`log_access()`）而不是散落的 `INSERT`；③ 保留期进 `retention_policy`（`docs/06` §6 已定 24+12 个月）。

### 5.8 加密密钥与密文同机存放

- **现象**：`person_pii` 用 `pgcrypto` 加密（有 `encryption_key_id` 列），但密钥存在同一台机器、同一个仓库、甚至同一个环境变量里。
- **为什么危险**：备份、dump、开发机复制都会**同时带走密文与密钥**，加密退化为编码。本项目 `ops/backup/backup.py` 默认不导出 `person_pii`（`docs/12` 一.2 ③），这是好设计；但**只要密钥在本机，任何一次全库 dump 的泄漏都包含密钥**。
- **怎么发现**：搜密钥字面量 / `.env` / `encryption_key_id` 的取值来源；核对备份包内是否含密钥材料。
- **怎么防**：密钥与密文**分离**（不同主机/不同凭据体系/HSM）；备份**不含密钥**；`encryption_key_id` 轮换流程写进 `docs/06` §8 的应急流程（已有"轮换 `encryption_key_id`"一条）。
- **未验证**：本项目当前密钥的实际存放位置我**没有检查**（不在本次任务范围，且可能需要读取敏感配置）。**建议单独审计一次。**

### 5.9 只加不减的权限累积

- **现象**：给某人加了权限，事后移除时只删了"角色成员关系"，忘了列级 `GRANT`；或者反过来，策略表里删了一行但库里授权还在。
- **为什么危险**：`access_policy` 说"不许"，`pg_attribute.attacl` 说"可以"——**两套事实**，且**没有任何页面同时显示它们**。
- **怎么发现**：
  ```sql
  -- 策略说 X（禁止）但库里仍有 SELECT 授权的列（应为空集）
  SELECT cp.table_name, cp.column_name, a.grantee
    FROM mt.column_policy cp
    JOIN pg_attribute a ON a.attrelid = ('mt.'||cp.table_name)::regclass
                       AND a.attname  = cp.column_name
   CROSS JOIN LATERAL aclexplode(a.attacl) x
   WHERE cp.min_tier = 'X';
  ```
- **怎么防**：`apply_column_grants()` 的"先收回再重授"就是这条的解药（实测幂等）；**关键是它必须被真的定期跑**（建议：每次策略变更后 + 每日一次 + CI 里一次）。

### 5.10 把"忘了设身份"设计成"读到全部数据"

- **现象**：代码路径里等级默认为最高，或 `current_setting('mt.tier')` 取不到时 `COALESCE(..., 'T3')`。
- **为什么危险**：**默认值方向决定事故形态**。默认最高 → 配置错误时静默泄露；默认最低 → 配置错误时页面报错，立刻被发现。
- **本项目的现状（实测，值得肯定）**：`session_tier()` 缺省为 `'T0'`，`session_actor()` 缺省为 `'anonymous'`，`mt_portal` 自身零权限。**"忘了设等级 ⇒ 读不到任何数据"**（实测 `permission denied for table person`）。
- **怎么防**：把"默认拒绝"写进测试（`access_test` A2 就是这个）。

### 5.11 用 RLS 表达"列级"需求（错配）

- **现象**：想隐藏某列，却去写 `CREATE POLICY`。RLS **不管列**。
- **为什么危险**：写了策略、测了"看不到那个人的行"，于是以为列也安全了；实际 `SELECT *` 照样把那列带出来。
- **怎么防**：**列的问题用列权限/视图，行的问题用 RLS**。两者组合才是完整答案（本方案 = 列级 `GRANT` + 必要的 RLS + 视图形态）。

### 5.12 审计日志"记了没人看" / 缺 purpose 的访问

- **现象**：`access_log` 涨到几百万行，从来没人查；或 T3 读取的 `purpose` 为 NULL。
- **为什么危险**：合规上"有日志"不等于"有监控"。`docs/06` §8 明写"缺 `purpose` 的访问视为违规"，但**没有强制点**（`purpose` 列可空，实测）。
- **怎么防**：① 对 T2/T3 的 `log_access()` 调用**强制传 purpose**（把参数改为无默认值，或在函数内 `RAISE EXCEPTION`）；② 月度检查 `access_tier='T3' AND purpose IS NULL` 必须为 0；③ 把 `access_log` 的**读取**做成一个管理页面（本项目 `:8083` 已有 `/audit` 页，可扩展）。
