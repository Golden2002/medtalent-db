# 04 · 技术架构：可扩展人才数据模型与匹配引擎

> 目标：为医学生人才信息库建立「结构化存储 + 高自由度分析 + 可演进 schema + 人岗匹配」的技术参考。
> 标注约定：**【事实】**＝有公开来源支撑；**【建议】**＝本文作者的设计判断，需经项目验证。
> 环境前提：本地 Windows 单机、无云依赖、可离线。

---

## ① 建模范式对比与选型

### 1.1 五种可扩展建模范式

| 范式 | 核心机制 | 加字段成本 | 加实体成本 | 分析友好度 | 主要代价 |
|---|---|---|---|---|---|
| 类型化表 + 扩展属性（typed tables + JSONB overflow） | 稳定字段建列，长尾字段进 JSONB | 低（无 DDL 即可写） | 中（需新建表） | 高（列式扫描友好） | JSONB 无约束，需应用层治理 |
| 宽表（wide table） | 所有属性直接建列 | **高（DDL + 回填 + 锁表）** | 低 | 极高 | 列爆炸、稀疏、不可持续 |
| 长表 / EAV | 一行一个「实体-属性-值」 | 极低 | 低 | **低**（每次查询要 pivot，多层 join） | 无法做类型约束与统计 |
| Data Vault 2.0 | Hub（业务键）/ Link（关系）/ Satellite（描述性属性，带 load_date 与 hash diff） | 低（新增 Satellite 或 Satellite 加列，不动上游） | 低（新增 Hub/Link） | 中（需建 Business Vault / 星型呈现层） | 表数量膨胀、需自动化生成 |
| Anchor Modeling | Anchor（身份）+ Attribute（6NF，值+时间戳）+ Tie（关系）+ Knot（共享词表） | 极低（新增 Attribute 表，无 NULL、无 ALTER 历史表） | 低（新增 Anchor/Tie） | 中（需视图/物化层） | 建模门槛高、工具生态小 |

**关键事实**

- Data Vault 2.0 由 Dan Linstedt 提出，用 Hub/Link/Satellite 分离业务键、关系与描述属性，Satellite 天然按 load 时间戳记录历史，因此**新增属性只需新增 Satellite 或向 Satellite 加列，不触碰 Hub/Link**；查询侧通过 Bridge/Business Vault 重建星型（[Microsoft Data Vault 白皮书](https://azure.microsoft.com/mediahandler/files/resourcefiles/deploying-data-vault/MS_DataVault_Whitepaper_Final.pdf)、[EMSS 2018 论文](http://www.msc-les.org/proceedings/emss/2018/EMSS2018.pdf)）。
- Anchor Modeling 把每个属性拆成独立的 6NF 表（Anchor/Attribute/Tie/Knot），属性变化**只影响单表**，且天然带时间维（[anchor modeling 技术综述](https://www.codecentric.de/en/knowledge-hub/blog/agile-database-design-using-anchor-modeling)）。
- 传统规范化模型「不内建时间维捕获机制」，需要数据仓库层自己补（[贝尔格莱德大学比较研究](https://rfos.fon.bg.ac.rs/bitstream/handle/123456789/1756/1752.pdf?sequence=1&isAllowed=y)）——这正是人才库（学历、职称、执业资格都在变）必须处理的问题。
- EAV 的问题不是理论上的：它把类型约束、统计优化和可读性全部推给应用层；PostgreSQL 的 JSONB 在**保留 schema-less 写入自由度的同时**仍可建 GIN 索引、参与约束与函数索引（[PostgreSQL JSON 类型文档](https://www.postgresql.org/docs/current/datatype-json.html)、[索引类型文档](https://www.postgresql.org/docs/current/indexes-types.html)）。

### 1.2 选型结论

**【建议】三层混合，而不是单一范式：**

1. **稳定核心用类型化关系表**（person / education / experience / skill_claim / evidence / job_posting）——这些实体的属性在医学人才场景下高度可预测，且是匹配与筛选的主战场，必须是强类型 + 可索引。
2. **长尾属性用「受控 EAV + JSONB 溢出」**：只有当 `attribute_def` 注册过、且确实需要被筛选/排序时才落列或建表达式索引，其余进 `ext_attrs JSONB`。这是 EAV 与 JSONB 取长补短的折中。
3. **历史与审计用 Data Vault 思想做「时间切片」**：不整体上 DV，但每张核心表统一带 `valid_from / valid_to / recorded_at / source_system / record_hash`（bitemporal-lite），等价于给每张表挂了一个 Satellite。
4. **呈现层另建星型/宽视图**，由 dbt 生成，不污染规范层。

**不建议一开始就上完整 Data Vault 2.0 或 Anchor Modeling**——两者都要求数仓团队与自动化生成工具，单机小库场景下维护成本大于收益；但应把它们的「不可变 + 加列不动上游」原则借过来，成本几乎为零。

### 1.3 简历解析后的归一化（入库前置步骤）

解析器吐出的 JSON 不能直接入库，同一实体有多种写法，需四步归一：

1. **切分归类**：按 section 切成 education / experience / skill / evidence 片段，保留原文 `span` 定位（这是后续可解释匹配的前提）。
2. **实体归一**：学校/医院/企业走 `org.name_norm`（去括号、去「附属/第一」等修饰、繁简统一）；专业与学位映射到 `ref.code_value`；技能短语经 `sem.skill_alias` 多对一归并到 `sem.skill`。
3. **时间归一**：`2021.09–2025.06`、`2021年9月至今` 统一为 `start_date/end_date`；**无法确定的写 NULL 而不是猜**，用 `ext_attrs.time_precision` 记录精度。
4. **冲突消解**：同字段多来源时按 `source_priority` 取权威值，其余进 `evidence` 而不覆盖——保留「简历说她 2024 年规培结束，证书显示 2025 年」这类矛盾供人工复核。

**【事实】** 行业已有公开的简历交换标准可借用字段命名与枚举，无需自造：[HR Open Standards LER-RS](https://www.hropenstandards.org/ler-rs)（前身 HR-XML）。

## ② 推荐架构（四层）

```
┌─ 服务层 Service ────────────────────────────────────────────┐
│ 人岗匹配 API · 分析 API（dbt metrics / MetricFlow）· 检索 API │
│ explain_match / candidate_search / cohort_analysis          │
├─ 语义层 Semantic ──────────────────────────────────────────┤
│ skill / concept 本体（O*NET + ESCO 骨架 + 本地扩展）          │
│ embedding 表（pgvector）· 特征快照（feature store）           │
├─ 规范层 Canonical ─────────────────────────────────────────┐│
│ person / education / experience / skill_claim / evidence     ││
│ job_posting / job_requirement · 全部带时间切片与 ext_attrs   ││
├─ 原始层 Raw ───────────────────────────────────────────────┤│
│ resume_document（原文件 + 解析 JSON 原样）· 导入批次 · 血缘    ││
└────────────────────────────────────────────────────────────┘
        DuckDB / Parquet 分析副本（只读，从规范层导出）
```

**【建议】分层不变量**：原始层只追加、永不修改；规范层可重建（幂等 ETL）；语义层可换词表版本；服务层无状态。这样任何一层重构都不需要动上层数据。

## ③ 可扩展性机制（代码骨架）

### 3.1 词表与代码表版本化（所有本体/枚举的统一底座）

```sql
-- 代码系统（词表）——版本是独立事实，不覆盖
CREATE TABLE ref.code_system (
  code_system_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  code            text NOT NULL,                -- 'ESCO' | 'ONET' | 'CN_MOE_MAJOR' | 'LOCAL_SKILL'
  name            text NOT NULL,
  authority_uri   text,                          -- 官方发布地址
  license         text,
  UNIQUE (code)
);

CREATE TABLE ref.code_version (
  code_version_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  code_system_id  bigint NOT NULL REFERENCES ref.code_system,
  version         text   NOT NULL,              -- '1.2.1' / 'O*NET 29.0' / '2021'
  released_on     date,
  is_current      boolean NOT NULL DEFAULT false,
  notes           text,
  UNIQUE (code_system_id, version)
);
CREATE UNIQUE INDEX ON ref.code_version (code_system_id) WHERE is_current;

CREATE TABLE ref.code_value (
  code_value_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  code_version_id bigint NOT NULL REFERENCES ref.code_version,
  code            text   NOT NULL,               -- 外部原始 code
  label_zh        text,
  label_en        text,
  parent_code     text,                          -- 层级（专业目录、ISCED 等）
  relations       jsonb NOT NULL DEFAULT '{}',   -- {broader:[],narrower:[],related:[]}
  deprecated      boolean NOT NULL DEFAULT false,
  replaced_by     text,
  UNIQUE (code_version_id, code)
);
```

**【建议】规则**：(a) 词表升级＝插入新 `code_version`，不 UPDATE 旧值；(b) 业务表引用 `code_value_id`（具体版本），同时冗余 `code`；(c) 跨版本映射单独建 `ref.code_crosswalk(from_code_value_id, to_code_value_id, confidence)`，把「同义/等价」变成数据而不是代码。

### 3.2 核心人事实体（带时间切片与扩展槽）

```sql
CREATE SCHEMA IF NOT EXISTS core;

CREATE TABLE core.person (
  person_id      uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  person_no      text NOT NULL UNIQUE,            -- 内部业务键（不含姓名）
  birth_year     smallint,                        -- 只存年份，降精度即是去标识化
  gender_code    text,
  domicile_prov  text,
  -- 时间切片（Data Vault Satellite 思想）
  valid_from     timestamptz NOT NULL DEFAULT now(),
  valid_to       timestamptz,                     -- NULL = 当前
  recorded_at    timestamptz NOT NULL DEFAULT now(),
  source_system  text NOT NULL,
  record_hash    bytea NOT NULL,                  -- 行内容 hash，用于幂等与变更检测
  -- 扩展槽
  ext_attrs      jsonb NOT NULL DEFAULT '{}'::jsonb,
  ext_schema_ver text  NOT NULL DEFAULT 'v1',
  CHECK (jsonb_typeof(ext_attrs) = 'object')
);
CREATE INDEX person_ext_gin ON core.person USING gin (ext_attrs jsonb_path_ops);

-- 姓名/证件等高敏字段单独隔离，最小权限
CREATE TABLE core.person_identity (
  person_id      uuid PRIMARY KEY REFERENCES core.person,
  full_name      text NOT NULL,
  name_pinyin    text,
  id_type        text,
  id_ciphertext  bytea,          -- 应用层加密，DB 不可读
  id_fingerprint bytea,          -- HMAC 指纹，用于去重比对
  updated_at     timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE core.education (
  education_id   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  person_id      uuid NOT NULL REFERENCES core.person,
  school_id      uuid,                                   -- → core.organization
  degree_code_value_id bigint REFERENCES ref.code_value,
  major_code_value_id  bigint REFERENCES ref.code_value, -- 专业目录（可跨版本）
  start_date     date, end_date date,
  is_primary     boolean NOT NULL DEFAULT false,
  ext_attrs      jsonb NOT NULL DEFAULT '{}'::jsonb,
  source_system  text NOT NULL,
  valid_from     timestamptz NOT NULL DEFAULT now(),
  valid_to       timestamptz
);
CREATE INDEX edu_person ON core.education (person_id) WHERE valid_to IS NULL;
```

### 3.3 能力与证据（匹配引擎的事实来源）

```sql
CREATE TABLE core.organization (
  org_id     uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  org_type   text NOT NULL,        -- hospital | university | company | society
  name_norm  text NOT NULL,        -- 归一化名称（去括号/去后缀）
  name_raw   text,
  UNIQUE (org_type, name_norm)
);

-- 能力声明：不存布尔标签，存「强度 + 来源 + 时间」
CREATE TABLE core.skill_claim (
  skill_claim_id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  person_id      uuid NOT NULL REFERENCES core.person,
  skill_id       uuid NOT NULL,                    -- → sem.skill
  level          smallint CHECK (level BETWEEN 0 AND 7),  -- 对齐 ESCO/O*NET 等级
  level_type     text,                             -- self_reported | inferred | certified
  confidence     numeric(4,3) NOT NULL DEFAULT 1.0,
  first_seen_at  timestamptz,
  last_seen_at   timestamptz,
  ext_attrs      jsonb NOT NULL DEFAULT '{}'::jsonb,
  UNIQUE (person_id, skill_id, level_type)
);

-- 证据：能力必须有证据链，否则匹配不可解释
CREATE TABLE core.evidence (
  evidence_id    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  person_id      uuid NOT NULL REFERENCES core.person,
  evidence_type  text NOT NULL,        -- paper | project | license | award | internship | course
  title          text,
  org_id         uuid REFERENCES core.organization,
  occurred_on    date,
  payload        jsonb NOT NULL DEFAULT '{}'::jsonb,
  source_doc_id  uuid,                 -- → raw.resume_document，支撑血缘
  span           jsonb                 -- 原文定位 {page, char_start, char_end}
);
```

**【建议】`span` 字段是解释性匹配的地基**：任何一条能力都能回溯到原文片段，前端才能给出「因为你写了『在 XX 医院 ICU 轮转 6 个月』，判定你具备重症监护经验」。

### 3.4 长尾属性的受控 EAV（只对真正开放的实体开放）

```sql
CREATE TABLE meta.attribute_def (
  attr_id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  entity_type  text NOT NULL,             -- 'person' | 'experience' | 'job_posting' ...
  attr_key     text NOT NULL,             -- 'snake_case'
  value_type   text NOT NULL CHECK (value_type IN ('string','number','boolean','date','enum','json')),
  is_searchable boolean NOT NULL DEFAULT false,   -- true 时才允许提升为列/表达式索引
  enum_system_id bigint REFERENCES ref.code_system,
  json_schema  jsonb,                     -- 该字段的值约束
  introduced_in text NOT NULL,            -- schema 版本
  deprecated_in text,
  UNIQUE (entity_type, attr_key)
);

-- 双写：类型化列 + JSONB 溢出，二者由 CHECK 保证一致
CREATE TABLE core.person_attribute (
  person_id    uuid NOT NULL REFERENCES core.person,
  attr_id      bigint NOT NULL REFERENCES meta.attribute_def,
  value_text   text,
  value_num    numeric,
  value_date   date,
  value_bool   boolean,
  value_json   jsonb,
  PRIMARY KEY (person_id, attr_id),
  CHECK (num_nonnulls(value_text, value_num, value_date, value_bool, value_json) = 1)
);
-- 只在 is_searchable 的字段上建部分索引
CREATE INDEX person_attr_num ON core.person_attribute (attr_id, value_num)
  WHERE value_num IS NOT NULL;
```

### 3.7 JSON Schema（扩展属性与解析结果校验）

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://medtalent.local/schema/ext/person.ext.v1.json",
  "title": "core.person.ext_attrs",
  "type": "object",
  "additionalProperties": false,
  "properties": {
    "hukou_province":   { "type": "string", "maxLength": 32 },
    "expected_city":    { "type": "array", "items": { "type": "string" }, "maxItems": 5 },
    "research_score":   { "type": "number", "minimum": 0, "maximum": 100 },
    "willing_night_shift": { "type": "boolean" },
    "source_channel":   { "enum": ["campus", "referral", "job_board", "self"] }
  },
  "x-dsh": {
    "entity": "core.person",
    "introduced_in": "v1",
    "promote_to_column_when": "filtered_in >= 1000 queries/day"
  }
}
```

**【事实】兼容性规则的可操作定义**：Confluent Schema Registry 把兼容性分为 BACKWARD（新 schema 可读旧数据）、FORWARD（旧 schema 可读新数据）、FULL、NONE，**推荐默认 BACKWARD**——新增字段必须带默认值、删除字段必须先标记 deprecated（[Confluent 文档](https://docs.confluent.io/platform/current/schema-registry/fundamentals/schema-evolution.html)）；Google Cloud 的 schema lifecycle 同样把兼容性作为「注册前置校验」而非事后检查（[Google Cloud 文档](https://docs.cloud.google.com/managed-service-for-apache-kafka/docs/schema-registry/schema-lifecycle)）。

**【建议】落到本项目的四条演进规则**：
1. **只加不删**：字段先 `deprecated_in`，保留 ≥ 2 个版本再物理清理。
2. **新增字段必须有默认值**（JSONB 缺键即默认值，DDL 用 `DEFAULT`），保证旧代码可读新数据。
3. **不改语义**：要改含义就换新键（`expected_city` → `expected_cities_v2`），并写 crosswalk。
4. **expand-contract 迁移**：先加列/加表（expand）→ 双写 → 回填 → 切换读路径 → 停止写旧路径（contract），全程零停机（[Expand/Contract 模式](https://devopsdays.org/events/2019-seattle/program/leena-s-n)）。

每次迁移登记一行：

```sql
CREATE TABLE meta.schema_change (
```

## ④ 匹配引擎设计

### 4.1 召回—融合—重排三段式

```
候选集生成               混合召回                 融合        重排         解释
结构化过滤(SQL/RLS) ─┬─ BM25 (tsvector/pg_trgm) ─┐
                     └─ 向量召回 (pgvector HNSW) ─┴─ RRF ─→ LTR ─→ reason
                     └─ 图召回 (skill 2-hop)
```

**【事实】** 混合检索的主流做法是分别执行词法检索（BM25）与稠密向量检索，再用 Reciprocal Rank Fusion 融合排名——Azure AI Search、DigitalOcean 的 Postgres 向量库文档都以 RRF 作为默认融合策略（[Azure 混合搜索](https://learn.microsoft.com/hi-in/training/modules/aaai-implement-advanced-rag-azure-ai-search/2-design-hybrid-search-architectures)、[DigitalOcean 混合检索](https://docs.digitalocean.com/products/vector-databases/postgresql/how-to/use-hybrid-search/)）。RRF 由 Cormack 等 2009 年提出，不需要两路分数量纲对齐，这是它对工程最友好的性质。

```sql
-- 混合召回：结构化硬过滤 + 向量近邻，一次查询完成
WITH pool AS (
  SELECT p.person_id
  FROM core.person p
  JOIN core.education e ON e.person_id = p.person_id AND e.valid_to IS NULL
  WHERE p.ext_attrs @> '{"willing_night_shift": true}'::jsonb
    AND e.degree_code_value_id = ANY($1)       -- 学历门槛：硬条件在 SQL 层收窄
),
vec AS (
  SELECT em.owner_id AS person_id,
         1 - (em.vec <=> $2) AS sim,
         row_number() OVER (ORDER BY em.vec <=> $2) AS rnk
  FROM sem.embedding em
  WHERE em.owner_type = 'person' AND em.model = 'bge-m3'
    AND em.owner_id IN (SELECT person_id FROM pool)
  ORDER BY em.vec <=> $2 LIMIT 500
),
kw AS (
  SELECT person_id,
         ts_rank_cd(tsv, plainto_tsquery('simple', $3)) AS score,
         row_number() OVER (ORDER BY ts_rank_cd(tsv, plainto_tsquery('simple', $3)) DESC) AS rnk
  FROM sem.person_text WHERE person_id IN (SELECT person_id FROM pool)
  LIMIT 500
)
SELECT COALESCE(vec.person_id, kw.person_id) AS person_id,
       COALESCE(1.0/(60+vec.rnk),0) + COALESCE(1.0/(60+kw.rnk),0) AS rrf_score
FROM vec FULL OUTER JOIN kw USING (person_id)
ORDER BY rrf_score DESC LIMIT 100;
```

### 4.2 图算法：什么时候真的需要图

**【建议】把图限定在四个问题上**，其余不要用图：
1. **共同技能 / Jaccard 相似度**：`person → skill ← person` 两跳聚合。
2. **技能近邻补全**：`skill -[BROADER/RELATED]→ skill`，把「心内科轮转」补到「心血管」。
3. **路径可达性**：`person → org ← person`（同院/同导师），用于内推与冷启动。
4. **二部图硬约束分配**：岗位-人 `bipartite matching`（名额、地区、科室配额），用带权匈牙利或贪心。

技术选择：**数据量 < 1 亿边时，PostgreSQL 的 `sem.edge` 边表 + 递归 CTE 足够**；需要图算法库时再挂 [Apache AGE](https://age.apache.org/)（PostgreSQL 内的 openCypher 图扩展）。独立图库（[Neo4j GDS](https://neo4j.com/docs/graph-data-science/current/)、[JanusGraph](https://janusgraph.org/)）的价值在 PageRank/NodeSimilarity/LinkPrediction 这类预置算法与大规模遍历，属于 v2 选项。

### 4.3 排序与冷启动

- **【事实】** Learning-to-Rank 的主流损失是 pairwise/listwise：RankNet → LambdaRank → LambdaMART 这条线由 Burges 系统总结，LambdaMART 直接对「交换两文档位置带来的 NDCG 变化」加权（[From RankNet to LambdaRank to LambdaMART](https://www.microsoft.com/en-us/research/publication/from-ranknet-to-lambdarank-to-lambdamart-an-overview/)）。
- **【建议】** 排序三阶段：v1 用规则加权（可解释、可审计、零训练数据）；v2 用 LightGBM 的 LambdaMART；标签来自 HR 的「进入面试 / 录用」事件，而非点击——招聘场景点击信号噪声极大。
- **可解释性**：`match_score.reason` 存每个 `job_requirement` 的贡献值（树模型的 SHAP 值按需求聚合），前端渲染成「满足 4/5 项硬性要求，其中『规培完成』权重最高」。这同时满足 PIPL 第 24 条对自动化决策「说明 + 拒绝」的要求。
- **冷启动**：新人无行为数据 → 纯内容匹配（能力向量 + 硬条件）；岗位无历史 → 用同 job_family 的岗位画像做先验；两边都冷 → 用词表层级（科室 → 一级学科）做粗粒度召回，宁可召回多、排序弱。

## ⑤ 合规与治理

### 5.1 法律基线

- **【事实】**《个人信息保护法》第 13 条第（二）项把「按照依法制定的劳动规章制度和依法签订的集体合同实施人力资源管理所必需」列为可**不依赖单独同意**的处理合法性基础；但该豁免范围必须严格限定，用人单位不得任意扩大（[程啸：论实施人力资源管理所必需的个人信息处理活动](https://www.aisixiang.com/data/164442.html)）。
- **【事实】** 第 24 条要求自动化决策「保证决策的透明度和结果公平、公正」，对个人权益有重大影响的决定，个人**有权要求说明并有权拒绝仅通过自动化决策作出决定**（[律所解读](https://www.dentons.com/en/insights/articles/2021/august/30/-/media/0c35405e79204977b4eaab54aa783819.ashx)）。人岗匹配如果没有人工复核环节，就落在这条上。
- **【事实】**《数据安全法》要求建立数据分类分级保护制度（第 21 条）——对应到本库即「简历原文 / 身份信息 / 能力标签 / 聚合统计」四级。
- **【事实】** GDPR 第 22 条赋予数据主体「不受完全自动化决策约束」的权利，Recital 26 明确**假名化数据仍是个人信息**（只有不可逆匿名化才出局）；[EUR-Lex 2016/679](https://eur-lex.europa.eu/eli/reg/2016/679/oj)。
- **【事实】** UK Biobank 采用**分层访问（tiered access）**：不同数据层级对应不同审批与访问方式，敏感层级只能在受控环境内分析、禁止下载（[Tiered access 指南](https://uk-biobank.gitbook.io/data-access-guide/readme/tiered-access)、[申请流程](https://www2.ukbiobank.ac.uk/use-our-data/apply-for-access/)）。这是本库最值得抄的治理模型。

### 5.2 落地机制（表结构）

```sql
CREATE SCHEMA IF NOT EXISTS gov;

-- 1) 同意与合法性基础：按目的登记，不是一次性全库同意
CREATE TABLE gov.consent_record (
  consent_id    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  person_id     uuid NOT NULL REFERENCES core.person,
  purpose_code  text NOT NULL,        -- talent_pool | matching | analytics | publication
  legal_basis   text NOT NULL,        -- consent | hr_management_necessary | contract
  policy_version text NOT NULL,
  granted_at    timestamptz, withdrawn_at timestamptz,
  evidence      jsonb                 -- 签署方式、原文快照
);

-- 2) 数据分级：一列定义级别，策略集中
CREATE TABLE gov.data_classification (
  entity_type text, column_name text, tier smallint NOT NULL,  -- 1公开 2内部 3敏感 4高敏
  mask_rule   text,                   -- 'hash' | 'year_only' | 'null' | 'pseudonym'
  PRIMARY KEY (entity_type, column_name)
);

-- 3) 访问分级 + 行级安全（对齐 tiered access）
CREATE TABLE gov.access_grant (
  grant_id    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  subject     text NOT NULL,          -- 用户/角色/服务账号
  max_tier    smallint NOT NULL,
  purpose_code text NOT NULL,
  row_filter  jsonb,                  -- {"domicile_prov":["310000"]}
  expires_at  timestamptz,
  approved_by text, approved_at timestamptz
);

ALTER TABLE core.person ENABLE ROW LEVEL SECURITY;
CREATE POLICY person_tiered_access ON core.person
  USING (EXISTS (SELECT 1 FROM gov.access_grant g
                 WHERE g.subject = current_user
                   AND g.max_tier >= 3
                   AND (g.expires_at IS NULL OR g.expires_at > now())));

-- 4) 审计日志：只追加，含查询指纹
CREATE TABLE gov.audit_log (
  audit_id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  at         timestamptz NOT NULL DEFAULT now(),
  actor      text NOT NULL, action text NOT NULL,
  object_type text, object_id text,
  purpose_code text, query_hash bytea, row_count integer,
  ip inet, session_id text
);

-- 5) 数据血缘（列级）
CREATE TABLE gov.lineage (
  lineage_id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  target_entity text, target_column text,
  source_entity text, source_column text,
  transform     text, pipeline text, pipeline_version text,
  recorded_at   timestamptz NOT NULL DEFAULT now()
);

-- 6) 保留与删除：策略即数据，到期即动作
CREATE TABLE gov.retention_policy (
  policy_id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  entity_type text NOT NULL, purpose_code text,
  retain_days integer, action text NOT NULL,  -- delete | anonymize | archive
  legal_hold boolean NOT NULL DEFAULT false
);
CREATE TABLE gov.subject_request (
  request_id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  person_id uuid NOT NULL, request_type text NOT NULL,  -- access | delete | withdraw_consent | explain
  received_at timestamptz NOT NULL DEFAULT now(),
  due_at      timestamptz, completed_at timestamptz, outcome text, detail jsonb
);
```

**【建议】五条不可妥协的治理规则**：
1. **分析用副本去标识化**：对外分析只在 `analytics` schema 上进行，`person_id` 用项目内稳定假名（HMAC），姓名/证件/联系方式不进入副本；导出聚合结果前做 k-匿名（k ≥ 5）与小样本抑制。
2. **自动化决策必留人工复核**：`match_score` 只是推荐，任何淘汰动作写入 `gov.subject_request` 可被申诉与解释。
3. **同意是属性不是前提**：人才库场景需区分「投递该岗位」与「进入长期人才库」，后者必须单独同意且可撤回，撤回即触发 `withdraw_consent` 流程。
4. **跨境零默认**：简历数据境内存储，任何导出记录到 `gov.audit_log`。
5. **保留期到期自动执行**：`retention_policy` 由定时任务执行，结果写审计，不做「只写策略不执行」的合规装饰。

## ⑥ 分阶段技术路线

### MVP（0–3 个月，单机 Windows 全本地）

```
PostgreSQL 16 + pgvector (Windows 安装包/便携版)
  ├─ 全部 core / ref / sem / match / gov schema
  ├─ pg_trgm + tsvector 做词法检索
  └─ HNSW 索引做向量召回（万级到百万级足够）
DuckDB CLI + Parquet：规范层导出为按 entity 分区的 Parquet，供自由分析
dbt-core（dbt-postgres + dbt-duckdb 双 target）：星型视图与指标
FastAPI + 本地 embedding 模型（bge-m3，CPU 可跑）
```

**【事实】** 单机分析链路的可行性有直接支撑：DuckDB 是进程内 OLAP 引擎，可直接查询 Parquet；`pg_duckdb` 把 DuckDB 引擎嵌进 PostgreSQL，让 Postgres 直接跑列式分析（[pg_duckdb](https://github.com/duckdb/pg_duckdb)）。dbt 侧用 [MetricFlow 定义语义指标](https://docs.getdbt.com/docs/build/about-metricflow)，避免每个分析员各写一套口径。特征定义统一在 [Feast](https://docs.feast.dev/) 风格的 registry 里管理，防止训练/服务特征漂移。

**MVP 明确不做**：LTR 模型、独立图库、独立向量库、Iceberg。

### v1（3–9 个月）

- 词表接入：导入 [O*NET Content Model](https://www.onetcenter.org/dl_files/ContentModel_Detailed.pdf) 与 [ESCO API](https://ec.europa.eu/esco/api/doc/esco-api-doc.pdf) 的技能/职业节点，构建 `sem.skill` + `sem.skill_edge`，本地扩展节点挂在 ESCO 之下。
- 混合检索 + RRF + 规则加权排序上线，`match_run` 记录算法版本与索引版本。
- 特征仓：把 `match_score.feature_vector` 回流为训练集，启动 LambdaMART 影子模式（不影响线上）。
- 治理：行级安全 + tiered access + 审计日志 + 到期删除任务全部运行。
- 分析：dbt 星型层（`mart_person_skill` / `mart_job_demand` / `mart_flow`）+ DuckDB 交互式分析。

### v2（9–24 个月）

- 数据量过千万级人或十亿级边时：湖仓化（规范层写 Iceberg/Delta，利用其 schema evolution 与快照隔离，[Iceberg 表规范](https://iceberg.apache.org/spec/)、[Delta 模式演进](https://learn.microsoft.com/en-us/fabric/data-engineering/delta-lake-schema-evolution)）；向量检索迁至 [Milvus](https://milvus.io/docs) 或 GPU 版 [FAISS](https://github.com/facebookresearch/faiss)；图迁至 Neo4j/JanusGraph 做社团发现与链接预测。
- 多机构联邦：本院只出「能力向量 + 假名 ID」，简历原文不出域；跨机构匹配走联邦检索。
- 全链路血缘与影响分析（改一个词表版本，自动列出受影响的分析与模型）。

### 规模阈值速查

| 规模 | 数据库 | 检索 | 分析 |
|---|---|---|---|
| < 10 万人 | PostgreSQL 单机 | tsvector + pgvector | DuckDB on Parquet |
| 10 万–1000 万人 | PostgreSQL + 只读副本 | pgvector HNSW + 物化召回池 | DuckDB / dbt 星型层 |
| 1000 万–1 亿人 | PostgreSQL 分片 或 Iceberg 湖仓 | Milvus / FAISS | Trino/Spark + Iceberg |
| > 1 亿人 / 十亿边 | 湖仓 + 图库 + 向量库三件套 | 独立向量库 + 图库 | 湖仓 + 特征平台 |
