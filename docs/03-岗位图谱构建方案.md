# 03 · 岗位图谱构建方案（数据库的第一优先任务）

> 用户的明确要求：**数据库的建立需要首先检索岗位和岗位描述**；医学生就业中临床只是其中之一，必须覆盖全社会全方位岗位。
> 本文件定义"岗位侧"如何从零建到可用。岗位侧是人才库的**需求端**，没有它，人才档案只是一堆无法匹配的简历。

---

## 1. 产出物：岗位图谱的四层结构

| 层 | 名称 | 内容 | 对应表 | 规模目标（v1） |
|---|---|---|---|---|
| L1 | 职业分类骨架 | 大类/中类/小类/细类 + 外部标准映射 | `occupation` | 400–800 节点 |
| L2 | 岗位族画像 | 17 族画像卡：典型岗位、雇主、路径、执照、能力、薪酬锚点 | `occupation` + `job_competency_weight` | 17 族 × 完整字段 |
| L3 | 真实岗位样本库 | 结构化 JD 记录（含原文） | `job_posting` `job_task` `job_requirement` | 3,000–10,000 条 |
| L4 | 能力权重矩阵 | 岗位族 × 概念 → 重要性/要求等级/必需性 | `job_competency_weight` | 17 族 × 150–300 概念 |

**验收一句话**：给定任意一个岗位族的任意一条真实 JD，能回答"它要求什么能力、要什么程度、哪些是硬性、医学背景算不算加分、还有哪条替代路径"。

---

## 2. 数据来源的三层架构

### 2.1 A 层：权威标准（骨架，不可替代）
| 来源 | 用途 | 获取方式 |
|---|---|---|
| 《中华人民共和国职业分类大典（2022 年版）》 | 中国职业分类主干（大/中/小/细类） | 官方出版物；需人工/OCR 建库 |
| ISCO-08 / 美国 SOC / O*NET-SOC | 国际映射与跨库对照 | 公开下载 |
| O*NET 数据库（内容模型：Skills/Knowledge/Abilities/Work Activities/Work Context/Work Styles/Interests/Tasks + importance/level 量表） | **能力权重矩阵的方法论直接来源** | 公开下载（CC 许可，需署名） |
| ESCO（skills & competences，含 essential/optional、reusability level） | 技能本体与"可迁移性"分级 | 公开 API / 下载 |
| 人社部《企业薪酬调查信息》 | 薪酬锚点（A 级口径） | 官方发布 |

> 这一层决定"岗位/能力叫什么、怎么编码"。**没有编码骨架，后面的 JD 抽取会各自为政，半年后无法聚合。**

### 2.2 B 层：真实 JD（血肉，先检索再结构化）
采集渠道按合规风险排序：

| 优先级 | 渠道 | 合规结论 | 备注 |
|---|---|---|---|
| ★★★ | 公司官网 Career 页 | 通常允许，需遵守条款与频率 | 一手、字段干净、含校招 |
| ★★★ | 高校就业信息网 / 卫健委与事业单位招聘公告 | 公开政务信息 | 应届视角最关键 |
| ★★★ | 官方 API（如 O*NET、ESCO、部分平台开放接口） | 按许可 | 优先于抓取 |
| ★★ | 猎聘**静态薪资聚合页** | 已核实 robots.txt 允许静态页 | 只取聚合统计，不取个人数据 |
| ★ | 智联/前程无忧/丁香人才 | 页脚明文禁止转载/抓取 | **仅人工抽样**，不自动化 |
| ✗ | BOSS 直聘 | robots.txt 明确禁 `/*?*` 与 `/job_detail/l*.html` | **禁止自动化抓取** |
| ✗ | LinkedIn / Indeed | 条款禁止 | 禁止 |

**红线（写进 `source_registry.license_note` 并在采集前强制校验）：**
1. 只采**机构公开的岗位信息**，**绝不采集求职者个人简历**（个人数据必须来自本人授权）。
2. 遵守 robots.txt 与服务条款；不绕过验证码/反爬/登录墙。
3. 控制频率（建议 ≥3 秒/请求），不造成对方服务压力。
4. 保留 `source_url` 与 `fetched_at`，可按来源一键下架（合规响应）。
5. 每个 source 必须登记 `credibility` 与 `evidence_grade`，未登记者不得入库。

### 2.3 C 层：人工专家（补盲区）
D 级"未证实"的岗位族（法务 IP、创业、公务员、博后、专利代理）无法靠抓取补全，必须用**从业者访谈**：每族 3–5 位从业者，结构化访谈稿 → 直接写入 `transition_case` 与 `occupation` 画像。**这条路必须走，否则图谱会有系统性空洞。**

---

## 3. 证据分级（A/B/C/D）——吸收为数据库字段

岗位版图调研（`research/03-...md`）建立的分级纪律必须固化到 schema，否则无法在报告里诚实标注可信度：

| 级 | 含义 | 落地字段 |
|---|---|---|
| A | 官方统计/部委规章原文 | `provenance.evidence_grade='A'` |
| B | 招聘平台聚合统计（含样本量） | `evidence_grade='B'` |
| C | 单条在招 JD（不可外推） | `evidence_grade='C'` |
| D | 未证实（自媒体/转述） | `evidence_grade='D'`，**禁止进入对外报告的主结论** |

> 行动项：在 `provenance` 表增加 `evidence_grade` 字段，并在 `source_registry.credibility` 之外单列；所有对外图表必须能按 `evidence_grade >= B` 过滤。

---

## 4. 检索策略：先"找全"，再"做深"

### 4.1 关键词矩阵（避免只见临床）
对每个岗位族，用 `岗位名 × 城市 × 学历` 组合检索。**必须包含非临床关键词**：
- 药企：`MSL 医学联络官`、`医学经理`、`临床监查员 CRA`、`药物警戒 PV`、`注册专员 RA`、`医学写作`
- 器械：`临床评价工程师`、`临床应用专员`、`注册专员 器械`
- 保险：`核保 医学`、`理赔 医学审核`、`健康管理师`
- 投资/咨询：`医药行业研究员`、`医疗投资`、`医药咨询顾问`
- 数字健康：`医学经理 互联网医疗`、`真实世界研究 RWS`
- 跨行：`医学背景 数据分析`、`医学背景 产品经理`
- 政府：`选调生 医学`、`疾控 招聘`、`药审中心 审评员`

### 4.2 每族目标样本量（v1）
每族 ≥150 条结构化 JD（临床族 ≥500），其中校招/应届可投 ≥30%。**样本不足的族必须显式标注 `coverage_gap`，不得用少量样本外推。**

### 4.3 反偏差要求
- 地域：覆盖一线/新一线/二线/县域各 ≥10%。
- 单位性质：公立/民营/外企/国企/创业各有样本。
- 时间：优先近 12 个月，历史数据保留用于趋势分析（`published_at`）。
- **明确记录"抓不到什么"**：招聘平台样本天然偏向"正在招人的岗位"与"愿意公开薪资的岗位"，这是已知偏差，必须写进数据说明书。

## 5. JD 结构化流程（六步）

```
① 采集      → L0 原始 HTML/文本 + sha256 + source_url + fetched_at（只增不改）
② 清洗      → 去导航/广告/模板噪声；保留正文；记录清洗版本
③ 抽取      → LLM + 规则混合：岗位主干字段、职责条目、要求条目
④ 归一化    → 职位名→occupation；要求→concept；学历→CT_DEGREE_LEVEL；薪资→区间+周期
⑤ 质量门    → 必填字段完整率、代码映射覆盖率、原文可回溯率；未过门不入 L1
⑥ 人工抽检  → 每批次抽 5%（不少于 20 条）人工核对，记录准确率；低于阈值整批重跑
```

**硬性规则：**
- `title_raw` 与 `raw_text_ref` 必须保留 —— **只存归一化结果是不可逆的信息损失**。
- 每条 `job_requirement` 必须带 `raw_text` 原文片段（否则无法回查、无法申诉）。
- LLM 抽取结果一律 `verify_status='V1(parsed)'`，`confidence` 不超过 0.8，且必须记录 `extractor_version` 以便换模型重跑。
- 抽取器版本升级后，**必须能对历史 JD 全量重跑并对比差异**（这是 L0/L1 分离的回报）。

---

## 6. 从 JD 到能力权重矩阵（方法）

1. 把每条 `job_requirement` 映射到 `concept`（技能/知识/能力）。
2. 按 `occupation` 聚合：`importance = 出现频次占比 × 硬性权重系数`（硬性 > 软性 > 加分）。
3. `level_required` 取该岗位族内 `min_level` 的中位数（需 ≥30 条样本才计算，否则标 `insufficient_sample`）。
4. 与 O*NET 的 importance/level 做**人工对照校验**（发现异常即回查映射）。
5. 结果写入 `job_competency_weight`，保留 `evidence_basis`（JD 统计 / 专家评定 / 访谈）与 `sample_size`。

**这是全库最有商业价值的一张表**：它把"医学生能去哪"从意见变成可计算的匹配。

---

## 7. 质量门与验收指标（岗位侧 v1）

| 指标 | 阈值 |
|---|---|
| 结构化 JD 总数 | ≥3,000 |
| 覆盖岗位族 | 17/17（不足者显式记录 `coverage_gap`） |
| 必填字段完整率（title_raw/employer/family/city/raw_ref） | ≥99% |
| 要求条目的能力概念映射覆盖率 | ≥70%（其余保留 `raw_text` 待人工） |
| 原文可回溯率 | 100% |
| 抽检准确率 | 关键字段（岗位族/学历要求/硬性要求）≥90% |
| 每条来源均有 `evidence_grade` 与 `license_note` | 100% |
| 采集合规：无 robots.txt 禁止渠道的自动化记录 | 0 违规 |

---

## 8. 面向客户的产出（岗位图谱的"可交付形态"）

1. **岗位地图**：17 族 × 医学依赖度 × 可迁移度 的二维矩阵（一眼看到"我还能去哪"）。
2. **进入路径图**：应届可进 / 需考证 / 需经验 / 需再读学位，四色标注。
3. **薪酬锚点表**：岗位族 × 城市 × 学历 → 分位数，每条带 `evidence_grade` 与年份。
4. **能力需求清单**：该族最需要的 20 项能力及要求等级。
5. **转行案例卡**：真实的人怎么转的、花了多久、桥梁能力是什么。

> 第 5 项是"打开视野"最有说服力的材料，也是竞品最难复制的资产 —— 建议 v1 就启动访谈采集。
