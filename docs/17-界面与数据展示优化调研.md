## 0. 方法与可核查性声明

### 0.1 三个约束，本文每一条建议都要过这三关

| 约束 | 含义 | 标注 |
|---|---|---|
| 技术约束 | 两个站点是**服务端渲染的零 JS、零 CDN** 页面（标准库 `http.server` + 内联 HTML/SVG），单个 HTML 可离线拷走打开 | **A** = 纯 HTML/CSS/SVG 可实现；**B** = 需要少量渐进增强 JS；**C** = 需要前端框架或重写渲染层 |
| 真实性约束 | 任何界面元素背后**必须真有数据与真实查询**，不允许假按钮、假图、写死的数字 | 需要新数据的建议，我写明"需要什么查询/视图" |
| 代价约束 | (B)(C) 必须写清破例的代价：会失去离线可看、零依赖、可断言、审计友好中的哪几项 | 见每条的"代价" |

### 0.2 哪些页面我**实际打开看过**（本会话直接取回正文）

本机可用代理是 **7892**（7890 不通）。工具链事实：`web_fetch` 对多数这些站点会超时；
Python `urllib` 走 7892 代理 + 浏览器 UA + `Connection: close`（或对证书已过期的站点关闭校验）

的部分路径、`www.encodeproject.org` 全部路径）在这个代理上返回 403/405，只能靠 `web_fetch` 或放弃。

## 2. 方向一：interface 的视觉效果

> 15 号文档已做：页头带、面包屑、对比度三处、`:focus-visible`、导航分隔可写入口、字段表双列。
> 本节只谈它**没做**的：字段级元数据的呈现、导航分组、数字与单位的落位、密度。

### 2.1 字段级元数据应该像 UKB 一样"一屏在顶"，而不是埋在 35 列表里

**成熟产品怎么做的**：UKB 的 Data-Field 21001 页把**14 项元数据**放在字段页顶部的一张"标签-值"网格里，包括
`Value Type Continuous, Kg/m2`、`Item count 639,668`、`Item Type Data`、`Instances Defined (4)`、
`Version Sep 2025`、`Stability Complete`、`Strata Derived`、`Array No`、`Cost Tier o1 s1`、`Debut Jan 2012`
（<https://biobank.ndph.ox.ac.uk/showcase/field.cgi?id=21001>，亲验）。注意它把**版本**和**稳定性**
当字段级属性——不是文档里的说明，是页面上的值。Allen 的下载表同样把工具版本写进正文
（"hdf5 (version 0.7.8)"、"Seurat (v4.0.4)"，分会话核实，
<https://portal.brain-map.org/support/documentation/data-catalog-user-guide>）。

**我们现在什么样**：本库有 `field_catalog`（**实测 35 列**，我查库确认）与 `v_dimension_registry`（22 列），
但门户只在 `/t/field_catalog` 把它当**数据表**铺开，没有"一个字段一页"的页面。
`/talent/<id>` 的画像向量卡（`portal.py:2632-2648`）列出了维度、取值、匹配角色、字段登记、说明五列——
**没有版本、没有稳定性、没有访问层级、没有"是否分次测量"**。而 `field_catalog` 里
`instanced > 0`（分次测量）这一列是真实存在的：`portal.py:1294` 就有一句
`sum(CASE WHEN f.instanced > 0 THEN 1 ELSE 0 END) AS "分次测量"`。
也就是说**数据在库里，页面上没有**。

**建议怎么改（A）**：把 `/talent/<id>` 的画像向量卡里每个维度行补三列（`版本/稳定性/分次`），
数据源就是已有的 `dimension` + `field_catalog` join，不加任何新表；
再给 `/t/<表>` 的"列定义"表（`portal.py:983-984`）补一列"访问层级"，因为
`field_catalog` 已有该列。这是**纯 SELECT 加宽**，无新查询类型。

**代价与验证**：代价是 `/talent/<id>` 那张表从 5 列变 8 列、在 `.tscroll`（`max-height:620px`）里更容易横向溢出——
而 `.tscroll` 恰好**没有**首列吸左（见 §3.2），所以这一改会**放大一个已知缺陷**，两条应当一起做。
验证：`python code\demo\portal.py --check` 会拦住"字段没登记"类问题；
`ops/tests/portal_test.py` 现有断言会检查页面渲染；
有效性验证用 `python ops\screenshots.py --only talent-detail` 出前后对比图，
并新增一条断言"每个维度行的版本列不是空字符串"（因为 `dimension` 表 50 行都有 `version`）。

### 2.2 导航 15 项的问题，换一个杠杆：不动入口结构，先加"章节标题"

**成熟产品怎么做的**：Superset 的左栏是"a collapsible **treeview**"（分会话核实，
<https://superset.apache.org/docs/using-superset/exploring-data>）；GDC 的导航按
`Repository / Cohort Builder / Analysis Center / Projects / Clinical Data Analysis / … / Set Operations`
分组（我亲验 <https://docs.gdc.cancer.gov/> 的导航结构）。**分组线索先于收敛**。

**我们现在什么样**：`portal.py:458-463` 的 `NAV` 有 **15 项**（15 号文档写作时是 13 项，
之后又加了"真实案例"与"可视化"分组内的变化）。`nav a{padding:12px 11px;font-size:13px}`（`portal.py:311`），
按 13px × 1.6 行高 + 24px 内边距 + 2px 下边框估算，导航条高约 **47px**；
15 号文档 §S3-1 已经实测 940px 宽时折成两行（约 70px+）。
**15 号文档 §4.1 明确"导航收敛/分组"建议单独立项、不要塞进视觉评审——我遵守这个判断，
所以这里不提议收敛，只提议一个零风险的替代物。**

**建议怎么改（A）**：在 `NAV` 里给每个栏目加一个 `group` 字段（"看数据 / 查结构 / 分析 / 治理 / 运维"），
渲染时在**组与组之间**插入 `<span class="navsep">`——这个组件**已经存在**（`portal.py:316`，
15 号文档为"可写"徽标加的），所以是复用而不是新增。
它不改变任何入口、不动 URL、不改测试断言的导航项数量。

**代价与验证**：代价是导航条再宽一点点（4 条分隔线共约 40px），
在 940px 下**可能**从两行变三行——这一点必须实测，不能假设。
验证：`serve_all.py --check-only` 保住渲染；截图 `--only overview`（1600px）与手动 940px 各一张；
断言"导航项数量仍为 15"（`portal_test.py` 已有类似检查）。

### 2.3 数字旁边要同时有**单位**和**这个单位的来源口径**

**成熟产品怎么做的**：Grafana 把单位做成**字段属性**（"Unit | Choose which unit a field should use."）；
Vega-Lite 把**聚合函数写进轴标题**（"If the field has an aggregate function, the function is displayed as part of
the title (e.g., 'Sum of Profit')"）；GTEx 更进一步——单位变更本身被记录成数据集属性
（releaseDescription 原文 "units updated from RPKM to TPM"）（分会话核实，
<https://vega.github.io/vega-lite/docs/encoding.html>、<https://gtexportal.org/api/v2/metadata/dataset>）。

**我们现在什么样**：`portal_viz.py:51-200` 的 `VIZ` 里每个面板都有 `unit` 字段
（`unit="%"`、`unit=" 行"`、`unit=" 人"`、`unit=" 个节点"`），但 `unit` 只被传进
`CH.bar_h(..., unit=...)` 用于**值标签与悬停提示**（`charts.py:130`、`136-138`），
**没有进轴标题**——`charts.py` 的 `bar_h` 根本不画轴标题。
而 `/quality` 的 KPI（`portal.py:3687-3692`）里"审计流水行数"没有单位行，
"概念映射覆盖率"有 `"目标 ≥70%"` 作为说明——**同一页两种情况并存**。

**建议怎么改（A）**：① 给 `charts.bar_h/line/scatter` 增加 `x_label`/`y_label` 参数，
在 SVG 里画轴标题，内容是"聚合 + 列名 + 单位"；② 由 `portal_viz.panel()`（`portal_viz.py:394-403`）
统一在卡片副标题里印 `grain · unit`，因为它已经有 `item.get("grain")`（第 402 行在用）。

**代价与验证**：代价是每张图多占约 16px 高度，`/viz` 16 张图合计多约 250px——
15 号文档 §S3-5 已经判定"16 面板竖排约 10 屏"是**对的、不该改**，
所以这 250px 必须承认是净增。验证：`ops/tests/viz_test.py` 有"7 种图在空数据下都返回明确的空状态"
（15 号文档 §5 实测 31 项），可扩展成"每张非空图都含轴标题"；
出图用 `python ops\screenshots.py --only viz`。

### 2.4 行密度：给一个 42px 的锚点，并明确 24px 是硬下限

**成熟产品怎么做的**：AG Grid 的行高"**42px for Quartz**"（主题默认），密度是主题参数
（<https://www.ag-grid.com/javascript-data-grid/row-height/>，亲验 605138 字节页面可达）；
WCAG 2.5.8 要求指针目标至少 **24×24 CSS px**，且**有"交互式数据可视化目标天然密集"的 Essential 例外**
（分会话核实 <https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html>）。

**我们现在什么样**：`table{border-collapse:collapse;width:100%;font-size:13px}`（`portal.py:342`）+
`th,td{...;padding:6px 9px;...}`（`portal.py:343`）。
按 CSS 算：13 × 1.6 = 20.8px 行盒 + 12px 内边距 + 1px 下边框 ≈ **33.8px/行**（计算值，非实测像素）。
没有密度控制。列选择器里的复选框是 `label{padding:2px 4px;font-size:12.5px}`（`portal.py:390-391`）+
`input{width:auto;margin:0;padding:0}`（`portal.py:394`）→ 命中区约 12.5×1.6+4 ≈ **24px**，
**恰好压在 2.5.8 的门槛上，没有余量**。

**建议怎么改（A）**：加两个 CSS 类 `.dense`（行高 26px）与 `.cozy`（行高 42px），
通过 `/t/<表>?density=cozy` 这样的 GET 参数切换（零 JS，与 `size` 参数同一套机制，
`portal.py:883` 已有 `_int_param` 的白名单范式可仿）。
同时把列选择器的 `label` 内边距从 `2px 4px` 提到 `3px 5px`，让命中区到 26px。

**代价与验证**：代价是"密度"成为一个新的 URL 状态，需要纳入 `qs_encode`（`portal.py:622`）以免
排序/翻页时丢失——这个函数 15 号文档已修过一次"点一下筛选丢 34 列"的 bug，改动它**属于高风险区域**，
必须逐条回归。验证：`python ops\tests\run_all.py --only 13`（门户 144 项断言）；
截图 `--only table` 前后对比；命中区尺寸按 CSS 估算后**仍需真机点一次**（我不能替用户做这一步）。

### 2.5 空值的三种表达要收敛，且 `.chart-empty` 现在是**没有样式的死类**

**成熟产品怎么做的**：Grafana 的空值约定是显示 **`-`**（"The default value is a hyphen (-)"）；
NN/g 有一篇专门讲复杂应用的 empty state 三条准则
（<https://www.nngroup.com/articles/empty-state-interface-design/>，亲验页面可达，
标题 "Designing Empty States in Complex Applications: 3 Guidelines"）。

**我们现在什么样**：**同一份代码里有四种空状态表达**：
① `.empty` 虚线框（`portal.py:446-447` 定义，用 7 处：`1078`、`3028`、`3031`、`3063`、`3070`、`3127`、`3129`）；
② `render_rows()` 的裸 muted 段落 `<p class="muted">（0 行）</p>`（`portal.py:672`）；
③ `mini_analysis()` 的裸 muted 段落（`portal.py:1732`）——它被 `/talent` 的 6 个分析、
`/tree` 的 2 个、`/schema` 的 1 个、`/match` 的 3 个共用；
④ `charts._empty()` 输出 `<div class="chart-empty" style="height:%dpx">`（`charts.py:98`），
而 **`class="chart-empty"` 在整个 `portal.py` 的 `CSS` 常量里没有任何规则**——
我在 `code/demo/*.py` 全量搜过，`chart-empty` 只出现在 `charts.py:98` 这一行。
也就是说空图渲染出来的是一句**左对齐、无边框、固定像素高**的裸文字。

**建议怎么改（A）**：① 在 `CSS` 里补 `.chart-empty` 规则（复用 `.empty` 的视觉：虚线框 + 居中）；
② 让 `render_rows`（`portal.py:672`）与 `mini_analysis`（`portal.py:1732`）改用 `.empty`。
**文案一字不改**——15 号文档 §3.5 明确"所有空状态文案一字未改（测试与文档引用了这些句子）"，
所以我只改 class 不改字。

**代价与验证**：代价是虚线框比裸文字多占约 30px 高，`mini_analysis` 在 `/talent` 一页最多出现 6 次——
但只有真的 0 行时才出现，正常状态下无影响。
验证：新增断言"渲染出的 HTML 里不出现 `class="chart-empty"` 而无 CSS 定义"（等价于断言 CSS 含 `.chart-empty`）；

### 2.6 状态色：给 15 号文档 §4.8 明确留下的问题一个可执行的答案（颜色 + 字形）

**成熟产品怎么做的**：这是本次调研里最完整的一套**状态语义规范**，来自 ENCODE 的一手源码
（`making_audits.md`、`audit.js`、`facets/audit.js`、`_audits.scss`、`matrix_audit.js`，
分会话核实——**注意 ENCODE 的渲染页面在本机代理上全部 405，这份证据是它自己仓库里的声明规则，
不是截图**）：四档状态各有操作性定义，并把 **语义 / 字形 / 色值**三者绑成一张表——
`("error", warning, #cc0700)`、`("warning", circle, #e0e000)`、`("not_compliant", file-text, #ff8000)`、
`("internal_action", ambulance, #a0a0a0)`、`("ok", check, #4c994c)`。
关键在**字形与颜色同时编码同一件事**，所以严重度在灰度打印和色觉缺陷下都还在；
而且矩阵的行序**硬编码成严重度序**（`WARNING→NOT_COMPLIANT→ERROR→INTERNAL_ACTION`），
**质量表不会因为计数变化而重排**。

**我们现在什么样**：15 号文档 §S3-7 与 §4.8 把这个缺口写得很准——
"`green/amber/red` 表示'达标/接近/不达标'（语义色），而分类调色板是 `blue/green/amber/purple/teal`
（类别色）——**同一个绿色既表示'通过'也表示'第 2 个类别'**"，并判定
"需要一张色板规范 + 逐图核对，超出'低风险'范围，**留作下一轮**"。
我把当前的调用点逐个数清了：`charts.py:37-41` 的 `PALETTE` 里 `green`/`amber`/`red` 同时被
**语义位置**（`target_bar` 的 `col = PALETTE["green"] if ok else PALETTE["red"]`，
`charts.py:369`；`gauge` 的三档，`charts.py:449-450`）与**分类位置**
（`stacked` 的 `colors = [blue, green, amber, purple, teal, gray]`，`charts.py:310-311`；
`line` 的 `colors = [blue, green, purple, amber, teal]`，`charts.py:161-162`）共用。
另外 `portal.py:2896-2897` 的码状态 pill 用 `{"V":"p-t","E":"p-e","N":"p-n"}` 映射到
`p-t/p-e/p-n` 三个 class（`portal.py:410-413`），**只有颜色、没有字形**——
所以打印成灰度后，"码 V / 码 E / 码 N"三个 pill 完全一样。

**建议怎么改（A）**：① 新增一份**色板常量**（不是新文件，就是 `charts.py` 里的一个 dict），
把语义色固定成 `ok/warn/bad` 三个**不与类别色重叠**的色相，类别色改用同明度的蓝/紫/青系
（这一步 15 号文档 §4.8 已经指明了方向，我只是把它变成可执行的常量表）；
② **每个状态色都配一个字形**：给 `p-t/p-e/p-n` 的 pill 文字前面各加一个
**内联 SVG 或纯文本字符**（✓ / ! / – ），字形随 pill 一起走。
**必须用内联 SVG 或 Unicode 字符，不能用图标字体**——ENCODE 用的是 FontAwesome，
**那正是我们会被迫引入 CDN 的地方**，这条要写进代码注释防止下一轮有人照抄；
③ 顺手处理 15 号文档 §4.9 点名的 `PALETTE["gray"] = #8c959f`（在 `#fff` 上 3.04:1，
"恰好压在非文本 3:1 门槛上、没有余量"）——它同时是 `stacked` 的第 6 个类别色
（`charts.py:311`），做色板规范时应一并换成有余量的灰。

**代价与验证**：代价有三条——
**(a)** 动 `charts.py` 的 `PALETTE` 会**改变全部 16 张图的配色**，
15 号文档 §4.8 拒绝它的理由正是"会动到 `charts.py` 的绘图语义"，**这个风险没有变小**；
**(b)** 新增字形会改变 pill 的宽度，`/tree` 一页最多 151 个节点 × 每个最多 5 个 pill（`badge()`，`portal.py:2890-2906`），
可能让节点行换行——**必须在 1600px 与 940px 两个宽度上各看一次**；
**(c)** `ops/tests/viz_test.py` 若按 SVG 颜色字符串匹配会红。
验证：可以做一条**很便宜也很硬的断言**——"语义色与类别色两个集合的交集为空"
（纯常量比较，不连库），以及"每个状态色 class 在渲染出的 pill 里都伴随一个字形"
（正则匹配 `class="pill p-[ten]"` 后面紧跟一个 SVG 或非空白字符）。
**这两条断言的价值在于：它们把"颜色不能兼职两种语义"从一条设计原则变成一条 CI 规则**，
这正是 15 号文档 §4.8 想做但没做的事。

## 3. 方向二：table

### 3.1 表头语义只覆盖了 `render_rows`，**旗舰表 `/talent` 反而不在其中**

**成熟产品怎么做的**：15 号文档 §1.3 已引 GOV.UK Table 的原文："Use the `<caption>` element to describe
a table in the same way you would use a heading." 与 "Use the `scope` attribute to help users of assistive
technology distinguish between row and column headers."（<https://design-system.service.gov.uk/components/table/>）。
**一个反直觉的实测**：UK Biobank 的字段页 `scope=` **0 个**、`<caption>` **0 个**、`<th>` 5 个
（我亲验 `field.cgi?id=21001` 的原始 HTML）。所以这一条我们**不是落后于标竿，而是领先于它**——
不该用"UKB 也这样"来辩解，也不该因为"UKB 没做"而认为不重要。

**我们现在什么样**：`scope="col"` 在 `portal.py` 里**只出现 1 处**（`portal.py:673`，`render_rows()` 内）。
`render_rows()` 有 **27 个调用点**，所以多数小表有语义；但**手写的 `<table>` 有 39 处**（我在
`portal.py` 里逐个数过），其中 **5 处有 `<thead>` 但没有 `scope`**
（`2641`（`/talent/<id>` 画像向量）、`3247`、`3253`、`3258`（`/real` 三张表）、`3317`），
其余**既无 `<thead>` 也无 `scope`**，包括：
`/schema` 的列定义/约束/索引/触发器四张（`portal.py:983-994`，写的是 `<div class="tscroll"><table>\n<tr><th>列</th>…`，
**连 thead 都没有**）、`/quality` 的"岗位侧数据质量门"（`3654-3659`，**一个 `<th>` 都没有**，
是 4 列 `<td>` 拼的"标签/值/标签/值"网格）、`bar_table()`（`1751`）、
`table_profile_blocks()`（`1655`）、以及**旗舰页 `/talent` 的人才清单**
（表头在 `2326-2334` 拼成 `<th class="…"><a href=…>`，在 `2482-2484` 输出——
**没有 `scope`**）。
`<caption>` 在整个 `code/demo/` 里是 **0 个**。

**建议怎么改（A）**：① 把 `render_rows` 的 `thead`+`scope` 模式抽成一个
`thead_html(cols, n_right)` 辅助函数，供 5 处手写 thead 复用（改 5 行）；
② `<table>` 无 thead 的约 33 处**机械补 thead**（约 70 行 diff，纯机械）；
③ `/quality` 的"岗位侧数据质量门"不是数据表，应按 GOV.UK 的
"**Never use the table component to layout content on a page**"改成 `<div class="kv">`——
`.kv` 已存在（`portal.py:450`），15 号文档 §3.3 刚给它做了宽屏双列，正好合适；
④ 给 3–5 张**真有标题**的表加 `<caption>`（人才清单、岗位侧质量门、时点对比、列定义）。

**代价与验证**：代价是纯机械改动会产生**很大但很浅**的 diff，code review 成本高于技术风险；
且 `/quality` 那张表改成 `.kv` 会**改变现有断言**（`portal_test.py`/`quality_test` 若按文本匹配会有影响），
必须先跑一遍看红不红。
验证：新增一条**可机器判定的断言**——对每个页面，`body.count("<table")` 与
`body.count('scope="col"')` 的差值要么为 0，要么等于该页"非数据表"的白名单数量
（`/quality` 1 张、`/overview` 的若干 `<td>` 布局表）。
这条断言比"页面上有 scope"强得多，而且它**会随新页面自动生效**。
`python code\demo\portal.py --check` 与 `python ops\tests\run_all.py --only 13` 必须为绿。

### 3.2 `.tablewin` 有首列吸左，`.tscroll` 没有——而最宽的表走的是 `.tscroll`

**成熟产品怎么做的**：Metabase 文档原文 "**Sticky columns** are especially useful when viewing wide tables,
as you can keep the column that identifies the row (like `account_name`) on the screen as you scroll across
the columns."；AG Grid 的列固定实现之一就是"keep all columns in the same table, but use the pinning state
to order the columns correctly and **use sticky CSS** to pin the columns to the left or right"
（分会话核实，<https://www.metabase.com/docs/latest/questions/visualizations/table>、
<https://www.ag-grid.com/javascript-data-grid/column-pinning/>）。

**我们现在什么样**：`.tablewin`（`portal.py:358-368`）同时有 `thead th{position:sticky;top:0}`
**和** `th:first-child,td:first-child{position:sticky;left:0;…}`；`.tscroll`（`portal.py:354`）
只有 `max-height:620px;overflow:auto`，吸顶靠全局 `th{position:sticky;top:0}`（`portal.py:344`），
**没有首列吸左**。`render_rows()` 输出的正是 `.tscroll`（`portal.py:682`）。
于是：`/talent`（走 `2482` 的 `.tablewin`）有首列吸左；而 **`/t/job_posting` 走 `render_rows`
（`portal.py:1011`），我查库确认 `job_posting` 有 41 列（`information_schema.columns` 实测 41），
是全库最宽的表，横向滚动时"这是哪一行"看不见**。
`portal.py:355-357` 的注释把"首列也要吸"写成了 `.tablewin` 的设计理由——
但最需要它的那张表不在这里。

**建议怎么改（A）**：把 `.tablewin` 的 sticky-first-child 三条规则（`365-368`）
抽成一个共享选择器 `.sticky-first`，同时挂到 `.tablewin` 与 `.tscroll` 上。
注意 `.tablewin` 用的是 `border-collapse:separate`（`portal.py:360`）而 `.tscroll` 用全局 `border-collapse:collapse`
（`portal.py:342`）——**collapse 下表头下边框会被吃掉**，这正是 15 号文档 §3.6 给 `th` 加
`box-shadow:inset 0 -1px 0 #d0d7de` 的原因；首列吸左在 collapse 下的右边框同样不可靠，
需要同法补一条 `box-shadow:1px 0 0 #e6e8eb`。

**代价与验证**：代价是 `.tscroll` 的表会多一层 stacking context（`z-index`），
如果某张表里嵌了 `<a>` 或 `title` 悬停层，可能被遮挡——**这是必须逐页看一遍的回归面**
（15 号文档 §6.1 已自认 `/viz`、`/analyze`、`/quality`、`/lineage`、`/search`、`/dev` 只做了前后对照级检查）。
验证：截图 `python ops\screenshots.py --only table`（已有 `before/after-sticky-header.png` 这一对夹具，
说明项目已有"把滚动容器拉到底"的测试手法，我按 15 号文档 §3.6 的说明使用它）；
加一条断言"`.tscroll` 的 CSS 里含 `first-child{position:sticky`"。

### 3.3 排序能力被静默砍到前 12 列

**成熟产品怎么做的**：AG Grid 的排序是列定义上的能力，没有"只有前 N 列能排"这种概念；
Metabase 原文强调列设置在**可视化层**（"Hiding columns in table visualization settings only affects the
visibility of the columns in the visualization, **not in the query results**"）——
即"能对哪些列做什么"应该是**显式的列配置**，不是隐式截断
（分会话核实，<https://www.metabase.com/docs/latest/questions/visualizations/table>）。

**我们现在什么样**：`portal.py:956-962`：
`sort_links = " · ".join('<a href="%s">按 %s %s</a>' … for x in cols[:12])`。
**只有前 12 列有排序链接**，而且页面上**没有任何文字说明**"其余列不能排"。
`/t/job_posting` 41 列 → **第 13–41 列无法排序**；
`/t/occupation`（实测 25 列）→ 后 13 列无法排序。
同时 `/t/<表>` 永远是 `SELECT *`（`portal.py:901`），
**没有列可见性管理**——`/talent` 有完整的字段选择器（`portal.py:2346-2404`，`<details class="pickerbox">`），
`/t/<表>` 没有。这就是"同一个门户里同类元素两套能力"。

**建议怎么改（A）**：① 把 `cols[:12]` 的截断改成"全部列可排 + 排序入口收进一个
`<details>` 里按组列出"（复用 `pickerbox` 的视觉，`portal.py:375-382` 已有）；
② 给 `/t/<表>` 加列可见性：URL 参数 `cols=`,复用 `/talent` 已经在用的
`require_column()` 白名单（`portal.py:617`）与 `qs_encode`（`portal.py:622`），
这两条路径**已经是安全的**（README 明确说"能显示什么由列注册表决定，不由 URL 决定"，
`portal.py:2393-2404` 还有一段专门的说明与错误提示）。

**代价与验证**：代价是 `/t/<表>` 的 `SELECT *` 变成动态列清单后，
**CSV 导出范围必须显式决定**（AG Grid 文档原话："When false only the columns currently being displayed
will be exported"）——我建议**列可见性只影响显示，导出仍导出全列**，
并在 CSV 链接文字里写明（`/talent` 就是这么做的：`下载 CSV（当前 %d 列）`，`portal.py:2481`），
因为"下载一份看得见的子集"会让人误以为拿到了全量。**这是产品决策，必须写进页面文字而不是默默选一个。**
验证：`ops/tests/portal_test.py` 里已有一节在验证 `/talent` 的列白名单行为，
同款断言平移到 `/t/<表>`；并断言"`/t/job_posting` 页面上出现的排序链接数 == 该表列数"
（这条断言直接取代 `cols[:12]` 那个隐式行为）。

### 3.4 NULL 的表达已经比标竿更明确，但"0 行 / 没观测 / 空串"还没有分开

**成熟产品怎么做的**：Grafana 的空值默认显示 `-`；NHANES 的 codebook 把四种"没有"**分开列**
（`77 Refused 6`、`99 Don't know 0`、`. Missing 3685`），并说明计数是为了
"understand the coding of skip patterns … and verify the sample size"；
cBioPortal 用**三态单元格**（altered / no alteration / "Not profiled"）表达"样本没测过这个基因"
（分会话核实，<https://wwwn.cdc.gov/Nchs/Data/Nhanes/Public/2017/DataFiles/DEMO_J.htm>、
<https://docs.cbioportal.org/user-guide/faq/>）。

**我们现在什么样**：`.nul{color:#6e7781;font-style:italic}`（`portal.py:408`，
15 号文档 §3.4 已把对比度从 2.00:1 提到 4.55:1），`cell_html()` 对 `None` 输出字面量
`<span class="nul">NULL</span>`（`portal.py:518-519`），
并且 `/t/<表>` 与 `/talent` 都在页脚写明"灰色斜体 NULL 表示该字段为空——这与'值为 0'
或'值为空串'是不同的事实"（`portal.py:979-980`、`2486-2487`）。**这一条我们做得好。**
缺口在**图**上：`charts._fmt()` 对 `None` 返回 `"—"`（`charts.py:81-82`），
而 `histogram` 直接把 `None` 丢掉（`charts.py:392`：`vals = [_num(v) for v in values if _num(v) is not None]`），
`scatter` 也是（`charts.py:262`），**图上完全看不到有多少行因为没有值而被排除**。
`portal_viz` 的空态只在**整个结果集为空**时才提示（`portal_viz.py:390-393`），
"20 行里有 7 行没值"这种情况没有出口。

**建议怎么改（A）**：在 `_svg()` 的图下方（或 `_result()` 里）统一加一行**口径脚注**：
"n = <参与绘制行数>，另有 <被排除行数> 行因该字段为空未参与"。
数据不需要新查询——`fetch()` 已经有完整 `rows`（`portal_viz.py:235-365`），
被排除数就是 `len(rows) - chart["rows"]`。**注意 gnomAD/GTEx 那类做法要的是"分母"，我们要的也是分母，
不是新数据。**

**代价与验证**：代价是每张图多一行文字（约 18px × 16 图 = 约 290px），
且这行必须**不能**写成"缺失 7 行"这种含糊说法，要区分"字段为空"与"该维度不适用"——
后者我们目前**没有数据支撑**（`dimension` 表只有 50 行的注册表，没有逐行的适用域），
所以只能写"该字段为空"。**不要为了好看而编一个'不适用'的计数。**
验证：`ops/tests/viz_test.py` 已断言 7 种图的空状态，扩展成"图卡里含 n=/排除= 脚注"；
再用手算例子对照（项目已有这个手法：README 说"统计量用手算例子对照"）。

### 3.5 超长值的处理在两个表格组件里不一致

**成熟产品怎么做的**：AG Grid 提供 `value-formatters`（值格式化是列配置的一部分，
<https://www.ag-grid.com/javascript-data-grid/value-formatters/>，亲验页面可达）；
Grafana 的最小列宽默认 **150px**、小屏可降到 50px（分会话核实）。

**我们现在什么样**：`.tscroll td{max-width:320px;overflow:hidden;text-overflow:ellipsis;white-space:nowrap}`
（`portal.py:351`）——截断 + `cell_html()` 的 `title` 属性给全值（`portal.py:528-529`，最长 400 字符）；
而 `.tablewin th,.tablewin td{white-space:nowrap; …}`（`portal.py:361`）**没有 `max-width`、没有 ellipsis**。
所以**旗舰页 `/talent`（`.tablewin`，`portal.py:2482`）里一个长 free-text 单元格会把整列撑宽**，
而 `/t/<表>`（`.tscroll`）会截断。同一份 `talent_cell()` 渲染逻辑，因容器不同行为不同。
更麻烦的是 `title` **只在悬停时出现**——触摸屏与键盘用户拿不到完整值。

**建议怎么改（A）**：给 `.tablewin td` 也加 `max-width`（建议 260px，比 `.tscroll` 略窄因为
`.tablewin` 已经横向空间紧张）；并把全值出口从"只靠 title"升级为**列可展开**：
`/talent` 已有 `maxlen` 参数化的 `talent_cell()`，可以把"展开本列"做成
`?maxlen=400` 的 GET 参数（零 JS，与现有 `size`/`density` 参数同机制）。

**代价与验证**：代价是 `.tablewin` 加 `max-width` 会**改变 `/talent` 现有的列宽分配**，
可能让"能力"这类中文长列变窄——15 号文档 §4.5 明确拒绝了斑马纹与行高压缩，
理由是"收益/风险比不划算"，本条的**风险类似**，但收益更具体（触摸屏可读）。
如果不确定，**降级为只加 `maxlen` 参数、不动 CSS** 也是可接受的。
验证：截图 `--only talent`（该夹具已存在）与 `--only talent-columns-open`；
新增断言"`/talent` 页面里长度 > 100 的单元格都带 `title`"。

### 3.6 分页 vs 虚拟滚动：结论是**不做虚拟滚动**，理由是可引用的

**成熟产品怎么做的**：TanStack 官方文档说得很直白——客户端分页意味着"the data that you fetch will contain
**ALL** of the rows"，设计目标是 "**10s of thousands of rows**"，官方例子加载 **100,000 行**
仍可接受，并且明确 **"The UI/UX of both virtualization and pagination have their own trade-offs,
so see which one works best for your use-case"**；AG Grid 的 `paginationPageSize` 默认 **100**、
可选 `[20, 50, 100]`，虚拟化原文 "only renders the rows you currently see"，viewport 模型默认页大小 5 / 缓冲 5
（分会话核实，<https://tanstack.com/table/v8/docs/guide/pagination>、
<https://www.ag-grid.com/javascript-data-grid/viewport/>）。

**我们现在什么样**：`/t/<表>` 用服务端 `LIMIT %s OFFSET %s`，
`size` 参数默认 `PAGE_SIZE`、范围 `lo=5, hi=500`（`portal.py:883`），
并有 `total = count(*)` 精确值（`portal.py:899`）与 `pager_links()`（`portal.py:654-665`）；
`/talent` 固定 `size = 25`（`portal.py:2303`）**没有 size 参数**。两处都是服务端分页。

**建议怎么改（A）**：**不改渲染模型**。只补两件事：
① 给 `/talent` 也加 `size` 参数（复用 `_int_param`，`portal.py:2302-2303` 一行改动）；
② 在分页条旁显示"共 N 行 / 每页 M 行"的显式口径——
Grafana 那句 "This option doesn't affect queries" 提醒我们：**分页尺寸是显示参数，
不能让人以为它改变了统计口径**。我们的 `pager_links` 在 `n_pages<=1` 时返回
`single_label`（`portal.py:659-660`），`/t/<表>` 传的是 `<span class="muted">共 1 页</span>`（`portal.py:954`），
**没有行数**。

**代价与验证**：代价近乎为零。**明确不采纳虚拟滚动（C 级）**——
它需要把行渲染搬到浏览器，代价是：离线单文件打开失效（首屏无数据）、
"页面行数 == 库里 count(*) 精确值"这条 README 点名的断言失效、
以及 SVG/表格可断言性下降（`charts.py:11` 明确写了"图上画了 7 根柱子"在 canvas 里只能截图比对）。
**这三项代价都直接打击本项目自称的卖点，所以不换。**
验证：`ops/tests/portal_test.py` 已有"页面行数 == 库里 `count(*)`"的断言（README §测试点名），
`size` 参数这条改动必须让它保持为绿。

### 3.7 CSV 导出缺公式注入防护，且导出范围口径两处不一致

**成熟产品怎么做的**：AG Grid 的 CSV 导出文档逐字列出风险：
"spreadsheet applications like Excel, Apple Numbers, Google Sheets and others will automatically execute
cell values that start with the following symbols as formulas: **`+`, `-`, `=`, `@`, Tab (0x09) and
Carriage Return (0x0D)**"，并建议用回调让它们不以这些字符开头；同时导出范围要显式选
"all columns" 还是 "only the columns currently being displayed"（分会话核实，
<https://www.ag-grid.com/javascript-data-grid/csv-export/>，我亲验该页 721441 字节可达）。

**我们现在什么样**：`to_csv()`（`portal.py:711-717`）只做
`csv.writer` + `"\ufeff" + buf.getvalue()`（BOM 让 Excel 不乱码），**没有任何前缀防护**。
`/talent.csv` 的链接文字写明列数（`portal.py:2481`：`下载 CSV（当前 %d 列）`），
而 `/t/<表>.csv`（`portal.py:964-965`）**不说明导出的是全列**——
虽然它实际上就是 `SELECT *`（`portal.py:901`），
但 `talent` 侧的注释（`portal.py:632-633`）专门讲过"点一下筛选就丢 34 列"的事故，
说明这个项目**已经在乎导出范围的可预期性**。

**建议怎么改（A）**：在 `to_csv()` 里加一行：值以 `= + - @ \t \r` 开头时前置一个单引号或空格
（AG Grid 文档给的就是这个字符集），并把这条写进函数 docstring；
`/t/<表>.csv` 的链接文字改成 `下载 CSV（全部 %d 列）`，
数据来自已有的 `len(colnames)`（`portal.py:879`）。

**代价与验证**：代价是导出的值会多一个前缀字符——**这会让 CSV 与库里值不完全逐字节一致**，
而本项目有"备份/导出逐表核对"的纪律（README 提到备份带 sha256），
所以这条必须**只作用于门户的 CSV 下载，不能碰到 `ops/backup` 的 XLSX 副本**。
验证：加一条纯函数断言，喂 `["=1+1","+x","-x","@x","\tx","\rx","normal"]`，
断言前 6 个带前缀、第 7 个不带；`to_csv` 是纯函数（不连库），**这条断言不需要数据库就能跑**，
属于最便宜的一类验证。

## 4. 方向三：tree

> 我们的对象：**151 个节点 / 17 族 / 3 层**（我查库实测：`level=1` 17 个、
> `level=2` 36 个、`level=3` 98 个，`status` 全部 `active`），
> 且带 as-of 时间旅行（`occupation_asof()`）与演化变更（`occupation_change` / `occupation_migration`）。

### 4.1 151 个节点一次性全展开，且层级只靠"左内边距"传达

**成熟产品怎么做的**：D3 的 hierarchy 分类学里，indented tree 的价值在
"useful for **interactive browsing**"，并强调好图要支持
"**rapid multiscale inference**: micro-observations of individual elements and
macro-observations of large groups"（<https://d3js.org/d3-hierarchy>，亲验）；
Allen 的本体浏览把树、复选框、逐节点可见性开关、搜索框、透明度滑杆**放在同一个盒子里**，
并且本体是**平表驱动**的（`Structure/query.json` 返回 1327 行，含 `depth`、`structure_id_path`、
`parent_structure_id`、`color_hex_triplet`、`graph_order`、`st_level`），
父节点统计**由子节点测量合并**（分会话核实，
<https://portal.brain-map.org/support/documentation/api-for-mouse-brain-atlas>）。
NN/g 还有一条相关的树测试经验：用户会**回避标签过宽的类别**
（"many users avoided a certain category because the label was so broad that they feared the content
would be overwhelming"）——这条对我们 17 个族名同样适用。

**我们现在什么样**：`view_tree()`（`portal.py:2870-2979`）用
`render(parent, depth)`（`2908-2920`）递归输出
`'<div style="padding:3px 0 3px %dpx">'`（`2913`），每个节点一行，
**151 个节点全部展开、无折叠**。层级由三样东西表达：
① 左内边距 `depth * 22` px；② 一个字形 `{1:"●", 2:"○", 3:"·"}`（`2911`）；
③ 节点 ID 里的 `OCC-F02-01-01` 片段。
**没有 `<ul>/<li>` 嵌套、没有 `role="tree"`、没有 `aria-level`、没有 `<details>` 折叠、
没有给节点加 `id` 锚点**——所以既不能在页内跳到某个节点，屏幕阅读器读到的也是
151 个平级 div（字形 `●/○/·` 确实传了层级，但父子关系没有）。
排序是 `sorted(kids.get(parent, []), key=lambda x: x["occupation_id"])`（`2910`），
即**按 ID 字符串序**，不是语义序（我查库确认节点标签最长 11 字符，所以不是被长标签逼的）。

**建议怎么改（A）**：① 用**嵌套 `<ul>/<li>`** 替代缩进 div（`role="list"` 天然表达层级），
左缩进改由 `<ul>` 的 `padding-left` 承担——视觉不变，语义从"151 个 div"变成真正的嵌套列表；
② 17 个族（`level=1`）用 `<details open>`，第一层折叠**是零 JS 的**；
③ 每个节点加 `id="occ-<occupation_id>"`，并在页面顶部给 17 个族做一个跳转索引
（`/viz` 的面板已经有 `id` 却没有跳转索引，见 §5.4，是同一个缺失）；
④ 补每族节点数与岗位数——**数据已经查好了**：`jd_n`（`2883-2885`）与 `comp_n`（`2886-2888`）
两个字典就在函数里，`badge()`（`2890-2906`）已经在用，只是没上到族级。

**代价与验证**：代价是折叠会**改变现有测试对页面文本的匹配**——
如果把 `level=2/3` 放进默认收起的 `<details>`，`portal_test.py` 里
"页面上出现某职业名"这类断言会失败（内容仍在 HTML 里，但**断言方式**需要确认是按 body 文本匹配还是按可见文本），
**这是必须先跑一遍的**。另外 D3 那句 "macro-observations of large groups" 提醒我们：
折叠第一层恰恰是把"宏观"从"微观"里救出来。
验证：`python code\demo\portal.py --check`；
`ops/tests/portal_test.py`（15 号文档 §5 实测 122 项）先跑红绿；
截图 `python ops\screenshots.py --only tree`（该夹具已存在）；
新增断言"页面含 17 个 `<details` 与 ≥151 个 `id="occ-"`"。

### 4.2 as-of 日期没有进页头——"我到底在看哪一天"靠一栏 KPI 说明

**成熟产品怎么做的**：GDC 把当前队列名**固定在 Main Toolbar**（无队列时回退 `Unsaved_Cohort`），
并用常驻的 Query Expressions 区回答"当前筛了什么"
（分会话核实，<https://docs.gdc.cancer.gov/Data_Portal/Users_Guide/getting_started/>）；
GTEx 把版本做成**每次查询都带的参数**（`datasetId=gtex_v8`）而不是文档里的说明；
Superset 文档也强调非显然的默认筛选要写明（"By default, Apache Superset only shows the last week of data"）；
All of Us 更是把"控件标签与实际有效范围不一致"写成正式说明
（"the age slider is labeled '18–125'; however, it only returns participants aged '18–90'"）。

**我们现在什么样**：`view_tree()` 把 as-of 结果放进变量 `src`（`2874`/`2877`），
渲染在页面中部的 muted 行里（`2959-2960`：`数据源：<code>%s</code>`），
但**页面的 `page("职业树", body, subtitle="层级浏览 + as-of 时间旅行")`（`2979`）
标题与副标题都不含日期**；日期只出现在
① KPI 卡"本时点节点数"的说明行（`2967`：`metric(..., "本时点节点数", asof or "今天")`）
与 ② SQL 折叠块（`2976`）。
也就是说：**用户截图或收藏这一页时，页面上层看不到它代表哪一天。**
更要紧的是 `asof` 直接来自 `qs.get("asof")` 并原样进 `%s::date`（`2873`）——
15 号文档 §0 提到的 `_int_param()`（`portal.py:589-607`）就是为这类输入写的
（它的 docstring 说得很清楚：裸 `int()` 会把 ValueError 穿透到 socketserver，
浏览器看到"连接被重置"），**日期参数没有对应的 `_date_param()`**。

**建议怎么改（A）**：① 让 `subtitle` 带上实际时点（如
`"层级浏览 + as-of 时间旅行 · 当前时点：2026-09-27（occupation_asof）"`）；
② 加一个 `_date_param()`，非法日期给 400 而不是让 psycopg 抛错，
与 `_int_param()` 同一套写法（`portal.py:589-607`）；
③ 页头加一个"回到今天"的显式链接——**已经有了**（`2957`），
但它在表单里而不是页头，可以上移一个位置。

**代价与验证**：代价极小（3 处字符串）。
但注意 `subtitle` 参与了 `page()` 的渲染（`portal.py:491`），
若测试按副标题文本匹配会受影响。
验证：`--check` + `portal_test`；新增断言"带 `asof=2020-01-01` 的请求返回 200 且正文含该日期"
与"带 `asof=abc` 的请求返回 400 而不是连接重置"（后者正是 `_int_param` 守住的那类故障，
有前例可循）。

### 4.3 逐节点的"变更"信息只有聚合数，树上看不出来

**成熟产品怎么做的**：NHANES 把跨周期可用性做成**可渲染的区间**——
`Variable Name | Description | Data File Name | Begin Year | End Year | Component | Use Constraints`，
再配一份"Survey Content"变更手册说明哪些组件何时上线、**何时改过**；
而 Add Health 的 Navigator 虽做了跨波次变量比较，却是 **jQuery/DataTables**，
其 Study Documentation 表**服务端渲染为空**、codebook API 对非浏览器客户端 404
（分会话核实，<https://wwwn.cdc.gov/nchs/nhanes/tutorials/datasets.aspx>、
<https://addhealth-navigator.cpc.unc.edu/>）—— **这正是"为了跨期比较而破例上框架"的代价清单**。

**我们现在什么样**：`badge(r)`（`portal.py:2890-2906`）每个节点显示
`status`（非 active 才显示）、`code_status` 码、`自 <valid_from>`、`N 项能力`、`N 份 JD`。
**没有"自上次以来变了吗"**。整个 as-of 的比较只有"时点对比"表的 **4 行**（`2929-2941`：
今天 / 半年前 / 种子基线起点 / 全部含退役），
聚合到 `节点数` 与 `岗位数` 两列。
而演化层的数据是齐的：`occupation_migration`、`occupation_change`、
`v_evolution_health`（`2946` 在读它）、`change_log`（**我查库实测 563,349 行**）。
`/extend` 页（`3389`）与 `/tree` 的分析面板（`1687-1699` 的"候选池：等评审的新枝"）
都只给**聚合计数**。

**建议怎么改（A，但需要一个明确的查询）**：给树节点加一个"在两个时点之间发生变化的节点名册"区块：
对 as-of 日与今天各跑一次查询，取两个 `occupation_id` 集合的**对称差**，
再 join `occupation_change` 拿变更类型与理由。
**需要的查询**（这是本条的"新数据"要求，写清楚）：
```
-- 两个时点的节点差集；occupation_change 提供变更类型与理由
SELECT o.occupation_id, o.label_zh, o.parent_id, o.level,
       coalesce(c.change_type, '未知') AS change_type, c.note
  FROM occupation o
  LEFT JOIN occupation_change c ON c.occupation_id = o.occupation_id
 WHERE o.occupation_id IN (
       SELECT occupation_id FROM occupation_asof(%(t1)s::date)
       EXCEPT SELECT occupation_id FROM occupation_asof(%(t2)s::date))
```
（`occupation_change` 的真实列名我**没有逐列核对**，写前必须用
`/t/occupation_change` 或 `information_schema` 确认——**本文档不假设它**。）
要显示的字段全部已在树上（`label_zh`、`parent_id`、`level`）。

**代价与验证**：代价是**每次渲染 `/tree` 多两条查询**，
而 `/tree` 已经在读 `occupation_asof`、`jd_n`、`comp_n`、`tl`、`v_evolution_health`
共 5 组查询（`2873`–`2946`），渲染时间会上升——
`/real` 页为了这个问题专门做了缓存（`portal.py:3276-3282`，注释写"现算 20+ 秒会拖垮页面渲染"），
**所以如果这条查询慢，必须同样走缓存而不是硬算**。
验证：新增断言"两个已知时点的差集规模 == 手算值"；
`python code\demo\portal.py --check` 会做一次全页渲染自检（README 说约 16 秒），
渲染时间明显上升就要走缓存。

### 4.4 明确不采纳：treemap 与 sunburst

**成熟产品怎么做的**：NN/g 对 treemap 给了三条"不该用"：
**数据不是层级的**不该用（"functionally equivalent with a pie chart"）、
**项与项大小接近（balanced trees）**不该用、
以及 **area 不是前注意属性**所以"not suited for tasks involving precise comparisons"，
结论是 "**A bar chart would communicate this information more accurately and more quickly**"；
Data to Viz 补一句"**Don't annotate more than 3 levels**"与"severe clutter"
（亲验 NN/g 文章可达；Data to Viz 主页亲验，子页分会话核实，
<https://www.nngroup.com/articles/treemaps/>、<https://www.data-to-viz.com/graph/treemap.html>）。

**我们现在什么样**：我们的树是 **17 族 / 36 中类 / 98 岗位**，族与族之间规模接近
（**平衡树**）。`/tree` 目前用缩进列表，`/viz` 的 `m_tree` 用折线（`portal_viz.py:178-186`），
没有任何面积编码；`charts.py` 也没有 treemap 函数（`PALETTE`/`RAMP`/`DIVERGE` 只支持
bar/line/heatmap/scatter/stacked/target_bar/histogram，`charts.py:112-421`）。

**建议怎么改**：**不加 treemap，也不加 sunburst**。如果要补层级规模的图，
用已有的 `bar_h` 做"每族节点数 + 每族岗位数"的**成对横条**（`charts.py:112-140` 直接可用），
并且**只标 1 层**（族），符合 Data to Viz 的"≤3 层标注"。

**代价与验证**：代价是放弃了"一眼看到层级占比"的观感；
收益是避免一张**在平衡树上不可精确比较**的图被当成结论。
验证：这条不需要验证——它是**不新增**的决策，写进文档是为了防止下一轮有人重新提出来。

### 5.1 "图 + 口径 + SQL 三者同屏"我们做到了——但 `/quality` 的 SQL 是**假的**

**成熟产品怎么做的**：Grafana 的每个 panel 是"query and a visualization"，
"Inspect → Query" 能看到实际查询；Superset 有 "View query" 与 "SQL Lab"；
GDC 的每张图都能导出 SVG/PNG + JSON/TSV 并能"print all cards to one PDF"；
Open Targets 的证据页对每一段数据都给出 `Data type :` 与 `Evidence scoring :`
（<https://platform-docs.opentargets.org/evidence>，亲验 27521 字节）。
共同点是：**展示的查询必须是真正跑过的那一条**。

**我们现在什么样**：`sql_box()`（`portal.py:703-708`）把 SQL 放进 `<details>`，
`panel()`（`portal_viz.py:394-403`）每个面板都带它，`/viz` 的导语也写明了这个承诺
（`portal_viz.py:413-421`）。
但 `/quality` 页末尾那段 SQL（`portal.py:3711-3714`）是：
```
-- 空表清单
SELECT c.relname FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
 WHERE n.nspname='mt' AND c.relkind='r' AND c.reltuples = 0;
```
两个问题：① 它**不是**产出页面上"表填充率"（`3665`：`%d / %d 张基础表有数据`）的那条查询——
那个数字来自 `meta()` 的**逐表精确 `count(*)`**（`portal.py:215` 的注释与 `220` 的执行）；
② 它用了 **`reltuples`**，而 `reltuples` 在 `portal.py` 里的另外 3 次出现
（`28`、`215`、`1714`）**全部是在说"不要用它"**——
README §设计纪律第 6 条原文："行数用精确 `count(*)`，不用 `reltuples` 估算（实测它已经过时：
`code_table` 估 53 / 实 49）"。也就是说：**`/quality` 这一页——专门用来证明"可核的数字"的那一页——
展示了一条违反本项目自己纪律、且不是它实际执行的 SQL。**

**建议怎么改（A）**：把 `3711-3714` 换成真实口径：一条"逐表精确行数 + 空表判定"的
`SELECT … WHERE n_rows = 0` 形式（可以照抄 `meta()` 的实现方式，或直接引用
`portal.py:220` 那段 `count(*)` 的写法），并在注释里写明"与 `meta()` 同口径"。
**这是本文所有建议里性价比最高的一条：约 8 行改动，修的是项目最核心承诺上的一个事实错误。**

**代价与验证**：代价为零（只改一个字符串常量）。
验证分两层：① `python code\demo\portal.py --check` 与 `ops\tests\run_all.py --only 13` 保绿；
② **新增一条断言"门户渲染出的任何页面文本中都不出现 `reltuples`"**——
这条断言直接把这个纪律变成机器可判定的，而且它守的是**全站**而不只是这一页。
（注意 `/t/<表>` 的 SQL box 走 `select.as_string(c)`，`/analyze` 走 `a[3]`，
所以这条断言覆盖它们全部。）

### 5.2 度量注册表与代码里的口径**没有一致性断言**——这是"一个指标只有一个定义"的漏洞

**成熟产品怎么做的**：整套 BI 的语义层（Superset 的 dataset/metric、dbt 的 metric、
Metabase 的 Model）存在的理由就是**口径只定义一次**；
Grafana 面板的查询是可检视的（分会话核实，
<https://grafana.com/docs/grafana/latest/panels-visualizations/>）。

**我们现在什么样**：`register_metrics()`（`portal_viz.py:598-619`）把 `VIZ` 列表的
`title/desc/sql/grain` 写进 `mt.metric_definition`（幂等 `ON CONFLICT DO UPDATE`）。
但面板渲染时用的是**代码里的 `item["sql"]`**（`portal_viz.py:403`），
**不是**数据库里的 `definition_sql`。
而 `ops/tests/viz_test.py:156-158` 只断言 `n_metric >= len(V.VIZ)`（**数量**）。
也就是说：**如果有人改了 `VIZ` 里的 SQL 却忘了跑 `--register-metrics`，
数据库会静默地留着一份旧口径，而页面上显示的是新口径——没有任何测试会发现。**
本项目的纪律是"一个指标只有一个定义"（README §设计纪律第 7 条），
README §常见问题里还专门记录过一次真实的口径漂移事故
（"质量门 90.2% vs 可视化页 61.7%，差别只在分母用 `IN (RT5..RT8)` 还是 `NOT IN (RT5,RT6)`"），
`viz_test.py:131-143` 因此有一条"四处口径完全一致"的断言——**但它只覆盖了 `m_gate` 这一个指标，
16 个面板里另外 15 个没有。**

**建议怎么改（A）**：加一条断言，对 `VIZ` 的每一项查
`SELECT definition_sql, version FROM metric_definition WHERE metric_id = <id>`，
断言它与代码里的 `item["sql"]` **逐字符相等**（或规范化空白后相等），
不一致就报"请跑 `--register-metrics`"。

**代价与验证**：代价是这条断言会**在开发过程中变红**（改了 SQL 还没重注册时），
而这恰恰是它存在的意义——代价是"多一步操作要记得做"，收益是"漂移不再可能静默发生"。
考虑到项目已经在 README 里记录过一次真实的漂移事故，这个代价应该接受。
验证：就是这条断言本身；另外可以通过**故意改一处 SQL 不重注册**来证明它会红
（这是验证断言有效性的标准做法，项目在 `schema/checks/` 下已有同类"自写测试"的习惯）。

### 5.3 "零 JS"的声明与实际实现不一致，而且现有测试只检查了**声明**

**成熟产品怎么做的**：All of Us 的数据浏览器与 Add Health 的 Navigator 都是必须靠 JS 才有内容的
（Add Health 的文档表**服务端渲染为空**）；反过来，UKB Data Showcase 是
服务端渲染的 CGI 页面，它甚至在页面上明说 "WARNING: your browser does NOT have JavaScript enabled.
Not all features of this website will be available to you."——**它承认自己有 JS 依赖，而不是宣称零 JS**
（我亲验 <https://biobank.ndph.ox.ac.uk/showcase/field.cgi?id=21001>）。

**我们现在什么样**：README 第 380 行写"**零 JS / 零 CDN**。图表是服务端生成的内联 SVG，
拷走一个 HTML 文件就能看"；`charts.py:8` 也写"引一个图表库就意味着 CDN、离线失效…"。
但 **`portal_viz.py:565` 有一处内联 JS**：
`<select name="t" onchange="this.form.submit()">%s</select>`——
在 `/viz/build` 的表选择器上。这是全站唯一的 JS（我在 `code/demo/` 全量搜过
`onchange|onclick|onsubmit|<script|javascript:`：`app.py:401` 的 `onsubmit` 与
`console.py:562` 的 `onclick` 在另外两个站点，`portal.py` 与 `charts.py` 里一处都没有）。
更关键的是**测试**：`viz_test.py:152` 断言的是
`check("零 JS" in body and "零 CDN" in body, "声明零 JS / 零 CDN")`，
`154-155` 只检查有没有 `src|href="https?://…"`（外部资源）。
**内联 `on*=` 属性不在任何一个断言的射程内。** 所以这条测试验证的是**广告词**，不是**性质**。

**建议怎么改（A 或 B，二选一，必须显式选）**：
- **方案 A（推荐）**：去掉 `onchange`，表选择器改成一个显式的"切换表"提交按钮。
  代价是选表要两次点击（选 + 提交），收益是"零 JS"从口号变成**可断言的性质**。
- **方案 B**：保留 `onchange`，但把 README 与 `charts.py:8` 的措辞改成精确的
  "门户与可视化层零 JS；`/viz/build` 的表选择器有一处 `onchange` 渐进增强，禁用后仍可用提交按钮"。
  代价是文案变长、卖点变弱；收益是不说谎。

**代价与验证**：我倾向 A，因为 B 会把"零 JS"从一句可验证的硬话变成一个需要解释的软话，
而这个项目所有其它卖点都是硬话。验证：把 `viz_test.py:152` 从"检查声明存在"
升级为**真正的性质断言**——遍历全部页面，断言正文里**不出现任何 `on[a-z]+="` 属性**
（正则 `\son[a-z]+\s*=`）；注意 `/dev` 页指向 8083，需按页面白名单处理。
这条改良比新增十条检查都值。

### 5.4 每张图是 `role="img"` 的**无名图像**，且所有数值只藏在悬停里

**成熟产品怎么做的**：Vega-Lite 的轴有 `description` 属性，
"for SVG output the '**aria-label**' attribute will be set to this description"，
且**未指定时自动生成**；轴标题默认由字段名与聚合派生（"Sum of Profit"）；
带 `subtitle` 的标题能承载单位与来源
（分会话核实，<https://vega.github.io/vega-lite/docs/axis.html>、
<https://vega.github.io/vega-lite/docs/title.html>）。

**我们现在什么样**：`_svg()`（`charts.py:90-94`）产出
`<svg … role="img" …>`——**有角色、没有名字**（无 `aria-label`、无 `<desc>`、无 `<title>` 子元素）。
所有数值通过 `_title_tag()`（`charts.py:105-106`）写成内部 `<title>`：
`bar_h`（`131`/`135`）、`line` 的圆点（`200-202`）、`heatmap` 的格（`241-245`）、
`scatter` 的点（`295-297`）、`stacked` 的段（`336-339`）、`target_bar` 的条与目标线（`373-381`）、
`histogram` 的柱（`411-415`）、`sparkline`（`438-440`）。
`<title>` 只表达悬停，**触摸与键盘拿不到**；
而 `sparkline()`（`437`）与 `gauge()`（`463`）连 `role="img"` 都没有
（它们直接拼 `<svg …>`，不走 `_svg()`）。
`/talent/<id>` 的画像向量表（`portal.py:2641-2644`）里那 50 个维度的取值是**文本**，是可读的；
问题集中在图表。

**建议怎么改（A）**：① 给 `_svg()` 增加 `label=None` 形参，
在 SVG 上写 `aria-label="…"`，并在 `<svg>` 内加一个 `<desc>`；
label 的内容**必须由画图时用的同一份数据生成**（例如
"横条图：17 个岗位族，最大 F01 医学临床 120 份 JD"），**不能写死**；
② `sparkline`/`gauge` 改走 `_svg()`；
③ 每张图下面补一张**可读的数据摘要**——最小实现是 `<details>` 里放
`render_rows` 渲染的原始行（`panel()` 已经持有 `rows`，`portal_viz.py:385` 的
`chart, _rows = fetch(c, item)` 把它丢掉了，改为保留即可）。

**代价与验证**：代价是第 ③ 项会把每张图的高度**再增加一块**——
但这块默认收起，且它同时解决了"图上数值拿不到"和"图与表要不要同屏"两个问题
（15 号文档 §1.2 引的 Shneiderman "details-on-demand" 正是指这个）。
另一个代价是 `aria-label` 是**中文自然语言**，写不好就是噪音，需要逐图措辞。
验证：新增断言"每个非空图表 dict 的 `svg` 含 `aria-label=` 与 `<desc>`"，
加在 `charts.self_check()`（`charts.py:469-517`）里——**它是纯函数、不连库**，
是最便宜的验证位置；`ops/tests/viz_test.py` 会连带覆盖。

### 5.5 `/viz` 16 张图有 `id` 却没有页内索引——而这个缺口是"零成本"的

**成熟产品怎么做的**：NN/g 的 progressive disclosure 原文

Superset 的左栏是"a collapsible treeview"（分会话核实）。

id 就是 `metric_id`，如 `m_gate`），7 个分组的标题用 `<h1 style="margin:26px 0 8px;font-size:17px">`

**本文不重提双列，只指出"既然不能压缩长度，就该给跳转"。**

**建议怎么改（A）**：在 `head`（`portal_viz.py:413-429`）之后加一个

加一条"页面含 ≥16 个 `href="#m_…"` 且对应 id 都存在"；

### 5.6 图表的"解释与免责"：我们的散点图最需要一句话

**成熟产品怎么做的**：FT Visual Vocabulary 对 Correlation 类的原文警告是
"Be mindful that, unless you tell them otherwise, **many readers will assume the relationships you
show them to be causal**"；对 Part-to-whole 的建议是
"If the reader's interest is solely in the size of the components, consider a **magnitude-type chart instead**"；
Data to Viz 的 caveats 页有"**Annotate your chart**"与
"If your color does not represent anything, don't use it"
（分会话核实，<https://github.com/Financial-Times/chart-doctor>、
<https://www.data-to-viz.com/caveats.html>）。
Open Targets 的做法是把**评分方法**与**数据来源**逐段写在证据旁边（亲验）。

**我们现在什么样**：`VIZ` 里每个面板都有 `desc` 字段（`portal_viz.py:54-199`），
渲染成卡片副标题（`portal_viz.py:398`），内容质量不低——
例如 `m_sd`（技能供需对照）写"右下=供给过剩，左上=供给缺口"（`159-160`），
`m_match` 写"**unknown 不是不合格**——把它单独成一色，就是不让它被读成失败"（`170`），
`m_ver` 写"<b>只画一个量纲</b>：行数/覆盖职业/覆盖能力三者量级不同，
塞进同一个 y 轴会让读者误判"（`134-135`）。
**已经比多数产品讲究**。缺的是**因果与相关的那一句**：
`m_sd` 的横纵轴是"具备该能力的人数"与"要求该能力的岗位数"，
这是**两个聚合量的散点**，很容易被读成"某能力导致需求"。
`m_heat`（岗位族 × 能力平均重要性，`110-120`）同理。

**建议怎么改（A）**：给 `VIZ` 增加一个可选字段 `caveat`，只给**需要免责**的面板填
（`m_sd`、`m_heat`、`m_degree`（合成数据与真实数据同权，`144-145` 已经点出）、`m_drift`），
渲染成卡片底部一行带警示色的短句。**注意真实性约束**：caveat 是**关于口径的陈述**，
不是关于数据的数字，所以它不需要新查询——但**不能编造统计显著性**，
例如不能说"相关性不显著"（我们没有做检验）。

**代价与验证**：代价是每张图多一行文字；风险是**免责话术会变成免责套话**
（一页 16 张图每张都加免责，等于都没有免责）——所以我建议**只给 4 张以内**加。
验证：断言"`caveat` 字段的面板数 ≤ 4"（用一个上限断言防止免责通胀，
这个手法本身值得写进文档），并用 `--only viz` 截图确认视觉不吵。

### 5.7 自助构建器与只读 SQL 控制台：安全性是够的，**可解释性**还差一步

**成熟产品怎么做的**：Superset 原文 "SQL Lab queries must first be saved as datasets before they can be
used as persistent chart datasources"——**自由查询与持久图表之间有一道显式的"保存"**；
Metabase 区分 question / dashboard / data source 三层
（分会话核实，<https://superset.apache.org/docs/using-superset/exploring-data>）。

**我们现在什么样**：`build_sql()`（`portal_viz.py:462-481`）先与 `meta()` 的系统目录比对，
再用 `sql.Identifier` 转义（表名/列名），并已实测挡住注入（`viz_test.py:180-191`
断言"注入尝试后 person 表仍在"）；
`/sql`（`portal.py:1431`）走 `validate_sql()`（`portal.py:1414-1428`）——
只允许单条 `SELECT/WITH`、禁分号、查关键字黑名单，
而**真正的防线是数据库的 READ ONLY 事务**（README §设计纪律第 8 条 + `portal_test` 里
`SELECT 1 INTO t` 被拒的断言）。**这套设计是对的，本文不建议改它。**
缺口在：`/viz/build` 的结果**不能被保存**，`/sql` 的结果也不能——
用户做了一个分析，只能下载 CSV 或截图，**没有"把这次口径注册成第 17 个面板"的路径**，
而 `metric_definition` 表已经在那里（16 行），`register_metrics()` 也已经有幂等写入逻辑
（`portal_viz.py:598-619`，注意它是**写**操作，只允许在命令行做——`portal_viz.py:596-597` 的注释写明了）。

**建议怎么改（A）**：给 `/viz/build` 的结果卡加一个**"把这套口径导出为 metric_definition 的 INSERT 语句"**链接
（只生成 SQL 文本、显示在页面上，**不执行**）。
用户把它拷到开发者模式（8083）的 `/sql` 里执行——这条路径**完全复用已有的两个组件**，
不新增写权限、不违反"只读门户"的信任边界（README §架构图里两个端口是"有意的信任边界"）。

**代价与验证**：代价是页面上会多出一段 SQL 文本，`/viz/build` 本来就已经很长；
且必须确保生成的 `metric_id` **不与现有的 16 个冲突**（`metric_definition` 的主键）。
验证：新增断言"`/viz/build?t=…&dim=…` 的返回正文里含 `INSERT INTO metric_definition`，
且其中的 `metric_id` 不在现有 16 个里"。

| 1 | **引入 React/Vue/DataTables/D3/ECharts/TanStack 运行时（含任何 CDN）** | 立刻得到排序/筛选/虚拟滚动/列拖拽 | 直接违反硬约束。代价是**四条卖点同时失效**：① 单个 HTML 拷走离线打开（首屏无数据，因为要等 JS）；② 零依赖（构建链、版本漂移、CDN 离线失效）；③ **可断言**——`charts.py:11` 明说"'图上画了 7 根柱子''最大值那根最长'在 SVG 里是可检查的事实，而在 canvas 里只能截图比对"，`viz_test` 的 31 项断言正是靠这个；④ 审计友好（页面行数 == 库里 `count(*)` 的精确值这条断言会失效）。**Add Health 的 Navigator 就是这条路的现成对照组：它做了我们想做的跨期比较，代价是文档表服务端渲染为空、codebook API 对非浏览器客户端 404。** |

### L1 · `/quality` 底部那段 SQL 换成真实口径，并全站禁用 `reltuples`

**① 成熟产品怎么做的**：Grafana 的每个 panel 都可以 "Inspect → Query" 看到**实际执行的查询**，
Superset 有 "View query"，GDC 的每张图都能导出 SVG/PNG + JSON/TSV 且导出**与表格所见一致**
（分会话核实，<https://grafana.com/docs/grafana/latest/panels-visualizations/>、
<https://docs.gdc.cancer.gov/Data_Portal/Users_Guide/clinical_data_analysis/>）。
这三家的共同点不是"能看 SQL"，而是"**看到的 SQL 就是跑过的那一条**"。

**② 我们现在什么样（具体证据）**：`portal.py:3711-3714`，`/quality` 页末尾 `sql_box()` 的内容是
`SELECT c.relname … WHERE n.nspname='mt' AND c.relkind='r' AND c.reltuples = 0;`。
它有两个事实错误：**(a)** 它不是产出页面上"表填充率"（`portal.py:3665`）的那条查询——
那个数字来自 `meta()` 的逐表精确 `count(*)`（`portal.py:215-222`）；
**(b)** 它用了 `reltuples`，而 `reltuples` 在 `portal.py` 的另外 3 次出现
（第 `28`、`215`、`1714` 行）**全部是"不要用它"的说明**，README §设计纪律第 6 条也写着
"行数用精确 `count(*)`，不用 `reltuples` 估算（实测它已经过时：`code_table` 估 53 / 实 49）"。
我用 grep 逐处确认过：`portal.py` 里 `reltuples` 只有 4 处，**唯一真正使用它的就是这一行**。
换句话说，**门户里唯一一条违反"不猜数字"纪律的 SQL，出现在唯一一页专门用来证明"可核"的页面上。**

**③ 建议怎么改（A）**：把这段常量替换成与 `meta()` 同口径的写法
（逐表 `SELECT count(*)`，再筛 `= 0`，或直接引用 `meta()` 的实现），
注释里写明"-- 与 portal.meta() 同口径：逐表精确 count(*)，不用 reltuples"。

**④ 代价与验证**：代价≈0（改一个字符串常量，约 8 行）。验证有两层：
`python code\demo\portal.py --check` 会把 22 个页面各渲染一遍；
`python ops\tests\run_all.py --only 13` 跑门户 144 项断言。
**并新增一条全站断言："门户渲染出的任何页面文本中都不出现 `reltuples`"**——
这条断言不只是修这一页，它把"不猜数字"从文档纪律变成机器可判定的性质，
而且由于 `/t/<表>`（`portal.py:1018`）、`/analyze`（`portal.py:1400`）、
`/viz`（`portal_viz.py:403`）的 SQL box 都走同一条渲染路径，这条断言覆盖它们全部。

### L2 · 数值列右对齐从"中文列名子串猜测"改成"读列类型"

**① 成熟产品怎么做的**：15 号文档 §1.3 已引 GOV.UK Table 的
"macro 选项里有 `format`：'Specify format of a cell. Currently we only use **"numeric"**'"——
数字单元格是一种**格式**，是**列的类型属性**，不是从列名猜的。
AG Grid 的 `value-formatters` 同样是列配置（亲验该文档页可达）。

**② 我们现在什么样（具体证据）**：`/analyze` 在 `portal.py:1376-1378` 用
`n_right = tuple(cn for cn in cols if any(k in cn for k in ("数","率","量","重要性","变化","上","下","可信度","%","样本")))`；
`mini_analysis()` 在 `portal.py:1729-1730` 用
`any(k in cn for k in ("数","率","量","均","分","人","%","比","级"))`。
**这是对中文列名做子串匹配**，会误判：列名含"上"（如"上级机构"）或含"分"（如"分类"）会被右对齐，
而它们是文本列；反过来"年份"不含这些关键字，会被左对齐（15 号文档 §3.7 已判定日期不该右对齐，这条是对的）。
**正确的机制已经存在于同一个文件里**：`portal.py:1012` 的
`n_right=tuple(x["column_name"] for x in cols if is_numeric(x["data_type"]))`，
`is_numeric()` 在 `portal.py:532-537`，注释还专门说明"`format_type` 会带修饰符
（`numeric(3,2)` / `character varying(64)`），必须剥掉再比"。
也就是说：**同一个代码库里有一套正确的、经过考虑的实现，和两处猜的实现并存**。
`mini_analysis` 被 `/talent` 的 6 个分析、`/tree` 的 2 个、`/schema` 的 1 个、
`/match` 的 3 个共用（`portal.py:1670-1699`），影响面不小。

**③ 建议怎么改（A）**：给 `render_rows()` 增一个可选的 `types=None`（列名→PG 类型）参数；
`/analyze` 与 `mini_analysis` 的调用点把 `n_right=启发式` 换成
`n_right=tuple(c for c in cols if is_numeric(types[c]))`。
类型可以从已经拿到的行集推断（`float/int` 即数值）——
`portal.py:562-563` 的 `auto_chart()` 已经在做类似的类型嗅探（`is_num()`），
所以不需要新查询，**也不需要改 SQL**。

**④ 代价与验证**：代价是中文列名里那些**真是数字但类型是 text** 的列
（例如 `dimension.weight` 若以 text 存）会从左对齐变回左对齐——**这是正确的**，
但要逐一确认没有回归（我的建议是先用 SQL 列出 `/analyze` 全部 8 条分析
与 `TALENT_ANALYSES` 6 条的列名与类型，人工过一遍，这是 20 分钟的事）。
验证：加**手算对照断言**——列名"分类"（text）必须**不**右对齐、
列名"人数"（bigint）必须右对齐、列名"年份"**不**右对齐。
项目已有这个手法（README：统计量用手算例子对照，`cramers_v` 的 bug 就是这么抓出来的）。
页面级验证：`python ops\tests\run_all.py --only 13,15`。

### L3 · `/tree` 的 as-of 日期进页头 + 日期参数校验

**① 成熟产品怎么做的**：GDC 把当前队列名固定在最上方的 Main Toolbar（无队列时回退 `Unsaved_Cohort`）
并用常驻 Query Expressions 区显示当前筛选；GTEx 把版本做成**每次查询都带的参数**
（`datasetId=gtex_v8`）；All of Us 把"控件标签与实际有效范围不一致"写成正式说明
（"the age slider is labeled '18–125'; however, it only returns participants aged '18–90'"）
（分会话核实，<https://docs.gdc.cancer.gov/Data_Portal/Users_Guide/getting_started/>、
<https://support.researchallofus.org/hc/en-us/articles/51716409164308>）。
**共同原则：用户当前看的是哪个切片，必须在最上层说出来。**

**② 我们现在什么样（具体证据）**：`portal.py:2870-2979`。`asof` 从 `qs` 取出后
放进变量 `src`（`2874`/`2877`），渲染在页面中部的 muted 行（`2959-2960`），
并在一个 KPI 卡的说明位出现（`2967`：`metric(f"{len(rows):,}", "本时点节点数", asof or "今天")`）。
但 `page("职业树", body, subtitle="层级浏览 + as-of 时间旅行")`（`2979`）
的**标题与副标题都不含日期**——截图、打印、收藏时，上层看不出这是哪一天的树。
同时 `asof` **未经验证**就进 `%s::date`（`2873`）：`asof=abc` 会让 psycopg 抛错，
而 `portal.py:589-607` 的 `_int_param()` 正是为同一类问题写的，它的 docstring 原话是
"`/t/person?page=abc` 会抛 ValueError，而 `do_GET` 只接 `PortalError` 与 `psycopg.Error`——

日期可见性是个真问题，只是**只做到了正文，没做到页头**。

**③ 建议怎么改（A）**：① `subtitle` 改为带实际时点，例如

② 新增 `_date_param(qs, key)`，与 `_int_param()` 同一套语义（非法值抛 `PortalError(400, …)`）；
③ 把"回到今天"的链接（`2957`，现在在表单里）同时放进页头区。

**④ 代价与验证**：代价≈3 处字符串 + 约 15 行校验函数；风险是 `subtitle` 参与 `page()` 渲染
（`portal.py:491`），若测试按副标题文本匹配会红——**先跑一遍 `portal_test` 再改**。
验证：`python code\demo\portal.py --check`；
新增两条断言——`/tree?asof=<某历史日期>` 返回 200 **且正文含该日期**，
`/tree?asof=abc` 返回 **400 且不是连接重置**（后一条正是 `_int_param` 存在的理由，
有先例可循）；截图 `python ops\screenshots.py --only tree`。

### L5 · `/t/<表>` 加列可见性 + `.tscroll` 补首列吸左

**① 成熟产品怎么做的**：Metabase 原文 "**Sticky columns** are especially useful when viewing wide tables,
as you can keep the column that identifies the row (like `account_name`) on the screen as you scroll
across the columns."，并强调列隐藏"only affects the visibility of the columns in the visualization,
**not in the query results**"；AG Grid 的列固定实现之一就是"keep all columns in the same table,

`making_audits.md` / `audit.js` / `_audits.scss` / `matrix_audit.js` —— **徽标长相未验证**。
另注意它用 FontAwesome 图标字体，**那个做法我们不能抄**，见下。）

**② 我们现在什么样（具体证据）**：15 号文档 §S3-7 与 §4.8 把这个缺口定义得很准，
原文是"`green/amber/red` 表示'达标/接近/不达标'（语义色），而分类调色板是
`blue/green/amber/purple/teal`（类别色）——**同一个绿色既表示'通过'也表示'第 2 个类别'**"，
并判定"需要一张色板规范 + 逐图核对，超出'低风险'范围，**留作下一轮**"（§4.8），
以及"`charts.py` 的 `PALETTE['gray']` = `#8c959f` 用于散点/分类填充，
3.04:1 恰好压在非文本 3:1 门槛上、没有余量"（§4.9）。
我把调用点逐个数清了：`charts.py:37-41` 的 `PALETTE` 里 `green`/`amber`/`red` 同时出现在
**语义位置**——`target_bar` 的 `col = PALETTE["green"] if ok else PALETTE["red"]`（`charts.py:369`）、
`gauge` 的三档（`charts.py:449-450）——与**类别位置**——
`stacked` 的 `colors = [PALETTE["blue"], PALETTE["green"], PALETTE["amber"], PALETTE["purple"], PALETTE["teal"], PALETTE["gray"]]`（`charts.py:310-311`）、
`line` 的 `colors = [blue, green, purple, amber, teal]`（`charts.py:161-162`）。
另外 `/tree` 节点上的码状态 pill 由 `{"V":"p-t","E":"p-e","N":"p-n"}` 映射（`portal.py:2896-2897`）
到 `p-t/p-e/p-n` 三个 class（`portal.py:410-413`）——**只有颜色、没有字形**，
所以灰度打印后"码 V / 码 E / 码 N"三个 pill 完全一样，
而 `/tree` 一页有 151 个节点、每个节点最多 5 个 pill（`badge()`，`portal.py:2890-2906`）。

**③ 建议怎么改（A）**：① 在 `charts.py` 里把语义色与类别色拆成**两个互不相交的常量集**
（语义 `ok/warn/bad` 固定三档；类别改用同明度的蓝/紫/青系，且不含语义色的色相），
这就是 15 号文档 §4.8 指明方向的那张"色板规范"，我把它落成一张可执行的常量表；
② 给 `p-t/p-e/p-n` 三个 pill 各配一个**内联 SVG 或 Unicode 字形**（如 ✓ / ! / –），
字形随 pill 一起走——**必须内联，不能用图标字体**（ENCODE 用 FontAwesome，
那会迫使我们引入外部资源，与零 CDN 直接冲突；把这句话写进代码注释，
防止下一轮有人照抄 ENCODE）；
③ 顺手把 `PALETTE["gray"]` 换成有余量的灰（它在 `#fff` 上只有 3.04:1，见 §4.9）。

**④ 代价与验证**：代价有三条，都要认——
**(a)** 动 `PALETTE` 会**改变全部 16 张图的配色**，
15 号文档 §4.8 拒绝它的理由就是"会动到 `charts.py` 的绘图语义"，**这个风险没有变小**，
所以本条排在清单最后（收益确定但回归面最宽）；
**(b)** pill 加字形会加宽，`/tree` 151 个节点行可能折行，**必须在 1600px 与 940px 各看一次**；
**(c)** 若 `viz_test` 按 SVG 颜色字符串匹配会红。
验证：两条**很便宜也很硬**的断言——① "语义色集合 ∩ 类别色集合 = ∅"
（纯常量比较，不连库，可放进 `charts.self_check()`，`charts.py:469-517`）；
② "每个状态 pill 的标记里都伴随一个字形"（正则匹配 `class="pill p-[ten]"` 后紧跟 SVG 或非空白字符）。
**这两条断言的意义超出本条本身：它们把"颜色不能兼职两种语义"从一条设计原则变成一条 CI 规则**——
这正是 15 号文档 §4.8 中止的地方。截图 `--only tree` 与 `--only viz` 各出一对前后对比图。
