## 1. 软件与数据质量模型（ISO 25010 / 8000 / 25012 / DAMA 维度）

### 1.1 ISO/IEC 25010:2023 产品质量模型

**它衡量的是什么**（一句话）：一个软件/ICT 产品在**九个质量特性**上满足明示与隐含需求的程度，用特性—子特性的两层结构给"质量"规定可被指定、测量和评价的参照模型。

**当前版本的准确清单**（依据官方摘要原文 "composed of **nine** characteristics"，以及 ISO 25000 门户逐条定义）：

| # | 特性（2023 英文名） | 与 2011 版的关系 | 已验证的子特性（部分） |
|---|---|---|---|
| 1 | Functional Suitability | 同 2011 | Functional completeness / correctness / appropriateness |
| 2 | Performance Efficiency | 同 2011 | Time behaviour / Resource utilization / **Capacity** |
| 3 | Compatibility | 同 2011 | Co-existence / Interoperability |
| 4 | **Interaction Capability** | **取代 2011 的 Usability（改名并扩子项）** | Appropriateness recognizability / Learnability / Operability / User error protection / User engagement / Inclusivity / User assistance / Self-descriptiveness |
| 5 | Reliability | 同 2011 | （含 availability、fault tolerance、recoverability 一路） |
| 6 | Security | 同 2011 | Confidentiality / Integrity / Non-repudiation / Accountability / Authenticity |
| 7 | Maintainability | 同 2011 | Modularity / Reusability / Analysability / Modifiability / Testability |
| 8 | Portability | 同 2011 | Adaptability / Installability / Replaceability |
| 9 | **Flexibility**（官方摘要计为第 9 项） | **2011 版无此项** | 子特性：Adaptability / Scalability / Installability / Replaceability —— ⚠️ **我未能打开正文逐条核实*Flexibility* 的子特性归属，此格标"未核实"** |

**版本差异结论（可安全断言的部分）**：
- 官方生命周期显示 **2011 版状态为 Withdrawn**，2023 版（Edition 2，2023-11-15 发布）为现行版 —— 已验证。
- 2023 版摘要明确"**nine** characteristics"，而 2011 版被广泛引用的表述是"8 个特性"。因此"特性数量从 8 变 9"**这一条有官方摘要支撑**。
- "Usability → Interaction Capability"改名有 ISO 25000 门户的章节标题与子特性列表支撑 —— 已验证。
- ⚠️ 第 9 个特性的**确切拼写**（Flexibility）仅由官方摘要的"nine"加上门户未列出的差额推出，**正文未打开**。若要写进正式验收文件，需购买 ISO/IEC 25010:2023 确认第 9 项。

**可转成"跑一条 SQL"的指标**：
ISO 25010 本身是**质量模型（分类框架）**，不是测量方法；但它的每个特性在本项目都能落到一条查询上：

| ISO 25010 特性 | 本项目可测指标 | 测法思路 |
|---|---|---|
| Functional Suitability | 关键业务视图的**结果集断言**通过率 | 为一组"必须成立"的查询写断言（如 `SELECT count(*) FROM v_person WHERE ...` 应等于 N），做成回归清单 |
| Performance Efficiency | 关键查询 P95 延迟；缓存命中率；临时文件字节数 | `log_min_duration_statement`；`pg_statio_user_tables` 命中率；`pg_stat_database.temp_bytes` |
| Compatibility | **导出物能否被外部工具解析** | 导出 UTF-8 CSV/JSON 后做 schema 校验（本项目服务端零 JS，兼容性主要是文件级互操作） |
| Interaction Capability | 不适用（无自定义 UI；交互在 DSH 前端） | — |
| Reliability | 已提交数据可恢复性 | 备份/`pg_dump` 恢复演练的**成功次数与耗时**；`pg_stat_database.xact_rollback` |
| Security | 越权访问断言通过率 | `has_table_privilege`、`row_security_active` 的批量断言（见 §7） |
| Maintainability | 模式漂移检出数；注释覆盖率 | 对照迁移台账与 `pg_class`/`pg_description` |
| Portability | 能否在新机器上一键重建 | 在干净 PG16 上重放全部迁移并跑断言 |
| Flexibility | 加字段/加词表是否需要改代码 | 记录"最近 N 次扩展"中需改应用代码的次数 |

**本项目不适用或代价过高的部分**：
1. **Interaction Capability 整章不适用**。数据库没有终端用户界面；本项目前端在 DSH Web GUI，不是数据库的产物。硬套会产出无意义的"可学习性"指标。
2. **Compatibility 的"共存"子特性**（与其他产品共享环境而无损）在本项目**无对象**：单机便携版、2~3 用户、无多租户。
3. **Capacity 的"参数极值"子特性**在 56 万行、2~3 并发下**没有测量意义**——不会触及容量上限，把容量当 KPI 是浪费。
4. **取得 ISO 25010 认证的成本（CHF 155 只是文档价，认证另计）远超收益**。本项目应把它当**分类词汇表**用，而不是认证目标。

### 1.2 ISO/IEC 25012 数据质量模型

**它衡量的是什么**（一句话）：**数据产品本身**的质量，用 15 个特性分两类——"固有质量"（数据自身，含值域、值间关系、元数据）与"系统依赖质量"（数据在计算机系统中被达到并保持的程度）。

**已验证的定义原文（ISO 25000 门户，逐字）**：
- **Accuracy** — "The degree to which data has attributes that correctly represent the true value of the intended attribute of a concept or event in a specific context of use." 并分 **Syntactic Accuracy**（与语法正确值域的接近度）与 **Semantic Accuracy**（与语义正确值域的接近度）。
- **Completeness** — "The degree to which subject data associated with an entity has values for **all expected attributes** and related entity instances in a specific context of use."
- **Consistency** — "The degree to which data has attributes that are **free from contradiction** and are coherent with other data… either or both among data regarding one entity and across similar data for comparable entities."
- **两类划分** — Inherent Data Quality："refers to data itself, in particular to: data domain values and possible restrictions; relationships of data values (e.g. consistency); metadata." System-Dependent："refers to the degree to which data quality is reached and **preserved within a computer system**… depends on the technological domain… hardware devices, computer system software (e.g. backup software to achieve recoverability), and other software (e.g. migration tools to achieve portability)."
- 标准共 **15 个特性**（门户原文："composed of 15 characteristics"）；门户首页列举的示例含 Accuracy、Completeness、Consistency、**Credibility**、**Currentness**、**Accessibility**。
  ⚠️ **15 个的完整名单与每一个归 Inherent 还是 System-Dependent，我未能取全**（门户分 4 页，只读到第 1 页正文）。**不建议在验收文件里逐条引用 15 个特性名。**

**可转成"跑一条 SQL"的指标**（这是 ISO 25012 最有价值的部分——它的每个特性几乎都能直接落 SQL）：

| 25012 特性 | 指标名 | 测法（示意 SQL 思路） |
|---|---|---|
| Completeness（列级） | `null_rate(col)` | `SELECT count(*) FILTER (WHERE c IS NULL)::numeric / count(*) FROM t`；或用 `pg_stats.null_frac` **免全表扫描估算**（已验证 pg_stats 含 `null_frac`） |
| Completeness（关系级） | `orphan_rate` | 每个外键：`SELECT count(*) FROM child c LEFT JOIN parent p ON ... WHERE p.<pk> IS NULL` |
| Accuracy（语法） | `domain_violation_count` | 对每个受控字段做值域断言：`WHERE status NOT IN (...)`、`WHERE birth_date > current_date`、`WHERE email !~ '...'` |
| Consistency（跨列/跨表） | `contradiction_count` | 业务不变式：`WHERE offer_start > offer_end`；`WHERE experience_years > age`；同一人两处出生日期不一致 |
| 唯一性（项目要求单列） | `dup_key_rate` | `SELECT count(*) - count(DISTINCT k) FROM t`；或 `GROUP BY k HAVING count(*)>1` |
| System-dependent / Recoverability | 恢复演练成功率 | 备份后到干净实例恢复，跑同一套断言 |

**本项目不适用或代价过高的部分**：
1. **ISO 25012 的 System-Dependent 这一类，在本项目大部分不可测也不必要**：单机、无 HA、无跨系统迁移工具。为"可移植性"造指标等于给自己造工作量。
2. **"Credibility / Currentness"在本项目的合成档案里语义空洞**：合成数据没有"权威来源"可言，测"可信度"会退化成测"字段是否存在"。
3. **Accuracy 的"语义正确"原则上不可自动化**：合成档案里的"这位候选人的技能等级是否真实"没有 ground truth。**本项目只能测语法/值域 Accuracy，语义 Accuracy 必须标注为"不适用"**，否则会产出一条永远无法通过的指标。

### 1.3 DAMA-DMBOK 的数据质量维度

**它衡量的的是什么**（一句话）：从**数据管理实践**的角度，把数据质量拆成一组业务可沟通的维度，用于组织数据治理工作。

**核对结果（诚实说明）**：
- DAMA International 官网 **https://dama.org/ 可达（HTTP 200），但正文被截断为几乎空白**，我**未能**从官方站点取到知识领域清单或维度定义。
- 因此：**"DAMA-DMBOK2 列举 11 个知识领域"这一条我未能核实。**
- 六个常用维度名（completeness / accuracy / consistency / timeliness / uniqueness / validity）确实与 ISO/IEC 25012 高度重叠，但**"DAMA 官方对每个维度的标准定义"我未取到**。

**建议的处理方式（重要）**：
> **在本项目的验收文件里，数据质量维度的"定义依据"应引用 ISO/IEC 25012（有官方门户定义可引用），而不是 DAMA。** DAMA-DMBOK 可以写成"与本指标集一致的业界治理框架（未核实版本与条目）"，绝不写具体知识领域编号或维度定义。

**可转成 SQL 的部分**（与 §1.2 相同，无需重复）：
completeness → `null_rate`；uniqueness → `dup_key_rate`；validity → `domain_violation_count`；consistency → `contradiction_count`；**timeliness → 这一个是 DAMA 侧独有且本项目真能测的**：
```
timeliness_us = now() - max(source_updated_at)   -- 或对每个数据域算 staleness
```

### 3.2 范式（1NF–BCNF / 3NF）与无损分解

**它衡量的是什么**（一句话）：**函数依赖**在关系模式上的组织程度——消除部分依赖与传递依赖，使每个事实只存一处，从而让插入/更新/删除异常从"靠纪律避免"变成"结构上不可能"。

**判定条件（这部分是数学定义，可自证，不需要引用权威页面）**：
- **1NF**：每个属性的值域是原子的，不存在"一行一格里塞一个集合"。
- **2NF**：1NF 且不存在非主属性对候选键**部分**函数依赖。
- **3NF**：对每个非平凡函数依赖 X→A，要么 X 是超键，要么 A 是主属性。（等价说法：不存在非主属性对候选键的传递依赖。）
- **BCNF**：对每个非平凡函数依赖 X→A，X 必须是超键。
- **无损分解**：把 R 分解为 R₁、R₂ 是无损的，当且仅当 `R₁ ∩ R₂ → R₁` 或 `R₁ ∩ R₂ → R₂`（即公共属性集是其中一个的超键）。这是**可判定的**，因而可自动化。
- **依赖保持**：3NF 总能做到既无损又保持依赖；**BCNF 不一定能保持依赖**（这是 3NF 存在的根本理由）。

**可转成 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `fd_violation(X→A)` | 对每个待检验的函数依赖：`SELECT count(*) FROM (SELECT x FROM t GROUP BY x HAVING count(DISTINCT a) > 1) q`。返回 0 即该依赖成立 |
| `partial_dep_count` | 复合主键表：分别按主键前缀分组，看非键属性是否有多个不同值 |
| `redundant_attr_count` | 若 A 可由 B 推出（fd 成立且反方向不成立），则 A 是冗余存储 → 用上面的查询判定 |
| `denormalization_ledger` | 维护一张"已知反范式点"表，每行含：表、字段、来源表、刷新方式、一致性校验 SQL |

**已验证的工具**：PostgreSQL 16 的**扩展统计**能直接收集函数依赖系数（`CREATE STATISTICS ... (dependencies)`），把结果读在 `pg_statistic_ext_data.stxddependencies`，文档示例里 `"1 => 5": 1.000000` 表示"列1 完全决定 列5"。**这给"范式实际达成度"提供了一个免手写的测量入口**（来源见 §0.1 #12）。

**纠正"范式越高越好"**：PostgreSQL 官方文档在讲扩展统计时明确写道："in practice many data sets are **not fully normalized** for various reasons; **intentional denormalization for performance reasons is a common example**."（来源 §0.1 #12）
→ 规范化是**消除更新异常**的手段，不是目的。当读多写少、且能证明冗余的一致性时，反范式是正当工程决策。**判据是"冗余是否被一条校验 SQL 守住"，而不是"是否达到 BCNF"。**

**本项目适用性**：
- 适用：**主键/候选键存在性、fd 校验、反范式台账**。这些在 80+ 表上可以脚本化，是"优秀"最硬的证据之一。
- 部分适用：BCNF 追求。56 万行的规模下，为消除一处传递依赖而多一次 join 通常无收益；**优先用 `CREATE STATISTICS (dependencies)` 让规划器知道相关性**，而不是硬拆表。
- 不适用：把"达到 3NF/BCNF"本身当验收项。它没有阈值可言，且与性能目标可能冲突。

### 3.3 ACID 的准确表述

（这是定义性内容，我用可靠性工程的可测口径重述，不引用具体页面）

| 字母 | 准确含义 | 本项目可测指标 |
|---|---|---|
| **A**tomicity | 事务内的多个写，要么全部生效要么全部不生效 | 制造一次"第 2 条语句失败"的事务，断言第 1 条也没留下 → `atomicity_violation_count = 0` |
| **C**onsistency | **由约束定义**：事务把数据库从一个满足全部约束的状态带到另一个满足全部约束的状态。⚠️ 注意：ACID 的 C **不是** CAP 的 C（后者是线性一致性）。这是最常见的名词混淆 | 全库约束列表非空 + 关键不变式断言全过（`CHECK`/`FK`/`UNIQUE` 数量与通过率） |
| **I**solation | 并发事务的相互影响被限制在所选隔离级别允许的异常之外 | `default_transaction_isolation` + 见 §6 的异常测法 |
| **D**urability | 提交后的数据在崩溃后仍在 | **必须实测**：写入 → 立即强杀 postgres 进程 → 重启 → 断言数据在。这是唯一有效的 D 验证 |

**已验证的相关事实**：PostgreSQL 的序列（`serial`/identity）**不参与回滚**——"changes made to a sequence … are immediately visible to all other transactions and are **not rolled back** if the transaction that made the changes aborts"（来源 §0.1 #5）。所以"主键出现空洞"**不是** Atomicity 失败，验收时不得据此判缺陷。

### 3.4 CAP 与 PACELC 的正确表述

**CAP 的准确表述（以及必须纠正的误解）**：

流行的"CAP 三选二"表述是**误导性的**。正确的表述要点：
1. **P（分区容忍）不是你可以放弃的选项**。分区是网络的一种**故障现象**，不是一个可以"不选"的设计特性。CAP 说的是：**当分区发生时（这是必须接受的），你只能在 C 与 A 之间选一个。**
2. 因此 "CA 系统" 只在"网络永不分区的假设下"存在；而该假设在分布式系统里不成立。
3. CAP 只在**分区期间**约束行为；**没有分区时，你既可以得到 C 也可以得到 A**。这正是后来 PACELC 要补的洞：**E**lse（无分区时）要在**L**atency 与 **C**onsistency 之间权衡。

> ⚠️ **核实状态**：Brewer 的 PODC keynote PDF 与 IEEE Computer 2012 文章我**均未能打开**（跨域重定向 / 主机不可达）。**PACELC 论文（Abadi）我也未打开正文。**
> 因此上面的 PACELC 展开**标注为未核实**，不建议作为引用依据写进验收文件；CAP 的核心纠正（P 不可放弃）在逻辑上自明，且是业界共识表述，但**具体出处请以能打开的版本为准**。

**本项目适用性：明确不适用。**
理由：本项目是**单机单实例 PostgreSQL**。没有副本、没有网络分区、没有跨节点一致性协议。CAP/PACELC **没有任何测量对象**。

### 4.1 SLO / SLI / 误差预算（Google SRE）

**它衡量的是什么**（一句话）：用**用户可感知的指标（SLI）**设定一个**可接受的目标（SLO）**，目标与完美之间的差额就是**误差预算**——它把"可靠性"从价值判断变成可花销的预算。

**未核实**：SLI/SLO/误差预算的官方定义原文与章节位置。**不在本文引用具体页码或章节号。**

**落到数据库上的做法（可执行，不依赖引用）**：

| 概念 | 本项目数据库上的落地 |
|---|---|
| SLI（指标） | 关键查询的**延迟分布**：`p50 / p95 / p99`，来自 `log_min_duration_statement` 日志或 `pg_stat_statements` 的 `mean_exec_time`/`total_exec_time` |
| SLI（正确性） | 断言通过率：每次体检跑的 N 条不变式断言中通过的条数 |
| SLO（目标） | 例：*在 2~3 并发的典型负载下，体检用关键查询全部 p95 < 200ms*；*断言通过率 = 100%* |
| 误差预算 | 若 SLO 是"100 次体检中 99 次全绿"，则预算 = 1 次失败；**超预算即停止加功能，先修可靠性** |
| 烧钱率（burn rate） | 用滚动窗口看"最近 20 次体检中的失败次数"，超过预算消耗速度就告警 |

- **适用**：SLO 的**思想**——先写可测量的目标，再验收。这是本项目最该借的骨架。
- **不适用**：2~3 并发用户下，
  - `p99` **统计上无意义**（样本里"第 99 百分位"可能只有 1~2 个观测）。
  - **多窗口烧钱率告警、错误预算策略、值班轮换**都不成立——没有值班人，没有足够流量产生可辨识的告警。

### 4.3 USE 方法（Brendan Gregg）——已完整验证

**它衡量的是什么**（一句话）："**For every resource, check utilization, saturation, and errors.**" —— 遍历资源清单，对每个资源问三个问题，用于**早期快速定位系统性瓶颈**。

**已验证的定义（逐字）**：
- **resource** — "all physical server functional components (CPUs, disks, busses, …)"，也可考虑软件资源与软件施加的限制。
- **utilization** — "the average time that the resource was busy servicing work"（以时间区间内百分比表达）。
- **saturation** — "the degree to which the resource has extra work which it can't service, often queued"（以队列长度表达）。
- **errors** — "the count of error events"（标量计数）。

**已验证的解释阈值（逐字要点）**：
- utilization：100% 通常是瓶颈信号；"**High utilization (eg, beyond 70%) can begin to be a problem**"，原因是 (a) 长区间平均会掩盖瞬时 100% 峰值，(b) 硬盘等不可中断资源在 70% 以上排队延迟变频繁。
- saturation：**"any degree of saturation can be a problem (non-zero)"**。
- errors：非零错误计数值得调查，**尤其是性能差时仍在增长**。

**它也明确警告**："A burst of high utilization can cause saturation and performance issues, **even though utilization is low when averaged over a long interval**. This may be counter-intuitive!"（有 5 分钟平均 CPU 从不超过 80% 但实际间歇打满的实例）

**落到 PostgreSQL 的 USE 清单**：

| 资源 | Utilization | Saturation | Errors |
|---|---|---|---|
| CPU（宿主） | 进程 CPU 占用 | 运行队列 | — |
| 内存 / 共享缓冲 | `pg_stat_io`/`pg_statio_*` 的缓存命中率 | 匿名换页 / swap | OOM（`53200 out_of_memory`） |
| 磁盘 I/O（数据目录） | 设备 busy% | I/O 等待队列；`pg_stat_activity.wait_event_type='IO'` | 设备错误 |
| **表/索引（PG 特化）** | 顺序扫描比例、索引命中率 | 锁等待队列、`pg_locks` 未授予数 | `xact_rollback`、死锁数 |
| **连接（PG 特化）** | `count(*) FROM pg_stat_activity` / `max_connections` | 等待连接的会话数 | `53300 too_many_connections` |

**本项目适用性：适用（推荐作为主框架之一）。**
- **适用**：清单化的三问结构在 80+ 表上极好用，且**它自带"未知的已知"价值**——没测的资源是被记录的空白，不是被忽略的空白。
- **部分适用**：错误计数在本项目**基数太小**（2~3 用户，一天可能 0 错误），零值不构成信号；解释时要区分"无错误"与"无流量"。
- **注意纠正**：USE 页面自己指出"a burst of high utilization can cause saturation even though utilization is low when averaged"——**所以只取平均值会漏掉问题**。本项目采集时应记录峰值而非仅均值。

### 4.4 Little 定律在校验并发与延迟关系时的用法

**它衡量的是什么**（一句话）：排队系统的恒等式 **L = λ × W** —— 系统中平均并发数 L 等于到达率 λ 乘以平均停留时间 W。**它不是经验规律，是算术恒等式**（在稳定、守恒的观察窗口内必然成立）。

**在数据库上怎么用（这才是它的价值）**：
1. **交叉校验**：从 `pg_stat_database` 得到每秒事务数 λ，从慢查询日志/`pg_stat_statements` 得到平均事务时长 W；两者乘积应约等于"平均活跃会话数"。活跃会话数可从 `pg_stat_activity` 的 `state='active'` 计数得到。
   → **若 L 与 λ×W 显著不符，说明你的观测窗口不稳、或统计口径不一致（例如把 `idle in transaction` 漏算了）。**这是发现"测量本身有错"的廉价手段。
2. **容量反推**：给定可接受的 W（例：p95 延迟 200ms）和已知峰值 λ，可算出需要的并发连接/工作进程数下限，用来**判断连接池是否需要**。
3. **反直觉提醒**：并发数增加而吞吐不变时，W 必然上升——**"并发高"不等于"吞吐高"**。

**注意**：Little 定律的 L 是**系统内**的平均数。若把 `idle` 会话计入 L，等式会失真；`idle in transaction` 则**会**占用资源，应计入"在系统内"。这是实践中最容易错的口径。

**本项目适用性：适用于"验证测量口径"这一用途；不适用于容量规划。**
- 2~3 并发用户下，λ 极小，L≈1~3，**乘积校验的数值分辨率很低**（±1 个会话就让等式差 30%+）。因此它在本项目的主要价值是**提醒口径一致性**（是否把 `idle in transaction` 算进去），而不是精确核算。
- **不要**用它去推"该开多少连接"。2~3 用户下连接数由进程模型决定，不由排队论决定。

## 5. 索引与查询设计（sargability / 选择性 / EXPLAIN 判读 / 何时不建索引）

### 5.1 sargability（可索引性）

**它衡量的是什么**（一句话）：`WHERE` 子句是否能被转换为**对索引键的范围/等值查找**，而不是只能对每行做一次函数求值。

**判据**：
- **sargable**：`col = 常量`、`col > 常量`、`col BETWEEN a AND b`、`col IN (...)`、`col LIKE 'abc%'`（前缀锚定，且用对 opclass）。
- **not sargable**：`f(col) = 常量`（函数包住列）、`col::text = 'x'`（类型转换包住列）、`col LIKE '%abc'`（后缀通配）、`a + b = c`（列参与运算）、`col <> 常量`（低效）。
- **修复办法**：改写成对列直接比较（`col >= date_trunc(...)` 而非 `date_trunc('day', col) = ...`），或建**表达式索引**。PostgreSQL 官方明确支持后者："an index computed on `upper(col)` would allow the clause `WHERE upper(col) = 'JIM'` to use an index."（来源 §0.1 #17）

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `non_sargable_predicate_count` | 静态扫描应用 SQL 文本（本项目零 JS 服务端，SQL 集中在迁移/视图/函数中）：检出 `函数名(` 后紧跟列名再 `=` 的模式，人工复核清单 |
| `index_cond_ratio` | `EXPLAIN` 输出里 `Index Cond:` 行数 / (`Index Cond:` + `Filter:` 行数)。**Filter 行意味着条件只在取回行之后才生效**——已验证文档："the `stringu1` clause cannot be applied as an index condition… Instead it is applied as a filter" |
| `rows_removed_by_filter` | `EXPLAIN ANALYZE` 输出的 `Rows Removed by Filter:`。**这个数远大于 `actual rows` 就是低效扫描的硬证据** |

### 5.2 覆盖索引（covering index）与 index-only scan

**它衡量的是什么**（一句话）：让查询**只读索引不读堆表**，从而消除随机堆访问。

**已验证的关键事实**（来源 §0.1 #9）：
- 使用条件有两条硬性前提：① 索引类型必须支持 index-only scan（**B-tree 一定支持**；GiST/SP-GiST 仅部分 opclass；**GIN 不支持**，因为索引项只存原值的一部分）；② 查询引用的列必须**全部在索引中**。
- 追加前提：PostgreSQL 还需**visibility map** 判定行可见性。文档原文："it will be a win **only if a significant fraction of the table's heap pages have their all-visible map bits set**."
- **`INCLUDE` 语法**：`CREATE INDEX tab_x_y ON tab(x) INCLUDE (y);` —— 非键列只是"payload"，**不参与唯一性判定**（"the uniqueness condition applies to just column `x`"）。
- 代价警告（原文）："non-key columns duplicate data from the index's table and **bloat the size of the index, thus potentially slowing searches**"，且"there is little point in including payload columns … **unless the table changes slowly enough**"，还有"**B-tree deduplication is never used with indexes that have a non-key column**"。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `index_only_scan_ratio` | `EXPLAIN (ANALYZE, BUFFERS)` 输出中 `Index Only Scan` 节点数 / 全部 scan 节点数；同时看 `Heap Fetches:` 字段——**`Heap Fetches` 接近 `actual rows` 说明 visibility map 没帮上忙，覆盖索引白建** |
| `vm_all_visible_ratio` | 对目标表 `VACUUM VERBOSE` 输出中 all-visible 页比例；或侧面用上一条的 `Heap Fetches` |

### 5.3 选择性与基数

**它衡量的是什么**（一句话）：**选择性** = 满足条件的行占全表的比例；**基数** = 列上不同值的个数。选择性越低（返回比例越高），索引越不划算。

**已验证的工具**（来源 §0.1 #23，pg_stats 列定义逐字）：
- `n_distinct` — "If greater than zero, the estimated number of distinct values… If less than zero, the **negative of the number of distinct values divided by the number of rows**… For example, **-1 indicates a unique column**".  → **`n_distinct = -1` 等价于该列唯一**，这是"基数是否饱和"的直接读出。
- `null_frac` — 空值比例（免全表扫描）。
- `most_common_vals` / `most_common_freqs` — 最高频值与频率。
- `histogram_bounds` — 等人口分桶边界。
- `correlation` — 物理行序与逻辑序的相关性，**越接近 ±1，索引扫描的随机访问越少，规划器估计越便宜**（原文："When the value is near -1 or +1, an index scan on the column will be estimated to be cheaper… due to reduction of random access to the disk."）

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `selectivity(col)` | `SELECT 1/abs(n_distinct) FROM pg_stats WHERE tablename=... AND attname=...`（负值需按行数还原）；或直接 `EXPLAIN` 里 `rows=` 估计值 / `reltuples` |
| `cardinality_ratio` | `abs(n_distinct) / reltuples`，**接近 1 = 高基数（唯一/近唯一），远小于 1 = 低基数** |
| `stats_staleness` | `pg_stat_user_tables.last_analyze` 与数据变更量（`n_mod_since_analyze`）的对比 |
| `mcv_skew` | `most_common_freqs` 的最大值与平均值之比；比值大表示数据倾斜，等值查询计划会不稳 |

### 5.4 EXPLAIN 里真正要看的要点

**已验证的判读要点**（来源 §0.1 #11）：
1. **`Seq Scan` 不必然是坏事**。文档给出成本公式：`cost = relpages × seq_page_cost + rows × cpu_tuple_cost`。默认 `seq_page_cost=1.0`、`cpu_tuple_cost=0.01`。
2. **`Filter:` vs `Index Cond:` 是最重要的区分**。`Filter` 意味着"取回后再筛"，`Rows Removed by Filter` 大就是浪费。
3. **`EXPLAIN ANALYZE` 的 `rows=` 估计值 vs `actual rows=` 的偏差是核心健康指标**。文档原文："The thing that's usually most important to look for is **whether the estimated row counts are reasonably close to reality**."
4. **`loops=` 的陷阱**：嵌套循环内层节点的 `actual time` 与 `rows` 是**每次执行的均值**，总量要**乘以 `loops`**。文档明确警告这一点。**漏乘 loops 是最常见的误读。**
5. **`EXPLAIN (ANALYZE, BUFFERS)` 是 I/O 定位的唯一手段**：`Buffers: shared hit=N read=M` 能区分"命中缓存"与"真的读了盘"。
6. **单页小表几乎总是 Seq Scan**：文档原文："on a table that only occupies **one disk page**, you'll nearly always get a sequential scan plan **whether indexes are available or not**." → **对本项目许多小维度表，Seq Scan 是正确结果，不构成缺陷。**
7. **采样噪声**：`ANALYZE` 用随机采样，"your estimated costs and row counts might vary slightly"。
8. **`Planning time` 与 `Execution time` 的分界**：后者含执行器启停与 BEFORE 触发器，**不含**解析/重写/规划。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `estimate_error_ratio` | `EXPLAIN ANALYZE` 文本解析：`max(actual rows / rows, rows / actual rows)`，取全计划最大比。**>10 触发复查** |
| `seq_scan_on_large_table` | `pg_stat_user_tables.seq_scan` 与 `seq_tup_read`，筛 `n_live_tup > 100000`（本项目 56 万行大表）的表 |
| `filter_waste_ratio` | `Rows Removed by Filter / (Rows Removed by Filter + actual rows)` |
| `buffers_read_ratio` | `EXPLAIN (ANALYZE, BUFFERS)` 中 `read` / (`hit`+`read`) |

### 5.5 什么时候**不该**建索引

**已验证的依据（原文，来源 §0.1 #17）**：
> "Indexes are primarily used to enhance database performance (**though inappropriate use can result in slower performance**)."

这条官方陈述是本节所有"不该建"结论的授权。

| 不该建索引的情形 | 为什么（机制） | 怎么检测 |
|---|---|---|
| **低选择性列**（如性别、状态只有 3 个值） | 规划器算出扫描索引+回表比顺序扫全表更贵，**索引根本不会被用**，只承担写放大的代价 | `pg_stat_user_indexes.idx_scan = 0`（长期零使用） |
| **表很小**（单页/几页） | 官方：单页表"nearly always"走 Seq Scan | `pg_class.relpages <= 1` 且有未使用索引 |
| **冗余索引**（`(a)` 与 `(a,b)` 并存） | `(a,b)` 的最左前缀已能服务所有 `(a)` 的查询，`(a)` 纯属重复 | 对比 `pg_index` 的键列序列，检出前缀包含关系 |
| **写多读少表** | 每个索引都要在 INSERT/UPDATE/DELETE 上维护；`fillfactor` 低的索引还会页面分裂 | 对比表的 `n_tup_ins+n_tup_upd` 与索引的 `idx_scan` |
| **EXCLUDE/INCLUDE 塞宽列** | 官方警告：非键列复制数据、膨胀索引、且**禁用 B-tree 去重** | `pg_relation_size(index)` 与表大小之比 |
| **为了 `<>`、`LIKE '%x'` 建索引** | 这些谓词不可 sargable，索引用不上 | 见 §5.1 的断言 |
| **只为满足"看起来规范"而给每个 FK 建索引** | 反例：**外键子表侧通常需要索引**（否则父表删除/更新会全表扫子表）；但父表侧的唯一索引已由约束提供 | 检查每个 FK 在子表上是否有可用的前导索引 |

**可转 SQL 的核心指标（这条最该进验收集）**：

```sql
-- 未使用索引（排除唯一约束隐含的索引）
SELECT schemaname, relname, indexrelname, idx_scan, pg_size_pretty(pg_relation_size(indexrelid)) AS size
FROM pg_stat_user_indexes
JOIN pg_index ON pg_index.indexrelid = pg_stat_user_indexes.indexrelid
WHERE idx_scan = 0 AND NOT pg_index.indisunique AND NOT pg_index.indisprimary
ORDER BY pg_relation_size(indexrelid) DESC;
```
**判读注意**：`idx_scan` 是从**上次统计重置**起累计的。刚建的索引或统计被重置后必然为 0。**必须结合"重启/重置时间"看**，否则会把新索引误判为垃圾——这是本指标最容易误用的地方。

### 5.6 统计信息与 ANALYZE 的作用

**它衡量的是什么**（一句话）：给查询规划器提供**行数、值分布、不同值个数、物理相关性**的估计，使代价比较有意义。

**已验证的事实（来源 §0.1 #12、#13）**：
- 表/索引规模存于 `pg_class.reltuples` / `relpages`。**它们不是实时更新的**："`reltuples` and `relpages` are not updated on-the-fly, and so they **usually contain somewhat out-of-date values**"，由 `VACUUM`、`ANALYZE`、`CREATE INDEX` 更新；且**非全表扫描的 vacuum 只会增量更新，得到近似值**。
- 分布信息存于 `pg_statistic`（只有超级用户可读），**对外应读 `pg_stats` 视图**（"`pg_stats` is readable by all… restricted to show only rows about tables that the current user can read"）。
- **`ANALYZE` 用随机采样**，统计"always approximate even when freshly updated"。
- 统计目标默认 100 项，可用 `ALTER TABLE ... SET STATISTICS` 或 `default_statistics_target` 调整。
- **扩展统计**解决多列相关性：`dependencies`（函数依赖）、`ndistinct`（多列不同值数）、`mcv`（多列高频值组合）。文档给出量化例子：Washington, DC 的实际频率 0.003467 vs 按单列独立假设计算的基频 2.7e-05，**低估两个数量级**。
- ⚠️ **重要的运维陷阱（已验证）**：autovacuum **不对分区表本身**发 `ANALYZE`；**继承父表只在父表本身被修改时才被 analyze，子表变更不触发父表 autoanalyze**；外部表也不 autoanalyze。→ **这些情况必须手工 `ANALYZE`。**

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `never_analyzed_tables` | `SELECT relname FROM pg_class c LEFT JOIN pg_stat_user_tables s ON ... WHERE s.last_analyze IS NULL AND c.relkind='r'` |
| `stats_drift` | `n_mod_since_analyze / reltuples`（>0.2 提示该重新 ANALYZE） |
| `stats_target_low` | `pg_attribute.attstattarget = -1`（用默认）**且** `pg_stats.most_common_freqs` 高度倾斜 → 该列应提高 target |
| `correlated_cols_without_extstats` | 检出 `WHERE a=... AND b=...` 常用组合，但 `pg_statistic_ext` 里没有对应统计对象 |

## 6. 事务与并发（隔离级别防什么 / 死锁 / 长事务）

> 本节几乎全部**已验证**（来源 §0.1 #5、#10、#16、#21），是本文证据最硬的一节。

### 6.1 隔离级别各自防什么异常——官方表

**它衡量的是什么**（一句话）：通过规定"哪些并发异常**不允许**发生"，来定义事务之间可见性的强度。

**已验证的官方表（PostgreSQL 16 Table 13.1，逐字转录）**：

| Isolation Level | Dirty Read | Nonrepeatable Read | Phantom Read | Serialization Anomaly |
|---|---|---|---|---|
| Read uncommitted | Allowed, but not in PG | Possible | Possible | Possible |
| Read committed | Not possible | Possible | Possible | Possible |
| Repeatable read | Not possible | Not possible | **Allowed, but not in PG** | Possible |
| Serializable | Not possible | Not possible | Not possible | Not possible |

**官方对四个异常的逐字定义**：
- **dirty read** — "A transaction reads data written by a concurrent uncommitted transaction."
- **nonrepeatable read** — "A transaction re-reads data it has previously read and finds that data has been modified by another transaction (that committed since the initial read)."
- **phantom read** — "A transaction re-executes a query returning a set of rows that satisfy a search condition and finds that the set of rows satisfying the condition has changed due to another recently-committed transaction."
- **serialization anomaly** — "The result of successfully committing a group of transactions is inconsistent with all possible orderings of running those transactions one at a time."

**已验证的 PostgreSQL 特化事实**：
1. **PG 内部只实现三个级别**："PostgreSQL's Read Uncommitted mode **behaves like Read Committed**."
2. **PG 的 Repeatable Read 不允许幻读**（比 SQL 标准要求更强）："PostgreSQL's Repeatable Read implementation **does not allow phantom reads**." 标准允许更高保证，故合规。
3. **PG 的 Repeatable Read = Snapshot Isolation**（文档明说），**Serializable = Serializable Snapshot Isolation (SSI)**。
4. **Serializable 用谓词锁**，且"these locks **do not cause any blocking** and therefore can **not** play any part in causing a deadlock"。
5. **Read Committed 是 PostgreSQL 默认级别**。
6. **序列化失败必须重试**，SQLSTATE = **`40001`**（已验证，来源 §0.1 #16）。
7. 官方建议：`READ ONLY` 声明、控制活跃连接数、**不要把不必要的操作塞进一个事务**、**不要让连接长期 `idle in transaction`**（可用 `idle_in_transaction_session_timeout` 自动断开）。

**关于"写偏斜（write skew）"**：
- 写偏斜**不是** SQL 标准的四个异常之一，它是 Snapshot Isolation 允许、而 Serializable 禁止的一类异常。
- **PoC 与官方给的"两个 class 互算 SUM 再插入"例子等价**：PostgreSQL 文档给的示例正是——A 算 `SUM(value) WHERE class=1` 得 30 插入到 class=2；B 算 `SUM(value) WHERE class=2` 得 300 插入到 class=1；**Repeatable Read 下两者都能提交**，Serializable 下会回滚一个并报 `could not serialize access due to read/write dependencies among transactions`。
- ⚠️ **核实状态**："write skew"这个术语及其原始定义出自 Berenson 等 1995 年的论文，**我未能打开该论文**。因此本文只描述上面这个**官方文档给出的行为**，不引用该术语的原始出处。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `default_isolation_level` | `SHOW default_transaction_isolation`（对每个应用连接与 `pg_settings` 均查） |
| `serialization_failure_rate` | 从日志按 `SQLSTATE 40001` 计数 / 总事务数 |
| `deadlock_rate` | 日志 `SQLSTATE 40P01` 计数；`pg_stat_database.deadlocks` |
| `rollback_ratio` | `pg_stat_database.xact_rollback / (xact_commit + xact_rollback)` |
| `ssi_overhead` | 开启 Serializable 前后同一工作负载的 p95 对比 |

### 6.2 死锁检测与避免

**它衡量的是什么**（一句话）：检测"互相持有对方所需锁"的循环等待并**主动中止其中一个事务**，使系统不会永久停滞。

**已验证的事实（来源 §0.1 #10）**：
- 机制原文："PostgreSQL **automatically detects deadlock situations** and resolves them by aborting one of the transactions involved… (Exactly **which transaction will be aborted is difficult to predict and should not be relied upon**.)"
- **行级锁也会死锁**，且**不用显式锁也会发生**。文档给了完整的两事务交错例子（更新 11111 与 22222 的两条 UPDATE 交叉）。
- **官方给的最佳防御**（原文要点）：
  1. "**being certain that all applications using a database acquire locks on multiple objects in a consistent order**"（统一加锁顺序）；
  2. "**the first lock acquired on an object in a transaction is the most restrictive mode that will be needed**"（一次到位取最强锁）；
  3. 若做不到，就"**retrying transactions that abort due to deadlocks**"。
- **重要警告**："So long as no deadlock situation is detected, a transaction seeking either a table-level or row-level lock will **wait indefinitely**… This means it is a bad idea for applications to hold transactions open for long periods of time."

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `blocked_session_count` | `SELECT count(*) FROM pg_stat_activity WHERE cardinality(pg_blocking_pids(pid)) > 0` |
| `lock_wait_visible` | `log_lock_waits = on`（已验证该参数：会话等待超过 `deadlock_timeout` 时产生日志）→ 统计日志条数 |
| `longest_lock_wait_ms` | `pg_stat_activity` 中 `wait_event_type='Lock'` 的 `state_change` 时长 |
| `lock_mode_audit` | 静态审查 DDL 是否可取更轻的锁（见 §8.3 表）|

### 6.3 长事务的危害

**它衡量的是什么**（一句话）：长事务（尤其 `idle in transaction`）会**钉住 xmin horizon**，使 vacuum 无法清理任何比它更晚的死元组，同时阻塞 XID 冻结推进。

**已验证的机制（来源 §0.1 #13）**：
- 文档给出的**排障顺序**（原文）在 XID 回卷熔断时用来定位"谁挡住了"：
  1. `pg_prepared_xacts` 中 `age(transactionid)` 很大的；
  2. `pg_stat_activity` 中 **`age(backend_xid)` 或 `age(backend_xmin)` 很大**的；
  3. `pg_replication_slots` 中 `age(xmin)`/`age(catalog_xmin)` 很大的。
- **回卷的数量级（已验证）**：XID 32 位 → **"at least once every two billion transactions"** 必须全库 vacuum 一次；**"forty million transactions from the wraparound point"** 开始发 WARNING；**"fewer than three million transactions left"** 时**拒绝分配新 XID**（`ERROR: database is not accepting commands to avoid wraparound data loss`），此时**只有只读事务能开始**。
- 冻结相关参数：`vacuum_freeze_min_age`、`vacuum_freeze_table_age`（**有效上限为 0.95 × `autovacuum_freeze_max_age`**）、`autovacuum_freeze_max_age`（**即使关闭 autovacuum 也会触发**反回卷 vacuum）。`autovacuum_freeze_max_age` 默认 2 亿事务。
- **autovacuum 会被打断**：若某进程申请与 autovacuum 持有的 `SHARE UPDATE EXCLUSIVE` 冲突的锁，**autovacuum 会被中断**；**但反回卷 autovacuum 不会**（`pg_stat_activity` 中 query 名以 `(to prevent wraparound)` 结尾）。
- **已验证的严重警告（原文）**："Regularly running commands that acquire locks conflicting with a `SHARE UPDATE EXCLUSIVE` lock (e.g., `ANALYZE`) can **effectively prevent autovacuums from ever completing**."
- **标准 `VACUUM` 也持锁**：它持有 `SHARE UPDATE EXCLUSIVE`（已验证，来源 §0.1 #10）——**所以"VACUUM 不锁表"是不准确的说法**。

**可转 SQL 的指标（本项目最该纳入的运维指标之一）**：

```sql
-- 长事务 / 钉住 horizon 的会话
SELECT pid, usename, state, now() - xact_start AS xact_age,
       now() - state_change  AS state_age,
       age(backend_xid)      AS xid_age,
       age(backend_xmin)     AS xmin_age,
       left(query, 80)       AS query
FROM pg_stat_activity
WHERE xact_start IS NOT NULL
ORDER BY xact_start;
```

| 指标名 | 阈值建议 |
|---|---|
| `max_xact_age` | `idle in transaction` 超过 60s 即告警（配 `idle_in_transaction_session_timeout`） |
| `max_xmin_age` | 监控趋势，避免长期增长 |
| `max_relfrozenxid_age` | `SELECT max(age(relfrozenxid)) FROM pg_class WHERE relkind IN ('r','m')`；与 `autovacuum_freeze_max_age`（默认 2 亿）比 |
| `max_datfrozenxid_age` | `SELECT datname, age(datfrozenxid) FROM pg_database` |
| `oldest_dead_tuples_table` | `SELECT relname, n_dead_tup, last_autovacuum FROM pg_stat_user_tables ORDER BY n_dead_tup DESC LIMIT 10` |

## 7. 安全与隐私（最小权限 / RLS / SECURITY DEFINER / 审计 / 合规要点）

> **法律声明：本节第 7.6 小节仅为工程要点整理，不构成法律意见。**

### 7.1 最小权限

**它衡量的是什么**（一句话）：每个主体（角色/应用/人）只持有完成其职责所必需的、**最小范围与最小时长**的权限。

**已验证的依据（来源 §0.1 #6、#19）**：
- 权限共 14 种：`SELECT, INSERT, UPDATE, DELETE, TRUNCATE, REFERENCES, TRIGGER, CREATE, CONNECT, TEMPORARY, EXECUTE, USAGE, SET, ALTER SYSTEM`。
- **支持列级授权**：`GRANT SELECT (col1), UPDATE (col1) ON mytable TO role;`，psql `\dp` 会分列显示"Column privileges"。
- **默认 PUBLIC 权限表（逐字要点，本项最有用）**：表、列、序列、外部数据包装器、外部服务器、大对象、**schema**、表空间、配置参数——**默认都不授给 PUBLIC**。其余对象授给 PUBLIC 的是：DATABASE 的 `CONNECT` + `TEMPORARY`；**FUNCTION/PROCEDURE 的 `EXECUTE`**；LANGUAGE 与 TYPE/DOMAIN 的 `USAGE`。
  → **两个必须注意的默认敞口**：① **新建函数默认对所有角色可执行**（所以 SECURITY DEFINER 函数必须显式 `REVOKE ... FROM PUBLIC`）；② 从 PG 14 及更早升级来的库里 **`public` schema 的 `CREATE` 权限默认给所有人**（PG 15+ 已改）。
- **`REFERENCES` 与 `TRIGGER` 权限的危险性（官方原文警告）**：
  - REFERENCES — "a user who creates a foreign key can arrange for enforcement of that foreign key to call an arbitrary function, such as a cast function, and such functions will be called with the privileges of the **table owner**."
  - TRIGGER — "any triggers added to a table or view will be executed with the privileges of users who modify it."
- **超级用户的边界（原文，这条极其重要）**："It should be noted that **database superusers can access all objects regardless of object privilege settings.** This is comparable to the rights of `root`… it's unwise to operate as a superuser except when absolutely necessary."
- 关于加固时序的建议（原文）："For maximum security, issue the `REVOKE` **in the same transaction that creates the object**; then there is no window in which another user can use the object."

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `superuser_count` | `SELECT count(*) FROM pg_roles WHERE rolsuper` —— 除维护角色外应为 0 |
| `bypassrls_count` | `SELECT count(*) FROM pg_roles WHERE rolbypassrls` |
| `table_public_grants` | `SELECT * FROM information_schema.role_table_grants WHERE grantee='PUBLIC'` 应为空 |
| `schema_public_create` | `SELECT has_schema_privilege('public','public','CREATE')` 应为 false |
| `function_public_execute` | `SELECT p.proname FROM pg_proc p JOIN pg_namespace n ON ... WHERE has_function_privilege('public', p.oid, 'EXECUTE') AND p.prosecdef` —— **SECURITY DEFINER 且仍对 PUBLIC 可执行 = 缺陷** |
| `column_level_grants_used` | 若设计意图是字段级最小权限，检查是否真的用了列级 `GRANT` 而不是表级 |

### 7.2 RLS（行级安全）——以及它**防不住**什么

**它衡量的是什么**（一句话）：在表上按行过滤"谁能看到/改哪些行"，把授权粒度从对象级下沉到行级。

**已验证的事实（来源 §0.1 #7）**：
- 启用后，**所有**正常访问都必须被某条策略允许；**没有任何策略 = 默认拒绝**（"a default-deny policy is used, meaning that no rows are visible or can be modified"）。
- **多策略组合规则**：permissive 策略用 **`OR`** 组合（默认），restrictive 策略用 **`AND`** 组合。
- 策略表达式**先于**用户查询的条件求值；**唯一例外是 `leakproof` 函数**（优化器可以把它提前执行）。
- 策略表达式以**执行查询的用户**的权限运行（除非用 security definer 函数）。
- **⚠️ 绕过 RLS 的主体（本节最重要的纠正依据，逐字）**：
  > "**Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system** when accessing a table. **Table owners normally bypass row security as well**, though a table owner can choose to be subject to row security with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`."
- **⚠️ 引用完整性绕过 RLS（隐蔽信道，官方原文）**：
  > "Referential integrity checks, such as unique or primary key constraints and foreign key references, **always bypass row security** to ensure that data integrity is maintained. Care must be taken… to avoid '**covert channel**' leaks of information through such referential integrity checks."
- **⚠️ 策略里做子查询会有竞态（官方给了完整 PoC）**：策略中 `(SELECT group_id FROM users WHERE user_name = current_user)` 在 Read Committed 下**可能读到旧快照**，导致被降权用户仍看到新写入的敏感行。官方给的三种缓解：策略子查询改用 `SELECT ... FOR SHARE`（需额外 `UPDATE` 权限，有性能代价）；或在更新被引用表时取 `ACCESS EXCLUSIVE` 锁；或等并发事务结束再改安全态势。
- **⚠️ 不是万能的开关**：`TRUNCATE` 与 `REFERENCES` 这类**整表操作不受 RLS 约束**（原文："Operations that apply to the whole table, such as `TRUNCATE` and `REFERENCES`, are not subject to row security."）。
- 备份场景的护栏：把 `row_security` 配置设为 `off` 时，**若任何查询结果会被策略过滤则报错**（不是绕过，是报警）。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `rls_enabled_coverage` | `SELECT relname FROM pg_class WHERE relkind='r' AND relrowsecurity` 与"应将含个人信息的表清单"对比，覆盖率应 100% |
| `rls_policy_count` | `SELECT count(*) FROM pg_policies`；**`relrowsecurity=true` 但 `pg_policies` 无条目 = 该表默认全部拒绝**（可能是有意，也可能是事故） |
| `force_rls_gap` | `SELECT relname FROM pg_class WHERE relrowsecurity AND NOT relforcerowsecurity` —— **这些都是"表主仍可绕过"的表，若表主就是应用角色，则 RLS 形同虚设** |
| `bypassrls_roles` | 见 7.1 |
| `policy_subquery_present` | `SELECT * FROM pg_policies WHERE qual::text LIKE '%SELECT%'` → 检出需评估竞态的策略 |
| `rls_effective_assertion` | **必须有行为测试**：以低权角色 `SET ROLE` 后执行查询，断言返回行数与预期一致（文档给的 passwd 例子就是这种自测） |

### 7.3 SECURITY DEFINER 与 search_path 劫持

**它衡量的是什么**（一句话）：让函数以**属主**权限运行以实现受控提权；但若 `search_path` 可被低权用户影响，就会被"同名对象遮蔽"劫持。

**已验证的事实（来源 §0.1 #20、#8）**：
- `SECURITY DEFINER` 原文："`SECURITY DEFINER` specifies that the function is to be executed with the **privileges of the user that owns it**."（默认是 `SECURITY INVOKER`）
- **官方给出的安全写法要点（原文）**：
  - "`search_path` should be set to **exclude any schemas writable by untrusted users**"；
  - "**Particularly important in this regard is the temporary-table schema, which is searched first by default, and is normally writable by anyone.**"
  - 安全安排示例：`SET search_path = admin, pg_temp;` —— **把 `pg_temp` 放最后**。
  - 官方反例说明：没有 `SET` 子句（或只写 `admin`）时，函数可被"创建一个名为 `pwds` 的临时表"颠覆。
  - 若函数要创建角色且以非超级用户运行，还应把 **`createrole_self_grant`** 设为已知值。
  - **默认 `EXECUTE` 授给 PUBLIC**，所以"you must revoke the default `PUBLIC` privileges and then grant execute privilege selectively"，且应"create it and set the privileges **within a single transaction**"以免出现窗口期。
- **`search_path` 劫持的一般原理（来源 §0.1 #8，原文）**："adding a schema to `search_path` **effectively trusts all users having `CREATE` privilege on that schema**. When you run an ordinary query, a malicious user able to create objects in a schema of your search path **can take control and execute arbitrary SQL functions as though you executed them**."
- **三种 schema 使用模式的定性（官方原文）**：
  1. 每用户私有 schema（PG 15+ 默认支持）——安全模式；
  2. 从默认 search_path 移除 public——安全（除非把函数/扩展建在 public）；
  3. **保留默认 search_path 且授予 public 建对象权限——原文："this is never a secure pattern. It is acceptable only when the database has a single user or a few mutually-trusting users."**
  - ⚠️ 官方还指出：**"unless an untrusted user is the database owner or has been granted `ADMIN OPTION`… in which case no secure schema usage pattern exists."**

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `secdef_without_searchpath` | `SELECT p.proname, p.proconfig FROM pg_proc p WHERE p.prosecdef AND (p.proconfig IS NULL OR NOT EXISTS (SELECT 1 FROM unnest(p.proconfig) c WHERE c LIKE 'search\_path=%'))` —— **返回非空即缺陷** |
| `secdef_searchpath_unsafe` | 上面结果的 `proconfig` 中 `search_path` 不以 `pg_temp` 结尾，或包含可写 schema |
| `writable_schemas_on_path` | `SELECT nspname FROM pg_namespace WHERE has_schema_privilege('public', oid, 'CREATE')` 与当前 `search_path` 求交 |
| `public_schema_create_priv` | `has_schema_privilege('public','public','CREATE')` |
| `pg_temp_shadowing` | 检出 `pg_temp` 排在任何受信 schema 之前的会话/函数设置 |

### 7.4 审计（audit）

**已验证的事实与手段**：
- PostgreSQL 日志层面（来源 §0.1 #15）：
  - `log_statement`：`none`（默认）/ `ddl` / `mod` / `all`。**⚠️ 官方警告两点**：① "Statements that contain **simple syntax errors are not logged even by the `log_statement` = `all` setting**"，因为日志在基本解析之后才发出；② "Logged statements **might reveal sensitive data and even contain plaintext passwords**."
  - `log_min_duration_statement`：慢语句阈值（可含查询文本）。`log_min_duration_sample` + `log_statement_sample_rate` 用于高流量采样。
  - `log_connections` / `log_disconnections`（默认 off；**`log_connections` 不能与会话内改**，且注意 psql 可能连两次）。
  - `log_line_prefix` 可用转义：`%m`（毫秒时间戳）、`%u`（用户名）、`%d`（库名）、`%a`（应用名）、`%h`/`%r`（客户端）、`%p`（PID）、`%c`（会话 ID）、`%x`（事务 ID）、`%v`（虚拟事务 ID）、`%e`（SQLSTATE）、`%Q`（query id，需 `compute_query_id`）。
  - **结构化日志**：`log_destination` 可含 `csvlog` / `jsonlog`。**官方给出可直接建表的 CSV 列定义**（含 `session_id`、`session_line_num`、`transaction_id`、`sql_state_code`、`query`、`application_name`、`backend_type`、`query_id`），并**建议用 `PRIMARY KEY (session_id, session_line_num)` 防止重复导入**。JSON 日志字段表也已验证。
  - `log_temp_files`：临时文件大小日志（`-1` 默认关闭）。
  - `log_lock_waits`：见 §6.2。
- **本项目的关键判断：日志 ≠ 数据库认定的审计**。
  - 日志可被有文件系统权限的人修改/删除；`log_line_prefix` 里的 `usename` 是**客户端自报的应用名**与**数据库认证身份**的混合，`application_name` 完全由客户端设定（原文：`application_name` "is typically set by an application upon connection"）→ **`application_name` 不可作为审计证据**。
  - 数据库只对**认证身份**、**事务 ID**、**SQLSTATE**、**时间戳**负责。**业务语义（"谁改了哪条记录、改成了什么"）数据库不认定**，必须由应用层或触发器自己写审计表。

**审计日志该记什么（六要素）与实现方式**：

| 要素 | 数据来源 |
|---|---|
| **谁** | 数据库认证身份（`session_user` / `current_user`）；**不要**依赖 `application_name` |
| **何时** | 服务器时间戳（`clock_timestamp()`，事务内单调推进，不受 `now()` 事务快照影响） |
| **对什么** | 表名 + 主键值 |
| **做了什么** | 操作类型 + 旧值/新值 |
| **结果** | 成功 / 失败 + SQLSTATE |
| **多少行** | `GET DIAGNOSTICS row_count` 或触发器中的 `TG_OP` 计数 |

**append-only 的实现方式（按强度递增）**：
1. **权限层**：审计表只给 `INSERT`，**不给 `UPDATE`/`DELETE`**（`REVOKE UPDATE, DELETE ON audit_log FROM app_role`）。⚠️ 但**表主与超级用户仍可改**——所以要把表主设为与应用角色不同的角色。
2. **触发器层**：在审计表上加 `BEFORE UPDATE OR DELETE` 触发器 `RAISE EXCEPTION`，把"篡改"变成运行时错误。
3. **链式哈希**：每行存 `prev_hash` 与 `row_hash = H(prev_hash || 行内容)`，定期校验链完整性。**能检出篡改**（不能阻止）。这是"可信度边界"的正确表达：**数据库不能证明自己没被改，只能让改动可被检出。**
4. **导出**：定期把审计片段导出到数据库之外（本项目单机，导出到另一台机器/介质）。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `audit_enabled` | `SHOW log_statement`、`SHOW log_connections`、`SHOW log_destination`、`SELECT current_setting('log_min_duration_statement')` |
| `audit_table_append_only` | `has_table_privilege('app_role','audit_log','UPDATE')` 与 `...'DELETE'` 均应为 false |
| `audit_trigger_present` | `SELECT tgname FROM pg_trigger WHERE tgrelid='audit_log'::regclass AND tgtype & 16 > 0`（UPDATE 触发器）|
| `audit_chain_ok` | 重算 `row_hash` 链，比对；返回 break 位置 |
| `audit_coverage` | 敏感表清单 vs 有审计触发的表清单，覆盖率 |
| `log_line_prefix_sufficient` | `SHOW log_line_prefix` 是否含 `%m %u %d %c %x %e` 等要素 |

### 7.5 PIPL / GDPR 的工程要点

**⚠️ 再次声明：以下不是法律意见。**

| 主题 | 条文 | 关键原文（节录） |

| 敏感个人信息 | 第二十八条 | 定义与列举（生物识别、宗教信仰、特定身份、医疗健康、金融账户、行踪轨迹；**不满十四周岁未成年人的个人信息**）；"只有在具有特定的目的和充分的必要性，并采取严格保护措施的情形下"方可处理 |

| **跨境提供** | **第三十八条** | 四条件之一：①通过国家网信部门组织的**安全评估**；②经专业机构**个人信息保护认证**；③按标准合同与境外接收方订立合同；④其他 |
| 跨境告知同意 | 第三十九条 | 告知境外接收方信息并取得**单独同意** |
| 境内存储（CIIO/达量） | 第四十条 | 关键信息基础设施运营者与达量处理者应**境内存储**；确需出境须过安全评估 |
| **删除权 / 删除情形** | **第四十七条** | 应**主动删除**（个人也可请求删除）的五种情形：①处理目的已实现、无法实现或不再必要；②停止提供产品或服务，或**保存期限已届满**；③个人**撤回同意**；④违法违约处理；⑤其他。**且**："法律、行政法规规定的保存期限未届满，或者**删除个人信息从技术上难以实现的**，个人信息处理者应当**停止除存储和采取必要的安全保护措施之外的处理**。" |
| 更正补充权 | 第四十六条 | 发现不准确或不完整，有权请求更正、补充 |
| 安全措施 | 第五十一条 | 含"（二）对个人信息实行**分类管理**；（三）采取相应的**加密、去标识化**等安全技术措施；（四）**合理确定个人信息处理的操作权限**，并定期对从业人员进行安全教育和培训" |
| 合规审计 | 第五十四条 | "应当**定期**对其处理个人信息遵守法律、行政法规的情况进行**合规审计**" |
| 影响评估（PIA） | 第五十五条 / 第五十六条 | 四类情形**事前**做影响评估（含**敏感个人信息**、**自动化决策**、委托/提供/公开、**出境**）；评估报告与处理情况记录**至少保存三年** |

**关键的工程含义（由条文直接推出）**：
1. **第四条**明确定义个人信息"**不包括匿名化处理后的信息**"。→ **真正匿名化的数据不受 PIPL 约束**；而**去标识化（假名化）的数据仍然是个人信息**。本项目含"真实个人信息的合成档案"与"3 位真实公开人物"，**这两类都不是匿名数据**（前者含真实字段，后者是可识别的真实人）→ **按个人信息处理**。

## 8. 可演进的模式治理（追加式迁移 / expand-contract / 锁表）

### 8.1 不可变/追加式迁移（forward-only migration）

**它衡量的是什么**（一句话）：模式变更以**只增不改**的有序脚本序列表达，配一张台账记录"哪个脚本、何时、成功与否、校验和"，使任何机器都能从零重放出同一模式。

**为什么 forward-only 而不是"可回滚迁移"**：
- 数据迁移（DML）**在语义上常常不可回滚**（例：把 `full_name` 拆成 `first`/`last` 后，原拼接方式丢失）。声称"能回滚"往往只是"能重建表结构"，数据回不去。
- **可测量性**：forward-only 的验收只需要一条查询——"台账条目数 == 实际模式版本"，而双向迁移需要验证两套路径。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `migration_ledger_exists` | 存在台账表（如 `schema_migration`），且 `PRIMARY KEY (version)` |
| `migration_gap_count` | 台账版本序列中是否有缺号（序号连续性检查） |
| `migration_checksum_drift` | 台账记录的文件校验和 vs 磁盘上脚本的校验和；不一致 = 有人改过历史脚本（**禁止**） |
| `schema_drift` | 在干净实例重放全部迁移 → `pg_dump --schema-only` 与当前库的 dump 做差异比较；**差异数应为 0** |
| `unapplied_migration_count` | 磁盘上的脚本数 − 台账条目数 |
| `invalid_index_leftovers` | `SELECT indexrelid::regclass FROM pg_index WHERE NOT indisvalid` —— **`CREATE INDEX CONCURRENTLY` 失败会留下 INVALID 索引**（已验证，来源 §0.1 #17）|

### 8.2 expand-contract（先加后删）

**它衡量的是什么**（一句话）：把一次破坏性接口变更拆成 **expand（同时支持新旧）→ migrate（迁移使用者）→ contract（删掉旧的）** 三步，使每一步都能独立发布且安全。

**已验证的定义（来源 §0.1 #28，Martin Fowler bliki "Parallel Change"，作者 Danilo Sato，2014-05-13）**：
- 原文："**Parallel change**, also known as **expand and contract**, is a pattern to implement **backward-incompatible changes** to an interface in a safe manner, by breaking the change into **three distinct phases: expand, migrate, and contract**."
- expand 阶段："In the _expand_ phase you augment the interface to support **both the old and the new versions**… Existing clients will continue to consume the old version."
- migrate 阶段："During the _migrate_ phase you update all clients using the old version to the new version. This can be done incrementally and, in the case of external clients, this will be the **longest phase**."
- contract 阶段："Once all usages have been migrated to the new version, you perform the _contract_ phase to **remove the old version**."
- **与本项目的直接相关性（原文）**："_Database refactoring_: this is a key component to **evolutionary database design**. Most database refactorings follow the parallel change pattern, where the **migrate phase is the transition period between the original and the new schema**, until all database access code has been updated to work with the new schema."
- **原文里的风险提示（值得引用）**："The downside of using parallel change is that during the migrate phase the supplier has to support two different versions… **If the contract phase is not executed you might end up in a worse state than you started**, therefore you need discipline to finish the transition successfully."

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `pending_contract_count` | 维护"已 expand 未 contract"的清单（旧的列/表仍在但已无引用）；**每项有到期日** |
| `dual_write_consistency` | expand 期若双写：一条 SQL 比对新旧两处的值，`mismatch_count = 0` |
| `old_column_read_count` | 若无法从 PG 统计读取列级访问，则用视图/函数封装旧字段，统计其调用（本项目零 JS，可把访问收口到视图） |
| `contract_deadline_overdue` | 清单中 `deadline < now()` 的条目数 |

> **注意**：Martin Fowler 的原文**没有讨论 PostgreSQL 锁级别**。把 expand-contract 与"零停机 DDL"绑定时，锁的分析依据应来自 PostgreSQL 官方文档（见 §8.3），不要声称 Fowler 讲过锁。

### 8.3 零停机 DDL 与 PostgreSQL 的锁——关键纠正

**核对结果：`ALTER TABLE ADD COLUMN` 带常量默认值，在 PG 11+ 确实已不重写全表。**

**已验证的原文（来源 §0.1 #4，PostgreSQL 16 §5.6.1 的 Tip，逐字）**：
> "**From PostgreSQL 11, adding a column with a constant default value no longer means that each row of the table needs to be updated when the `ALTER TABLE` statement is executed.** Instead, the default value will be returned the next time the row is accessed, and applied when the table is rewritten, making the `ALTER TABLE` very fast even on large tables.
> However, **if the default value is volatile** (e.g., `clock_timestamp()`) **each row will need to be updated** with the value calculated at the time `ALTER TABLE` is executed."

**ALERT TABLE 的默认锁级别（已验证，来源 §0.1 #18，原文）**：
> "Note that the lock level required may differ for each subform. **An `ACCESS EXCLUSIVE` lock is acquired unless explicitly noted.** When multiple subcommands are given, the lock acquired will be the strictest one required by any subcommand."

**已验证的、锁级别较轻的例外（原文明确标注的）**：

| ALTER TABLE 子形式 | 锁级别 | 说明 |
|---|---|---|
| **默认（未特别注明者）** | **`ACCESS EXCLUSIVE`** | 阻塞一切，包括 `SELECT` |
| `ADD FOREIGN KEY` | **`SHARE ROW EXCLUSIVE`** | 且**同时在被引用表上也取 `SHARE ROW EXCLUSIVE`** |
| `VALIDATE CONSTRAINT` | **`SHARE UPDATE EXCLUSIVE`** | 因此可先用 `ADD ... NOT VALID`（跳过全表扫描，立即提交）再 `VALIDATE` |
| `SET STATISTICS` | `SHARE UPDATE EXCLUSIVE` | |
| 设置 per-attribute options | `SHARE UPDATE EXCLUSIVE` | |
| `DETACH PARTITION CONCURRENTLY` | 父表 `SHARE UPDATE EXCLUSIVE`（分区上 `ACCESS EXCLUSIVE`） | 两事务实现；**不能在事务块内运行**；有默认分区时不允许 |
| `ATTACH PARTITION` | 父表 `SHARE UPDATE EXCLUSIVE`；被附加表上 `ACCESS EXCLUSIVE` | 若被附加表有匹配的 `CHECK` 约束可**跳过校验扫描** |

**已验证的其他关键事实**：
- **`ACCESS EXCLUSIVE` 是唯一阻塞 `SELECT` 的锁**："Only an `ACCESS EXCLUSIVE` lock blocks a `SELECT` (without `FOR UPDATE/SHARE`) statement."
- **`CREATE INDEX`（非 CONCURRENTLY）取 `SHARE`**，只挡写不挡读（已验证，来源 §0.1 #10 与 #17）。
- **`CREATE INDEX CONCURRENTLY`**：更慢（两遍扫描），且必须等待可能修改/使用该索引的在途事务结束；**不能在事务块内运行**；失败会留 INVALID 索引。**分区表上的分区索引不支持 `CONCURRENTLY`**，官方给的做法是：先在父表 `CREATE INDEX ON ONLY`（invalid），在各分区 `CREATE INDEX CONCURRENTLY`，再 `ALTER INDEX ... ATTACH PARTITION`，全部 attach 后父索引自动变 valid。
- **加 `CHECK` / `NOT NULL` 约束需要扫描全表但不需要重写表**（已验证："Adding a `CHECK` or `NOT NULL` constraint requires scanning the table… but does not require a table rewrite."）
- **`SET NOT NULL` 可跳过扫描**：若已存在能证明无 NULL 的有效 `CHECK` 约束（且不在同命令中删除）。
- **`DROP COLUMN` 不回收空间**："The `DROP COLUMN` form does not physically remove the column… it will **not immediately reduce the on-disk size** of your table." 空间要等行被更新才逐步回收；要立刻回收必须做表重写。
- **表重写不是 MVCC-safe**（已验证，来源 §0.1 #21）："after the truncation or rewrite commits, the table will appear **empty** to concurrent transactions, if they are using a snapshot taken before the DDL command committed."
- **`VACUUM FULL` / `CLUSTER` / 表重写形式 `ALTER TABLE` 都取 `ACCESS EXCLUSIVE`**（已验证）。
- **改列类型的行为（已验证，来源 §0.1 #18）**：默认需要重写表与索引；但**例外**——当 `USING` 不改变内容且新旧类型 binary-coercible（或新类型是旧类型上的无约束 domain）时**不需重写**；且**索引必须重建**，除非系统能证明新索引逻辑等价（例：`text` ↔ `varchar` 无排序变化时可免重建，**有 collation 变更则必须重建**）。重写会临时占用约两倍磁盘空间。

**推荐的"零停机"DDL 配方（针对本项目 2~3 并发，实际影响小，但仍应按此写脚本以便复用）**：
1. 加列：加**常量**默认值 → 免重写（PG 11+）。**绝不用 volatile 默认值加列**。
2. 加约束：`ADD CONSTRAINT ... NOT VALID` → 提交 → `VALIDATE CONSTRAINT`（`SHARE UPDATE EXCLUSIVE`）。
3. 建索引：小表可直接建；大表用 `CREATE INDEX CONCURRENTLY`（注意不能在事务块内、失败留 INVALID）。
4. 改类型：先评估是否 binary-coercible；否则按 expand-contract 加新列 → 回填 → 切读 → 删旧列。
5. 删列：知道它**不回收空间**；若确需回收，安排一次维护窗口做重写（并意识到重写不是 MVCC-safe）。
6. **一次 `ALTER TABLE` 尽量合并多个子命令**（官方原文：合并可把"multiple table scans or rewrites"合为"a single pass over the table"），**但**注意合并后锁级别取**最严**的那一个。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `ddl_scripts_without_lock_annotation` | 静态审查：每个迁移脚本文件头是否标注了所需锁级别与预计时长 |
| `access_exclusive_risk_list` | 对所有迁移脚本，检出含 `ALTER TABLE ... ADD COLUMN ... DEFAULT <volatile>`、`ALTER COLUMN ... TYPE`、`SET NOT NULL`、`ADD CONSTRAINT`（无 NOT VALID）、`VACUUM FULL`、`CLUSTER`、非 CONCURRENTLY 的 `CREATE INDEX`（大表）的条目 |
| `lock_timeout_set` | 迁移脚本是否设置 `SET lock_timeout = '5s'`（防止 DDL 无限等待锁）与 `SET statement_timeout` |
| `rewrite_avoidance_ok` | 检查所有 `ADD COLUMN ... DEFAULT` 的默认值是否为常量（非 `now()`/`clock_timestamp()`/`random()` 等 volatile） |
| `contract_backlog` | 见 §8.2 |

## 9. 可观测性与可移植性（审计 / FAIR / codebook / crosswalk）

### 9.1 审计（与 §7.4 互补的"可观测性"视角）

本节不重复 §7.4 的内容，只补**可信度边界**这一条最重要的判断：

**审计日志的可信度分层**：

| 层次 | 证据强度 | 数据库能认定什么 |
|---|---|---|
| PostgreSQL 服务器日志（`log_statement` 等） | 中 | **认证身份、服务器时间戳、事务 ID、SQLSTATE、后端类型**由数据库认定；**SQL 文本与 `application_name` 由客户端提交**，可被客户端伪造 |
| 数据库内的审计表 | 中低 | 表内容由数据库保证 ACID；但**表主与超级用户可改**（`GRANT` 文档原文），因此 append-only 只能靠"不给 UPDATE/DELETE 权限 + 触发器 RAISE + 哈希链"来**检出** |
| 导出到库外的审计片段 | 高（相对） | 一旦离开该实例，篡改需要同时攻陷外部介质 |

**结论（应写进验收文件的表述）**：
> **数据库不能"证明"自己的审计未被篡改，只能让篡改"可被检出"。** 因此"审计可信"的正确验收指标不是"审计表存在"，而是"**篡改能被检出**"——即哈希链校验能定位断点、且 UPDATE/DELETE 权限确实被吊销。

（相关可测指标见 §7.4 的 `audit_table_append_only`、`audit_trigger_present`、`audit_chain_ok`。）

### 9.3 数据字典 / codebook 的发布

**它衡量的是什么**（一句话）：把"每个字段是什么、允许什么值、由谁负责"写成**可被程序读取、可随代码一起版本管理**的产物。

**为什么这在本项目必须做（可测性论证）**：
- 80+ 张表、最大 56 万行，**唯一能防止"字段语义漂移"的手段就是把定义外化**。
- 数据字典一旦是文件（而非某人的记忆），就能对它跑断言：**覆盖率、孤儿字段、未定义枚举值**——全是可测量的。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `dict_table_coverage` | 数据字典中的表数 / `pg_class` 中 `relkind='r'` 的用户表数 |
| `dict_column_coverage` | 数据字典中的列数 / `pg_attribute` 中 `attnum>0 AND NOT attisdropped` 的列数 |
| `dict_orphan_entries` | 字典里有、但库里已不存在的表/列（迁移后未同步） |
| `comment_coverage` | `SELECT count(*) FROM pg_description d JOIN pg_class c ON d.objoid=c.oid WHERE c.relkind='r'` —— PG 原生注释覆盖率（可作为字典的低配替代） |
| `enum_domain_documented` | 所有 `CHECK (col IN (...))` 或枚举类型是否在 codebook 中有对应取值表 |

**已验证的辅助手段**：PostgreSQL 原生支持 `COMMENT ON`（可挂在表、列、约束、函数上），且 `psql \d+` 会显示它们。→ **可以把"最低限度的数据字典"直接写进数据库**，代价极低，且随 dump 一起迁移。这是本项目最划算的一步。

### 9.4 标准词表与版本化 crosswalk

**它衡量的是什么**（一句话）：对外部职业/技能分类体系（ISCO / ESCO / O*NET 等）建立**版本化、可追溯的映射表**，使"同一个岗位"在不同版本与不同体系间可换算。

**核实状态（重要）**：
- **我未能打开 ISCO / ESCO / O*NET 的官方页面**（本轮未抓取），因此本文**不列这些词表的具体版本号、层级数或编码规则**。
- 本节只给**结构**与**可测量**，不给具体词表内容。

**crosswalk 表的最小可用结构（这是可测性的关键）**：

| 字段 | 作用 |
|---|---|
| `source_scheme`, `source_version`, `source_code` | 源体系与**版本**（版本必须显式，否则映射无法复现） |
| `target_scheme`, `target_version`, `target_code` | 目标体系与版本 |
| `mapping_type` | `exact` / `narrower` / `broader` / `related` / `no_match` |
| `confidence` | 人工或算法置信度 |
| `valid_from`, `valid_to` | **时间有效区间**（词表会改版，映射也会改版） |
| `provenance` | 谁在何时依据什么做的 |
| `superseded_by` | 若被新映射取代，指向新行（**不物理删除**） |

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `crosswalk_version_pinned` | 每条映射是否都带 `source_version` 与 `target_version`（NULL 数应为 0） |
| `crosswalk_orphan_source` | `source_code` 在源体系表中不存在（悬空映射） |
| `crosswalk_orphan_target` | 同上，目标侧 |
| `crosswalk_ambiguity` | 同一 `source_code` 映射到多个 `target_code` 且 `mapping_type='exact'` → 冲突 |
| `crosswalk_temporal_overlap` | 同一对 (source,target) 的有效区间重叠 → 同一时刻有两个答案 |
| `mapping_coverage` | 有映射的源码 / 全部源码 |
| `no_match_rate` | `mapping_type='no_match'` 占比（用于评估词表差距，不是缺陷） |

**已验证的同类做法**：PostgreSQL 的**扩展统计**用 `dependencies` 收集列间依赖系数，其**版本/时点语义**由 `ANALYZE` 决定；`pg_statistic_ext_data` 只有当前快照。**这说明"映射会随数据变化"需要外部台账来记录历史**，不能只靠库内表——本项目应把 crosswalk 的历史版本作为**追加式台账**（见 §8.1）。

## 10. 成本与资源（膨胀 / vacuum / 临时文件 / 连接）

> 本节全部依据已验证的 PostgreSQL 16 文档（来源 §0.1 #13、#14、#15、#16）。

### 10.1 表 / 索引膨胀（bloat）

**它衡量的是什么**（一句话）：MVCC 下 UPDATE/DELETE 留下的**死元组**在表和索引中占用的空间；它由 vacuum 回收，但回收速度可能跟不上产生速度。

**已验证的机制（原文要点）**：
- "In PostgreSQL, an `UPDATE` or `DELETE` of a row **does not immediately remove the old version** of the row."（这是 MVCC 的必然代价）
- **标准 `VACUUM` 不把空间还给操作系统**："it will **not return the space to the operating system**, except in the special case where one or more pages at the end of a table become entirely free and an exclusive table lock can be easily obtained."
- **`VACUUM FULL` 能缩表但取 `ACCESS EXCLUSIVE`**，且"can take a long time"、"requires extra disk space for the new copy"。
- 官方策略表述："The usual goal of routine vacuuming is to do standard `VACUUM`s **often enough to avoid needing `VACUUM FULL`**… the idea is not to keep tables at their minimum size, but to **maintain steady-state usage of disk space**."
- **autovacuum 永不发 `VACUUM FULL`**（原文："in fact will never issue `VACUUM FULL`"）。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `dead_tuple_ratio` | `SELECT n_dead_tup::numeric / NULLIF(n_live_tup + n_dead_tup, 0) FROM pg_stat_user_tables` |
| `table_bloat_bytes` | `pg_relation_size(relid)` vs `pg_stat_user_tables.n_dead_tup × 平均行宽`；或用 `pgstattuple` 扩展得到精确 dead space（**推荐，精确**） |
| `index_bloat_bytes` | `pgstattuple` 作用于索引（`pgstatindex`） |
| `last_autovacuum_age` | `now() - GREATEST(last_autovacuum, last_vacuum)`；对 `n_dead_tup` 大的表更关键 |
| `vacuum_needed_estimate` | 对照官方阈值公式：`dead tuples > autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × reltuples`（默认 50 + 0.2×reltuples）。**本项目表最大 56 万行 → 默认阈值约 11.2 万死元组**，对小表（几百行）阈值只有 50+，可能长期不触发 |
| `bloat_top10` | 上列按 `dead_tuple_ratio` 排序取前 10，作为维护清单 |

**关键判断（对本项目）**：56 万行、2~3 用户 → **默认 autovacuum 阈值（20%）在大表上意味着要积累 11 万死元组才触发**。若这张表是频繁更新的，膨胀可能明显。**必须按表设置更低的 `autovacuum_vacuum_scale_factor`**，并用上表指标验证。

### 10.2 autovacuum 健康

**已验证的 autovacuum 机制要点**：
- 由 **launcher + worker** 组成；launcher 每 `autovacuum_naptime` 秒尝试在每个库启动一个 worker；并发上限 `autovacuum_max_workers`；**worker 不计入 `max_connections`**。
- **触发阈值（已验证公式）**：
  - vacuum 阈值 `= autovacuum_vacuum_threshold + autovacuum_vacuum_scale_factor × reltuples`
  - insert 阈值 `= autovacuum_vacuum_insert_threshold + autovacuum_vacuum_insert_scale_factor × reltuples`（新增，用于"只插入不更新"的表也能被标记 all-visible 与冻结）
  - analyze 阈值 `= autovacuum_analyze_threshold + autovacuum_analyze_scale_factor × (insert+update+delete 总数)`
- **`relfrozenxid` 超过 `autovacuum_freeze_max_age` 的表总是被 vacuum（即使 autovacuum 名义关闭）**。
- **autovacuum 会被锁冲突打断**；但**反回卷 autovacuum 不会**。
- ⚠️ **已验证的严重反模式**："Regularly running commands that acquire locks conflicting with a `SHARE UPDATE EXCLUSIVE` lock (e.g., ANALYZE) can **effectively prevent autovacuums from ever completing**." → **不要定期跑会与 `SHARE UPDATE EXCLUSIVE` 冲突的命令**（`ANALYZE`、`VACUUM`、`CREATE INDEX CONCURRENTLY`、`REINDEX CONCURRENTLY`、部分 `ALTER TABLE` 都取这个锁）。
- ⚠️ **分区表不直接被 autovacuum 处理**；**继承父表不因子表变更而被 autoanalyze** → 需手工 `ANALYZE`。
- `log_autovacuum_min_duration` 默认 **10min**，设 0 可记录全部动作。**本项目应设小值（如 250ms）以便观察**。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `autovacuum_enabled` | `SHOW autovacuum`（必须为 on） |
| `autovacuum_starvation` | 存在 `n_dead_tup > 阈值` 但 `last_autovacuum` 很久以前的表 |
| `autovacuum_interrupted_logs` | 设 `log_autovacuum_min_duration != -1` 后，日志中出现"skipped due to conflicting lock"的次数（**官方：该参数非 -1 时会记录因冲突锁或并发 drop 而跳过的动作**） |
| `freeze_age_headroom` | `max(age(relfrozenxid))` 与 `autovacuum_freeze_max_age`（默认 2 亿）之比；**>0.5 就该介入** |
| `mxid_age_headroom` | `SELECT max(mxid_age(relminmxid)) FROM pg_class`；与 `autovacuum_multixact_freeze_max_age` 比 |
| `tables_never_autovacuumed` | `last_autovacuum IS NULL AND n_dead_tup > 0` |
| `vacuum_cost_delay_walltime` | `VACUUM VERBOSE` 或日志中单次 vacuum 的持续时间（确认 cost-based delay 没有让它跑不完） |

### 10.3 临时文件用量

**它衡量的是什么**（一句话）：查询计划中的**排序/哈希/物化**在 `work_mem` 不够时溢写到磁盘的字节数——这是"内存参数不足"或"计划选择了大排序/大哈希"的直接证据。

**已验证的事实**：
- **`pg_stat_database.temp_bytes`** 是每库临时文件字节数（来源 §0.1 #14 的 `pg_stat_database` 视图）。
- **`log_temp_files`**（默认 `-1` 关闭）：设 0 记录所有临时文件，设正值只记录 ≥ 该大小的文件；**日志条目含文件名与字节数，在文件被删除时发出**（来源 §0.1 #15）。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `temp_bytes_total` | `SELECT datname, temp_bytes, temp_files FROM pg_stat_database` |
| `temp_files_per_xact` | `temp_files / (xact_commit + xact_rollback)` |
| `large_temp_file_events` | 设 `log_temp_files = 1MB`，统计日志条目数与最大字节 |
| `work_mem_pressure` | 把 `large_temp_file_events` 与 `SHOW work_mem` 关联：出现大临时文件即说明该查询需要提高 `work_mem` 或改写 |
| `sort_spill_events` | `EXPLAIN (ANALYZE)` 输出中 `Sort Method: external merge  Disk: NkB` 的出现次数（**内存排序会显示 `quicksort Memory:`**，这是已验证的输出差异，来源 §0.1 #11）|

### 10.4 连接数上限与连接池

**已验证的事实**：
- `max_connections`、`superuser_reserved_connections` 存在；**autovacuum worker 不占这两者**（来源 §0.1 #13）。
- 连接过多报 `SQLSTATE 53300 too_many_connections`（来源 §0.1 #16）。
- **官方在 Serializable 章节列出的优化建议包含**："**Control the number of active connections, using a connection pool if needed.** This is always an important performance consideration…"（来源 §0.1 #5）
- **官方还建议**：`idle_in_transaction_session_timeout` 可用于自动断开滞留会话。
- 进程模型代价（对本项目很重要）：PostgreSQL 是**每连接一进程**。在 **Windows 无管理员权限**下，进程创建与共享内存的开销比 Linux 更明显。

**可转 SQL 的指标**：

| 指标名 | 测法 |
|---|---|
| `connection_utilization` | `SELECT count(*) FROM pg_stat_activity` / `current_setting('max_connections')::int` |
| `connection_reserved_headroom` | 同上，与 `superuser_reserved_connections` 之和对比 |
| `idle_in_transaction_count` | `SELECT count(*) FROM pg_stat_activity WHERE state = 'idle in transaction'`（**本项目最该盯的一条**） |
| `longest_idle_in_transaction` | `now() - state_change` 的最大值，其中 `state='idle in transaction'` |
| `idle_in_transaction_timeout_set` | `SHOW idle_in_transaction_session_timeout`（应为非 0） |
| `too_many_connections_events` | 日志中 `53300` 计数 |

**本项目适用性判断**：
- **2~3 个并发用户下，连接池基本不需要**。引入 PgBouncer 之类的中间件会：增加一个要维护的进程、引入 `SET`/prepared statement/`search_path` 的兼容问题，**收益远低于成本**。
- **真正该做的是**：设 `idle_in_transaction_session_timeout`（把"忘记提交"从"钉住 vacuum"降级为"连接被断开"）+ 监控 `idle_in_transaction_count`。**这两条覆盖了本项目 90% 的连接相关风险。**

## 12. 常见误解纠正清单

> 每条给出：**误解 → 事实 → 依据**。依据一律指 §0.1 中已验证的来源；凡依据未核实者，本文明确标注。

### 12.1 「CAP 就是三选二」 ❌

- **事实**：P（分区容忍）不是一个可选的设计特性，而是**网络的故障现象**。CAP 说的是：**分区发生（不可避免）时，只能在 C 与 A 之间取舍**；没有分区时，C 与 A 可以同时得到。"CA 系统"只在"网络永不分区"的假设下成立。
- **依据**：⚠️ Brewer 的 PODC keynote 与 IEEE Computer 2012 文章**在本环境均不可达，我未能打开**。因此此处**不引用原文**。该纠正的正确做法是：**在验收文件中不讨论 CAP**（本项目是单机单实例，CAP 无测量对象），从而绕开未核实的引用。

### 12.2 「PostgreSQL 加列一定会重写全表」 ❌

- **事实**：**PG 11 起，加列且默认值是常量时不再重写全表**，默认值在下次访问该行时返回。**但**：默认值是 **volatile**（如 `clock_timestamp()`）时必须逐行更新；**改列类型**（除 binary-coercible 等例外）仍要重写表与索引。
- **依据**（逐字）："From PostgreSQL 11, adding a column with a constant default value **no longer means that each row of the table needs to be updated**… However, **if the default value is volatile** (e.g., `clock_timestamp()`) each row will need to be updated…"
  https://www.postgresql.org/docs/16/ddl-alter.html
- **推论（必须一起记）**：加列虽快，**但 `ALTER TABLE` 默认取 `ACCESS EXCLUSIVE`**（原文："An `ACCESS EXCLUSIVE` lock is acquired unless explicitly noted."）——所以"不重写"**不等于"不锁表"**。
  https://www.postgresql.org/docs/16/sql-altertable.html

### 12.3 「有索引就一定快」 ❌

- **事实**：① 官方明说"**inappropriate use can result in slower performance**"；② 规划器可能**根本不用**索引（低选择性、小表）；③ 官方指出**单页表几乎总是走 Seq Scan，无论有没有索引**；④ 索引本身要维护写放大，且宽 `INCLUDE` 列会膨胀索引并**禁用 B-tree 去重**。
- **依据**：https://www.postgresql.org/docs/16/sql-createindex.html （"inappropriate use…"、"B-tree deduplication is never used with indexes that have a non-key column"）；https://www.postgresql.org/docs/16/using-explain.html （"on a table that only occupies one disk page, you'll nearly always get a sequential scan plan whether indexes are available or not"）

### 12.4 「RLS 能防住超级用户（也防住表主）」 ❌

- **事实**：**超级用户与带 `BYPASSRLS` 的角色总是绕过 RLS**；**表主默认也绕过 RLS**（除非显式 `FORCE ROW LEVEL SECURITY`）。另外，**引用完整性检查（唯一约束、外键）总是绕过 RLS**，官方明确警告这会形成"**covert channel**"信息泄露；`TRUNCATE` 与 `REFERENCES` 这类整表操作也不受 RLS 约束。
- **依据**（逐字）："**Superusers and roles with the `BYPASSRLS` attribute always bypass the row security system**… **Table owners normally bypass row security as well**, though a table owner can choose to be subject to row security with `ALTER TABLE ... FORCE ROW LEVEL SECURITY`." / "Referential integrity checks… **always bypass row security**… to avoid 'covert channel' leaks…" / "Operations that apply to the whole table, such as `TRUNCATE` and `REFERENCES`, are not subject to row security."
  https://www.postgresql.org/docs/16/ddl-rowsecurity.html
- **配套依据**："**database superusers can access all objects regardless of object privilege settings**."
  https://www.postgresql.org/docs/16/sql-grant.html

### 12.5 「NULL 等于 0（或空字符串）」 ❌

- **事实**：三者语义完全不同。在 SQL 三值逻辑里，`NULL = 0` 的结果是 `NULL`（未知），**不是 true**，因此 `WHERE col = 0` **匹配不到 NULL 行**；`col <> 0` 也匹配不到。这直接影响完整性指标的正确性：`null_frac` 与"值为 0 的比例"是两个独立量。
- **依据**（PostgreSQL 关于统计的字段定义）：`pg_stats.null_frac` 定义为"**Fraction of column entries that are null**"，是**独立于** `most_common_vals`/`most_common_freqs` 的一个列——即数据库自己就把 NULL 与普通值分开统计。
  https://www.postgresql.org/docs/16/view-pg-stats.html
- **推论（工程上必须注意）**：计算"完整率"时必须用 `IS NULL` / `IS NOT NULL` 或 `count(*) FILTER (WHERE c IS NOT NULL)`，**不能用 `c = 0` 或 `c <> ''` 代替**。

### 12.6 「范式越高越好」 ❌

- **事实**：规范化是**消除更新异常**的手段，不是目标本身。PostgreSQL 官方在讲扩展统计时明确承认反范式的合法性："in practice many data sets are **not fully normalized** for various reasons; **intentional denormalization for performance reasons is a common example**." 另外，**BCNF 分解不一定保持函数依赖**（这正是 3NF 存在的理由）——盲目追求 BCNF 可能把一个可局部校验的约束变成跨表约束。
- **依据**：https://www.postgresql.org/docs/16/planner-stats.html
- **正确的判据**：不是"达到第几范式"，而是"**每处冗余是否被一条校验 SQL 守住**"（见 §3.2 的 `denormalization_ledger`）。

### 12.7 补充：「审计表存在就等于审计可信」 ❌

- **事实**：数据库**不能证明自己未被篡改，只能让篡改可被检出**。append-only 需要三层：吊销 `UPDATE`/`DELETE` 权限、加 `BEFORE UPDATE OR DELETE` 触发器 `RAISE EXCEPTION`、以及哈希链。此外 **`log_statement = all` 也不记录简单语法错误的语句**，且官方警告**日志可能包含敏感数据甚至明文密码**。
- **依据**："Statements that contain **simple syntax errors are not logged even by the `log_statement` = `all` setting**"；"Logged statements **might reveal sensitive data and even contain plaintext passwords**."
  https://www.postgresql.org/docs/16/runtime-config-logging.html
  权限侧依据：https://www.postgresql.org/docs/16/ddl-priv.html

### 12.8 补充：「`VACUUM` 不锁表」 ⚠️（不准确）

- **事实**：**标准 `VACUUM` 取 `SHARE UPDATE EXCLUSIVE` 锁**（不是无锁）。它不与 `SELECT`/`INSERT`/`UPDATE`/`DELETE` 冲突，但**与另一个 `VACUUM`、`ANALYZE`、`CREATE INDEX CONCURRENTLY` 等冲突**。官方还给出严重反模式：**定期跑与 `SHARE UPDATE EXCLUSIVE` 冲突的命令（如 `ANALYZE`）会"effectively prevent autovacuums from ever completing"**。
- **依据**：https://www.postgresql.org/docs/16/explicit-locking.html （SHARE UPDATE EXCLUSIVE 的获取者清单）https://www.postgresql.org/docs/16/routine-vacuuming.html （prevent autovacuum completing 的警告）

### 12.9 补充：「2~3 个用户不需要关心并发/隔离级别」 ⚠️（半对）

- **事实**：**用户数少不等于没有并发异常**。PostgreSQL 官方文档给出的**写偏斜类**例子（两个事务各自 `SUM` 后 `INSERT`）在 **Repeatable Read 下两者都能提交**并产生不一致结果；官方还给出 **RLS 策略子查询的竞态 PoC**（在 Read Committed 下被降权用户仍能看到新写入的敏感行）。
- **依据**：https://www.postgresql.org/docs/16/transaction-iso.html （"If either transaction were running at the Repeatable Read isolation level, **both would be allowed to commit**"）https://www.postgresql.org/docs/16/ddl-rowsecurity.html （race condition 段落）
- **正确做法**：并发用户少 → **默认 Read Committed 够用**；但**不能因此假设"并发问题不存在"**。凡涉及"先读后写判业务规则"的逻辑，要么用 Serializable + 重试，要么在 RLS 策略里避免子查询（或按官方给的三种缓解方式处理）。

### 12.10 补充：「序列空洞 = 事务原子性被破坏」

- **事实**：**PostgreSQL 的序列变更立即对其他事务可见，且事务回滚不会撤销它**。因此主键出现空洞是**正常现象**，不是 ACID 的 A 被破坏。
- **依据**（逐字）："changes made to a sequence (and therefore the counter of a column declared using `serial`) are **immediately visible to all other transactions and are not rolled back** if the transaction that made the changes aborts."
  https://www.postgresql.org/docs/16/transaction-iso.html
