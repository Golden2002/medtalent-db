# 00 · 医学生人才信息库 · 实施方案总纲

> **一句话定位**：把"医学生能做什么"从口耳相传的模糊经验，变成**结构化、可查询、可解释、可扩展**的数据资产。
> **客户**：每一位医学硕博。**第一价值不是"帮你找工作"，而是"让你看见原本看不见的选择"。**

- 版本：v1.0 ｜ 编制日期：2026-09-27 ｜ 状态：**待评审**
- 配套文档：`01-数据模型设计` `02-对标借鉴清单` `03-岗位图谱构建方案` `04-人才档案与证据模型` `05-匹配与分析引擎方案` `06-合规与数据治理` `07-数据字典与扩展机制` `08-实施计划与任务分解`
- 调研原始产出：`research/00`～`research/04`

## 1. 需求解析：六条要求 → 六个设计承诺

| 用户要求 | 设计承诺（可验收） |
|---|---|
| ① 建医学生人才信息库 | 覆盖"人才侧 × 岗位侧 × 语义层 × 治理面"四域，`schema/sql/001`+`002` 已定义 40 张代码表、88 个登记字段 |
| ② 结构化存储，利于高扩展性分析 | 长表 + 星型 marts + 派生层可重算；**新增一个分析维度不改表结构** |
| ③ 数据库本身高扩展，遇真实需求可加条目 | **三条受控扩展机制**（加词表 / 加属性 / 加断言），加字段 ≤30 分钟、加实体 ≤1 天，且不破坏既有数据 |
| ④ 参考 UK Biobank 等成熟库的组织与下载方式 | 已提取 12 条模式并**已落入 schema**（字段级访问策略、观测期、分类树、统一值表、字典即代码…），见 `docs/02` |
| ⑤ **首先检索岗位与岗位描述**，覆盖全社会 | 岗位侧为一期工程；17 岗位族 + 3,000 条结构化 JD + 能力权重矩阵；证据分级 A/B/C/D |
| ⑥ 成熟商业项目、行业前沿、可靠结果 | 新建独立项目目录；方案可评审、任务可执行、验收可量化、数据可溯源 |

## 2. 为什么"岗位优先"

用户的要求顺序是对的，而且有硬理由：

1. **没有岗位侧，人才档案无法被解读**。一份写着"能独立完成 200 例阑尾切除术"的档案，如果没有岗位侧说出"哪些岗位需要这个、值多少分、还能迁移到哪"，它就只是一份电子简历。
2. **岗位侧是需求端，决定了整个数据库的字段设计**。先知道 JD 里有什么（薪资周期、证照要求、替代路径、职责条目），才知道人才侧要收什么字段。反过来做，一定返工。
3. **岗位侧是获客资产**。岗位地图本身就能免费开放（T0 公开层），是"打开眼界"最直接的钩子，也是竞品最难快速复制的资产。
4. **岗位侧数据可公开采集**，而人才侧数据必须依赖用户授权。先做能做的，能更快跑通闭环。

**因此一期工程 = 岗位图谱**（`docs/03`）。

## 3. 数据资产蓝图（要建什么）

```
                   ┌──────────────── 语义层（L2）────────────────┐
                   │ 概念本体 concept（技能/知识/能力/任务/技术…） │
                   │ 代码表 40 张 · 字段目录 88 项 · 分类树        │
                   │ 映射血缘 concept_mapping · 层级闭包 ancestor  │
                   └──────────────┬────────────────┬─────────────┘
                                  │                │
        ┌─────────────────────────▼──┐        ┌────▼──────────────────────┐
        │  人才侧（供给）L1           │        │  岗位侧（需求）L1          │
        │  person 假名主体            │        │  occupation 职业树         │
        │  education/training/clinical│        │  job_posting 结构化 JD     │
        │  credential/employment      │        │  job_task / job_requirement│
        │  research/project/award     │        │  employer / salary_benchmark│
        │  ★ skill_assertion 能力主张 │        │  ★ job_competency_weight   │
        │  evidence / assessment      │        │  transition_case 转行案例  │
        │  preference / person_constr    │        │  job_channel               │
        └─────────────┬───────────────┘        └────────────┬──────────────┘
                      └──────────────┬──────────────────────┘
                                     ▼
                    连接层：match_run / match_result / gap_analysis
                    治理面：source_registry · provenance · consent_record
                            access_policy · observation_window · access_log · change_log
                    分析层：dim_* / fact_* 星型模型 + metric_definition
```

**四张"价值最高"的表**（决定项目成败）：
1. `skill_assertion` —— 能力 = 等级 × 依据 × 证据 × 置信度 × **可迁移性**
2. `job_requirement` —— 岗位需要什么，硬性/软性/加分，含**可替代路径**
3. `job_competency_weight` —— 岗位族 × 能力 → 重要性/要求等级（对标 O*NET）
4. `match_result` —— 分数 + 分解 + **可解释理由 + 缺口**

## 4. 三条扩展机制（要求③的全部答案）

真实需求只可能落在三种情况，**不允许第四种**（临时 ALTER TABLE）：

| 机制 | 适用 | 做法 | 代价 |
|---|---|---|---|
| **A 代码表驱动** | 多了一个枚举值（新岗位族/技能/证书/城市） | `code_value` 插一行 | 近零 |
| **B 属性登记驱动** | 多了一个普通字段 | `attribute_definition` 登记 + 写 `field_value`（UK Biobank 式 `field × instance × array` 统一值表） | 低，**零 DDL** |
| **C 断言驱动** | 多了一个全新维度，尚在探索 | `assertion` 通用三元组，稳定后**固化**为正式实体 | 中，**必须定期固化，否则腐烂成垃圾桶** |

升级路径写死：`attribute_definition.status = proposed → active → promoted`，promote 时提升为正式列并记录 `change_log`。

## 5. 对标借鉴：12 条已落地的模式（要求④）

来源：`research/01-对标-生物样本库与成熟数据基础设施.md`（UK Biobank Showcase、OMOP CDM、Croissant、CHARLS、NHANES、All of Us、dbGaP/EGA）。

| 借鉴点 | 原始做法 | 本项目落位 |
|---|---|---|
| **字段元数据即产物** | UKB Schema 1 把 27 个字段属性做成可 `wget` 的 `scdown.cgi?fmt=txt\|xml`（[来源](https://biobank.ndph.ox.ac.uk/showcase/schema.cgi?id=1)） | `field_catalog` 表 + `make catalog` 导出 CSV/JSON-LD，可进 git、可 diff |
| **值为 `field × instance × array`** | UKB 的字段是语义锚点，值为其笛卡尔展开 | `field_value` 统一值表 → 加字段零 DDL |
| **字段级 × 访问方式级 的访问策略** | UKB Cost Tier `dNoNsN`，例 `d3 o2 s3`（Tier2 能看、Tier3 才能下） | `access_policy(object, action, min_tier)`，`access_tier` 降为默认值 |
| **分类树是独立实体** | UKB Category 有 id/父子/双向计数，5–6 级 | `category_node` + `refresh_category_counts()` |
| **派生层显式分层** | UKB `strata=derived`、First occurrences | `field_catalog.strata` + `first_occurrence` 表 |
| **原文与标准码并存** | OMOP `source_value`（逐字）+ `concept_id`（标准） | 所有业务表保留 `*_raw` 与归一列，禁止只存归一结果 |
| **来源是有词表的概念** | OMOP `*_type_concept_id` | `CT_PROVENANCE_METHOD` 正式码，而非布尔 flag |
| **映射血缘 + 层级闭包** | OMOP `SOURCE_TO_CONCEPT_MAP` / `CONCEPT_ANCESTOR` | `concept_mapping` / `concept_ancestor` |
| **观测期纪律** | OMOP：只在观测期内"无记录"才等于"未发生" | `observation_window` + 匹配前置校验 |
| **字典/数据集描述标准** | Croissant 1.0（JSON-LD + SemVer + sha256） | `dataset_release.record_set_jsonld`，MINOR=只加字段 |
| **轻量申请 + 明确 SLA + 文档三件套** | CHARLS：注册→按数据集申请→**3 工作日**审批，配「指南+问卷+codebook」 | T1 申请流程；**没有 codebook 不允许发布**（DDL 已用 CHECK 强制） |
| **数据不落地分析** | UKB RAP / All of Us Workbench | T2 数据仅返回汇总，个体级不外发 |

**未证实项已单独标注**（`research/01` §5，如 UKB Table Exporter 细节、字段级 QC flag 枚举），**不得写入 schema 注释当作事实**。

## 6. 技术选型（单机可跑，零云依赖）

| 层 | 选型 | 理由 |
|---|---|---|
| 事务库 | **PostgreSQL 16** + `pgvector` | JSONB、数组、递归 CTE、行级安全（RLS）、向量检索一体 |
| 分析 | **DuckDB + Parquet**，dbt-core 双 target | 单机列式分析，直接读 Parquet，无需数据仓库 |
| 采集/解析 | Python 3.12 + httpx + Playwright（合规渠道）+ LLM 抽取 | 复用既有项目代码（见下） |
| 字典与发布 | CSV/JSON Schema/JSON-LD（Croissant 风格）+ sha256 | 可进 git、可 diff、可对客户交付 |
| 调度 | Windows 任务计划 / 轻量 cron | 一期无需 Airflow |

## 7. 既有资产复用（不做重复建设）

盘点结论见 `research/00-既有资产盘点与复用判断.md`。要点：

**直接复用**
- `medical-resume-agent/schemas/canonical-experience-v2.schema.json`：原子活动 + 责任等级 + `scope.coverage` + 证据强制 → 并入 `employment_record` / `project_record` 的能力证据链
- `bullet-claim-v2.schema.json`：表述 ↔ 证据分离 → 并入 `skill_assertion` + `evidence`
- `career.schema.json` 的 `sourcedClaim` + `source` → 岗位主数据模板
- `medical-resume-agent` 四道门禁（experience_draft / confirmation_gate / claim_gate / claim_ledger）→ 人才档案入库门禁
- `ai-job-search-derived-agent/product/data/role_packs/*.json` 与 `capability_tags/general_v1.json` → 岗位族画像与能力标签种子
- `job_portal.py`（Posting 契约 + 适配器注册）、`job_evaluation.py`（五维 + 硬门 + jieba）、`salary_benchmark.py`、`robots_check.py`

**必须警惕的既有坑**（已在调研中确认）
- 旧项目 `schema_version` 是硬编码常量，**同一时刻只能存在一个版本** → 本库必须记录在行上
- `capability_tags` 结构与 `capability_taxonomy.tag_experience()` 契约不匹配，**标签功能实际失效** → 改造前不得依赖
- 6 个抓取门户**全是北欧/国际渠道，无中国渠道**，且 `job_scraper/` 为空 → 中国岗位采集**从零建**
- 旧库大量 C 级线索数据未入生产；本库用 `evidence_grade` + `verify_status` 强制区分

**必须完全新建**：字段级数据字典、代码表与受控词表、schema 版本化与迁移、实体关系与去重键（DOI / 统一社会信用代码 / 岗位规范化链接）、结构化存储与检索层（既有项目**没有任何数据库**）。

## 8. 路线图（要求⑤⑥：先岗位，再人才，最后匹配）

| 阶段 | 周期 | 目标 | 交付物 | 验收门 |
|---|---|---|---|---|
| **P0 地基** | 1 周 | 结构可执行 | 建库脚本、导入器、字典质检门、目录规范 | `validate_catalog.py` 0 错；DDL 可在 PG16 一次跑通 |

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **抓取合规** | 法律与商誉风险 | 三层来源架构；BOSS/智联/51job/LinkedIn **禁止自动化**；`source_registry.license_note` 强制登记；可按来源一键下架 |
| **样本偏差** | 结论外推失真 | 招聘平台样本偏向"在招且愿公开薪资"；显式记录"抓不到什么"；多源交叉；A 级官方数据校准 |
| **LLM 抽取幻觉** | 污染整库 | 一律 `verify_status=V1` + `confidence ≤0.8` + 5% 人工抽检 + 保留原文可全量重跑 |
| **"没记录"被当"不具备"** | 匹配结论错误 | `observation_window` 强制前置校验（P0 已落地为视图 `v_gap_candidates`） |
| **PII 泄露** | 致命 | PII 独立加密表 + `access_policy` 字段级控制 + T2 数据不落地 + 访问审计 |
| **词表失控** | 无法聚合 | 代码表版本化、废弃不删除、外部标准映射 |
| **扩展机制腐烂** | 库变成垃圾场 | 机制 C 设定期"固化/清理"节拍，`assertion.status` 必须收敛 |
| **商业不确定性** | 投入浪费 | 一期只做能公开采集的岗位侧，先验证获客；人才侧随用户增长 |
