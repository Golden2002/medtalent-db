# 09 · 动态建模与前端表单方案（行/列动态增删）

> 本文回答三个问题，并附实测证据：
> ① 真实使用中冒出一个新的用户画像维度 A，能不能方便地加进去？——**能，且不需要改表结构**
> ② 能不能根据用户输入动态创建实例（记录）？——**能**
> ③ 每个字段预设 n 个选项让用户选、选完入库——**能，选项本身就是数据库里的数据**
>
> 实现：`schema/sql/008_dynamic_model.sql`；验证：`ops/tests/dynamic_model_test.py`、`ops/tests/form_server_test.py`。

---

## 1. 一句话结论

**在这个库里，"列"和"行"都不是结构，而是数据。**

- 加一个画像维度 = 往 `field_catalog` 写一行 + （可选）往 `code_value` 写 n 行；
- 加一条记录 = 往类型化表写一行，或往 `field_value` 写若干行；
- 两者都**不执行任何 DDL**，因此不需要停机、不需要迁移脚本、不需要发版。

实测（`ops/tests/dynamic_model_test.py`，28 项断言全通过）：

| 指标 | 结果 |
|---|---|
| 新增一个带 4 个选项的维度耗时 | **12.8 – 15.6 ms** |
| 动态创建 20 条档案耗时 | **62.6 – 73.6 ms**（3.13 – 3.68 ms/行） |
| 基础表数量变化 | **59 → 59（未变）** |
| `person` 表列数变化 | **16 → 16（未变）** |
| 已登记字段数变化 | 112 → 117（+5） |
| **本次操作的 DDL 次数** | **0** |

## 2. 能力一：列（维度）的动态增删

### 2.1 怎么加

```sql
-- 一次调用搞定：登记字段 + 建词表 + 写入 n 个选项
SELECT mt.add_dimension(
    p_entity   => 'person',
    p_field_id => 'F_PROFILE_A',
    p_title    => '基层服务意愿',
    p_options  => '[{"code":"A1","label":"非常愿意"},
                    {"code":"A2","label":"愿意"},
                    {"code":"A3","label":"犹豫"},
                    {"code":"A4","label":"不愿意"}]'::jsonb,
    p_required => true,
    p_section  => '就业偏好');
```

它做的事（全部是 DML）：
1. 在 `code_table` 建 `CT_F_PROFILE_A`；
2. 在 `code_value` 写入 4 个选项；
3. 在 `field_catalog` 登记字段（含类型、是否多选、是否必填、分组、访问层级）；
4. 往 `change_log` 记一条审计流水。

**没有 `ALTER TABLE`。** `person` 表结构从头到尾没动。

### 2.2 三种数据类型都能加

| 需求 | 调用方式 | 存储位置 |
|---|---|---|
| 单选维度（n 个选项） | `p_options => '[...]'::jsonb` | `field_value.value_code` |
| 多选维度 | 再加 `p_multi => true` | `field_value.value_codes`（数组） |
| 数值 / 文本 / 日期 | `p_data_type => 'number' / 'text' / 'date'` | `value_num` / `value_text` / `value_date` |

一个字段同时支持"值 + 第几次采集（instance）+ 同次内第几个（array）"，
所以"第 1 段工作经历"和"第 2 段工作经历"共用同一个字段定义（对标 UK Biobank）。

### 2.3 怎么删

**软删除，数据一条不丢**：

```sql
SELECT mt.deprecate_dimension('F_PROFILE_A', '字段设计不合理，改用新维度');
```

- `field_catalog.status` 变 `deprecated`，词表同步废弃；
- 已有的值**全部保留**（实测：废弃后 20 条值仍在）；
- 该维度**自动从表单 schema 中消失**，前端不再渲染它；
- `change_log` 记录废弃原因与时间。

> 为什么不物理删除：数据字典里的一个维度可能被历史报告、派生指标、外部导出引用。
> 物理删除会让"上个月的报告怎么算出来的"变成悬案。废弃 + 保留 = 可回溯。

## 3. 能力二：实例（行）的动态创建

```sql
SELECT mt.create_instance(
    p_entity  => 'person',
    p_id      => 'per_2026_000123',
    p_payload => '{"person_id":"per_2026_000123",
                   "subject_code":"MT-2026-000123",
                   "F_PROFILE_A":"A2"}'::jsonb);
```

`create_instance` 会**逐键分流**：

| 键的类型 | 去向 |
|---|---|
| 是目标表的列 | 进类型化表（只插入显式给出的列，未给出的列走默认值） |
| 是已登记的扩展字段 | 进 `field_value` |
| 是已登记的 `attribute_definition` | 进该行的 `attrs` |
| **都没登记** | **直接报错**，提示先调用 `add_dimension` |

最后一条是关键：**它允许你随时加字段，但不允许你偷偷加字段。**

### 3.1 纯值实体：连表都不用建

```sql
SELECT mt.register_entity('profile_survey', 'talent', 'EK2');   -- EK2 = 纯值实体
SELECT mt.add_dimension('profile_survey', 'F_SURVEY_Q1', '每周可投入学习时长',
                        '[{"code":"Q1","label":"<5小时"},...]'::jsonb);
SELECT mt.create_instance('profile_survey', 'per_001', '{"F_SURVEY_Q1":"Q2"}'::jsonb);
```

`entity_catalog.table_name` 为 NULL，全部数据存在 `field_value`。
实测确认库里**没有** `profile_survey` 这张表，但数据照常写入、照常查询。

> 这就是 UK Biobank 的思路：一切都是 field × instance × array。
> 只有当一个实体需要强约束、外键或高并发查询时，才把它"提升"为类型化表。

## 4. 能力三：每个字段的 n 个选项（前端的数据来源）

### 4.1 选项存在哪里

选项就是 `code_value` 的行。字段通过 `field_catalog.code_table_id` 指向它：

```
field_catalog(F_PROFILE_A) ──code_table_id──▶ CT_F_PROFILE_A
                                                    │
                                        code_value ├─ A1 非常愿意
                                                    ├─ A2 愿意
                                                    ├─ A3 犹豫
                                                    └─ A4 不愿意
```

**前端不硬编码任何选项**。改选项 = 改数据，不改代码。

### 4.2 前端契约：一个接口拿全表单

```
GET /api/form-schema?entity=person
```

```json
{
  "entity": "person",
  "generated_at": "2026-09-27T15:02:11+08:00",
  "fields": [
    {
      "field_id": "F_PROFILE_A",
      "title": "基层服务意愿",
      "description": null,
      "data_type": "code",
      "cardinality": "scalar",
      "required": true,
      "section": "就业偏好",
      "option_count": 4,
      "options": [
        {"code": "A1", "label": "非常愿意", "en": null, "sort": 10},
        {"code": "A2", "label": "愿意",     "en": null, "sort": 20},
        {"code": "A3", "label": "犹豫",     "en": null, "sort": 30},
        {"code": "A4", "label": "不愿意",   "en": null, "sort": 40}
      ]
    }
  ]
}
```

渲染规则（演示站点 `code/demo/app.py` 即按此实现）：

| `option_count` | `cardinality` | 控件 |
|---|---|---|
| > 0 | scalar | 下拉框 / 单选按钮（n 个选项） |
| > 0 | array | 复选框组（n 个选项） |
| 0 | — | 按 `data_type` 给数字框 / 文本框 / 日期框 |

### 4.3 提交时的三条规则

1. **单选存码**：`set_value(..., p_code => 'A2')` → `value_code`
2. **多选存码数组**：`set_value(..., p_codes => ARRAY['F01','F02'])` → `value_codes`
3. **只能从给定选项里选**：写入未定义的码会被数据库拒绝

```sql
SELECT mt.set_value(p_entity=>'person', p_subject_id=>'per_001',
                    p_field_id=>'F_PROFILE_A', p_code=>'A9');
-- ERROR: 取值 A9 不在字段 F_PROFILE_A 的候选选项内（词表 CT_F_PROFILE_A）
```

这条防线在**数据库层**，不在前端——前端校验可以被绕过，数据库约束不能。

### 4.4 表单可以横跨多个实体

真实表单里，"性别"在 `person_demographics`，"就业偏好"在 `person`。
`submit` 时按每个字段自己的 `entity_id` 落库：

```python
ent = f["entity_id"]          # person 还是 person_demographics
cur.execute("SELECT mt.set_value(p_entity=>%s, p_subject_id=>%s, p_field_id=>%s, p_code=>%s)",
            (ent, pid, fid, val))
```

读取时用 `mt.profile_json(实体, 主体ID)` 分别取回再合并。
实测：一次提交 6 个字段，跨两个实体全部正确落库。

```powershell
cd D:\wbo-workspace\medtalent-db

python code\demo\app.py --serve       # 打开 http://127.0.0.1:8080

```

页面上可以直接做四件事：
1. 填写一份画像（所有选项都来自数据库）；
2. **现场新增一个维度**——填标题和 n 个选项，提交后刷新，表单里立刻多出这个字段；
3. 查看当前表单的字段与候选选项（数据库视角）；
4. 查看已入库的画像（含动态新增的列）。

端到端测试（`ops/tests/form_server_test.py`，30 项断言全通过）覆盖：
首页渲染 → schema 接口 → 页面新增维度 → 断言行数/列数未变 → 模拟提交 → 校验按码入库 →
非法选项被拒 → 一键清理。

## 6. 边界：什么时候**必须**真正改结构

动态机制不是万能的。以下情形应当走正式迁移（新增 `009_xxx.sql`），而不是塞进 `field_value`：

| 情形 | 为什么 |
|---|---|
| 该维度将成为高频筛选/排序/连接条件 | 需要索引；`field_value` 的 EAV 查询会随规模变慢 |
| 需要外键、唯一约束、CHECK 等强约束 | `field_value` 只能做有限校验 |
| 需要参与派生指标且被大量重算 | 类型化列 + 表达式索引性能好一个量级 |
| 该实体要独立生命周期、独立权限 | 应升级为类型化表 |

判据：**"探索期用扩展，稳定高频用列"**，并走 `attribute_definition.status: proposed → active → promoted` 的提升流程。

## 7. 操作速查

| 我想…… | 调用 |
|---|---|
| 加一个单选维度（n 个选项） | `mt.add_dimension(entity, field_id, title, p_options=>'[...]'::jsonb)` |
| 加一个多选维度 | 同上 + `p_multi => true` |
| 加一个数值/文本维度 | 同上 + `p_data_type => 'number'/'text'` |
| 注册一个不需要建表的新实体 | `mt.register_entity(id, domain, 'EK2')` |
| 建一条记录 | `mt.create_instance(entity, id, payload_jsonb)` |
| 写一个值 | `mt.set_value(entity, subject_id, field_id, p_code/p_codes/p_num/p_text)` |
| 软删一个维度（保数据） | `mt.deprecate_dimension(field_id, reason)` |
| 删一条记录 | `mt.delete_instance(entity, id)` |
| 取表单定义（含 n 个选项） | `mt.form_schema(entity)` 或视图 `v_form_schema` |
| 取某个人的完整画像 | `mt.profile_json(entity, subject_id)` |
| 取某个词表的全部选项 | 视图 `v_option_set` |
