# 13 · 演化层：职业树与能力的持续生长（T13）

> 需求：社会需求与岗位在动态变化，所以职业树的枝叶要能**生长**；个人画像与建模能力也在生长，
> 所以能力与职业之间的映射要具备**动态性、持续性、扩展性**。
>
> 实现：`schema/sql/012_evolution.sql` + `code/evolve/{discover,promote,recompute,restore_baseline}.py`
> 验证：`ops/tests/evolution_test.py`（33 项断言全通过）

---

## 一、三条设计原则

演化最容易做错的地方不是"加不上"，而是**加上去之后历史全乱**。所以先立三条原则：

| 原则 | 含义 | 反面做法（本项目禁止） |
|---|---|---|
| **P1 时间是第一等维度** | 每个演化对象带 `valid_from/valid_to`；任何结论都能回答"这是什么时候的事实" | 原地覆盖、只留最新状态 |
| **P2 ID 不复用、只退役** | 一个 `occupation_id` 一旦用过就永远指同一件事；拆分/合并/改名走迁移表 | 复用旧 ID 表示新含义 |
| **P3 提升必须有证据** | 新岗位/新能力不会因为"有人觉得该有"就进树；必须支撑 JD 条数 ≥ 阈值 + 有评审记录 | 人工随手插数据 |

## 二、职业树怎么"长"

### 2.1 发现：让数据自己冒出来

```powershell
python code\evolve\discover.py
```

- 把每条 JD 的标题与现有职业树比对，**匹配不上的进候选池**，按岗位名聚合证据条数；
- 支撑条数达到阈值（默认 5）→ 状态转 `ready`，等待评审；
- **候选池进不了正式层**，正式层只能由下面这步写入。

某次实测输出：
```
候选岗位：检查 690 条 JD → 聚合出 1 个未识别岗位名，其中 1 个已达阈值(ready)
  [30 条] 疾控中心公共卫生岗（推测族 F09）
```

### 2.2 提升：有门槛、有记录、有新 ID

```powershell
python code\evolve\promote.py list
python code\evolve\promote.py add <candidate_id> --family F09 --parent OCC-F09
python code\evolve\promote.py split OCC-F02-01-02 --parts "肿瘤:0.6,免疫:0.4"
python code\evolve\promote.py merge A,B --label "合并后的岗位" --family F02
python code\evolve\promote.py retire OCC-F17-01-02 --reason "需求萎缩"
```

每次提升都写 `occupation_change`（谁、何时、依据几条 JD、什么理由），
新节点用**新 ID**（`OCC-Fxx-X********`），旧 ID 通过 `occupation_migration` 保留可追溯。

**拆分与合并必须留迁移表**，否则历史报告与历史匹配结果会指向含义已经变了的节点：

```sql
SELECT * FROM mt.occupation_resolve('OCC-F02-01-02');
-- 返回该历史 ID 今天对应的全部后继节点及其关系（split_into / merged_into）
```

### 2.3 时点回溯：as-of 查询

```sql
SELECT count(*) FROM mt.occupation_asof(DATE '2026-01-01');   -- 年初的树
SELECT count(*) FROM mt.occupation_asof(CURRENT_DATE);        -- 今天的树
```

实测：今天 151 个节点 > 年初也有节点；测试里新提升的节点**在今天的树里、不在年初的树里**。

### 2.4 基线可恢复

踩过的坑：演化测试清理时把**种子基线里的真实节点**也退役了，树凭空少 4 枝。
现在把两者分开管理：

```powershell
python code\evolve\restore_baseline.py        # 把 occupation_seed.csv 里的基线节点恢复为 active
```

原则：`occupation_seed.csv` 是**基线**（必须存在），演化新长出来的节点是**增量**（允许退役）。

## 三、能力怎么"长"

```powershell
python code\evolve\discover.py     # 候选能力与候选岗位一起发现
```

两个关键过滤，都沿用本项目已确立的口径：

**① 只收能力类要求。**
学历(RT1)/经验(RT3)/证照(RT4) 是**资格门槛**，由 `education_req`/`license_req` 承载，
不进能力本体。实测：1590 条未映射要求里 **1380 条被正确剔除**，
剩下 53 个候选短语——若不剔除，词表会被"医学相关专业硕士及以上学历"这类文本迅速淹没。

**② 先别名、后新概念。**
若候选短语命中既有概念的关键词，说明它只是**同义说法**，应当作为别名并入，
而不是新建一个重复概念。实测 53 个候选里有 **44 个被判定为别名**。

```powershell
python code\evolve\promote.py alias <candidate_id> --into CON-K1-LIT   # 并入作别名（首选）
python code\evolve\promote.py concept <candidate_id> --type K1 --label "……"  # 确实是新概念
```

**重复概念是词表腐化的开始**——这条比"多收几个概念"重要得多。

## 四、能力↔职业映射：从"快照"改成"版本"

### 4.1 改造前的问题

原来是 `DELETE FROM job_competency_weight` + 重建。后果：
无法回答"半年前这项能力的需求是多少"、无法做趋势分析、每算一次历史就没了。

### 4.2 改造后

每次重算 = 一个**新版本**（`competency_run`）：

- 新版本的行 `valid_to` 为空（当前有效），旧版本被"封口"（`valid_to = 本次 as_of`）
- 两版之间逐 (职业, 能力) 比对，产出 `competency_drift`：
  `new`（上版没有）｜`rising`｜`falling`｜`vanished`（本版没有）｜`stable`
- 所有查询走 `v_competency_current`；**历史版本永远查得到**

```powershell
python code\evolve\recompute.py                              # 按当前数据算一版
python code\evolve\recompute.py --as-of 2026-06-30 --period 2026H1
python code\evolve\recompute.py --history                    # 版本历史
python code\evolve\recompute.py --drift                      # 最新漂移
```

实测（模拟"新岗位 + 某项能力需求被抬高"）：
```
[✓] 重算版本 cr_xxx（as-of 2026-09-27，期间 2026-09）
    写入 58 行能力权重；上一版本 cr_yyy
    漂移：新出现 1｜上升 0｜下降 0｜消失 0｜稳定 57
  最显著的漂移：[new] 医疗数据合规官 × 运营与增长
```

**这条 `new` 就是"市场变了"的信号**：一个新职业节点出现了，并且它带来了一项此前不在矩阵里的能力需求。

## 六、这轮抓到的问题

| # | 问题 | 教训 |
|---|---|---|
| 25 | 候选证据 `evidence_count` 用**累加** | 每次发现都是全量重算，累加会把同一条 JD 反复计数；应覆盖 |
| 26 | 能力候选池塞满学历/证照/培训文本 | 资格门槛 ≠ 能力；必须按 `requirement_type` 过滤 |
| 27 | 同义短语被当成新概念 | **先别名、后新概念**；重复概念是词表腐化的开始 |
| 28 | `promote_occupation` 开头用了未定义的连接变量 | 首次运行才暴露（静态检查看不见） |
| 29 | `concept` 表缺 `updated_at` | 词表是可增长对象，需要记录最近一次扩充时间 |
| 30 | `job_competency_weight` 的 `UNIQUE(occupation_id, concept_id)` **阻止保留历史版本** | 版本化的前提是先去掉"每对只允许一行"的约束 |
| 31 | 演化测试清理把**种子基线节点**也退役了 | 基线与增量必须分开管理；补 `restore_baseline.py` |
| 32 | 漂移为空——注入的 JD 没有职业映射 | 只有"已映射职业 + 已映射概念"的 JD 才参与聚合；测试要显式断言映射生效 |
| 33 | **`build_competency` 委派 `recompute` 时另开了连接** → 看不到本事务里刚写的映射，"映射明明写了，权重却是 0 行" | 同一逻辑事务内的多步派生必须共用连接（`recompute(..., db=c)`）；跨连接的可见性问题是静默的 |
| 34 | 演化测试清理**只按 label 删**：拆分的源节点是真实种子节点（label 不含 TAG），于是 ① 它永久停在 `retired` ② `occupation_change.to_ids` 指向已删节点成为**悬空引用** | 清理要**按引用关系**而不是按名字；并补 3 条完整性不变量进回归（节点从不物理删除 ⇒ 任何指向不存在节点的引用都是脏数据） |

**第 30 条最隐蔽**：一个看似合理的唯一约束，会让"保留历史版本"这件事根本做不到。

**第 33 条最容易被误读成"数据没写进去"**：`recompute` 是新连接，读不到 `build_competency`
事务里未提交的映射，于是算出 0 行；而同一次运行末尾的统计查的是**全表**（含历史版本），
所以打印出"覆盖职业 25 个"——写入 0 行却报 25 个职业，是一句**说谎的统计**。
修法两件：把连接传进去；统计只算 `valid_to IS NULL` 的当前有效版本。

**第 34 条提醒的是"清理"比"构造"更容易错**：测试构造数据时处处带 TAG，清理时却只按
label LIKE TAG 删——而它拆分的那个节点是**真实种子节点**。三次运行之后，职业树少了
一枝、变更表里躺着 5 条 `to_ids` 悬空的记录。现在清理按 `from_ids`/`to_ids` 引用关系走，
恢复源节点，并且 `restore_baseline.py` 也能自愈历史残留。

### 版本化带来的表增长（设计意图，不是泄漏）

`job_competency_weight` 每次重算**追加一版**、给旧版写 `valid_to`，从不覆盖历史。
所以"全表行数"会随重算次数单调增长（跑完整套回归约 900+ 行），而"当前有效"始终 58 行。
只要查询走 `v_competency_current`（`valid_to IS NULL`）就不受影响；反过来，
任何直接 `SELECT ... FROM job_competency_weight` 的统计都必须自己加这个条件——
第 33 条那句"写入 0 行却报覆盖 25 个职业"就是这么来的。

### 这一层怎么回归

```powershell
python ops\tests\run_all.py --only 12        # 只跑演化层 33 项
python ops\tests\run_all.py --after-only     # 复位基线 + 重建派生层
python ops\tests\run_all.py                  # 全量（12 套 + 2 个收尾）
```

`regression_guards.sql` 里有三条守卫专门盯这一层的数据完整性（11–13 号用例）：
变更记录不得有悬空 `to_ids`、迁移记录不得引用不存在的节点、每个退役节点必须留下
变更记录（"谁决定的？"）。三条都建立在同一个前提上：**节点从不物理删除**。

## 七、与既有文档的关系

- 三条扩展机制（`docs/01` §5）解决的是**加字段/加词表/加实体**；
  本演化层解决的是**这些扩展随时间如何演进、如何追溯、如何回退**。
- 小程序接入（`docs/11`）里"契约要求概念 ID 不复用、拆分合并用迁移表"——
  本层的 `occupation_migration` 与 `occupation_resolve` 就是那条要求的落地。
- 备份（`docs/12`）保证演化历史不丢；`valid_to` 封口 + `change_log` 审计保证演化可追溯。
