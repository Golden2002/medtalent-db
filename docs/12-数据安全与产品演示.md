## 一、备份与恢复（需求 a）

实现：`schema/sql/011_backup.sql` + `ops/backup/backup.py` + `ops/tests/backup_test.py`（31 项断言全通过）

### 1.1 一次备份产出什么

| 产物 | 内容 | 用途 |
|---|---|---|
| `medtalent.dump` | `pg_dump -Fc` 全库逻辑备份 | **权威恢复源** |
| `user_data.xlsx` | 用户 + 业务数据多 sheet 副本（本次 32 张表） | 人工核对、迁移、交付 |
| `manifest.json` | 逐文件 sha256 + 各表行数 + 策略快照 | 校验与恢复核对依据 |
| `RESTORE.md` | 脱离代码也能照做的恢复指引 | 灾难场景（人不在了也能恢复） |

### 1.2 三条设计选择

**① 保留策略是数据，不是脚本里的常量。**
`backup_policy` 表存 `keep_daily / keep_weekly / keep_monthly / min_copies / include_pii`。
改策略 = 改一行配置，不用改代码，也不用重新发版。

**② GFS 分层保留：日 7 / 周 4 / 月 6，且至少留 3 份。**
实测（40 份样本）：保留 12 份——日层 7 份、周层 5 份（7–27 天区间每周一份）、
加上兜底的 min_copies。**超期只删文件，记录保留并标记 `pruned`**，
所以"这个备份曾经存在过"仍然可查。

**③ 默认不导出 PII。**
`person_pii` 整表不导出，`person_demographics.health_limits`、
`person_constraint.description` 等敏感列剔除。
显式 `--include-pii` 才导出，并在 manifest 里标记 `accessTier: T3`
（对应 `docs/06` 的敏感个人信息要求）。

### 1.3 校验与恢复

- **sha256 校验**：实测篡改 1 个字节即被检出（"medtalent.dump 哈希不符（疑似损坏）"）。
- **自愈**：备份目录被手工删掉时，`verify` 会把记录标记为 `failed`，
  避免"库里显示 ok、实际文件已丢"的假象。
- **恢复演练会真删数据再恢复**：测试里删掉 10 条岗位 → 从未受损副本恢复到新库 →
  核对到 690 条、2970 条要求全部回来；**生产库全程不受影响**（恢复只写新库）。
- 生产库那 10 条由 L0 重跑解析确定性重建——**派生数据可由管道重建，原始数据才依赖备份**。

```powershell
python ops\backup\backup.py backup                       # 备份
python ops\backup\backup.py list                         # 看健康度
python ops\backup\backup.py verify --all                 # 校验
python ops\backup\backup.py prune --dry-run              # 清理演练
python ops\backup\backup.py restore --backup <id> --target-db medtalent_restore
```

```powershell
python code\demo\portal_dev.py --check   # 自检：含"试运行必须回滚"
```

**为什么读写分成两个进程**——这是本节最重要的一条设计选择：

门户的一半价值在于"它**能证明**自己只读"：测试用审计流水（遍历全部页面后
`change_log` 不增长）和 `SELECT 1 INTO t` 被 PostgreSQL 只读事务拒绝来证明。
同一个进程里只要存在一条能写的路由，这条证明就没了，只剩下"我相信没人误挂路由"。
所以 :8082 在任何配置下都写不进去，写能力全部在 :8083。

**另外五条纪律：**

1. 开发者模式的**写操作只走 POST**，`GET` 只渲染表单——否则浏览器预取或被误点的示例链接
   就可能改库。
2. **行数一律 `count(*)`**，不用 `reltuples`。实测它已经过时（`code_table` 估算 53、实际 49）；
   一个"看真实数据"的门户显示估算值就是自相矛盾。
3. **表名列名先与系统目录比对**，再用 `psycopg.sql.Identifier` 转义（URL 里的表名是用户输入）。
4. **空就是空**。空表、未使用的机制、0 行的分析都如实标注
   （`attribute_definition` 为 0 时页面直接写"机制未被使用"）。
5. **合成数据必须自证**。`/talent` 顶部直接给出"120 份带
   `quality_flags={synthetic_fixture}` 标记"，并列出可辨识特征
   （`per_mock_%` 前缀、`.invalid` 保留域、DOI 合成号段、机构名带"虚构"后缀）。
   成熟的数据集要能一句话说清"哪些行可以对外"。

**已验证**（`ops/tests/portal_test.py` **123 项** + `ops/tests/devmode_test.py` **39 项**）：

| 断言 | 为什么这么写 |
|---|---|
| 页面行数 == `count(*)`（抽查多张表） | 防止"页面显示一个好看的数字" |
| 外键链接逐个回库确认目标行存在 | 交叉引用不能是死链 |
| 分析页覆盖率 == 直接执行同样 SQL 的结果 | 口径必须可核，页面不能自己算一套 |
| 遍历全部 92 个对象的页面后 `change_log` 不增长 | 用审计流水证明"门户一个字节都没写" |
| `SELECT ... INTO` 被只读事务拒绝 | 证明真正的防线是数据库，不是我们的正则 |
| a4 分析的断言**分情况写** | 它有没有漂移取决于当前数据；把"此刻为空"写成断言就是在测试里钉死快照 |
| 开发者模式 **GET 带写语句也不会建表** | 写只走 POST，防预取 |
| 加一个维度后**基础表 78→78、person 列数 16→16** | 这才是"零 DDL"的证据，而不是嘴上说 |
| 开发者模式结束**零残留** | 能写就必须能收拾干净 |

> **顺带发现的一处口径差异**：静态校验器报 **79** 张表，实际库只有 **78** 张。
> 差额是 `004_vector.sql` 里的 `embedding` 表，而该迁移因本机无 pgvector 被跳过。
> 门户显示 78（真值）。静态计数与运行态不一致时，以运行态为准——
> 这正是"静态校验必要但不充分"的又一个实例。

## 三、这轮抓到的问题

| # | 问题 | 教训 |
|---|---|---|
| 21 | `Decimal` 无法 JSON 序列化 → 整次备份中断且记录停在 `running` | 导出要处理 Decimal/bytes/时间；任何异常都要把状态落成 `failed` |
| 22 | 包哈希把 manifest 自己算进去 → 自指矛盾，`verify` 永远报不符 | 自校验哈希必须只覆盖**被引用的产物** |
| 23 | `job_posting` 的列是 `job_family` 不是 `family` | 拼 SQL 前先确认列名（静态检查不覆盖字符串 SQL） |
| 24 | **重解析会重建 `job_requirement` 行，从而清空概念映射与权重矩阵** | 派生层必须紧跟重建；`jd_ingest` 现在会打印强制提醒，质量门也会立刻报 0% 覆盖率 |
| 35 | `SET LOCAL statement_timeout = %s` 报 `syntax error at or near "$1"` | PostgreSQL **不接受 `SET` 用参数占位符**（扩展协议把它发成 `$1`）；常量用 `sql.Literal` 内联 |
| 36 | 外键单元格只渲染了链接，把 `FOREIGN KEY (...) REFERENCES ...` 定义丢了 | 约束定义本身就是"这个库有哪些不变量"的证据，不能为了好看省掉 |
| 37 | 演示页数据表被超长列撑高，一行看不清一条记录 | 数据浏览器要"单行 + 省略号 + title 里放完整值"；这不是审美，是可读性 |
| 38 | **两个组件共用同一个 ID 前缀**：动态建模测试用 `per_mock_01…20` 并断言 `LIKE 'per_mock_%'` 等于 20；人才夹具后来生成了 120 行 `per_mock_0001…0120` → 断言数出 140，测试失败 | 持久化的夹具/测试必须**独占 ID 前缀**；否则"按前缀清理"会误删别人的数据。见 `ops/fixtures/README.md` 的命名空间约定表 |
| 39 | 职业树页"一年前"显示 0 节点，看起来像 bug | 那是对的（种子节点 `valid_from=2026-01-01`），但标签不带日期就会误导。**0 必须能被解释**："那时这棵树还不存在" |
| 40 | **控制台的「一键清除演示数据」清不掉它自己造的人**：`--reset` 只删 `per_live_%`，但「小程序接入」演示走 `exchange.ingest`，造出的人的本地 ID 是 `per_<sha1>` → 每跑一次全量回归净增 1 个人，而页面上写着"一键恢复干净状态" | 清理的**覆盖面必须等于构造的覆盖面**。现在 reset 按示例包前缀（`wx_demo_`/`wx_anon_`）与测试来源前缀（`bridge_test_`）清，并**动态发现 person 的 29 张外键子表**而不是写死清单 |

第 24 条最值得记：它是唯一一个**会静默削弱产品能力**的问题——
重跑一次解析，匹配结果就全变成 unknown，而表面上一切正常。
现在有两道防线：脚本末尾的提醒 + 质量门的覆盖率指标。

第 35 条是"参数化 ≠ 到处都能用"：参数占位符是**协议层**的能力，
`SET` 这类工具语句走的是另一条路径。遇到 `$1` 语法错误，先怀疑语句类型，而不是怀疑驱动。

第 38 条与第 34 条是**同一类错误的两个面**：按名字/前缀做清理或断言，
而那个名字并不专属于你。第 34 条是"清理时按名字删，删到了真实数据"；
第 38 条是"断言时按前缀数，数到了别人的数据"。
两者的解法也一样：**先确定命名空间的归属，再做按名操作**。

第 40 条是这条线上的第三次：**清理的覆盖面 ≠ 构造的覆盖面**。
它和 34、38 是同一个根因——"我以为我知道自己造了哪些数据"。
现在 `code/demo/console.py` 的 reset 不再假设，而是：
列出示例包与测试的 ID 前缀 → 从 `pg_constraint` 动态取 person 的全部外键子表 → 按依赖删除。
测试里也加了守卫：跑完 console_test 后人数必须不增加，且不残留 `wx_demo_` 前缀。

另外修了两处影响演示观感的问题：匹配页在无数据时不显示三态说明；
条形图标签区宽度为 0 导致中文标签被裁掉。
以及门户里残留的 Markdown `**` 被原样显示（HTML 里要写 `<b>`）。
