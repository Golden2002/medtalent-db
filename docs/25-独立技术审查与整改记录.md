## 二、P0 整改详解

### P0-1 主体标识的披露控制（迁移 044）

**问题**：030 的披露控制**只按表名写死** `person`/`person_pii`，紧接着的通用规则又把
`person_id` 判成 T0。实测 29 张表的 `person_id` 是 T0，而公开剖析视图
`v_column_profile_public` 把 `top_values` 一并交出：

```
evidence.person_id          → per_real_fengtang 21 / per_real_li_tiantian 21 / per_real_yu_ying 20
employment_record.person_id → per_real_yu_ying 6 / per_real_fengtang 5 ...
award_honor.person_id       → per_real_fengtang 7 ...
```

匿名因此同时拿到**编码了姓名的真实人物 id**与**"他产出最多"的精确统计**。

**根因**：**"主体标识"是值的语义，不是表名的属性。** 写成表名白名单，换个表名保护就失效。

**修法（两层）**：
1. `is_subject_identifier(table, column)` —— 列名是 `person_id`/`subject_code`，
   **或**该列是指向 `mt.person` 的外键（从 `pg_constraint` **动态发现**）。命中即 T1。
   新增任何子表自动被覆盖，不需要记得改白名单。
2. `is_enumeration_risk(table, column)` —— 主体标识本身，**或**指向"含 person_id 的表"的
   外键（如 `skill_assertion.evidence_id → evidence`）。公开视图对命中的列**置空 top_values**。
   理由：即使某列被判 T0，**公开它的取值列表仍是另一个更强的动作** ——
   这正是 030 写下的原则"能读一列 ≠ 可以枚举它的取值"，当时只用在了"编号"上，没用在"Top-K 列表"上。

**为什么两层都要**：第 1 层靠"我们记得把新列判成 T1"；第 2 层是**出口处的兜底**，
即使将来有人误判成 T0，公开视图也不会把取值列表交出去。

**验证**：T0 的 `person_id` 从 **29 张表 → 0**；公开视图里 `person_id` 的取值行 **0 条**；
匿名对 `evidence` 表直接 `permission denied`。断言固化在 `exposure_test.py` 的【I】段
（含"公开剖析视图没有交出主体标识 Top-K"）。

### P0-2 授权自愈入口（迁移 043）

**问题**：042 为解决性能问题 `DROP` 了无参 `public_counts()`，但
`apply_role_baseline()`（031/038 定义）里仍写着 `GRANT EXECUTE ON FUNCTION mt.public_counts()`。
实测 `apply_column_grants()` 直接报 `function mt.public_counts() does not exist`。

**为什么是 P0**：它是**唯一的授权对账入口**。它一报错，任何 `column_policy` 调整都落不到
实际授权上，只能手工 GRANT —— 权限模型失去可运维性。
更糟的是**没有任何指标盯着它**，所以只在"下一次需要自愈"时才炸。

**教训（已写进 043 注释）**：**`DROP FUNCTION` 之后必须全文搜索该函数的调用点** ——
函数体里的引用不出现在 `pg_depend` 的普通依赖里，常规依赖检查拦不住。

**验证**：新增 MUST 指标 **I5.0**「授权对账入口可用 且 权限不变式成立」，
每次门禁都真的调一次 `apply_column_grants()`。

## 三、P1-7 的真相：不是代码缺陷，是我方的运行方式

审查者在跑回归时得到 17/23 通过、6 个套件失败（含备份超时、外键错误
`Key (person_id)=()`、门户 90 项失败）。

**真因**：审查进行期间，**我同时跑了会改库的测试**（exposure_test 会建/删账号、
过载压测会占满连接）。两个会写库的测试并发 → 互相污染：
- 控制台套件报出荒谬的外键错误；
- 门户套件大面积失败；
- 备份套件被拖到异常退出。

**为什么值得单独记**：**现象指向代码，真因是运行方式。** 这种假失败最费时间，
而且会让人开始不信任回归结果 —— 那比没有回归更糟。

**整改**：给 `run_all.py` 加**互斥锁**（`.tools/run_all.lock`，含 pid 与启动时间）：
- 锁存在且 pid 还活着 → **拒绝启动**，并打印占用者信息与原因；
- 锁存在但 pid 已死（上次被强杀）→ 视为陈旧，接管并提示；
- `--force` 留后门，但必须自己说出口。
