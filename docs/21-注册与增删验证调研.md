## 2. 怎么证明「真的加入 / 真的删除」

这一节是全文核心。判据分四组：**计数类**（最便宜）、**独立复核类**（最有力）、**结构性类**（专抓假删除）、**反面类**（专抓假测试）。

> 读法：每条判据都给了可执行 SQL 或断言形式。凡标【实测】的，本文在真库上跑过。

### 2.1 计数类判据（写前/写后精确对比）

**J1 · 精确 `count(*)` 前后对比，且必须钉在「写前」快照上**

本项目纪律（README「设计纪律」第 6 条）：**行数用精确 `count(*)`，不用 `reltuples` 估算**（实测 `code_table` 估 53 / 实 49）。测试断言数据库状态，不断言页面文案。

```sql
-- 写前快照（在测试里存成变量，不要事后重算）
SELECT count(*) FROM person WHERE person_id LIKE 'per_regmock%';   -- 期望 0
-- …执行注册…
SELECT count(*) FROM person WHERE person_id LIKE 'per_regmock%';   -- 期望 1
```

**J2 · 幂等：同一 `eventId` 重放两次 → 人数不变**

这是用户「重复点提交」场景的直接判据。本项目已有等价断言（`ops/tests/bridge_test.py:129-135`）：第二次投递返回 `idempotent: true` 且 `external_identity` 人数仍为 1。

```sql
-- 重放后
SELECT count(*) FROM person WHERE person_id = :pid;                       -- 1
SELECT count(*) FROM external_identity WHERE person_id = :pid;            -- 1
SELECT count(*) FROM sync_event WHERE external_event_id = :event_id;      -- 1（不是 2）
```

**J3 · 外键子表是否被级联清理（动态发现，不写死表名）**

本项目已有「动态发现 person 的 29 张外键子表」的做法。**【实测】本次确认：`information_schema` 动态查询出的直接引用 `mt.person(person_id)` 的外键子表恰好 29 张，且 `delete_rule` 全部是 `NO ACTION`。**

```sql
-- 动态发现 person 的直接外键子表（本次实测返回 29 行）
SELECT tc.table_name, kcu.column_name
FROM information_schema.table_constraints tc
JOIN information_schema.key_column_usage kcu
  ON kcu.constraint_name = tc.constraint_name AND kcu.table_schema = tc.table_schema
JOIN information_schema.constraint_column_usage ccu
  ON ccu.constraint_name = tc.constraint_name AND ccu.table_schema = tc.table_schema
WHERE tc.constraint_type = 'FOREIGN KEY' AND tc.table_schema = 'mt'
  AND ccu.table_name = 'person' AND ccu.column_name = 'person_id'
ORDER BY 1;
```

**这 29 张全是 `NO ACTION`** ⇒ **只要任一子表还有行，`DELETE FROM person` 就会被数据库直接拒绝**。【实测】全部 29 张的 `delete_rule` 计数为 `NO ACTION: 29`。这既是保护也是约束：**硬删 person 必须自上而下按序清理，或者改用软删**（见 §4.4）。

顺带【实测】：全库 95 个外键里只有 **4 个是 `CASCADE`**，且都不指向 `person` —— `answer→response_session`、`experience_task→experience_episode`、`job_requirement→job_posting`、`job_task→job_posting`。所以「删 person 会自动带走子行」这个假设在本库**完全不成立**。

**J4 · 删除后全库无残留（孤儿行检测）**

关键前提（**【实测】一个容易被忽略的洞**）：`field_value` 表**没有**指向 `person` 的外键！实测 `field_value` 的外键只有 `field_catalog` 与 `source_registry` 两个，`subject_id` 是一根**裸 TEXT**。

推论（**【实测】已构造并确认**）：直接 `DELETE FROM person WHERE person_id='…'` 成功之后，`field_value` 里那条 `subject_id='…'` 的值**原样留着，没有任何报错**。这正是「删了主表留下孤儿从属行」的教科书场景。这也解释了 `mt.delete_instance` 为什么要在软删之后**手工**再删一次 `field_value`（`008_dynamic_model.sql:414`、`:419`）。

所以孤儿行检测必须是**独立的一条查询**，不能依赖外键：

```sql
-- 孤儿行检测之一：field_value 的悬空 subject_id（这次实测：全库当前 0 条）
SELECT count(*) AS dangling
FROM field_value fv
WHERE fv.subject_type = 'person'
  AND NOT EXISTS (SELECT 1 FROM person p WHERE p.person_id = fv.subject_id);
```

```sql
-- 孤儿行检测之二：把 29 张子表全部扫一遍（本次实测：总孤儿数 0，非零清单「(无)」）
CREATE TEMP TABLE orphan_report (child_table text, db_column text, orphan_rows bigint);
DO $$
DECLARE r RECORD; n bigint;
BEGIN
  FOR r IN
    SELECT tc.table_name AS child, kcu.column_name AS col
    FROM information_schema.table_constraints tc
    JOIN information_schema.key_column_usage kcu
      ON kcu.constraint_name = tc.constraint_name AND kcu.table_schema = tc.table_schema
    JOIN information_schema.constraint_column_usage ccu
      ON ccu.constraint_name = tc.constraint_name AND ccu.table_schema = tc.table_schema
    WHERE tc.constraint_type = 'FOREIGN KEY' AND tc.table_schema = 'mt'
      AND ccu.table_name = 'person' AND ccu.column_name = 'person_id'
  LOOP
    EXECUTE format(
      'SELECT count(*) FROM mt.%I c WHERE c.%I IS NOT NULL '
      'AND NOT EXISTS (SELECT 1 FROM mt.person p WHERE p.person_id = c.%I)',
      r.child, r.col, r.col) INTO n;
    INSERT INTO orphan_report VALUES (r.child, r.col, n);
  END LOOP;
END $$;

SELECT child_table, orphan_rows FROM orphan_report WHERE orphan_rows > 0;   -- 期望 0 行
```

> 这两段**建议直接进回归**：它比「我删干净了」这句人话强，因为它会随 schema 演进自动扩大覆盖面（将来新增一张 person 子表，它自动被扫到）。

**J6 · 通过第二个独立路径复核（导出 CSV / `change_log` / 只读门户）**

本项目已有 `change_log` 触发器审计（append-only，由 `mt.log_change()` 触发器强制），且【实测】它**确实记录 DELETE**：

```sql
-- change_log 结构（实测 9 列）
-- change_id, at, actor, object_type, object_name, change_type, from_version, to_version, detail
SELECT change_type, count(*) FROM change_log GROUP BY 1 ORDER BY 2 DESC;
-- 实测输出：update 292258 / insert 144224 / delete 128395 / add 395 / backfill 10
```

所以「删了没有」有**第二条完全独立的证据链**：即使应用层骗人，`change_log` 里应有对应的 `change_type='delete'` 行，`detail` 里带 `{"op":"DELETE","row":…,"table":…}`（【实测】看到过 `code_table` 的 delete 行形如 `{"op": "DELETE", "row": "code_table_id=CT_F_LIVE_B", "table"…`）。

注意两条边界（【读码】+【实测】）：
- `change_log` 是 **append-only**，**不能**把「`change_log` 里有 delete」当成「数据现在没了」——它是审计，不是状态。
- `app.py` 与 `mt.delete_instance()` 走的路径**未必**触发 `change_log`：实测 change_log 的行数（565,282）远大于业务变更量，但 `form_server_test` 的清理路径是否留痕**未逐一验证**。**用 `change_log` 做强断言前，先在真库上确认你这条写路径确实触发它。**【未验证】

**J7 · 只读第三路径：门户 / SQL 控制台**

`portal.py`（:8082）是**可证明的只读**（读写拆成两个进程正是为了让「门户写不进去」可被验证；README 设计纪律第 8 条）。用它做复核时，有一条现成的强断言可以借用：**遍历全部页面后 `change_log` 不增长**（README「测试」节）。反过来用：如果 mock 窗口走后，某个"只读"页面把它显示出来了，说明写路径确实落库了，而且门户一个字节都没写。

### 2.3 结构性判据（专抓「假删除」）

**J8 · 墓碑真的拦住了迟到的 upsert（本项目已有规则，需要一个「真能触发」的用例）**

规则位置：`schema/sql/010_bridge.sql:194-210`，触发器 `trg_sync_event_tombstone BEFORE INSERT ON sync_event FOR EACH ROW EXECUTE FUNCTION guard_tombstone()`（**【实测】确认该触发器存在且定义如上**）；应用层对应 `code/bridge/exchange.py:140-148`（R5）。

**为什么现有测试没真正打到数据库触发器**（【读码】，`ops/tests/bridge_test.py:244-257`）：T11 用例先在库里插了墓碑，再调 `exchange`。但应用层 R5 会在 `ingest()` 开头就用 `(person_id, source_system)` 查墓碑并抛 `PROFILE_DELETING` —— **函数在写任何数据之前就返回了**，数据库触发器根本没机会执行。于是现有断言证明的是「应用层会拦」，**不是**「数据库也拦得住」。

**本文设计的补充用例（【实测】真的触发了触发器，且证明了两件不同的事）**：让应用层检查落空、由数据库兜底。做法是关键：`exchange.py:141-143` 的墓碑查询**同时按 `(person_id, source_system)`** 过滤，所以只要让「包里的 `source_system`」与「墓碑行的 `source_system`」不一致，应用层就查不到墓碑；而用户级 L3 检查（`sync_event` 触发器）只按 `(person_id, source_system)` 查——因此必须用**同一 source**。本文探针采用的等价做法是：`source_system` 一致、但**绕过 `ingest()` 的 R5 检查**直接按 `ingest()` 的真实写入顺序执行，把 `sync_event` 的 INSERT 放在事务末尾。这恰好也验证了原子性。

**【实测】结果**（原文抄录）：


并用 `EXCEPTION WHEN check_violation` 把它变成一条正常结果行后，还得到两条对照证据（**【实测】**）：

| 观察 | 实测值 | 意义 |
|---|---|---|
| 迟到事件（v3 ≤ 墓碑 5） | `BLOCKED_BY_TOMBSTONE_TRIGGER`，`sync_event` 中 `evtprobe_late` 行数 = **0** | 数据库触发器真的拦住了，且没落库 |

| 拦下之后事务是否还能用 | 该 person 行仍在（= 1） | 触发器抛的是可捕获的 `check_violation`，不是把事务搞成不可恢复态 |

这三条合起来才是完整的判据：**「拦住了」+「没落库」+「只拦该拦的」**。只断言第一条（报错）会漏掉「实现改成一律拒绝」这种错。

**J9 · 删除受理 ≠ 删除完成（异步删除的判据）**

规则位置：`docs/11-小程序接入适配器.md` §4；实现 `code/bridge/api.py:164-200`。

```sql
-- 受理之后、完成之前，必须满足：
SELECT status, completed_at, downstream_confirmed
FROM talent_deletion_request WHERE request_id = :rid;
-- 期望：status='pending'，completed_at IS NULL，downstream_confirmed = false
```

现成断言（`bridge_test.py:234-241`）：`completedAt is None and downstreamConfirmed is False`，且此时 `matches` 必须返回 `PROFILE_DELETING`。

**J10 · 乐观并发控制：版本号不得倒退**

```sql
-- 同一人、同一来源：迟到的低版本必须被拒
SELECT last_seen_version FROM external_identity
WHERE source_system = :src AND external_person_id = :ext;   -- 不得因迟到包而变小
```

现成断言（`bridge_test.py:137-142`）：同版本不同载荷 → `CONFLICT`；版本倒退 → `CONFLICT`。

### 2.4 反面判据（比证明「生效」更重要）

**核心原则：一个测试的价值，等于「如果实现坏了，它会不会失败」。** 只会跟着实现走的测试是假测试。

**J11 · 「如果删除根本没生效，这个测试一定会失败」——设计法**

做法是**故意把断言钉死在「删掉之后的具体状态」**，而不是钉在「操作返回成功」：

| 反面对照 | 弱的写法（假测试） | 强的写法（会失败） |
|---|---|---|
| 删除 | 断言响应里带 `"status":"deleted"` | 断言 `count(*) = 0` **且** 29 张子表孤儿总数为 0 **且** 独立 psql 连接查不到该 `person_id` |
| 写入 | 断言页面出现「提交成功」 | 断言 `count(*)` 从 0→1、`field_value` 精确值等于提交的 code、且独立连接可查 |
| 幂等 | 断言第二次也返回 200 | 断言第二次返回 `idempotent=true` **且** `external_identity` 人数仍为 1 |
| 墓碑 | 断言报错 | 断言报错 **且** `sync_event` 无该行 **且** v6 对照包能通过 |

**J12 · 变异测试（mutation）自检法**

不引入工具也能做：**手工把实现改坏一行，跑测试，必须看到失败**，然后改回来。三个值得每月做一次的变异点：

1. 把 `exchange.py` 的墓碑过滤条件 `WHERE person_id=%s AND source_system=%s` 改成只按 `person_id` → 现有 T11 应仍通过（因为应用层会拦），但 §2.3 的补充用例应变化；

第 3 条尤其说明问题：**现有 514 项断言没有一条会因为这个变异而失败** —— 这正是「孤儿行检测」必须新增的理由。

**J13 · 清理覆盖面必须等于构造覆盖面（本项目踩过的坑）**

### 3.1 幂等性设计（Stripe / AWS）

**Stripe** —— [Idempotent requests](https://docs.stripe.com/api/idempotent_requests)（HTTP 200，已fetch）：

- 客户端自带一个 `Idempotency-Key`；Stripe **保存第一次请求的状态码与响应体，不论成功还是失败**，后续同 key 请求返回同样的结果 —— **包括 `500` 错误**。
- key 长度上限 **255 字符**；建议用 **V4 UUID** 或足够熵的随机串；**不要把敏感数据（邮箱、个人标识）当幂等键**。
- **key 至少 24 小时后才可被清除**；清除之后再复用同一 key，会**生成一个新请求**。
- 幂等层会**比较入参与首次请求是否一致，不一致就报错**，以防误用。
- 只在端点**开始执行之后**才保存结果：参数校验失败、或与并发请求冲突时**不保存**，所以这些请求可以重试。
- **`GET` 与 `DELETE` 不要带幂等键**：它们**按定义就是幂等的**，带了没有效果。

→ 对本项目的映射：本项目的幂等键是 `(source_system, external_event_id)`，正是「对方系统内唯一」的等效物；「同 key 不同载荷 → 报错」对应 `exchange.py:162-165` 的 `CONFLICT`。【读码】但 Stripe 的「24 小时后可清除」在本项目**没有对应设计**【未验证】—— `sync_event` 是永久累积的，需要决策是否要做保留策略。

**AWS EC2** —— [Ensuring idempotency in Amazon EC2 API requests](https://docs.aws.amazon.com/ec2/latest/devguide/ec2-api-idempotency.html)（HTTP 200，已fetch）：

- 有些操作**默认幂等**（`TerminateInstances`（终止实例）、`AssociateAddress`、`CreateVpnConnection`、`DisassociateAddress`、`ReplaceNetworkAclAssociation`）；另一些**必须显式传 client token**（`RunInstances`、`CreateVolume` 等）。
- client token 是**大小写敏感的、最多 64 个 ASCII 字符**的唯一串；**不应把同一 token 复用到别的请求**。
- **同 token + 同参数重试 → 成功且不再执行任何动作；同 token + 参数不同 → 失败并返回 `IdempotentParameterMismatch`**。
- 幂等的作用域分 **Regional** 与 **Zonal**：`RunInstances` 的幂等范围取决于是否显式/隐式指定了可用区。
- 重试建议按响应分级：`200` **不要重试**；`400` 系列**不要重试**（但这句有个例外：资源正在状态切换中时，重试可能成功）；`500` 系列**应当重试**并配合退避。

→ 对本项目的映射：「幂等作用域」这个概念本项目也有、而且是**踩坑得来的**：`uq_sync_event_dedup UNIQUE (source_system, person_id, aggregate_version, event_type, direction)`（【实测】该约束存在，见 §0 方法）。文档 `docs/11` §7 记录：最初漏了 `direction`，导致入向与出向的同版本同类型事件**互相顶掉**。这与 AWS 的「同一 token 在不同 Region 可用」是同一类问题：**幂等作用域必须把全部区分维度覆盖全**。

### 3.2 软删除与墓碑

**Rails `paranoia`** —— [rubydoc.info/gems/paranoia](https://rubydoc.info/gems/paranoia/2.2.1) 与 [rubygems.org/gems/paranoia](https://rubygems.org/gems/paranoia)（均可达；已确认为该 gem 的文档页）：这是 Rails 生态最常被引用的软删除实现，`acts_as_paranoid` 用 `deleted_at` 时间戳列代替物理删除，默认 scope 隐藏已删行，`really_destroy!` 才做物理删除。

> **诚实声明**：本次 fetch 只拿到 gem 文档页的标题与目录，**没有逐字确认 README 中对 `acts_as_paranoid` / `really_destroy!` 的具体描述**【未验证】。引用它作为「软删除的业界通行做法」是安全的，但**不要**把上面这句当逐字引文。

**Django** —— [Model field reference](https://docs.djangoproject.com/en/6.0/ref/models/fields/)（HTTP 200，已fetch）与 [Models](https://docs.djangoproject.com/en/6.1/topics/db/models/)：

- Django ORM **默认没有**软删除。`ForeignKey` 的 `on_delete` 是一个**必填**参数，文档中出现的取值包括 **`CASCADE`、`PROTECT`、`RESTRICT`、`SET_NULL`、`SET_DEFAULT`、`SET()`、`DO_NOTHING`**（在 Models 页的 FK 章节与 field reference 的 `ForeignKey` 章节列出）。
- 也就是说，Django 的哲学是**「删除就是删除，级联关系显式声明」**，软删除要靠第三方包或自己加 `is_deleted` 列。

→ 这与本项目形成有意思的对照：本项目在**两处**走了不同路线。`mt.delete_instance()`（`008_dynamic_model.sql:390-422`）是「**有 `status` 列就软删置 `withdrawn`，否则硬删**」；bridge 是「**软删 + 墓碑 + 独立删除请求**」。Django 的 `on_delete` 告诉我们的是：**这个选择应当是显式的、逐关系的，而不是全局默认**。本库 29 个 `person` 外键全部 `NO ACTION`（【实测】）事实上就是「全部 RESTRICT 语义」——这是有意的保守选择。

**PostgreSQL 手册** —— [5.4. Constraints](https://www.postgresql.org/docs/16/ddl-constraints.html)（HTTP 200，已fetch）：

- `RESTRICT` **阻止**删除被引用的行。`NO ACTION` 意思是「约束被检查时若仍有引用行就报错」，**这是不指定时的默认行为**。
- **两者的本质差别**：`NO ACTION` 允许把检查**推迟到事务稍后**（deferred），`RESTRICT` 不允许。
- `CASCADE` 表示被引用行删除时，引用它的行**自动一并删除**。

→ 这解释了一个本项目可以直接利用的能力：因为 29 个外键是 `NO ACTION` 而非 `RESTRICT`，理论上可以用 `SET CONSTRAINTS ALL DEFERRED` 把检查推迟到事务末尾（前提是约束声明为 `DEFERRABLE`）——**本项目这些约束是否为 DEFERRABLE 未验证**【未验证】。若否，则「先删主表、后清子表」在单事务内是不行的，必须严格按序删。

**事件溯源里的 tombstone** —— 本项目自身就是最好的对照物：`schema/sql/010_bridge.sql:183-191` 的 `tombstone` 表用 `deleted_through_version` 表达「至该版本为止的资料已删除」，并用 `BEFORE INSERT` 触发器（`guard_tombstone()`）在**数据库层**拒绝一切 `aggregate_version <= cut` 的写入。这是「删除」在 append-only 世界里的标准形态：**你不能收回已经发生的事实，但你可以宣布一个水位线，水位线以下的写入一律非法。**

### 3.3 GDPR「被遗忘权」的删除实现要点

**GDPR 原文** —— [Art. 17 GDPR – Right to erasure](https://gdpr-info.eu/art-17-gdpr/)（HTTP 200，已fetch）：

- 第 1 款：数据主体有权**不受不当迟延地（without undue delay）**从控制者处获得其个人数据的删除，控制者**有义务不受不当迟延地删除**。
- 第 3 款给出**五条例外**，其中与本项目最相关的是：**为公共利益的归档、科学或历史研究或统计目的**（依 Art. 89(1)），且**删除很可能使该处理目的无法实现或严重受损**；以及**为设立、行使或抗辩法律主张**所必需。
- 第 2 款：若控制者已**公开**该个人数据，须采取合理步骤（含技术措施）通知其他正在处理该数据的控制者删除其链接、副本或复制件。

**ICO 实务指引** —— [Right to erasure](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/individual-rights/individual-rights/right-to-erasure/)（HTTP 200，已fetch）：

- 「**你有 1 个月**回应删除请求」（at a glance）；期限**从收到请求当天起算**，到「下个月的对应日历日期」；若下月无对应日期（如 3 月 31 日 → 4 月 30 日），则为下月最后一天。
- **可以再延长 2 个月**（复杂请求或同一人多次请求），但必须在收到请求后 1 个月内**先告知本人并说明理由**。
- 「**删除请求可以口头或书面提出**」，且**不需要包含「删除请求」或「第 17 条」这类措辞**。
- **最重要的一条（正是本项目「受理 ≠ 完成」的合规依据）**：关于备份系统 —— 「如果收到有效的删除请求且无豁免适用，你**必须采取措施确保从备份系统以及在线系统中删除**。这些措施取决于你的具体情况、保留计划与技术机制。」并且：**「在线系统里的删除请求可能可以立即完成，但数据会在备份环境中留存一段时间直到被覆盖。」** 关键在于**让备份数据『置于无法使用（beyond use）』**，即便它不能被立即覆盖；必须确保**不再为任何其他目的使用备份中的数据**。
- 「**你必须向个人明确说明**当其删除请求被履行后其数据会怎样，包括在备份系统方面。」

→ **对「受理 ≠ 立即物理删除」的合规解释**，可以直接这样表述（有据可依）：GDPR 要求的是**不受不当迟延**删除（GDPR Art.17(1)），ICO 把它操作化为**1 个月（可延长 2 个月）内回应**，并**明确承认**「在线立即删、备份稍后覆盖」是正常且合规的，条件是**备份中的数据被置于无法使用**。因此本项目的 `talent_deletion_request.status='pending'` + `downstream_confirmed=false` + `completed_at IS NULL`（`docs/11` §4、`api.py:164-200`）**不是偷懒，而是把合规要求如实建模**：`downstream_confirmed=false` 正是「备份/下游副本尚未确认处置完毕」的机器可读表达。反过来，`completedAt` 必须在 `downstream_confirmed=true` 之后才非空（「**不能先显示完成再等下游**」，`docs/11` §4），这是防止对数据主体作出不实陈述。

> ⚠️ 边界：本项目是**技术验证项目**，`access_tier='T2'` 目前**只是标签不是拦截**（README 路线图 T21 明说）。上面这些是「如何把合规要求建模进数据结构」，**不构成**任何合规认证或法律意见。

### 3.4 测试金字塔与 E2E 的取舍；Playwright 该不该引入

**Martin Fowler / Ham Vocke：The Practical Test Pyramid** —— <https://martinfowler.com/articles/practical-test-pyramid.html>（HTTP 200，已fetch）：

- 金字塔的两条要点：**写不同粒度的测试**；**越高层测试数量越少**。「写**大量**小而快的单元测试，写**一些**粗粒度测试，写**极少**高层端到端测试」；当心变成「测试冰淇淋甜筒（test ice-cream cone）」，那会**极难维护且跑得太久**。
- 关于 E2E 的原话级结论：「端到端测试**出了名地不稳定（notoriously flaky）**，经常因为意外且不可预见的原因失败。**它们的失败往往是假阳性（false positive）。**」并且「端到端测试需要**大量维护**且**跑得相当慢**。**由于维护成本高，你应当把端到端测试的数量降到最低限度。**」
- 数据库集成测试的定位：数据库集成测试就是**启动一个真实数据库、连上去**（文中示例为省事用了内存 H2，**这也是一处可批评的失真**：H2 ≠ 生产用的 PostgreSQL）。
- 一条极有启发的**替代路线**：「避免走图形界面可以做出比完整 E2E 更少不稳定的测试，同时仍覆盖应用栈的很大一部分……一个**皮下测试（Subcutaneous Test）**，正好在图形界面之下测试，能在不牺牲太多信心的前提下走得很远。」

**Playwright Python** —— <https://playwright.dev/python/docs/intro>（HTTP 200，已fetch）：

- 安装是**两步**：`pip install pytest-playwright`，然后 **`playwright install`** —— 也就是**默认会下载浏览器二进制**（Chromium/WebKit/Firefox）。
- 系统要求：**Python 3.8+**；**Windows 11+、Windows Server 2019+ 或 WSL**。**本项目环境实测：Windows 11 Home China，build 22621 —— 满足**（`build 22621` 即 22H2 / Windows 11，≥ 22621 = Windows 11 2022 Update）。
- 也提供 pytest 插件（`pytest-playwright`）与库模式。

**本项目的结论：不引入 Playwright / Cypress。** 理由是具体的、不是偷懒：

| 判据 | 本项目事实 |
|---|---|
| 被测界面有多少「只有真浏览器才能验证」的东西？ | **零 JS**。两个站点是**零 JS、零 CDN** 的内联 HTML/SVG（README 架构节、设计纪律第 9 条）。没有 JS，就没有「点击后 JS 改状态」这类只能靠 DOM 驱动才能观测的行为 |
| 浏览器驱动的成本 | `playwright install` 要下载数百 MB 浏览器二进制；本项目约束是「Windows 无管理员、无 winget、不能用 curl、只能 Python urllib 下载」——下载链路本身就是一个脆弱点 |
| 现有覆盖已经足够吗？ | 已有 `form_server_test.py`（30 项）用**标准库 `urllib`** 真的发 HTTP、真的 POST、真的断言数据库（`form_server_test.py:157-194`）。这已经是一个**皮下测试**：它在图形界面之下、在 HTTP 之上，覆盖了服务端渲染 + 表单解析 + 数据库落库 |
| 金字塔怎么说 | 上述 Fowler 原文明确支持「用皮下测试替代完整 E2E」 |

**反向条件（什么时候应该重新评估）**：一旦满足下列任一条件，就值得重新评估引入浏览器驱动：① 页面引入 JS 且状态只在客户端变化；② 需要验证**布局/可访问性**（Fowler 指出布局可用截图对比，但「好不好看」无法自动断言）；③ 出现只在真实浏览器里复现的缺陷。目前三条都不成立。

**`playwright` 的替代品：本项目已有的三条「皮下测试」通道**（全都零新增依赖）：
1. `urllib.request`（标准库）→ 打真实 HTTP（`form_server_test.py` 现成范式）；
2. `psycopg` 直连 → 断言数据库最终状态（`_harness.py` 的 `connect/q1/q`）；
3. `code/bridge/api.py` 的 `Api` 类被设计成**纯逻辑层、不依赖 HTTP**（`api.py:64-65` 的注释原文：「纯逻辑层：不依赖 HTTP，便于单测直接调用」）→ 测试可以绕过 HTTP 直接调业务，这正是金字塔中低层的形态。

### 3.5 数据夹具的两条路子

| | 路子 A：`--seed` 生成 | 路子 B：事务内写入后回滚 |
|---|---|---|
| 本项目实例 | `code/demo/app.py --seed 30` / `--reset`；`code/demo/console.py --seed 12` / `--reset`；`ops/fixtures/*.py` | `ops/tests/dynamic_model_test.py`（「全程单事务，结束即回滚」，`main()` 里 `conn.autocommit=False`，末尾 `conn.rollback()`，`H.report(note="（事务已回滚，库中无残留）")`）；`ops/tests/smoke_schema.sql`（事务内 ROLLBACK）；`ops/tests/regression_guards.sql` |
| 优点 | 可以被**人**看见（浏览器打开就有数据）；跨进程可见，适合演示 | **不可污染库**，可反复跑；teardown 由数据库保证，不靠人写清理 SQL；**顺序无关**（每次都是干净起点） |
| 缺点 | 必须有**与构造覆盖面相等的清理**，否则就是净增长（本项目问题 #40 就是这么来的） | 只能在**同一连接**内验证；别的进程（浏览器、另一个 HTTP 服务）**看不到**未提交的数据；不能用来验证「门户页面上能不能看到」 |
| PostgreSQL 手册依据 | — | [3.4. Transactions](https://www.postgresql.org/docs/16/tutorial-transactions.html)（HTTP 200，已fetch）：「事务在**其他事务看来**要么完全发生要么完全不发生」；`ROLLBACK` 取代 `COMMIT` 时「**到目前为止的所有更新都会被取消**」；且「所有这一切都发生在事务块内部，**对其他数据库会话都不可见**」 |

**关键取舍（本项目的具体建议）**：mock 窗口是一个**给人看的 HTTP 页面**，所以：
- **交互式演示**必须用路子 A（`:8083` 开发者模式或 `:8080`），因为页面必须能读到已提交的数据；
- **回归测试**应当用**混合**：写路径用真实提交（否则测不到 HTTP 层与提交行为），但**断言与清理包在一个受控流程里**，并用 §2.4 J13 的前缀断言 + §2.1 J4 的孤儿检测兜底。
- `dynamic_model_test.py` 的路子 B **不能**直接照搬到 mock 窗口上：未提交的数据对 HTTP 服务进程不可见（上面的手册原文就是原因）。这一点必须在方案里写清楚，否则会写出一个「测试通过但页面永远空白」的怪物。

### 3.6 测试替身的边界（test double 与真实写入）

**Martin Fowler：Mocks Aren't Stubs** —— <https://martinfowler.com/articles/mocksArentStubs.html>（本次以搜索结果形式确认该文存在并给出「Mocks Aren't Stubs」标题与 `#TestIsolation` 锚点；**正文未逐字 fetch**，故此处结论标注为**通用共识而非逐字引文**【未验证】）：核心区分是 **state verification（断言状态）** 与 **behavior / interaction verification（断言调用顺序与次数）**，并主张过度 mock 会让测试通过而真实系统坏掉。

**Google：Software Engineering at Google 第 13 章「Test Doubles」** —— <https://abseil.io/resources/swe-book/html/ch13.html>（本次仅通过搜索结果确认章节名与主题存在；**正文未 fetch**）：给出 test double 的定义与 stub/fake/mock 的分类，并讨论「宁可要能工作的真实实现（fake）也不要 mock」。**逐字结论未验证**【未验证】。

→ **落到本项目，这条边界非常清楚，而且本项目已经画对了**：

| 该被替身化的 | 不该被替身化的 |
|---|---|
| 微信登录、CloudBase 云函数（`docs/11` §1 的分工：小程序 → CloudBase → 本服务 → PostgreSQL） | **PostgreSQL**（本项目的全部价值在于「数据库本身就是分析平台」，把它换成 H2/SQLite 就没测到任何东西） |
| 外部岗位来源（当前 `crosswalk` 故意为空，`docs/11` §8） | **本项目的 `mt.*` schema、触发器、约束、`add_dimension`/`set_value`**（这些恰恰是最容易坏、也最值钱的部分） |
| Bearer 令牌的发放方（开发时随机生成并打印，`api.py:56`） | **HTTP 层与表单解析**（用标准库 `urllib` 真打） |

一句话：**本项目应当「在 HTTP 之上用真东西，在组织边界之外用替身」。** 唯一允许的替身是「小程序/CloudBase 这一侧」，而 mock 窗口就是它的替身 —— **但它替身的只是「界面」，不是「数据库」。**

2. **未授权不是错误，但派生画像必须拒绝**：`api.py:119-122` —— 无有效 `CP1` 时 `matches` 返回 `CONSENT_REQUIRED`；`exchange.py:193-202` —— 撤回 `CP1` 后再写入分析产物（`facts`/`skillClaims`）直接抛 `CONSENT_REQUIRED`。
3. **页面必须让「不给授权」也能走完注册**（否则就是在用 UI 强迫同意）。正确行为：`personalAnalysis=false` 时注册仍成功，但**不产生任何分析产物**，并且后续查匹配报 `CONSENT_REQUIRED`（现成断言 `bridge_test.py:223-231`）。**这一条应当成为新测试的核心用例之一。**

### 4.3 提交后怎么「当场证明写进去了」

三层证据，从弱到强，页面上由弱到强排列：

| 层 | 证据 | 强度 |
|---|---|---|
| L1 | 页面回显「已写入，person_id = `per_regmock_xxxx`」 | **最弱**（这一层单独存在就是假测试，§5 反模式 #1） |
| L2 | 同页面**回显从数据库读回来的值**：`SELECT mt.profile_json('person', :pid)` 的结果按字段逐项显示「提交值 vs 库中值」 | 中（读回的是真库） |
| L3 | **独立复核按钮**：一个「用独立连接重新数一遍」的动作，显示 `person`/`field_value`/`external_identity` 的 `count(*)` 前后对比 + 孤儿检测结果 | **强**（跨连接、跨应用层） |

**L3 应当是页面上的一个按钮而不是自动的**：理由是「独立复核」的价值在于它**不共用**提交时的那个连接与事务。这正是 `portal_dev.py` 已有 `ddl_evidence(before, after)` 模式的精神（`portal_dev.py:212-230`）：**把证据做成一张可读的表，而不是一句「成功」。**

建议 L3 的展示内容（全部是 §2 的可执行判据）：
- `person` 计数：写前 / 写后 / 差值；
- `field_value` 计数：同上；
- **孤儿行检测**总数（§2.1 J4）；
- `sync_event` 里本次 `external_event_id` 的行数（幂等证据，§2.1 J2）；
- 本次操作是否做了 DDL：**基础表数 82 / person 列数 16 必须不变**（【实测】这两个数当前是 82 与 16；范式同 `ddl_counter()`/`ddl_evidence()`，`portal_dev.py:196-230`）。

### 4.4 删除怎么设计

这是全局最难的一节，因为本项目有**两套互不兼容的删除语义**。必须先选边并写下理由。

**现状（【读码】+【实测】）**：

| 机制 | 位置 | 语义 |
|---|---|---|
| bridge 删除 | `api.py:164-183` `request_deletion` | **软删**：`external_identity.status='deleting'` + `person.status='restricted'`；写 `talent_deletion_request(status='pending')`；**受理 ≠ 完成**（`completed_at` 需 `downstream_confirmed=true`）；事后由 `tombstone` 阻断迟到写入 |
| 动态建模删除 | `008_dynamic_model.sql:390-422` `delete_instance` | **有 `status` 列就软删置 `withdrawn` 并顺手删 `field_value`；否则硬删** |
| 硬删 `person` | 数据库层 | **会被 29 个 `NO ACTION` 外键直接拒绝**（【实测】） |

**推荐方案：删除分三档，按「谁有权删、删的是谁」区分。**

| 档 | 名称 | 操作者 | 删谁 | 机制 | 墓碑 |
|---|---|---|---|---|---|
| D-A | **撤回**（用户自助） | 页面上用户自己 | 自己的分析授权 | `POST /v1/persons/{pid}/consent {granted:false}` → `person.status='restricted'`，`CP1` 新增一条 `revoked_at=now()` 的 `consent_record` | 不写 |
| D-B | **注销资料**（用户自助，异步） | 页面上用户自己 | 自己整份资料 | `POST /v1/persons/{pid}/deletion` → 受理（`pending`）→ 显示「处理中」→ 状态查询原样返回 `completedAt: null` | **写**（`deleted_through_version` = 当前 `last_seen_version`） |
| D-C | **硬清理**（仅测试/运维，必须带围栏） | 只在回归测试或显式运维动作里 | **仅限本测试前缀** | 自上而下按外键序删，或整段事务回滚 | 不写 |

**为什么 D-B 要写墓碑**（这是本方案最该强调的一点）：删除之后，**小程序那边可能还在重试投递**。没有墓碑，一份迟到的 `profile_upsert` 就会**把已删除的人复活**。墓碑的语义是「至版本 N 为止的写入一律非法」，【实测】已验证它真的会拦、且只拦该拦的（§2.3 J8）。

**为什么 D-C 必须限制在测试前缀**：`bridge_test.py:64-93` 的 `cleanup()` 是现成范式，它的注释原文就是纪律：「按外键顺序删除，且**范围严格限定在本来源**，不误伤其他来源的遗留数据。」它按 `source_system` 与 `person_id` 双条件限定，**没有用 `LIKE '前缀%'` 去猜**。注意它列的 17 条 DELETE 里有 4 张表是按 `source_system` 而非 `person_id` 限定的（`response_session`/`experience_episode`/`sync_event`/`talent_deletion_request`）—— 这是因为这几张表带来源列，按来源清更准确。

**异步受理在页面上怎么体现**（不能只写「已删除」）：
- 提交删除后，页面显示：`状态：pending`、`完成时间：（无）`、`下游确认：否`，并给出**原始字段名**（`completedAt` / `downstreamConfirmed`），让外行也能看到「系统还没说删完了」；
- 提供一个「刷新状态」按钮，走 `GET /v1/persons/{pid}/deletion/{rid}`；
- 页面上要有一句人话解释，理由见 §3.3：**合规上「在线立即删、备份稍后覆盖」是允许的，前提是备份数据被置于无法使用**。这句话必须来自文档而不是我编的（ICO 原文见 §3.3）。

**顺带标注一个真实的缺口**【读码】：目前**没有任何代码路径**会把 `talent_deletion_request.status` 从 `pending` 推到 `completed`，也没有任何代码会把 `downstream_confirmed` 置真。`api.py:186-200` 的 `deletion_status` 只是**读**这张表。所以 D-B 目前只能停在 `pending` —— 这是**设计上的诚实**（受理 ≠ 完成），但 mock 窗口若要演示「跑完整条链」，就需要一个人工的、带权限提示的「模拟下游确认」动作，**且必须在 UI 上明确标注它是模拟的**。

### 4.5 ID 命名空间

**现状（【实测】真库前缀分布）**：

| 前缀 | 当前行数 | 用途（来源） |
|---|---|---|
| `per_mock_%` | **120** | 合成人才档案（README「数据来源声明」） |
| `per_real_%` | **3** | 真实公开案例（`docs/16`） |
| `per_live_%` | **0** | 业务控制台演示人才（`console.py:51` `LIVE_PREFIX`） |
| `per_demo%` | **0** | 表单站点（`app.py:75/90`；注意是 `%` 不是 `_%`） |
| `per_dmtest%` | **0** | 动态建模测试（`dynamic_model_test.py:122`） |
| 其它 | **0** | — |
| **合计** | **123** | — |

**新的一套该用什么**：**`per_regmock_`** + `subject_code = 'MT-REGMOCK-####'` + `source_system = 'regmock_<token>'`。（为什么不叫更顺口的 `per_mockreg_`，见下。）

**怎么保证不撞车**：先看一眼第一个候选为什么**被否掉**，这是本文查到的最危险的一处。

候选 `per_mockreg_` 看起来「只是多了一个 `r`」，但 `_` 在 `LIKE` 里是**单字符通配符**：

```sql
-- 【实测】在真库上跑过，逐条抄录：
SELECT 'per_mockreg_x' LIKE 'per_mock_%';    -- true   ← 危险！会被 per_mock_ 的清理误伤
SELECT 'per_regmock_x' LIKE 'per_mock_%';    -- false
SELECT 'per_regmock_x' LIKE 'per_mock%';     -- false
SELECT 'per_regmock_x' LIKE 'per_demo%';     -- false
SELECT 'per_regmock_x' LIKE 'per_live_%';    -- false
SELECT 'per_regmock_x' LIKE 'per_dmtest_%';  -- false
SELECT 'per_regmock_x' LIKE 'per_real_%';    -- false
```

原因：`LIKE 'per_mock_%'` 里的 `_` 先匹配掉 `r`，`%` 再匹配 `eg_x` —— **于是成立**。若新套件叫 `per_mockreg_*`，而将来有人用 `LIKE 'per_mock_%'` 清理合成档案（120 份），就会**连带删掉 mock 窗口的注册数据**；反过来也一样。**这正是 §5 反模式 #3 的完美案例，而且它藏在一个字符里。**

**结论：用 `per_regmock_`。**【实测】它对上表**全部 6 个现有清理模式都不匹配**，因此不可能被任何现有逻辑误伤，也不可能误伤它们。

三条收尾纪律（缺一不可）：
1. **前缀不得与任何现有前缀互为前缀** —— 上表就是验收方法，新前缀必须对全部现有模式返回 `false`；
2. **清理范围用「构造时用过的同一组常量」驱动**，不手抄字符串（见 §2.4 J13）；
3. **回归测试开场先断言命名空间是空的**：`SELECT count(*) FROM person WHERE person_id LIKE 'per_regmock%'` 必须为 0。若不为 0，说明上一轮没清干净 —— **此时应当直接失败并报出剩余 ID，而不是默默继续**（否则又变成问题 #40）。

### 4.6 怎么把「真实增删」接进已有回归且不污染库

**接入点**：`ops/tests/run_all.py` 的 `STEPS` 列表（`run_all.py:62-95`）。建议新增第 17 套 `注册与增删端到端`，`kind="py"`，`tier="full"`（因为它有真实提交，比 fast 档的纯事务套件贵）。

**副作用分类怎么填**（这是 `run_all.py` 的既有约定，填错会导致收尾动作不补）：
- 若套件**自清且清干净** → `edge="clean"`，不需收尾动作；
- ⚠️ **不要**填 `derived` 或 `tree`（那是给会重建派生层/拆职业树的套件用的），否则 `run_all.py:216-230` 会自动补上 R1/R2，白白多花 6.5 秒。

**「不污染库」的两条路线，建议混用**：

| 路线 | 适用 | 本项目证据 |
|---|---|---|
| **B1 事务回滚** | 纯数据库侧断言（不经过 HTTP，没有第二个进程要看数据） | `dynamic_model_test.py` 全程单事务 + `conn.rollback()` + 报告行注明「事务已回滚，库中无残留」 |
| **B2 写-验-清** | 必须经过 HTTP/浏览器的部分（mock 窗口的提交） | `form_server_test.py`（真提交再断言再清）、`bridge_test.py`（`cleanup()` 按来源精确清理） |

**建议的套件骨架**（伪代码，**不落地为代码**）：

```
[W1] 前置：断言 per_regmock% 命名空间为空（不为空 → 直接 FAIL 并列出残留 ID）
[W2] 读 schema：GET /mockreg → 断言字段数与 v_form_schema 的 count 相等（精确值，不是"大于 0"）
[W3] 真实加入：POST /mockreg（含 consent=CP1 勾选）→ 303
      直连断言：person LIKE 'per_regmock%' 计数 = 1
                field_value 中该 subject_id 的字段数 = 提交的字段数
                逐字段比对 value_code / value_codes / value_num（照抄 form_server_test.py:177-194 的做法）
[W4] 幂等：用同一 eventId/submissionId 重放 → 计数仍为 1，且返回 idempotent=true
[W5] consent 反面：POST 不勾 CP1 → 注册成功但无分析产物；GET matches → CONSENT_REQUIRED
[W6] 孤儿检测：跑 §2.1 J4 的两段查询 → 期望 0（当前库 0，本套件跑完仍应为 0）
[W7] 删除受理：POST deletion → 断言 status='pending' 且 completedAt IS NULL
[W8] 墓碑：按 §2.3 J8 的方式造墓碑 → 断言迟到 upsert 报错且 sync_event 无该行 + v6 对照通过
[W9] 硬清理 + 断言清理覆盖面等于构造覆盖面（6 张表、2 个前缀，全部 == 0）
[R ] 报告行：PASS n / FAIL m（格式由 _harness.report() 统一产出，格式不能改）
```

**几处必须照抄的既有约定**（否则会破坏现有基础设施）：
- 汇总行必须走 `H.report()`（`_harness.py:79-96`），因为 `run_all.py:109` 用正则 `PASS\s+(\d+)\s*项[，,]\s*FAIL\s+(\d+)\s*项` 解析；
- 断言用 `H.check(cond, msg)`（`_harness.py:42`）；
- 连库用 `H.connect(DSN)` + `H.q1/q`（`_harness.py:59-76`）；
- 测试端口避开在用的 8080–8083 与 8097，按现有约定取 **8097–8104**（README「常见问题排查」：测试各自用 8097–8104）；
- 每个断言都断言**数据库状态**，不断言页面文案（README 贡献指南第 4 条）。

### 4.7 明确**不该做**的

| 不该做 | 为什么 | 依据 |
|---|---|---|
| ❌ 为测试引入 Playwright / Cypress 等 JS 抓取框架 | 本项目两个站点**零 JS**，没有「只有真浏览器才能验证」的行为；且 `playwright install` 要下载浏览器二进制，而本机约束是「无管理员、无 winget、不能用 curl、只能 Python urllib 下载」。已有 `urllib` 的皮下测试范式足够 | §3.4；README 设计纪律第 9 条「零 JS / 零 CDN」 |
| ❌ 让 mock 窗口**直接写 `person` 表绕过 bridge**（除非有明确理由并写下来） | 绕过 bridge 就绕过了：R1 身份标识深度扫描、R3 幂等、R4 版本门、R5 墓碑、R6 授权门、R8 crosswalk 不臆造。**这六条正好是这次要验证的东西** —— 绕过它们再写一个页面，测到的只是一个 insert | `code/bridge/exchange.py` 全文；`docs/11` §2 |
| ❌ 让 mock 窗口走 `:8082` 只读门户 | 会摧毁「门户只读可被证明」这条纪律（README 设计纪律第 8 条）；而且 PostgreSQL 的 `READ ONLY` 事务会**直接拒绝**写入，页面只会报错 | 3.4 已确认 `SET TRANSACTION READ ONLY` 禁止 `INSERT/UPDATE/DELETE/MERGE`、`COPY FROM`、`CREATE/ALTER/DROP`、`COMMENT/GRANT/REVOKE/TRUNCATE` |
| ❌ 为了「让删除看起来成功」而硬删 `person` | 会被 29 个 `NO ACTION` 外键拒绝（【实测】）；即便想办法绕过，`field_value.subject_id` **没有外键**，会直接留下孤儿（【实测】已验证会留下） | §2.1 J3/J4 |
| ❌ 用 `TRUNCATE` 做清理 | 会**绕过** `mt.guard_tombstone()`（它是 `BEFORE INSERT` 触发器，TRUNCATE 不触发行级 DML 触发器），也会绕过 `change_log` 审计；而且 `TRUNCATE` 需要更高权限、在有外键引用时还需要 `CASCADE`（会波及 29 张子表） | `010_bridge.sql:208-210`；`change_log` 是触发器维护的 |
| ❌ 用 `LIKE 'per_mock%'` 或 `LIKE 'per_mock_%'` 做清理 | `_` 是单字符通配符，`'per_mockreg_x' LIKE 'per_mock_%'` 实测为 **true** —— 会**误伤** mock 窗口的数据（或反之）—— 见 §4.5 的前缀陷阱 | §4.5 |
| ❌ 测试自己造数据、自己断言、自己清理，全程不碰 HTTP | 那就成了一个只测 `INSERT` 的单元测试，无法回答「注册流程是否真的通」 | §3.4 金字塔：这个需求的价值恰恰在高层 |
| ❌ 把测试写进生产/演示库且没有清理 | 本项目有活生生的前车之鉴：问题 #40，每跑一次回归净增 1 个人 | `console.py:171-176` |
| ❌ 断言页面文案 | 文案会变、数据不该变（README 贡献指南第 4 条已明确）。现有测试的做法是断言 `count(*)` 或 `value_code` | README 贡献指南第 4 条 |
| ❌ 用 `recovery` / 备份恢复来「证明删干净了」 | `backup_test.py` 实测 **348 秒**，占 `run_all.py` 完整档 77% 的耗时；把它当清理手段会让回归不可用 | `run_all.py:82` 的 COST 注释 |

## 5. 反模式与「假测试」清单

按「最该警惕」排序。每条都给出**识别信号**与**修法**。

| # | 反模式 | 识别信号 | 修法 |
|---|---|---|---|
| 1 | **断言「提交成功」字样** | 测试里有 `assert "成功" in html` 或 `assert resp["ok"] is True` 而**没有**任何 `count(*)` 断言 | 加 §2.1 J1（精确计数）与 §2.2 J5（独立连接复核）。本项目 README 已把「断言数据库状态，不断言页面文案」写成纪律，**这是最重要的一条** |
| 2 | **删了主表、留下孤儿从属行** | 测试只 `DELETE FROM person`，从不检查子表 | 【实测】本库 `field_value.subject_id` **无外键**，直接删 person **不会**报错、值会留下。必须加 §2.1 J4 的孤儿检测（29 张子表全扫 + `field_value` 悬空扫描） |
| 3 | **清理使用 `LIKE '前缀%'` 却删到别人的数据**（或反之清不干净） | 代码里出现裸 `LIKE 'per_xxx%'`，且该前缀与别的功能前缀**互为前缀** | §4.5：新前缀取 `per_regmock_`（与 `per_mock_` 不构成前缀关系）；清理范围由**构造时用过的同一组常量**驱动；开场断言命名空间为空 |
| 4 | **测试自己造数据、自己断言**（自证循环） | 测试先 `INSERT` 期望值，然后断言读到该值 —— 没经过任何被测代码 | 至少让**一条**路径穿过真实边界：HTTP（`urllib`）、bridge（`Api.exchange`）或 `mt.*` 函数。参照 `form_server_test.py` 的做法：POST → 再直连断言 |
| 5 | **幂等只断言「第二次也成功」** | 没有「人数仍为 1」的断言 | 加 §2.1 J2。**「第二次返回 200」与「没有创建第二个人」是两件事** —— `exchange.py:155-170` 的提前返回确实保证了后者，但断言必须写出来 |
| 6 | **墓碑只断言「报错了」** | 只 `assert r["code"] == "PROFILE_DELETING"` | 【读码】现有 `bridge_test.py:244-257` 的 T11 只打到应用层 R5，**触发器从未被执行**。要加 §2.3 J8 的三条合一断言（报错 + 没落库 + 高版本对照能通过） |

| 8 | **用乐观断言的计数** | `assert count >= 1`、`assert count > 0`、`assert n_vals >= 6` | 改成精确值。⚠️ 注意：`form_server_test.py:184` **确实**用了 `n_vals >= 6`（不是 `== 6`）—— 这是一个**现存的可改进点**，因为它无法发现「多写了一个字段」这类错误。新套件不要照抄这个弱断言 |
| 9 | **测试之间有隐式顺序依赖** | 单独跑某一套会失败；或套件 A 通过、A 之后再跑 B 才通过 | 每条 fixture 自带前置清理（参照 `bridge_test.py:101-102` 开场先 `cleanup(c)`）；能用事务回滚的用回滚（`dynamic_model_test.py`），做到**顺序无关** |
| 10 | **清理不是 teardown，而是「我下次跑的时候顺便清」** | 清理逻辑写在 `main()` 开头而不是 `finally` | 现在的 `bridge_test.py` 在**开头**和**结尾**都清理（`:101-102` 与 `:322-323`）—— 这是对的做法（双保险），新套件照做 |
| 11 | **把 mock 窗口写进真实数据的地盘** | 新前缀与 `per_real_%`（真实公开人物，3 份）或 `per_mock_%`（120 份合成）混在一起 | §4.5：独立前缀 + `source_system` 独立 + `subject_code` 独立（`MT-REGMOCK-`），三层隔离；并且**永远不要**对 `per_real_%` 做任何写操作（README 许可章节：`per_real_*` 不得用于商业画像或对外发布） |
