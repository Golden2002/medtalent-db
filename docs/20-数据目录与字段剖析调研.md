# 20 · 数据目录与字段剖析调研

> 本轮调研的触发点是用户（数据库外行）的一句原话，它是本文的**唯一验收标准**：
>
> > 当前页面中，最重要的是数据库内容的展示，我能看到以 sql 存储的数据的字段名，数量，能够分类统计，能够检索
>
> 这句话翻译成专业能力是 **数据目录（Data Catalog）+ 列级剖析（Column Profiling）+ 检索（Search）+ 分类聚合（Group-by / Roll-up）**。
> 但本文不照抄这个翻译 —— 而是去查"看数据"这件事在成熟产品里的标准做法，
> 再说清**他没想到但必须有**的部分（§1 末列）。
>
> **承接关系**：[`docs/17-界面与数据展示优化调研.md`](17-界面与数据展示优化调研.md) 已覆盖 **界面/视觉/表格/树/图表可访问性**，
> 并已给出结论"不做虚拟滚动、不做 treemap"。本文**不重复**那 17 条落地清单，
> 只做它没做的那一层：**数据本身怎么被看**（目录、剖析、检索、权限标签）。

## 0. 方法与可核查性声明

### 0.1 三条硬约束（每条建议都要过这三关）

| 约束 | 具体含义 | 后果 |
|---|---|---|
| **零 JS / 零 CDN** | 服务端渲染（`http.server`），图表是内联 SVG，拷走一个 HTML 就能离线看 | 任何"前端算"的方案都要付代价 |
| **数字必须来自真实查询** | 页面上每个数字都必须是真库跑的；不许写死、不许演示假数据 | 剖析指标必须是真 SQL 算出来的 |
| **行数一律精确 `count(*)`** | 本项目明令不用 `pg_class.reltuples` 估算（README 设计纪律第 6 条） | 这条纪律直接决定了 §5 的实时/物化分界 |

每条建议标注 **(A) 纯 HTML/CSS/SVG 可实现 / (B) 需少量渐进增强 JS / (C) 需要重写渲染层**。
对 (B)(C) 一律写清代价：**会失去**离线可看、零依赖、可断言、审计友好。

## 1. "看数据"的标准能力清单

这张表是本文的核心。列"回答什么问题"是为了让**外行也能判断自己要不要它** —— 因为用户的原话只点了四项，
而成熟产品（§2）实际上都提供下面这一整套。

### 1.1 表级：资产目录

| 能力 | 回答什么问题 | 本项目现状 |
|---|---|---|
| 表 / 视图 / 物化视图 / 外表的**分型清单** | "我有哪些数据？哪些是存的、哪些是算出来的？" | **半**。`view_schema()`（`portal.py:839`）按 `DOMAINS` 分域列基础表，视图单列一块；`load_meta()`（`portal.py:157`）已读 `relkind='r'/'v'/'m'`，但**库里确实没有物化视图**，外表未涉及 |
| 表级**行数** | "这张表有多少数据？值不值得看？" | **有**。`load_meta()`（`portal.py:215-227`）对 97 个对象逐个 `count(*)`（实测 0.67 s） |
| 表级**列数** | "这张表有多宽？" | **有**。`load_meta()`（`portal.py:229-233`）由 `pg_attribute` 计数 |
| 表级**大小** | "它占多少空间？导出要不要紧？" | **无**。`view_schema()` 的 6 列表头只有 列/行数/约束/索引/触发器，**没有字节数** |
| **主键** | "这行怎么唯一标识？能不能点进去看？" | **半**。`load_meta()` 抽了 `m["pk"]`（`portal.py:239-240`），但表清单页不显示；`view_entity()` 依赖它 |
| **外键** | "表之间怎么连的？" | **半**。`view_table()` 有"被谁引用"反查表（`portal.py:943-950`）和约束表；但**表清单页没有出边/入边列**，跨表导航要一张张点进去 |
| **索引** | "哪些查询会快？" | **有**。`view_table()`（`portal.py:938-939`） |
| **约束**（PK/FK/UNIQUE/CHECK/EXCLUDE） | "什么写法会被数据库拒绝？" | **有**。`view_table()`（`portal.py:930-936`） |
| **注释 / 描述** | "这个字段到底是干什么的？" | **有**。列注释走 `col_description`（`portal.py:173`）、表注释走 `obj_description`（`portal.py:163`） |
| **属主（owner）** | "出问题找谁？" | **无**。`load_meta()` 未读 `pg_class.relowner` |
| **最后变更时间 / 最后 ANALYZE 时间** | "这数据是新的还是旧的？" | **半**。`view_quality()`（`portal.py:3680-3686`）对 6 张关键表 `max(时间列)`，**不是表级通用**，且没有 `pg_stat_user_tables` 那条路 |
| **数据域 / 主题分类** | "按业务主题怎么分？" | **有**。`DOMAIN_TABLES` + `domain_of()`（`portal.py:119-123`） |

### 1.2 列级剖析（Column Profiling）—— 用户最想要、本项目最缺的一层

| 能力 | 回答什么问题 | 本项目现状 |
|---|---|---|
| **空值数 / 空值率** | "这个字段有数据吗？还是只是建了结构？" | **半**。**只有两处、且都不是全库**：`table_profile_blocks()`（`portal.py:1642-1673`）在**每张表页**算"列空值数 Top 15"；`view_quality()`（`portal.py:3616-3632`）对 **8 张固定关键表**算全列空值率 |
| **去重值个数（基数 / cardinality）** | "这是枚举列还是自由文本？能不能当维度用？" | **几乎无**。全站唯一接近的是 `/search` 的 `field_catalog.cardinality` 列（**登记值，不是实测值**，`portal.py:1125`）。`field_catalog` 里那个 `cardinality` 是**人工登记的声明**，不是 `count(DISTINCT)` 算出来的 |
| **最小值 / 最大值** | "取值范围是多少？刻度对不对？" | **无**（列级）。`ANALYSES` 里的 a1 只有薪资 min/max 两列（`portal.py:1229-1230`） |
| **分位数（中位/四分位）** | "典型值是多少？长尾有多长？" | **无**。`charts.py` 没有箱线图函数 |
| **Top-K 值 + 频次** | "最常见的几个值是什么？" | **无**。`ANALYSES`/`TALENT_ANALYSES` 里是**人工写死的固定聚合**，不是"任意列都能看 Top-K" |
| **值分布直方图** | "分布是长尾还是双峰？" | **半**。`charts.py:histogram()` 存在，但只在 `/viz` 的**固定面板**里用；表页/字段页**看不到任意列自己的分布** |
| **字符串长度分布** | "有没有异常长/短的脏值？" | **无** |
| **编码 / 单位 / 枚举域** | "这一列的数字是什么单位？码值是什么意思？" | **半**。`field_catalog` 有 `data_type`、`code_table_id`、`unit`（如有）；`code_value` 有 584 条中文标签，`lbl()`（`portal.py:263`）能把码翻成中文。但**字段页没有把它们合成"这一列的枚举域 + 值标签"的一块** |
| **缺失码语义** | "0 是真的 0，还是'没问'？" | **无**（本项目恰恰是"空就是空"，不给 0/9/99 编码 —— 参见 §2.2 与 §6.5 的取舍） |

### 1.3 分类统计与下钻

| 能力 | 回答什么问题 | 本项目现状 |
|---|---|---|
| 按维度聚合 + **Top-N** | "哪个岗位族最多？" | **有**。`ANALYSES`（`portal.py:1222-1333`，8 个）、`TALENT_ANALYSES`（`portal.py:1786+`）、`page_analysis()`（`portal.py:1676`）按页分派、`bar_table()`（`portal.py:1766`）画横条排行 |
| **任意**表 × 任意维度自助聚合 | "我想按我没预料到的那个列看看" | **有（优秀）**。`/viz/build` → `build_sql()`（`portal_viz.py:462`），选表→维度→度量→聚合，表名列名先与系统目录比对再用 `sql.Identifier` 转义 |
| **交叉表（crosstab）** | "两个维度一起看，谁和谁相关？" | **有**。`charts.py:heatmap()`；`/viz` 有热力图面板 |
| **汇总行 / 小计 / 占比** | "总数对得上吗？占比多少？" | **半**。`bar_table()` 给了条与最大值比；**没有表内合计行**，也没有"分组小计" |
| **下钻（drill-down）** | "这个数是谁贡献的？" | **有（本项目的强项）**。`view_entity()`（`portal.py:1040`）任何一行 → 所有指向它的子表实际行数（`portal.py:1059-1080`），外键值可点 |

### 1.4 检索

| 能力 | 回答什么问题 | 本项目现状 |
|---|---|---|
| 按**表名 / 列名**检索（元数据检索） | "我要找的那个字段在哪张表里？" | **有**。`view_search()`（`portal.py:1154-1157`）在内存里对 `m["rels"]`、`m["cols"]` 做子串匹配，命中显示在前（`portal.py:1193-1204`） |
| 按**注释 / 描述**检索 | "我不记得字段名，只记得业务含义" | **半**。7 个 `SEARCH_SOURCES`（`portal.py:1098-1132`）里只有"字段目录"这一源搜了 `field_catalog.description`；**表注释、列注释本身不参与检索** |
| 按**列值**检索（数据检索） | "哪个表里出现过'协和'？" | **半**。7 个源覆盖 `occupation/concept/job_posting/job_requirement/code_value/field_catalog/source_registry`，全部 `ILIKE '%词%'`。**未覆盖 person、evidence 等实体；且不是"任意列"** |

| 检索**结果可解释**（来自哪张表哪个 ID） | "这条命中凭什么算命中？" | **有**。每条命中给出表名与 ID，可点进实体页（`portal.py:1178-1182`） |
| **中文**检索质量 | "搜'医学'能搜到'医学硕士'吗？" | **能，但靠的是 `ILIKE` 全表扫**，不是全文索引。原因见 §4 |

### 1.5 血缘与影响面

| 能力 | 回答什么问题 | 本项目现状 |
|---|---|---|
| 列级血缘：**这一列被哪些视图/外键用到** | "我改这一列会炸什么？" | **半**。`view_table()` 的"被谁引用"是**表级外键入边**（`portal.py:943-950`）；`load_meta()` 的 `m["inbound"]` 也是表级。**没有"哪些视图的 SQL 里 SELECT 了这一列"** |
| 表级 / 行级血缘 | "这个数从哪来？" | **有（本项目强项）**。`view_lineage()`（`portal.py:1516`）：来源登记 → 采集批次 → 逐条血缘 → L0 磁盘原文（真去数文件） |

### 1.6 数据新鲜度与更新频率

| 能力 | 回答什么问题 | 本项目现状 |
|---|---|---|
| 每张表的**最后写入时间** | "这表还在更新吗？" | **半**。`view_quality()`（`portal.py:3680-3686`）只覆盖 6 张表；`change_log` 有全量 append-only 流水（**565,282 行**），本可支撑"任意对象的最近变更" |

### 1.7 抽样预览 vs 全量统计

| 方式 | 代价 | 用途 | 本项目现状 |
|---|---|---|---|
| **抽样预览**（前 N 行） | 极低（LIMIT） | "这数据长什么样？" | **有**。`view_table()` 分页取真实行（`portal.py:910-914`，`PAGE_SIZE` 可调到 500）；`render_rows()`（`portal.py:677`） |
| **全量精确统计** | 与行数成正比 | "到底有多少？占比多少？" | **部分**。行数是精确 `count(*)`；**列级统计只做了空值，没有基数/取值域** |
| **采样统计**（`pg_stats`，ANALYZE 后） | 极低（读目录） | "大致估算，用于选计划" | **未用**，且**按纪律不该用在展示页**（§3.1） |

### 1.8 ⚠️ 用户**没想到但必须有**的能力（本节是最重要的产出）

用户说要"字段名 + 数量 + 分类统计 + 检索"。下面 7 项他没提，但**成熟产品全都有，且缺了会让"看数据"变成"看字面"**：

| # | 缺失能力 | 为什么必须有（不做的后果） |
|---|---|---|
| **1** | **空值率 / 填充率** | 用户说"能看到数量"。但**行数 ≠ 有值**。本库实测 `field_catalog` 有 176 个登记字段，而 `job_posting` 的 `deadline`/`employer_id`/`employment_type` 等列 `null_frac=1`（**整列全空**）。只给行数，用户会以为"690 行 = 690 条薪资"，而 `salary_min` 可能只有一部分有值。**"数量"必须拆成"行数 / 非空数 / 去重数"三个** |
| **2** | **去重值个数（基数）** | 它决定"这列能不能当分类维度"。基数 17 才能 group by，基数 690 的是自由文本。用户说"能够分类统计"，但**分类的前提是知道哪些列可分类** —— 基数就是那个开关。本项目目前**全库没有任何实测基数**（`field_catalog.cardinality` 是人工登记） |
| **3** | **Top-K 值 + 值标签翻译** | 用户要"分类统计"。但聚合出来的是**码**（本库纪律"存码不存标签"，README 设计纪律第 4 条）：`job_family='F02'`、`degree_level='D3'`。`lbl()`（`portal.py:263`）能翻译，但**只有已经写死在 `ANALYSES` 里的那几处翻了**。任意列的 Top-K 必须自动带上 `code_value` 的中文标签，否则用户看到一屏码 |
| **4** | **字段级权限等级（access_tier）在目录里可见** | 这是**同一批用户的另一个需求**（字段权限）。`field_catalog.access_tier` 实测 T0=53/T1=105/T2=13/T3=5，但**全站 UI 0 处引用**（我 grep 过整个 `portal.py`）。目录若不显示等级，用户会以为所有字段都能随便用；更危险的是 —— **当前"T2"只是标签，不是拦截**（README 与 `/real` 页已自陈这一点） |
| **5** | **数据新鲜度 / 最后变更** | "数量"是静态的。用户真正会问的是"这数是什么时候的？"。本库有 `change_log` 565,282 行 append-only 流水可支撑这一点，但只用了 6 张表的 max(时间列) |
| **6** | **可导出（CSV）** | 用户是"外行"，他看完一定要拿去用。本项目 `to_csv()`（`portal.py:720`）已在多处可用，但**字段剖析表本身还不能导出**。这是最低成本、最高满意度的一项 |
| **7** | **"空"的三种含义要分开** | 这是本库最有价值的一条纪律（README 设计纪律第 5 条"空就是空"，`view_table()` 的说明在 `portal.py:988`）。要区分**NULL（没采到）/ 空串（采到了但是空）/ 0（真的是 0）**。NHANES 那种 7/77/9/99 缺失码体系是**反面参照**：它把"拒答"和"不知道"编进值域，用户必须查 codebook 才知道 99 不是九十九。本库选择 NULL，代价是**必须把 NULL 率摆在最显眼处**否则用户读不出这个区别 |

## 3. PostgreSQL 自身能提供什么（含 `pg_stats` 的采样性质、扩展可用性核实）

### 3.1 `pg_stats` 是**采样估算**，不是精确值 ⚠️

**官方原文**（<https://www.postgresql.org/docs/16/view-pg-stats.html>，我实际打开）：

- `pg_stats` "provides access to the information stored in the `pg_statistic` catalog"。
- `null_frac`：*Fraction of column entries that are null* —— 是**比例**，不是计数。
- `n_distinct`：*If greater than zero, the **estimated** number of distinct values in the column.*
  —— **文档自己写了 estimated**。负数形式表示"distinct 数 / 行数"的比例（如 `-1` = 唯一列）。
- `most_common_vals` / `most_common_freqs` / `histogram_bounds`：MCV 列表与直方图**桶边界**，都是采样产物。
- *"The maximum number of entries in the array fields can be controlled … by setting `default_statistics_target`"*
  —— 本机实测 `default_statistics_target = 100`，**即 MCV 最多 100 项、直方图最多 100 桶**。

**本机实测的"过时"证据**（同一时刻对照）：

| 表 | `reltuples` 估算 | 精确 `count(*)` | 偏差 |
|---|---|---|---|
| `change_log` | 559,520 | **565,282** | **少 5,762 行（-1.0%）** |
| `job_competency_weight` | 4,891 | 4,949 | 少 58 |
| `preference` | 2,105 | 2,156 | 少 51 |
| `job_posting` | 690 | 690 | 一致（恰好） |

**本机 `pg_stats` 覆盖现状**：只有 **8 张表**被 ANALYZE 过
（`job_posting` 41 列、`field_catalog` 35 列、`education_record` 27、`occupation` 25、`dimension` 24、
`employment_record` 22、`research_output` 20、`concept` 18）。**其余 72 张表没有任何统计。**

`code_value` 的 `pg_stats` 实例（说明采样有多"粗"）：

| 列 | `null_frac` | `n_distinct` | 含义 |
|---|---|---|---|
| `label_zh` | 0 | **-0.947** | 估算 distinct ≈ 0.947 × 行数 |
| `code` | 0 | -0.969 | |
| `parent_code` | 0.918 | 13 | 估算 91.8% 为空 |
| `effective_from` / `effective_to` / `replaced_by` | **1** | 0 | 估算**整列全空** |

**结论（可直接写进代码注释）**：

| 场景 | 能不能用 `pg_stats` |
|---|---|
| **展示页上的任何数字** | ❌ **不能用**。本项目纪律是精确 `count(*)`，`reltuples` 已被 README 明令禁止 |
| 给用户"这张表大概多大"的**粗略排序/启发式** | ⚠️ 勉强，但必须标"估算"，且**与精确值同屏出现时必错**（用户会拿两个数对比） |
| **决定要不要做某个优化**（DBA 视角） | ✅ 合适。它是给**查询规划器**用的 |
| **发现"哪一列可能全空"以便优先调查** | ✅ 有价值：`code_value` 的 `effective_from` 估算 100% 空，可作为**离线调查的线索**（但结论必须回库精确确认） |
| **`n_distinct` 用来选维度** | ⚠️ 作为**初筛**可以，作为展示值不行。例如 `job_posting.city` 估 16 —— 我可以**精确验证**（见 §7 可重放 SQL） |

> **一句话**：`pg_stats` 是"**给规划器的草稿**"，不是"**给用户的账本**"。本项目的立场（精确 count）是对的，**继续坚持**。

### 3.2 `pg_stat_user_tables` / `pg_statio_*`

**本机实测：`pg_stat_user_tables` 返回 0 行**（`WHERE schemaname='mt' AND n_live_tup > 0` 也是 0 行）。
`track_counts` 是 **on**，所以这是**统计尚未累积**（实例刚经历恢复/重置，计数器从零开始）。

因此：

| 视图 | 提供什么 | 是否精确 | 本项目可用性 |
|---|---|---|---|
| `pg_stat_user_tables` | `n_live_tup`（活元组估算）、`n_dead_tup`、`seq_scan`、`idx_scan`、`last_vacuum`、`last_analyze`、`last_autoanalyze` | ❌ `n_live_tup` 是**估算** | **当前 0 行，不可用**。即使有数也不能当行数展示 |
| `pg_statio_user_tables` | `heap_blks_read` / `heap_blks_hit` / `idx_blks_read` … | 计数是精确的，但含义是"**本实例启动以来的 IO 次数**" | ❌ **不适合展示**：重启即归零，且会因页面渲染自身而增长（`/schema` 每访问一次就 +97 次 count 扫） |
| `pg_class.relpages` / `pg_total_relation_size` | 页数 / 字节数 | ✅ **精确** | ✅ **可用且应该有**（§1.1 的"大小"缺口）。我实测 `change_log` = `pg_total_relation_size` 132,980,736 B |

**建议**：表级"大小"用 `pg_total_relation_size(oid)`（精确、便宜、无需扩展）；
表级"最后变更"**不要**依赖 `pg_stat_user_tables`（本机 0 行），改用**本库自己的 `change_log`**（565,282 行 append-only，更可信）。

## 4. 检索：元数据 vs 值（含中文全文检索的现实）

### 4.1 ⚠️ 中文全文检索的实测结论（这条最反直觉，必须讲清）

**默认分词对中文是按"整段连续汉字"切，不是按字切。** 我在本机实测（UTF-8 `.sql` 文件方式）：

```
SELECT to_tsvector('simple','医学硕士在三甲医院工作五年');
--  '医学硕士在三甲医院工作五年':1        ← 整段 13 个字 = 1 个 token
SELECT to_tsvector('english','医学硕士在三甲医院工作五年');
--  '医学硕士在三甲医院工作五年':1        ← english 配置对中文也一样
SELECT to_tsvector('simple','abc 医学 def');
--  'abc':1 '医学':2 'def':3               ← 只有被空格隔开的才成 token
```

**所以下面这些查询全部返回 `f`（不命中）** —— 这是本节最关键的一屏：

| 查询 | 命中? |
|---|---|
| `to_tsquery('simple','医学') @@ to_tsvector('simple','医学硕士在三甲医院')` | ❌ **f** |
| `to_tsquery('simple','医院') @@ to_tsvector('simple','医学硕士在三甲医院')` | ❌ **f** |
| `to_tsquery('simple','三甲医院') @@ to_tsvector('simple','医学硕士在三甲医院')` | ❌ **f** |
| 单字 `'院'` | ❌ **f** |

**`ts_debug` 给出根因**：

```
SELECT alias, description, token, dictionaries FROM ts_debug('simple','医学硕士 abc 123');
   alias   |    description    |   token  | dictionaries
-----------+-------------------+----------+--------------
 word      | Word, all letters | 医学硕士 | {simple}     ← alias='word'，整段当一个"词"
 blank     | Space symbols     |          | {}
 asciiword | Word, all ASCII   | abc      | {simple}
 blank     | Space symbols     |          | {}
 uint      | Unsigned integer  | 123      | {simple}
```

**官方文档的解释**（<https://www.postgresql.org/docs/16/textsearch-parsers.html>，我实际打开）：

- *"At present PostgreSQL provides just **one built-in parser**"* —— 名为 `pg_catalog.default`，23 种 token 类型。
- *"The parser's notion of a 'letter' is determined by the database's locale setting, specifically `lc_ctype`."*
- `word` 的定义是 *"Word, all letters"*，例子是 `mañana`。
- **本机实测库的 locale**：`datcollate=C`、`datctype=C`（编码 `UTF8`）。
  **空格的判断是：任何字母串 = 一个 word**，中文汉字被当作字母，所以**连续汉字 = 一个 word**。

> **一句话结论**：**PostgreSQL 内置全文检索对中文不可用**（不是"效果差"，是"整段永远搜不到"）。
> 除非把词预先用空格切开 —— 这正是本项目 `schema/sql/003_retrieval.sql` 已经写下的方案。

### 4.3 元数据检索（列名/注释）vs 值检索（列值）是**两件事**

这是本节要建立的**核心分工**。用户说"能够检索"，但没说清检索什么 ——
**而这两种检索的代价差 3–4 个数量级**：

| | **元数据检索**（表名/列名/注释/域/权限等级） | **值检索**（列里存的内容） |
|---|---|---|
| 数据源 | `pg_class` / `pg_attribute` / `field_catalog` / `code_table` —— **约 176 字段 + 97 对象** | 业务表的所有行 —— **565,282 行（`change_log`）+ 全库** |
| 数据量级 | **KB 级**（实测 `load_meta()` 一次全读 **0.88 s 冷启动**，之后走进程内缓存 `META`，`portal.py:271-279`） | **MB–百 MB 级** |
| 实现方式 | **内存子串匹配即可**（`view_search()` 已在做，`portal.py:1154-1157`，零 SQL 成本） | 必须走 SQL；无索引时是**全表扫** |
| 实测代价 | **≈ 0**（内存操作） | `job_requirement` ILIKE：**10.5 ms**（2,970 行）；`change_log` ILIKE：**1,486 ms**（565,282 行） |
| 能不能实时 | ✅ 完全可以，甚至不需要索引 | ⚠️ 小表可以；**大表必须离线或建索引** |
| 用户意图 | "**我要找的东西在哪**" | "**哪里有这个东西**" |

**本项目的现状与缺口**：

- 元数据检索：**有但很浅** —— `view_search()` 只匹配**表名和列名**（`portal.py:1154-1157`），
  **不匹配表注释、列注释、`field_catalog.description`（除了那一个源）、不匹配域、不匹配 `access_tier`**。
  而 `load_meta()` **已经把 `comment` 读进来了**（`portal.py:163` 表注释、`portal.py:173` 列注释），
  **只是检索时没用** —— 这是**几行代码的零成本改进**。
- 值检索：**7 个固定源 + `ILIKE`**。不是"任意列"，且大表会慢。

**界面上的分开方式（这是用户问的"怎么在界面上分开"）**：

1. **两个不同的入口，不同的词表**：
   `/catalog`（元数据）的搜索框占位符写 *"找字段：输入列名、中文含义、域或权限等级"*，
   而 `/search`（值）的占位符写 *"找内容：输入你想在数据里找到的词"*。
2. **结果页必须互相指路**：元数据检索命中"`job_posting.education_req`"后，
   给一个"**看看这一列里有什么值 →**"的链接跳到 §6.3 的字段剖析页；
   值检索命中后，给"**这一列属于哪张表/哪个字段 →**"的链接跳回目录。
3. **成本提示是必须的**：值检索若命中 0 条，要说明"我扫了 N 行"（真实数字），
   而不是干巴巴"没找到" —— 否则用户不知道是"真没有"还是"我没扫到"。这符合本项目"空就是空"的纪律。
4. **默认不搜值**：`/search` 的值检索应**限定在那 7 个登记过的源**（现状如此，是对的），
   并**明示"只搜了这 7 个源"**（现状的 `/search` 空态页已经列了这 7 个源，`portal.py:1143-1149` —— 做得对，保持）。

### 4.4 `pg_trgm` 做模糊匹配的可行性（含中文的现实）

**官方文档要点**（<https://www.postgresql.org/docs/16/pgtrgm.html>，我实际打开）：

- trigram = **三个连续字符**。*"`pg_trgm` ignores non-word characters (non-alphanumerics)"*。
  每个词在提取前会**前缀两个空格、后缀一个空格**：`cat` → `"  c"`, `" ca"`, `"cat"`, `"at "`。
- **关键**：*"these index types also support trigram-based index searches for `LIKE`, `ILIKE`, `~`, `~*` and `=` queries"*
  → **`pg_trgm` 的 GIN/GiST 索引能直接加速 `ILIKE '%词%'`**，这正是我们 `/search` 现在最慢的地方。
- *"Unlike B-tree based searches, the search string need not be left-anchored."* → 中缀匹配是它的**主场**。
- ⚠️ **警告（原文）**：*"For both `LIKE` and regular-expression searches, keep in mind that **a pattern with no extractable trigrams will degenerate to a full-index scan**."*
- 阈值：`pg_trgm.similarity_threshold` 默认 **0.3**；`word_similarity_threshold` 默认 0.6；`strict_word_similarity_threshold` 默认 0.5。
- 函数族：`similarity`、`word_similarity`、`strict_word_similarity`、`show_trgm`；
  操作符 `%`（相似）、`<%` / `%>`（词相似）、`<<%` / `%>>`（严格词相似）、`<->` 系列（距离）。

**对中文的现实（我的分析，基于上述原文 + 中文是"无空格语言"这个事实）**：

| 中文输入 | trigram 情况 | 判断 |
|---|---|---|
| **1 个汉字**（如 `医`） | 无（不足 3 字，只能靠 `"  医"` 补齐的 1 个 trigram，甚至提不出） | ❌ **退化为全索引扫**，别指望 |
| **2 个汉字**（如 `医学`） | 可提取 `"  医"`, `" 医学"`, `"学 "` ≈ 2–3 个 trigram | ⚠️ **能用但选择性差**（词越短 trigram 越少） |
| **3 个汉字**（如 `医学硕`） | 3–4 个 trigram | ✅ 可用 |
| **≥4 个汉字**（如 `医学硕士`、`三甲医院`） | 4–6 个 trigram | ✅ **效果好**，这是推荐用法 |

> **结论**：`pg_trgm` 对**中文 ≥3 字的关键词是可行的**（中缀 `ILIKE` 加速是刚需），
> 对 **1–2 字关键词要预期退化**。这恰好与本项目的高频检索词吻合
> （岗位/能力/专业名普遍 ≥3 字；单字检索本来就该被引导到别处）。
>
> **但 `pg_trgm` 不是全文检索的替代品**：它做的是"**子串/相似**"，
> 不做**分词、词干、相关性排序**。要做中文分词检索，**只能走 §4.2 的 jieba + `search_document` 路线**。
> 两者互补：**`search_document`（jieba+GIN tsvector）负责分词检索与排序；
> `pg_trgm` 负责给 `ILIKE` 加速与容错（错别字）**。

**落地前提（未验证、必须第一步做掉）**：

```sql
-- 必须在可写连接（code/demo/portal_dev.py，:8083）或迁移文件里执行；
-- 只读门户跑这个会被数据库拒绝（本机实测：cannot execute CREATE EXTENSION in a read-only transaction）
CREATE EXTENSION IF NOT EXISTS pg_trgm;
```

建议写成 **`schema/sql/017_trgm.sql`**（走迁移，符合"结构变更唯一入口"纪律），
并**幂等**（`IF NOT EXISTS`）+ 在扩展不可用时**不阻塞**（因为 `pg_trgm` 装不上时 `ILIKE` 仍能跑，只是慢）。

| **列数 / 约束 / 索引 / 触发器 / 类型 / 注释 / 主外键** | ✅ **实时算**，目录查询 | `load_meta()` 已证明（0.88 s 含全部） |
| **表大小**（`pg_total_relation_size`） | ✅ **实时算** | 目录函数，精确且便宜 |
| **空值数 / 空值率**（`count(*) - count(col)`） | ✅ **实时算**（≤690 行与 ≤5k 行的表）；⚠️ 565k 行表 **≈0.3 s/9列**，仍可接受但要做上限保护 | 实测 296 ms / 9 列 |
| **min / max** | ✅ **实时算**（同样是一次扫） | 与空值数同一次扫可合并 |
| **`count(DISTINCT)`（基数）** | ⚠️ **小表实时，`change_log` 必须物化** | `job_posting` 10 列 6 ms；`change_log` **单列 1,319 ms** |
| **Top-K 值**（`GROUP BY ... ORDER BY ... LIMIT K`） | ⚠️ **小表实时**；大表需要**物化或加索引** | 与 `DISTINCT` 同量级 |
| **值分布直方图** | ⚠️ 小表可实时（`charts.py:histogram()` 已在用）；大表物化 | 同上 |
| **全库值检索（`ILIKE`）** | ❌ **不可实时**（`change_log` 1.5 s/次，且会随数据增长线性变差） | 实测 1,486 ms |
| **元数据检索** | ✅ **实时**（内存匹配，≈0） | `view_search()` 已在做 |

### 5.3 物化方案（**关键设计决策**）

**⚠️ 不要用物化视图（`MATERIALIZED VIEW`）。** 理由：

1. 本库**实测 0 个物化视图**，引入它是新机制。
2. **物化视图的 `REFRESH` 是全量的、且会锁**。它的刷新语义（`WITH DATA` / `CONCURRENTLY`）比一张普通表复杂。
3. **我们需要的是"带版本的统计历史"**（用于 §2.5 的漂移检测），而物化视图**只保留最新一份**。
4. 本项目纪律是"结构变更唯一入口 = `schema/sql/` 迁移"，一张**普通表 + 普通 INSERT** 更容易被
   `ops/tests/run_all.py` 断言（`--fast` 档 9 套约 16–19 秒，见 `run_all.py:263`）。

**建议：一张统计表 + 一个离线 CLI。**

```sql
-- 建议 schema/sql/017_column_profile.sql
CREATE TABLE mt.column_profile (
  profile_id     TEXT PRIMARY KEY,        -- cp_<ULID>
  run_id         TEXT NOT NULL,           -- 每次物化一批
  schema_name    TEXT NOT NULL DEFAULT 'mt',
  table_name     TEXT NOT NULL,
  column_name    TEXT NOT NULL,
  row_count      BIGINT NOT NULL,         -- 精确 count(*)（本库纪律：不用 reltuples）
  non_null_count BIGINT,                  -- 精确
  null_count     BIGINT,                  -- 精确
  distinct_count BIGINT,                  -- 精确 count(DISTINCT)
  min_value      TEXT,
  max_value      TEXT,
  top_values     JSONB,                   -- Top-K：[{"v":..,"n":..,"label":..}]
  histogram      JSONB,                   -- 分桶
  computed_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  method         TEXT NOT NULL,           -- 'exact' | 'sampled'（诚实标注！）
  UNIQUE (run_id, table_name, column_name)
);
```

**为什么 `method` 列是必须的**：本库纪律禁止估算值冒充实测值。
一旦将来某张大表改成采样，**页面必须能显示"这是采样，采样率 x%"**。
这与 §1.8 第 7 项同源：**不许让用户误读**。

**刷新策略**：

| 表 | 刷新时机 | 理由 |
|---|---|---|
| 全部 80 张表 | **挂到 `ops/tests/run_all.py` 的收尾动作旁边**（与 R1/R2 同级），**不进 `--fast` 档** | `--fast` 档实测 16–19 秒、且**故意零持久副作用**（`run_all.py:30-32`）。物化统计是**有副作用的写操作**，放进 fast 会破坏这个承诺 |
| `change_log`（565k 行） | **只在完整档**（`--tier full`）或手动 CLI | 单列 DISTINCT 1.3 s × 9 列 ≈ 12 s，会让 `--fast` 从 19 秒变 31 秒 |
| 其余 79 张表 | 完整档 | 实测都在毫秒级，总代价可忽略 |
| 触发式 | 提供一个 `--only <表>` 参数 | 改完某张表后只重算它 |

**渲染侧的保护（这是不能省的）**：

1. **页面只读 `column_profile`，不算统计**。页面上每个数字仍**可追溯到那条 INSERT 的 SQL**（符合本项目"数字旁边有 SQL"的做法）。
2. **`computed_at` 必须显示在数字旁边**，格式如 *"基于 2026-10-09 18:52 的物化（精确口径）"*。
   否则用户会把昨天的数当今天 —— 这比"没有数"更糟。
3. **剖析查询要有一层"代价闸门"**：任何实时剖析（若保留）先看 `row_count`，
   超阈值（建议 **50,000 行**，`change_log` 的 1/11）就**拒绝实时算并指向物化值**。
   本项目已有类似的参数校验先例：`_int_param()`（`portal.py:598`）带 `lo`/`hi` 边界。
4. **绝不拖垮 `run_all.py`**：`cmd_check()`（`portal.py:4005`）会**把每个页面渲染一遍**
   （97 个对象的表页 + 97 个对象的实体页 + 14 个固定页 + 16 个面板 + 8 个分析）。
   加了字段剖析后，这仍然是 **97 次读 `column_profile` 的查询，不是 97 次扫表**。
   实测 `/t/change_log` 现在 0.507 s，加剖析后**必须仍然 < 1 s**，否则 `run_all.py` 的门户套件（当前 30.85 s，`run_all.py:88`）会明显变慢。

**默认排序（决策）**：
**按"行数降序"**。理由：外行找表的第一直觉是"哪张表有货"。
但**行数为 0 的表不能消失** —— 它们要出现在**表尾并带醒目标注**（本库有大量 0 行表，`view_quality()` 在数它们）。

**为什么不做树的默认视图**：`docs/17` §4.1 已讨论过树的可折叠问题。
表目录只有 97 个节点、**两层**（域 → 表），**平铺 + chips 筛选比树更快**（少一次点击）。
树留给**字段级**（§6.3 的分类导航）。

**零 JS 的排序怎么做**：(A) 表头每个 `<th>` 是一个链接
`?sort=rows&dir=desc`，与 `view_table()` 现有的排序链接完全同构（`portal.py:965-971`）。
**代价**：每次排序一次页面加载。97 行数据、实测 `/schema` 0.039 s，**完全可接受**。

### 6.3 字段剖析页 `/field/<表>/<列>` —— **新建，本方案的核心页面**

这是 **NHANES codebook 的字段块**（§2.2）+ **UKB 字段页的 KPI 带**（§2.1）在本项目的合体。

**版式（自上而下，全部 (A) 零 JS）**：

```
┌ 面包屑：表与视图 / job_posting / education_req ────────────────────┐
│ (1) 标题：education_req  学历要求                                   │
│ (2) KPI 带（9 格，与 UKB 字段页同构）：                              │
│     类型        非空      精确行数    非空数    空值率    基数       │
│     text        否        690         690       0.0%      4         │
│     枚举域      code_table 值标签可用  权限等级   最近物化            │
│     CT-EDU      是          是          T1        2026-10-09 18:52   │
│ (3) 值分布（Top-K 表 + 直方图 SVG + 值标签中文）                      │
│ (4) 登记信息（来自 field_catalog：描述、is_required、is_arrayed、      │
│     instanced、code_table_id、单位、来源）                            │
│ (5) 用它的地方：哪些表有这个同名字段 / 哪些视图引用了它                 │
│ (6) 这一页执行的 SQL（可核）                                          │
└─────────────────────────────────────────────────────────────────────┘
```

**关键设计点**：

1. **数字旁边必须有口径与时间**（模仿本项目既有做法 + UKB）：每个统计量下方小字写
   *"精确 `count(DISTINCT)`，基于 2026-10-09 18:52 的物化"*。**没有时间的统计数字是有毒的。**
2. **Top-K 表照抄 NHANES 的列**：`值 | 中文标签 | 计数 | 累计 | 占比`。
   **`累计` 这一列是 NHANES 的灵魂** —— 它让"累计到 80% 需要前几个值"变成一眼可见。
   我们的 `code_value` 提供了**中文标签**（`lbl()`，`portal.py:263`）。
3. **零值也要列出来**（学 NHANES `DMDEDUC3` 的 `55 = Less than 5th grade, 0`）：
   `code_value` 里**登记了但频次为 0** 的码值必须显示，这是腐化信号。
4. **空值区必须区分三种空**（§1.8 第 7 项）：
   `NULL` 数 / `''` 空串数 / `0` 的个数 —— 三个不同的数字并排。
   这是一条**只在本库成立的强项**（本库"空就是空"，不玩 7/99 缺失码）。
5. **适用条件提示**（学 NHANES 的 `Target` / `Skip to Item`）：
   把 `field_catalog.description` 完整显示（不截断），并在空值率旁加一句
   *"若本字段的登记说明含适用条件，空值率可能来自'不适用'而非'未采集'"*。
   **这是诚实的写法** —— 我们当前没有适用条件字段，就**明说没有**，而不是编一个。

**入口（3 个）**：
- 从 `/t/<表>` 的列定义表点列名（最主要的入口）
- 从 `/catalog` 的元数据搜索结果直接跳
- 从 `/field/<表>/<列>` 之间互相跳（同名列 / 同 `code_table_id` 字段）

**⚠️ 不要为 176 个字段各建一个静态页**：用**一个 handler 函数 + 路径参数**
（与 `view_table()` / `view_entity()` 同构），并且**先 `require_column()` 校验**
（已有，`portal.py:295-300`）—— 否则 URL 可以被拼成任意字符串去撞数据库。

### 6.5 检索入口设计

**现状**（`view_search()`，`portal.py:1135-1216`）：一个框，7 个固定源 `ILIKE`，

**建议的分工（新增 `/catalog` 页承载元数据检索）**：

| 入口 | 页面 | 搜什么 | 实现 | 类型 |
|---|---|---|---|---|
| **找字段** | `/catalog?q=` | 表名、**列名**、**表注释**、**列注释**、`field_catalog.description`、`field_catalog.title`、域、`access_tier` | `META` 内存匹配（`load_meta()` 已把 comment 读进来了，`portal.py:163/173`，**只差匹配**） | **(A)** |

**三条界面规则**：

1. **两个框的文案必须不同**（这是用户问的"怎么分开"的答案）：
   `/catalog` → *"找字段：列名 / 中文含义 / 域 / 权限等级"*；
   `/search` → *"找内容：你想在数据里找到的词（只搜已登记的 7 个源）"*。
2. **结果必须能互相跳**：字段命中 → 字段剖析页；值命中 → 该行的实体页（现状已有，`portal.py:1178-1182`）。
3. **元数据检索的命中要显示"为什么命中"**：是列名匹配还是注释匹配？把匹配到的注释片段显示出来。
   这符合本项目"每个数字旁边都有它的 SQL"的同一个精神 —— **每个命中旁边有它的理由**。

## 附：本文的自我边界声明

1. **本文不含任何代码改动**，只写这一个文件。
2. **所有"现状"断言都给了函数名与行号**，行号对应本文件写作时的
