## 4. 新增个体 · 方式 b：Excel 表格导入（②b，本次新建）

### 4.1 场景与工具

小程序那边导出的一张表 → 导进本库。工具是本次新做的：

```powershell
python ops\import_persons.py --make-sample .tools\sample_persons.xlsx   # 生成示例表（故意含缺失）
python ops\import_persons.py --file .tools\sample_persons.xlsx          # **默认只看计划，不写库**
python ops\import_persons.py --file .tools\sample_persons.xlsx --apply  # 真正导入
python ops\import_persons.py --cleanup --yes                            # 清理本次导入（精确按来源）
```

### 4.2 最重要的一条纪律：**缺失 ≠ 空值**

"没填"有两种记法，差别很大：

| 做法 | 后果 |
|---|---|
| ✗ 写一个空串进库 | 以后没人分得清"他没填"和"他答了空"；统计时**空会变成一个合法类别** |
| ✅ **不写这一条记录** | 库里根本没这行，于是"缺失"是**可数的事实**：人数分母就是"填了的人" |

本工具一律用后者。并把"没填"分成**三种**分别统计：

| 类型 | 含义 | 你该做什么 |
|---|---|---|
| ① **整列缺失** | 表里压根没这列（这批人全都没这个数据） | 让导出方补这一列 |
| ② **单元格为空** | 列在，这格空着/写着"未填写" | 回去补数据，或接受"这些人就是没填" |
| ③ **值无法解析** | 写了内容，但不是字典里的合法码 | 改字典或改表格 |

### 4.3 实测输出（示例表 7 行）

示例表**故意**做了几种缺失：一行只有专业、一行写"未填写"、一行没勾授权、还有一列是"不认识"的列。

```
【结果】共 7 行：导入 5、失败 2（其中授权门拒绝 2）
       契约字段写入 24 次；动态字段写入 3 次

② 单元格为空（列在、这格没填）→ **不写该字段**：
   F_PSN_RES_OVERSEAS           2 行
   education.major              1 行
   current_stage                1 行
   education.degree_level       1 行
   current_city                 1 行

不认识的列（跳过，未写入）：备注（不认识的列）
```

**逐条解释这份报告**：
- **导入 5、失败 2**：失败的两行是**没授权**（一行写了"否"、一行空着）→ 授权门拒绝。**这是对的**。
- **"不认识的列"被报告出来，而不是静默丢弃**——表格里多出来的列不会污染数据库，但你**知道**它没进。
- **动态字段写入 3 次**：`海外经历` 那一列有 5 行有值、2 行空 → 只写 3 条。

### 4.4 列怎么映射的

工具按**中文表头**或**字段 id** 认列：

| 表格列 | 落到哪 | 走哪条路 |
|---|---|---|
| 外部编号 | 身份（去重、幂等、版本门都靠它） | bridge |
| 同意个人分析 | 授权门 | bridge |
| 当前阶段 / 学历 / 专业 / 意向城市 | 规范表（答卷） | bridge（契约字段） |
| 意向职业（逗号分隔的 occupation_id） | 偏好 | bridge |
| **海外经历** 等已登记字段 | `field_value`（动态模型） | `set_value` |
| 其它不认识的列 | **不进库，只在报告里列出** | — |

**为什么分两条路**：契约字段是**小程序注册契约**的一部分（有校验与 crosswalk）；
动态字段是**本库自己的扩展**（零 DDL 加列）。混在一条路上会破坏契约边界。

### 4.5 你怎么确认成了

```powershell
# 导入了几个人
python ops\pg.py psql -c "SELECT count(*) FROM mt.external_identity WHERE source_system='xlsimport'"
# 动态字段写了几条
python ops\pg.py psql -c "SELECT field_id, value_code, count(*) FROM mt.field_value GROUP BY 1,2"
# 答卷有没有落（契约字段）
python ops\pg.py psql -c "SELECT count(*) FROM mt.answer a JOIN mt.response_session s ON s.session_id=a.session_id WHERE s.source_system='xlsimport'"
```

⚠ **实测踩到的坑**：第一版示例表里"海外经历"我写了 `Y1/N1`，结果 3 行**全被拒**：

```
动态字段 F_PSN_RES_OVERSEAS 拒绝：取值 Y1 不在字段…
```

因为该字段的码表是 `CT_YES_NO`，**合法码是 `Y / N / U`**（不是 Y1/N1）。
**教训：表格里的取值必须是字典里的码。** 查字典的办法：

```powershell
python ops\pg.py psql -c "SELECT code, label_zh FROM mt.code_value WHERE code_table_id='CT_YES_NO'"
```

**幂等性**：同一个"外部编号"再导一次，不会重复建人——它走**版本门**，
第二次是"版本 2 的更新"而不是新增一行。这是设计，不是巧合。

## 5. 新增一个职业（③）

### 5.1 最短路径：直接插一行（含审计留痕）

```sql
-- 0) 先确认父节点存在（否则就是悬挂引用）
SELECT occupation_id, label_zh, level, family FROM mt.occupation
 WHERE occupation_id = 'OCC-F02-01';        -- 医学事务，level 2

-- 1) 插入新职业（三级：家族-二级-三级）
INSERT INTO mt.occupation (
  occupation_id, label_zh, label_en, level, parent_id, family,
  medical_reliance, transition_ease, description, code_status, code_source, status)
VALUES ('OCC-F02-99', '测试职业（演示用）', 'Demo Occupation', 3, 'OCC-F02-01', 'F02',
        2, 4, '演示数据，测试完成请删除', 'N', 'manual', 'active');

-- 2) 审计：直接插入**不会**自动留痕，所以要显式写一条
INSERT INTO mt.change_log (actor, object_type, object_name, change_type, detail)
VALUES (session_user, 'occupation', 'OCC-F02-99', 'add',
        jsonb_build_object('op','INSERT','table','occupation',
                           'row','occupation_id=OCC-F02-99','note','新增职业'));
```

**字段规矩**（数据库会拦）：
- `occupation_id` / `label_zh` / `status` 必填（其余可空）
- `medical_reliance`、`transition_ease` 只能是 **0–5**
- `code_status` 只能是 `V`（已核验）/ `E`（外部码待核）/ `N`（自有）
- `level` 是 **1/2/3**；`parent_id` 要指向真实存在的节点

**实测结果**：
```
 occupation_id |      label_zh      | level | parent_id  | family | status
 OCC-F02-99    | 测试职业（演示用） |     3 | OCC-F02-01 | F02    | active

  父节点  |       新节点       | 层级
 医学事务 | 测试职业（演示用） |    3
```
网页端也确认可见：`/tree` 与 `/occupations` 都能看到它。

**删除**（演示数据要清掉，否则职业树基线会被人为改动）：
```sql
BEGIN;
DELETE FROM mt.occupation WHERE occupation_id='OCC-F02-99';
INSERT INTO mt.change_log (actor,object_type,object_name,change_type,detail)
VALUES (session_user,'occupation','OCC-F02-99','delete',
        jsonb_build_object('op','DELETE','table','occupation',
                           'row','occupation_id=OCC-F02-99','note','删除演示职业'));
COMMIT;
```

### 5.2 正式路径：证据驱动（推荐用于真实新增）

直接插入的代价是**不留演变记录**。真实场景建议走这条（`occupation_change` 会记录
证据、审核人、生效时间）：

```powershell
python code\evolve\discover.py            # 从现有数据中发现"候选职业"
python code\evolve\promote.py list        # 看候选
```

**这条路上的每一步都有留痕**，所以审计能回答"这个职业怎么来的"。

## 6. 新增信息分类变量（= 新增一"列"）（④）

### 6.1 概念：这个项目里"加一列"是零 DDL 的

它**不做 `ALTER TABLE`**，而是把字段登记到 `field_catalog`，把值存进 `field_value`。
效果等价于加了一列，但**不用停服、可回滚、还能自动带字典**。

网页入口：`http://127.0.0.1:8083/model`（开发者模式，可写）
命令行等价写法：

```sql
SELECT mt.add_dimension(
  'person',                                 -- 给哪个实体
  'F_PSN_RES_JOB_OUTCOME',                  -- 字段 id
  '求职结果',                                -- 中文标题（**表格导入时就用这个表头**）
  '[{"code":"JO1","label":"已就业"},
    {"code":"JO2","label":"待业中"},
    {"code":"JO3","label":"升学深造"},
    {"code":"JO4","label":"出国出境"},
    {"code":"JO9","label":"不愿透露"}]'::jsonb,
  'code',       -- 有选项 → 自动建词表 CT_<字段id>
  false,        -- 非多选
  false,        -- **非必填**（调查必然有人不填，所以别设必填）
  '毕业时的求职结果（用于分析分类变量的影响）',
  '求职与结果',  -- 表单分组
  'T1',         -- 访问等级：注册用户可见
  'user');
```

## 7. 分析分类变量对求职结果的影响（⑤）

### 7.1 先有数据

实测：分析此前跑不起来，因为 `field_value` 是空的。用下面这条命令造一批**合成演示数据**
（只写在 `per_mock_*` 这些合成人身上）：

```powershell
python ops\seed_demo_analysis.py show      # 先看会造什么、分布如何
python ops\seed_demo_analysis.py apply     # 写入 120 人 × 3 变量
python ops\seed_demo_analysis.py cleanup   # 用完删掉
```

⚠ **必须说清楚**：这是**合成数据**，其中"有海外经历→就业率更高"这个效应是
**我们刻意塞进去的**（用来验证口径能不能跑通）。**不要**把它当成对真实人才的判断。
合成规则是**确定性**的（按 `person_id` 哈希），所以同一批人每次算出来一样，便于复核。

### 7.2 分析口径的第一次：把 EAV 转成宽表

值存在 `field_value` 里是"长表"（一行一个字段），分析需要"一行一个人"。这一步的口径
**只允许有一处**（否则各页面数字会对不上），所以做成了一个视图：

`mt.v_person_analysis_vars` — 列：`person_id / age_band / overseas / job_outcome`
（**含 person_id，所以只给 T3，不对匿名开放**——实测匿名读取被拒）

### 7.3 四种看法（实测输出）

**① 总体：海外经历 × 求职结果**
```sql
SELECT coalesce(overseas,'（未填）') AS 海外经历, count(*) AS 人数,
       count(*) FILTER (WHERE job_outcome='JO1') AS 已就业,
       count(*) FILTER (WHERE job_outcome='JO2') AS 待业中,
       count(*) FILTER (WHERE job_outcome='JO3') AS 升学深造,
       count(*) FILTER (WHERE job_outcome='JO4') AS 出国出境,
       round(100.0*count(*) FILTER (WHERE job_outcome='JO1')
             /nullif(count(*) FILTER (WHERE job_outcome IS NOT NULL),0),1) AS 已就业率
  FROM mt.v_person_analysis_vars GROUP BY 1 ORDER BY 1;
```
```
 海外经历 | 人数 | 已就业 | 待业中 | 升学深造 | 出国出境 | 已就业率
 N        |   92 |     32 |     31 |        9 |       20 |     34.8
 Y        |   28 |     12 |      5 |        6 |        5 |     42.9
```

**② 分层：按年龄段看（避免把年龄和海外经历混在一起）**
```
 年龄段 | 有海外_人数 | 有海外_已就业率 | 无海外_人数 | 无海外_已就业率
 AG1    |           1 |             0.0 |          13 |            38.5
 AG2    |          25 |            48.0 |          61 |            27.9
 AG3    |           2 |             0.0 |          18 |            55.6
```
→ **AG1/AG3 只有 1–2 个人，百分比没有意义**。这说明分层时必须同时看**人数**，
否则会被小样本骗（这在统计学上叫"小分母问题"）。

**③ 关联强度：Cramér's V**（0=无关，1=完全相关；比"看百分比差多少"严谨）
```
 卡方  | 海外经历类别数 | 求职结果类别数 | 样本量 | Cramér_V
 4.661 |              2 |              4 |    120 |    0.197
```
→ **0.197 属弱相关**。光看"42.9% vs 34.8%"会觉得有差别，加上这个系数才看得出
"差别不大、而且样本只有 120"。

**④ 缺失统计**（"字段缺失"在分析阶段的样子）
```
 总人数 | 有年龄段 | 有海外经历 | 有求职结果 | 三个变量齐全 | 缺海外经历 | 缺求职结果
    120 |      120 |        120 |        120 |          120 |          0 |          0
```
→ 本次演示数据齐全。**真实数据不会这样**：`count(变量)` 与 `count(*)` 的差
就是"没填的人数"，而所有比例的分母都应该是**填了的人**，不是全体。

### 7.4 三条必须记住的读数字纪律

1. **分母是谁**：`已就业率` 的分母是"填了求职结果的人"。缺数据的人不进分母，
   但要单独数出来告诉读者。
2. **小样本不给百分比**：组内不足 ~20 人时，百分比会剧烈波动（见 AG1/AG3）。
3. **相关不等于因果**：本次的"效应"是我们自己塞进去的；真实数据里
   海外经历可能与家庭条件、院校层次等**混杂因素**同时作用，需要控制变量后再看。

## 9. 常见错误速查（都是实测踩过的）

| 现象 | 真实原因 | 怎么办 |
|---|---|---|
| 表格导入后"动态字段被拒：取值 X 不在字段…" | 用了中文/自定义值，不是**字典里的码** | 查 `code_value` 拿码；表格里填码 |
| 导入"失败 N 行，授权门拒绝 N" | 表格里**没勾授权**（或授权列空着） | 这是门在工作。让用户在表格里确认授权 |
| 导入成功但"某个变量全是空的" | 那一列的**单元格大多为空**，或**整列缺失** | 看报告里的 ①②③ 分类；补数据或补列 |
| 新增职业后职业树数字变了 | 你确实加了一个节点 | 用完删掉，或跑 `run_all.py --after-only` 复位基线 |
| 网页上看不到刚加的东西 | 元数据缓存（TTL 300 秒）或页面缓存 | 等 5 分钟，或重启门户 |
| `psql` 报 `permission denied for table ...` | 你的等级看不到那张表 | 用 T3 登录；或看 `/quality` 确认是权限不是缺数据 |
| 分析里的百分比加起来怪 | **分母含了 NULL** 或小样本 | 用 `count(变量)` 当分母，组内人数少就别看百分比 |
| 想看某个数字怎么算出来的 | 每个分析页面都**打印它执行的 SQL** | 展开页面底部的「查看本页执行的 SQL」 |

## 11. 图形界面速查（全部可在浏览器里点）

| 界面 | 地址 | 能做什么 |
|---|---|---|
| **交互式透视** | `:8082/pivot` | 挑 1 个分类变量＝分布；挑 2 个＝交叉表；再选「分层看」＝**在每个分层内部重复同一张表**（判断"差异是不是第三个变量带出来的"）；选「目标变量+取值」＝每格显示**占比**（如已就业率）；自动算 **Cramér's V** 并标注小样本 ⚠ |
| **漏斗** | `:8082/funnel` | 按业务路径看阶段转化（供给/需求/匹配质量三条），带环比/累计与每阶段说明；**阶段只能变窄**，写错会直接报错 |
| **新增职业** | `:8083/occupation` | 表单新增职业：父节点/岗位族从库里实际数据里选（不用手打 id 猜），**必须填"为什么加它"**（进审计）；重复编号、悬挂父节点都被友好拒绝 |
| **批量导入** | `:8083/import` | 粘贴表格（Excel 复制＝制表符，也能用逗号）或填本机 `.xlsx`/`.csv` 路径；**默认只做计划**，看清"会写什么、缺什么、哪些列不认识"再点确认导入 |
| **口径/分类/漏斗注册表** | `:8082/t/metric_registry` `dimension_registry` `funnel_registry` | 每个口径/分类的定义、分子分母、**口径说明与使用注意**都在库里可查 |

**为什么透视界面里选不出"已就业率"**：因为"率"需要**分子是谁**。选「目标变量＝求职结果、目标取值＝JO1 已就业」，每一格就会显示该格的已就业率。分母是**该格填了该变量的人**（没填的人在库里没有那一行）。

**为什么要有"分层看"**：合计表会骗人。同一个"有海外经历的人就业率更高"，在 25–29 岁组可能成立、在 30–34 岁组可能反过来（辛普森悖论）。分层就是把这个可能性摆出来看。**它仍然不是因果推断**，只是排除了最明显的混杂。

## 12. 一句话总结

- **看数据**：`:8082` 的 `/catalog`（字段名+数量）、`/schema`、`/t/表名`、`/field/表/列`、`/sql`
- **加一个人**：`:8083/mockreg`（单个，带三层证据）或 `ops\import_persons.py`（表格，带缺失处理）
- **加一个职业**：`INSERT` + 写 `change_log`（短）或 `code\evolve\promote.py add`（正式、有留痕）
- **加一"列"**：`:8083/model` 或 `mt.add_dimension()`（零 DDL，自动建字典）
- **分析影响**：先有变量与数据，再用 `mt.v_person_analysis_vars` 做交叉表 + 分层 + Cramér's V，
  **永远说清分母、警惕小样本、区分相关与因果**
