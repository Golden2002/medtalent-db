## 二、后端数据管理

### 2.1 分层与访问控制（权限强制点在数据库）

```
T0 匿名公开  <  T1 注册用户  <  T2 可信  <  T3 运维/管理
mt_portal：零表权限，每次会话 SET LOCAL ROLE mt_tN —— 客户端 cookie 里只有会话 id，
           等级由**数据库里的行**决定（伪造 cookie 不等于伪造 T3）
```

- **列级策略是生成的，不是手写的**：`mt.column_policy` 由 `refresh_column_policy()` 为
  **每张表的每一列**重新生成（默认 `table_default = T1`），再由规则逐条覆盖。
  规则来源：字段字典（`field_catalog`）、人工策略（`access_policy`）、模式匹配（`pattern`）。
- **表级 GRANT 会被对账收回** —— 这是机制，不是 bug。所以**不要**直接 `GRANT`；
  要改等级就改策略表再对账（迁移 058 记录了这次教训）。
- **披露控制**：主体标识列（`person_id` 等语义上的标识）不得 ≤ T0（迁移 030/044）；
  计数可见性登记在 `public_count_excluded`（048/049）。
- **导出禁令**：`export_denied` 表登记不得带走的列（健康限制、PII）→
  导出时**明确列出被移除的列**（`X-Export-Denied` 响应头），不静默删列。

### 2.2 两个"注册表驱动"机制（本项目的核心手法）

| 注册表 | 作用 | 为什么必须这样 |
|---|---|---|
| `public_view_registry` | 登记"对全部等级开放"的视图；未登记视图默认只给 T3 | 视图以属主权限执行、绕过列级策略，必须显式声明意图 |
| `locked_object_registry`（迁移 062） | 登记"刻意为任何等级都不可读"的对象 + **理由** | **"刻意锁"与"忘了授权"在库里长得一模一样**，必须把意图写下来 |
| `metric_registry` / `dimension_registry` / `funnel_registry`（053/054） | 口径 / 分类 / 漏斗的**可执行**定义 | 口径即代码：只接受单条只读 SELECT/WITH，只有 T3 能写 |
| `algorithm_registry`（063） | 登记每套算法：版本、入口、用什么算、写到哪、**是不是用户侧** | 同一张表里混着多套算法的结果，不登记就无法机器检出"异版本被当成最新" |

### 2.3 审计与保留

- **行级审计**（`log_change()`）用于常规表；
- **按操作记**（`audit_mode='summary'`）+ `audit_bulk()` 用于**机械重算**类表
  （`job_requirement`/`job_task`：JD 解析"先删后插"，占审计流水 70%）；
- **缺口检测** `v_audit_gap`：用 PostgreSQL 自带行计数器与"最近一条汇总行的快照"比对，
  差额 = "改了但没有任何汇总行覆盖"。实测：写一行不写汇总 → 检出 +1；写汇总 → 归零。
  → **"换粒度"是可验证的，而不是关掉审计**；
- **保留期不发明**：`ops/retention.py` **只读项目既有的 `retention_policy`**
  （`rp_change_log` 1825 天、`rp_access_log` 1095 天、`rp_pii_contact` 30 天 + `legal_hold`），
  四道护栏：默认只 plan、必须给 `--max-rows`、未登记策略的表拒绝、`legal_hold` 拒绝。

### 2.4 数据性质隔离（本轮重点）

| 侧 | 判据 | 现状 |
|---|---|---|
| 人才 | `person.quality_flags` 含 `synthetic_fixture` | 3 真 / 120 合成 |
| 岗位 | `source_registry.is_synthetic`（**写入时登记的事实**） | **0 真 / 690 合成** |
| 能力权重 | 按职业关联到真实岗位的行数 | **0 / 10866** |

**不使用名称匹配**（`name LIKE '%fixture%'`）作为判据 —— 按命名判断数据性质一定会误伤。

新增口径 7 条（迁移 061）：真实/合成岗位占比、**按层级的**具体职业与方向覆盖率、
过期岗位比例、关键要求完整率、能力权重的真实支撑率。
迁移里带硬断言：**覆盖率分母必须是同层级**（防"23/151"那类错误重演）。

## 三、分析能力

### 3.1 三层分析，分工明确

| 层 | 页面 | 回答什么问题 | 关键实现 |
|---|---|---|---|
| 描述 | `/catalog` `/schema` `/t/<表>` `/field/<表>/<列>` | 库里有什么、字段什么分布 | 列级剖析物化（`column_profile`，1116 列） |
| 透视 | `/pivot` | 把人群分一分，结果在不同人群里有什么不同 | 维度注册表驱动 + 交叉表 + 目标占比 + Cramér's V + **分层对照** |
| 建模 | `/factors` | **多个因子同时进模型后，各自的贡献有多大** | 逻辑回归（IRLS，纯 numpy）+ **drop-one 似然比 χ²** 贡献排名 |
| 路径 | `/funnel` | 按业务路径的阶段转化 | 漏斗注册表；**阶段只能变窄**，写错直接报错 |
| 口径 | `/t/metric_registry` | 每个数字怎么算的 | 分子/分母/时间依据/修饰词/口径说明/**使用注意** |
| 接入 | `/integration` | 哪套算法接在哪、有没有东西卡住 | 算法注册表 + 版本冲突 + 未映射 + 投递队列 + 删除确认 |

### 3.2 分析的"诚实护栏"（这是本项目的特色）

1. **分母为 0 → NULL，不是 0**："还没有可算的对象"与"算出来是 0"是两件事。
2. **小样本不给百分比**：维度注册表带 `min_cell`，低于它标记 ⚠。
3. **缺失 ≠ 空值**：没填的字段**不写行**，所以比例的分母是"填了的人"。
4. **四道模型护栏**：EPV<10、稀疏格子、完全分离、完全共线 → 明确提示或**拒绝出 OR**。
5. **稀疏水平先合并，合并致共线则回退为排除稀疏个体**，两步都**写在页面上**。
6. **相关不是因果**：固定展示；提供分层对照作为最朴素的混杂检验。
7. **贡献 ≠ 因果**：Δχ² 大只说"有关联"。

### 3.3 已有真值验证（合成数据的正确用法）

`ops/seed_demo_analysis.py` 按**写明的规则**生成数据 → 我们知道真值 → 能检验分析：

| 写死的真值 | 分析实测结果 |
|---|---|
| 学历决定"是否进三级医院" | 贡献排第一，Δχ²=9.66，**p=0.008**（占 53%） |
| 海外经历**只由学历决定**、对去向无直接作用 | 粗 OR 2.21 → **独立贡献仅 6%**、p=0.288 |
| 户籍类型影响"去基层医疗" | 对三甲弱（p=0.63）✓ |
| 性别/年龄段无作用 | p=0.15 / 0.20，**无假阳性** ✓ |

### 3.4 ⚠ 分析的已知缺口

- **未映射概念 31.3%**（930/2970 条岗位要求）→ 这些要求只能进 `unknown`，
  直接构成匹配效果的天花板；
- **异版本匹配结果 100%**（150/150）→ 门户显示的匹配结果**不是**小程序返回的那套算法；
- **能力权重真实支撑率 0%** → 权重只能演示；
- 案例分析验证（`real_cases.py`，3 位公开人物）能发现缺陷，但**还不能证明推荐有效**
  ——缺带时间截点的验证集（评审优先级 4）。

## 四、前端设计

### 4.1 结构与信任边界

| 端口 | 是什么 | 能写吗 | 公网 |
|---|---|---|---|
| **8082** | 只读门户（28 页） | ❌（只读事务拒绝写入） | ✅ 已挂 |
| **8083** | 开发者模式（7 个写入口） | ✅ | ❌ **绝不** |
| 55432 | PostgreSQL | — | ❌ **绝不** |

两进程分开不是洁癖：**分开才能证明"门户在任何配置下都写不进去"**。

### 4.2 可用性（本轮重点改进）

**问题**：用户反馈"分析功能不明所以"。诊断：给了控件但没给**问题**，也没给
**结论**——人得自己从一堆数字里猜含义。

**改法（结论先行）**：

1. **首页最前面是「数据性质」卡** —— 因为它决定"下面这些数字该不该当业务结论读"。
2. **`/factors` 结论先行**：① 一句话结论（页面**自动从数据读出来**，含"谁只是影子"的警告）
   ② 贡献排名条形图 ③ 逐因子细节 ④ 数据与口径 ⑤ 能说什么/不能说什么。
   实测页面自动生成的结论：
   > **最高学历** 的贡献最大（Δχ²=9.66，p=0.008，占已解释偏差的 53%）。
   > ⚠ **海外经历 看着有关联、其实独立贡献很小**（粗 OR 2.21，Δχ²=1.13、p=0.288、占比仅 6%）
   > —— 它更像是被别的因子带出来的，不是独立的原因。
3. **`/pivot` 加引导 + 6 个一键预设**（点一下参数自动填好，不用理解每个控件）。
4. **`/integration` 顶部一句话结论**：
   > **门户上的匹配结果 100% 不是用户侧算法产出的** —— 它来自离线 50 维，
   > 而小程序返回的是规则版。这两者不可直接比较。
5. **`/match` 页面标注结果来自哪套算法**（版本冲突显式提示 + 链接到接入状态）。

**降级一律"说出来"**：权限不够、读不到、算不出来，页面都明确说明
（"需要登录" / "权限不足" / "还算不出来"），**不用"隐藏"来假装安全或假装完整**。

### 4.3 功能性

- **只读门户**：总览 / 数据目录 / 表与视图 / 单表 / 单字段 / 检索 / 透视 / 多因子 /
  漏斗 / 分析 / 可视化 / 人才库 / 职业库 / 职业树 / 匹配 / 真实案例 / 扩展演化 /
  血缘 / 质量 / 审计 / SQL / 接入状态 / 登录。
- **写入口（开发者模式）**：新增职业、批量导入（表格）、mock 注册窗口、
  动态建模（零 DDL 加字段）、SQL 控制台、运维工具、迁移与结构。
- **每个写动作都**：GET 只渲染、POST 才执行（防预取误触发）、必填审计理由、
  失败给**人能看懂的话**（重复编号 / 悬挂父节点 / 值不在字典）。
- **交互式透视**：选 1 个变量=分布、2 个=交叉表、选目标变量=每格占比、
  再选分层=每层重复同一张表；自动算 Cramér's V 并标小样本 ⚠。
- **表格默认列可切换**、排序、分页；人才库默认列含 **person_id + 来源编号**
  （用户反馈"看不到自己写的 id"后加的）。

### 4.4 视觉效果

- **零 JS 依赖**：服务端渲染 + 纯 CSS，`<table>` 语义化，键盘焦点可见，
  空状态有明确文案（不是空白页）。
- **热力表**：透视格子的底色按"占该行的比例"渐变，分布差异一眼可见。
- **贡献条形图**：`/factors` 的贡献排名用横向条形图（宽度＝Δχ² 占比）。
- **漏斗**：横向条 + 环比/累计两列 + 每阶段说明。
- **颜色语义固定**：⚠ 橙色边框＝需要警惕的结论（版本冲突、数据性质告警）；
  红色 `note err`＝故障；蓝色＝中性说明。

### 4.5 ⚠ 前端已知缺口（评审已指出，尚未做）

- **导航组织**：28 个页面的导航是一行平铺，**没有分组**；
- **移动端**：未做响应式验证；
- **真实任务验证**：没有"让真实用户按任务走一遍"的记录，可用性改进目前基于反馈与自查；
- **注册页（`/mockreg`）**：功能已修（人才库能看到自己填的编号、检索能按编号搜到人），
  但**表单外观与分组尚未重做**——已截图定位问题（整张表单是一个手写 flex 的墙、
  「外部编号」标签没说明"你填的会被强制加前缀"）。

### 5.0 审计：只记"真的变了什么"（迁移 066–068）

**先说一次我自己的错误归因（值得写下来）**：
一次完整回归里备份步骤报 **7224 秒（2 小时）**，而我当时正在看 `change_log` 的体积，
就写下"根因是审计体量把它拖慢了 10 倍"，还把这句写进了口径说明。
**实际原因是机器休眠。** 后来单独重测：**622.6 秒**（历史常态 664 秒）—— **没有劣化**。

这跟"两个变量一起变所以有因果"是同一个错误，而我刚刚在评审里反复强调
"相关不是因果"、还在页面上写了固定警示。**我对自己也该用同一个标准。**
迁移 068 专门更正了那两条口径里的错误因果链，并把纪律写进口径说明：
**看到某步骤变慢时，先确认它真的在干活还是被挂起（休眠/锁等待/网络超时都会表现成慢），再谈原因。**

**但核过的事实仍然成立，而且指向一个真实的质量问题：**

| 事实（已核） | 数值 |
|---|---|
| `change_log` 体量占库比例 | **210.5 MB / 255 MB = 82%** |
| 其中机械重算类表产生的行 | **83.4%** |
| `job_posting` 在 050 之后仍产生的行 | **31,790 行**（050 治了 `job_requirement`，没治它） |
| 这些审计行的**内容** | 只有 `{"op":"UPDATE","row":"job_id=…","mode":"row"}` —— **看不出改了哪一列** |

**所以问题不是"备份被拖慢"，而是"审计行没有信息量却占了 82% 的库"** ——
31,790 行既占 27 MB，又回答不了"到底改了什么"。它唯一的含义是"这一行被 UPDATE 过"，
**而这恰恰是零信息**。

**修法（066）**：让审计只记真的变了什么
1. **无实质变化的 UPDATE 不写审计**（值全一样 → 零信息，不该占体量）；
2. **有变化时记变化的列名**（不记值：避免体积膨胀与个人信息外泄）；
3. 只改**簿记列**（`updated_at`/`recorded_at` 之类，由 `now()` 自动维护）也算无实质变化 ——
   名单放注册表 `audit_ignore_columns`，可查可改，不写死在函数里。

实测（新增第 29 步，13 项）：
```
[PASS] 无实质变化的 UPDATE 不写审计（259 → 259）
[PASS] 只改簿记列（recorded_at）不写审计（259 → 259）
[PASS] 真实变更必须写审计（259 → 260）—— 不能拦过头
[PASS] 审计里记录了变化的列名（['title_normalized']）
[PASS] summary 模式的表逐行 UPDATE 仍不写审计（625561 → 625561）—— 050 的成果没被破坏
```

**历史 771,715 行噪声没有删** —— 那是**数据保留决策**（`rp_change_log` 保留 60 个月，
现有行全在保留期内），删它等于绕过保留策略，不该由一次排查顺手做掉。
新增口径 `M_AUDIT_NOISE_RATE`（83.4%）与 `M_AUDIT_CHANGELOG_MB`（210.5 MB）
把这件事变成可监控的数字，**归档与否留给保留策略的决策者**。

**又一次"只会在失败路径上出现的 bug"**：新门禁 I1.8 第一版写 `r[0]` 而连接是 `dict_row` ——
`no_grants` 为空时那行根本不执行，所以一直没暴露；等它**真的检出违规**时自己崩了，

### 5.2 优先级 4：有时间截点的真实验证集（迁移 069–071）

| 表 | 状态 |
|---|---|
| `occupation_change`（16 列，含 retire/remap，status 含 **reverted**） | **0 行** |
| `occupation_migration`（9 列，含 relation/coverage） | **0 行** |
| `dataset_release`（15 列，version/is_live/status） | **0 行** |

也就是说：**流程建模了，但没有任何计算把它们打通** ——
没有"改这个节点会碰到谁"的计算、变更与发布没有关联、迁移表没有一致性检查。

**补的三样计算（不新建流程，复用已有的表）：**

| 要求 | 落点 | 实测 |
|---|---|---|
| **变更影响预览** | `v_occupation_impact` —— 每个节点的下游依赖盘点 + 风险分级 | **76/151 节点是高影响**；**56 个零依赖**；依赖最多的是 `OCC-F01-01-01 住院医师`（30 岗位 + 3 权重 + 14 人经历 = **47**） |
| **发布管理** | `occupation_release_item` + `v_occupation_release_status` | 变更纳入发布的覆盖率；`published_with_pending` 指出"已发布却挂着未决变更" |
| **下游一致性** | `v_occupation_downstream_gap` | 三类缺口：**A** 停用但下游仍引用且无迁移映射（**静默悬挂，最危险**）、**B** 迁移指向不存在节点、**C** 已生效但未纳入发布 |

**风险分级的依据是「改动会不会让下游失效」，不是「这个节点重不重要」** ——
一个"重要但没人引用"的节点改起来是安全的，而一个"不起眼但有 30 份 JD"的节点
改起来会直接影响推荐。

#### 页面：`/extend` 顶部新增三块
`影响预览`（前 8 个高依赖节点 + 各下游分类计数）+ `发布管理` + `下游一致性`。
原来这一页只讲"树怎么长"，现在把"**改之前先看影响**"放在最前面。

#### ⚠ 这一项最重要的设计点：**"0 缺口"什么也证明不了**
`M_EVO_DOWNSTREAM_GAPS` 当前是 **0**，而库里**还没有任何变更记录** ——
一个"永远返回 0 的检查"和一个"真的能发现问题的检查"，在空库上**长得一模一样**。
所以口径的注意项里我自己写了这句，并配了一个 **`selfcheck`**：
**故意造出不一致 → 确认被检出 → 修好 → 确认消失 → 回滚 → 清理**。

实测（新增第 33 步，25 项）：
```
[✓] 停用但无迁移映射 → 被检出（期望 1，实测 1）
[✓] 已生效但未纳入发布 → 被检出（期望 1，实测 1）
[✓] 补上迁移映射 → A 类缺口消失（期望 0，实测 0）
[✓] 迁移指向不存在的节点 → 被检出（期望 True，实测 True）
[✓] 纳入发布 → C 类缺口消失（期望 0，实测 0）
[✓] 回滚后该变更不再产生缺口（期望 0，实测 0）
[✓] 发布状态视图反映变更归属（期望 1，实测 1）
清理：变更 0 · 归属 0 · 发布 0 · 迁移 0   ← 并在数据库层面复核，确认没留残渣
```

#### 过程中发现的两个**模式设计事实**（改代码前必须知道）
1. **`occupation_migration.new_id` 是 NOT NULL** —— 所以"停用"也**必须给出下游重映射目标**，
   无法表达"纯停用无后继"。这是**对的设计**（下游总得有地方去，否则就是静默悬挂），
   但我第一版自检写了 `new_id=NULL`，直接违反非空约束。
2. **`dataset_release.doc_codebook_uri` 是 NOT NULL** —— 每次发布都必须给出**码本位置**，
   否则别人拿到数据也不知道字段怎么解释。

#### 工具：`ops/evolution.py`
`impact <occupation_id>`（影响预览）· `check`（一致性）· `selfcheck`（真走一遍证明机制成立）。

### 4.9 默认列：按任务决定"先看哪几列"（迁移 073–074）

**先核验**：只有**人才库**有默认列机制；通用表页 `/t/<表>` 是 `SELECT *` 把所有列铺开 ——
`occupation` 25 列、`job_posting` **41 列**，最前面常是簿记时间戳与内部载荷。

**做法：规则 → 解析 → 注册表**（而不是逐表手写清单——那会重演"新表没人补"）

| 层 | 内容 |
|---|---|
| `default_column_rule` | 规则：表名模式 × 列名模式 → 可见性 + 排序位 + **理由** |
| `refresh_default_columns()` | 把规则解析到**每一张表的每一列**，并**从系统目录把真主键置顶** |
| `table_default_columns` | 解析结果（每表每列一行，含 `rule_id` 便于回答"为什么这列被藏了"） |

**默认顺序按用户的任务**：主键（这是哪条记录）→ 码值/状态 → 人可读名称 →
业务时间 → 数量/分值 → 说明。**默认隐藏**：簿记列、内部载荷（长 JSON）、技术校验字段。

实测：`job_posting` 默认 36/41 列（隐藏 `recorded_at, valid_from, valid_to, attrs, parse_version`）；
`occupation` 默认 21/25 列。**隐藏占比 14.2%，解析覆盖率必须 100%。**

#### ⚠ 隐藏 ≠ 不可达（页面上的"看不到 ≠ 没有"）
默认列是"**先看这些**"，不是"只能看这些"：`?all=1` 展开全部列，
而且页面**明确列出隐藏了哪些列、为什么隐藏**。否则就是本库最怕的
「看不到 ≠ 没有」在界面上的翻版。

#### 我在这里犯的一个错（已修，迁移 074）
073 用列名模式 `^(id|.*_id)$` 认"标识列"，于是 `job_posting` 里
`employer_id / ingest_run_id / job_id / occupation_id / source_id` **全部同档**，
按字母排序后 **真主键 `job_id` 被挤到第三位**，第一列成了 `employer_id`。

**这不是笔误，是我违反了自己反复强调的原则**：本库口径纪律写着「**判据是事实，不是名字**」——
我在 061 判数据性质时专门用 `source_registry.is_synthetic` 而拒绝名称匹配，
说"按命名判断一定会误伤"；转头就在默认列上用列名猜主键。
而主键在系统目录里是**确定的事实**（`pg_index.indisprimary`），根本不需要猜。

修法：列名规则降级为"引用列"（position 15）；主键由 `pg_index` 判定并置顶。
实测 `job_posting` 第一列 = `job_id`、`occupation` = `occupation_id`、`person` = `person_id`。

#### 还有一个防呆口径
`M_UI_DEFAULT_COL_COVERAGE`（解析覆盖率，**必须 100%**）——
**第一版我把它的值写成了 `visible/total`**，于是算出 85.8 并在断言处报错。
**断言是对的、口径写错了**：我们要求的是"每一列都被解析过（隐藏的仍可达）"，
不是"每一列都默认显示"。

#### ⚠ 我第三次踩进同一个坑：裸 try/except 毒化事务
第一版 `default_cols` 写的是 `try: q(...) except psycopg.Error: return None, []`。
**异常被吞了，但 PostgreSQL 的事务已经被毒化** —— 之后任何语句都报
`InFailedSqlTransaction`。表现是：**匿名访问 `/t/person`（本来该 403）变成了 500**，
而且错误信息与真正的权限问题**毫无关系**（日志里只有"事务已中止"）。

修法：改用项目里**现成的** `try_read()`（它用 SAVEPOINT 把失败圈在一小段里）。
更该记一笔的是 —— `try_read` 的文档字符串里明确写着：
> 「这个坑本项目踩过两次，**第二次就在这里**」

也就是说：**我绕开现成机制手写了一遍，于是第三次踩在同一个坑上。**
这类"降级读"必须走同一个入口，不能各写各的：一个吞异常的 `except` 看起来无害，
实际把整页打成 500。已由第 21 步「公网暴露面」165 项回归守住
（它专门断言"读不到的表返回 403 而不是 500"）。

### 5.1 优先级 3 的实测结果（匹配三态）

评审的三条判断**全部被实测数据证实**，而且数字很极端：

| 证据 | 实测 |

| **coverage 分母** | 6750 条维度评估里：两侧都没有值 3957 · **岗位侧没有值 1108（＝不适用）** · 人侧没有值 1093 · 满足 541 · 部分满足 31 · 确认不满足 20 |

   "人侧没有值""两侧都没有值"仍计入（那是**该采集而没采到**）。

2. **资格判定独立成三态**，且**只要有硬门槛 unknown，结论只能是"待核实"** ——

   实测：**150/150 全部"待核实"，平均 5.7/8 个硬门槛未知**。
3. **并列给名次范围**：同分共享 `[rank_min, rank_max]`，页面显示"并列第 1–50 名"。
   实测：**150/150 条存在同分**（最多一组 50 条）。

`provisional = true` —— 评审明确说"正式阈值应通过真实验证确定"，
所以页面标注"该阈值当前是临时值，尚未用带时间截点的真实验证集确定"。
