## 二、后端数据管理

### 2.1 分层与访问控制（权限强制点在数据库）

```
T0 匿名公开  <  T1 注册用户  <  T2 可信  <  T3 运维/管理
mt_portal：零表权限，每次会话 SET LOCAL ROLE mt_tN —— 客户端 cookie 里只有会话 id，
           等级由**数据库里的行**决定（伪造 cookie 不等于伪造 T3）
```

- **列级策略是生成的，不是手写的**：`mt.column_policy` 由 `refresh_column_policy()` 为
  **每张表的每一列**重新生成（默认 `table_default = T1`），再由规则逐条覆盖。
  规则来源：字段字典（`field_catalog`）、人工策略（`access_policy`）、模式匹配（`pattern`）。
- **表级 GRANT 会被对账收回** —— 这是机制，不是 bug。所以**不要**直接 `GRANT`；
  要改等级就改策略表再对账（迁移 058 记录了这次教训）。
- **披露控制**：主体标识列（`person_id` 等语义上的标识）不得 ≤ T0（迁移 030/044）；
  计数可见性登记在 `public_count_excluded`（048/049）。
- **导出禁令**：`export_denied` 表登记不得带走的列（健康限制、PII）→
  导出时**明确列出被移除的列**（`X-Export-Denied` 响应头），不静默删列。

### 2.2 两个"注册表驱动"机制（本项目的核心手法）

| 注册表 | 作用 | 为什么必须这样 |
|---|---|---|
| `public_view_registry` | 登记"对全部等级开放"的视图；未登记视图默认只给 T3 | 视图以属主权限执行、绕过列级策略，必须显式声明意图 |
| `locked_object_registry`（迁移 062） | 登记"刻意为任何等级都不可读"的对象 + **理由** | **"刻意锁"与"忘了授权"在库里长得一模一样**，必须把意图写下来 |
| `metric_registry` / `dimension_registry` / `funnel_registry`（053/054） | 口径 / 分类 / 漏斗的**可执行**定义 | 口径即代码：只接受单条只读 SELECT/WITH，只有 T3 能写 |
| `algorithm_registry`（063） | 登记每套算法：版本、入口、用什么算、写到哪、**是不是用户侧** | 同一张表里混着多套算法的结果，不登记就无法机器检出"异版本被当成最新" |

### 2.3 审计与保留

- **行级审计**（`log_change()`）用于常规表；
- **按操作记**（`audit_mode='summary'`）+ `audit_bulk()` 用于**机械重算**类表
  （`job_requirement`/`job_task`：JD 解析"先删后插"，占审计流水 70%）；
- **缺口检测** `v_audit_gap`：用 PostgreSQL 自带行计数器与"最近一条汇总行的快照"比对，
  差额 = "改了但没有任何汇总行覆盖"。实测：写一行不写汇总 → 检出 +1；写汇总 → 归零。
  → **"换粒度"是可验证的，而不是关掉审计**；
- **保留期不发明**：`ops/retention.py` **只读项目既有的 `retention_policy`**
  （`rp_change_log` 1825 天、`rp_access_log` 1095 天、`rp_pii_contact` 30 天 + `legal_hold`），
  四道护栏：默认只 plan、必须给 `--max-rows`、未登记策略的表拒绝、`legal_hold` 拒绝。

### 2.4 数据性质隔离（本轮重点）

| 侧 | 判据 | 现状 |
|---|---|---|
| 人才 | `person.quality_flags` 含 `synthetic_fixture` | 3 真 / 120 合成 |
| 岗位 | `source_registry.is_synthetic`（**写入时登记的事实**） | **0 真 / 690 合成** |
| 能力权重 | 按职业关联到真实岗位的行数 | **0 / 10866** |

**不使用名称匹配**（`name LIKE '%fixture%'`）作为判据 —— 按命名判断数据性质一定会误伤。

新增口径 7 条（迁移 061）：真实/合成岗位占比、**按层级的**具体职业与方向覆盖率、
过期岗位比例、关键要求完整率、能力权重的真实支撑率。
迁移里带硬断言：**覆盖率分母必须是同层级**（防"23/151"那类错误重演）。

## 三、分析能力

### 3.1 三层分析，分工明确

| 层 | 页面 | 回答什么问题 | 关键实现 |
|---|---|---|---|
| 描述 | `/catalog` `/schema` `/t/<表>` `/field/<表>/<列>` | 库里有什么、字段什么分布 | 列级剖析物化（`column_profile`，1116 列） |
| 透视 | `/pivot` | 把人群分一分，结果在不同人群里有什么不同 | 维度注册表驱动 + 交叉表 + 目标占比 + Cramér's V + **分层对照** |
| 建模 | `/factors` | **多个因子同时进模型后，各自的贡献有多大** | 逻辑回归（IRLS，纯 numpy）+ **drop-one 似然比 χ²** 贡献排名 |
| 路径 | `/funnel` | 按业务路径的阶段转化 | 漏斗注册表；**阶段只能变窄**，写错直接报错 |
| 口径 | `/t/metric_registry` | 每个数字怎么算的 | 分子/分母/时间依据/修饰词/口径说明/**使用注意** |
| 接入 | `/integration` | 哪套算法接在哪、有没有东西卡住 | 算法注册表 + 版本冲突 + 未映射 + 投递队列 + 删除确认 |

### 3.2 分析的"诚实护栏"（这是本项目的特色）

1. **分母为 0 → NULL，不是 0**："还没有可算的对象"与"算出来是 0"是两件事。
2. **小样本不给百分比**：维度注册表带 `min_cell`，低于它标记 ⚠。
3. **缺失 ≠ 空值**：没填的字段**不写行**，所以比例的分母是"填了的人"。
4. **四道模型护栏**：EPV<10、稀疏格子、完全分离、完全共线 → 明确提示或**拒绝出 OR**。
5. **稀疏水平先合并，合并致共线则回退为排除稀疏个体**，两步都**写在页面上**。
6. **相关不是因果**：固定展示；提供分层对照作为最朴素的混杂检验。
7. **贡献 ≠ 因果**：Δχ² 大只说"有关联"。

### 3.3 已有真值验证（合成数据的正确用法）

`ops/seed_demo_analysis.py` 按**写明的规则**生成数据 → 我们知道真值 → 能检验分析：

| 写死的真值 | 分析实测结果 |
|---|---|
| 学历决定"是否进三级医院" | 贡献排第一，Δχ²=9.66，**p=0.008**（占 53%） |
| 海外经历**只由学历决定**、对去向无直接作用 | 粗 OR 2.21 → **独立贡献仅 6%**、p=0.288 |
| 户籍类型影响"去基层医疗" | 对三甲弱（p=0.63）✓ |
| 性别/年龄段无作用 | p=0.15 / 0.20，**无假阳性** ✓ |

### 3.4 ⚠ 分析的已知缺口

- **未映射概念 31.3%**（930/2970 条岗位要求）→ 这些要求只能进 `unknown`，
  直接构成匹配效果的天花板；
- **异版本匹配结果 100%**（150/150）→ 门户显示的匹配结果**不是**小程序返回的那套算法；
- **能力权重真实支撑率 0%** → 权重只能演示；
- 案例分析验证（`real_cases.py`，3 位公开人物）能发现缺陷，但**还不能证明推荐有效**
  ——缺带时间截点的验证集（评审优先级 4）。

## 四、前端设计

### 4.1 结构与信任边界

| 端口 | 是什么 | 能写吗 | 公网 |
|---|---|---|---|
| **8082** | 只读门户（28 页） | ❌（只读事务拒绝写入） | ✅ 已挂 |
| **8083** | 开发者模式（7 个写入口） | ✅ | ❌ **绝不** |
| 55432 | PostgreSQL | — | ❌ **绝不** |

两进程分开不是洁癖：**分开才能证明"门户在任何配置下都写不进去"**。

### 4.2 可用性（本轮重点改进）

**问题**：用户反馈"分析功能不明所以"。诊断：给了控件但没给**问题**，也没给
**结论**——人得自己从一堆数字里猜含义。

**改法（结论先行）**：

1. **首页最前面是「数据性质」卡** —— 因为它决定"下面这些数字该不该当业务结论读"。
2. **`/factors` 结论先行**：① 一句话结论（页面**自动从数据读出来**，含"谁只是影子"的警告）
   ② 贡献排名条形图 ③ 逐因子细节 ④ 数据与口径 ⑤ 能说什么/不能说什么。
   实测页面自动生成的结论：
   > **最高学历** 的贡献最大（Δχ²=9.66，p=0.008，占已解释偏差的 53%）。
   > ⚠ **海外经历 看着有关联、其实独立贡献很小**（粗 OR 2.21，Δχ²=1.13、p=0.288、占比仅 6%）
   > —— 它更像是被别的因子带出来的，不是独立的原因。
3. **`/pivot` 加引导 + 6 个一键预设**（点一下参数自动填好，不用理解每个控件）。
4. **`/integration` 顶部一句话结论**：
   > **门户上的匹配结果 100% 不是用户侧算法产出的** —— 它来自离线 50 维，
   > 而小程序返回的是规则版。这两者不可直接比较。
5. **`/match` 页面标注结果来自哪套算法**（版本冲突显式提示 + 链接到接入状态）。

**降级一律"说出来"**：权限不够、读不到、算不出来，页面都明确说明
（"需要登录" / "权限不足" / "还算不出来"），**不用"隐藏"来假装安全或假装完整**。

### 4.3 功能性

- **只读门户**：总览 / 数据目录 / 表与视图 / 单表 / 单字段 / 检索 / 透视 / 多因子 /
  漏斗 / 分析 / 可视化 / 人才库 / 职业库 / 职业树 / 匹配 / 真实案例 / 扩展演化 /
  血缘 / 质量 / 审计 / SQL / 接入状态 / 登录。
- **写入口（开发者模式）**：新增职业、批量导入（表格）、mock 注册窗口、
  动态建模（零 DDL 加字段）、SQL 控制台、运维工具、迁移与结构。
- **每个写动作都**：GET 只渲染、POST 才执行（防预取误触发）、必填审计理由、
  失败给**人能看懂的话**（重复编号 / 悬挂父节点 / 值不在字典）。
- **交互式透视**：选 1 个变量=分布、2 个=交叉表、选目标变量=每格占比、
  再选分层=每层重复同一张表；自动算 Cramér's V 并标小样本 ⚠。
- **表格默认列可切换**、排序、分页；人才库默认列含 **person_id + 来源编号**
  （用户反馈"看不到自己写的 id"后加的）。

### 4.4 视觉效果

- **零 JS 依赖**：服务端渲染 + 纯 CSS，`<table>` 语义化，键盘焦点可见，
  空状态有明确文案（不是空白页）。
- **热力表**：透视格子的底色按"占该行的比例"渐变，分布差异一眼可见。
- **贡献条形图**：`/factors` 的贡献排名用横向条形图（宽度＝Δχ² 占比）。
- **漏斗**：横向条 + 环比/累计两列 + 每阶段说明。
- **颜色语义固定**：⚠ 橙色边框＝需要警惕的结论（版本冲突、数据性质告警）；
  红色 `note err`＝故障；蓝色＝中性说明。

### 4.5 ⚠ 前端已知缺口（评审已指出，尚未做）

- **导航组织**：28 个页面的导航是一行平铺，**没有分组**；
- **移动端**：未做响应式验证；
- **真实任务验证**：没有"让真实用户按任务走一遍"的记录，可用性改进目前基于反馈与自查；
- **注册页（`/mockreg`）**：功能已修（人才库能看到自己填的编号、检索能按编号搜到人），
  但**表单外观与分组尚未重做**——已截图定位问题（整张表单是一个手写 flex 的墙、
  「外部编号」标签没说明"你填的会被强制加前缀"）。
