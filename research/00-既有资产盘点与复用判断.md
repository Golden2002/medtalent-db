# 既有资产盘点与复用判断（新项目：医学生人才信息库）

> 盘点方式：**只读**，未修改任何既有项目文件。
> 对象：**A = medical**（`D:\桌面\智能体架构与开发（含大模型）\14.6_medical-resume-agent`，Flask + 42 个 .py / 9 个 Schema / 262 测试）；**B = ajs**（`D:\wbo-workspace\ai-job-search-derived-agent`，求职工作流 + `product/` Python 包 27 模块 / 448 测试）。
>
> **总结论**：两者都是"简历生成 + 岗位匹配"工具。强项是**证据溯源、事实门禁、来源分级**；弱项正是**结构化人才库本身**——无字段级字典、无代码表、无版本化、无实体关系、无数据库。故新项目应**复用规范与 Schema，新建元数据与存储**。

## 6. 完全缺失（必须从零建）

| # | 缺失项 | 现有资产为何不够 |
|---|---|---|
| 1 | **字段级元数据 / 数据字典** | 只有 JSON Schema，无字段名、中文名、类型、必填、单位、枚举取值、口径说明、来源、负责人、置信度、PII 级别的字典表。自助式分析需要可查询字典，Schema 文件做不到 |
| 2 | **代码表 / 受控词表** | 学历层次、学位、学科专业目录、院校（统一机构码）、职称、规培/执业资格、行政区划、语言等级、机构类型、岗位族、雇佣类型、薪资周期——现全为自由文本或散落局部 enum；无同义词/别名、无映射、无版本 |
| 3 | **版本化与迁移机制** | `schema_version` 是硬编码 `const`（如 `resume-document-v1`），**同一时刻只能存在一版**；无 Registry、无版本并存、无迁移脚本、无废弃流程 |
| 4 | **实体关系与主数据去重键** | 无 `person`/`education_record`/`employment_record`/`publication`/`credential`/`institution`/`posting`/`occupation` 关系表与外键；ID 规范各项目自定互不兼容（`experience_id` 正则 vs `ev_[0-9]+`）；无去重键（岗位规范化链接/岗位 ID、机构统一社会信用代码、论文 DOI） |
| 5 | **结构化存储与检索层** | 无 DB、无索引、无全文/结构化筛选、无聚合分页、无并发写入、无权限与访问审计；现状是"单文件 JSON + `data\.sessions` 平铺会话文件"（`file_session_store`） |
| 6 | **数据质量与入库门禁** | 只有零散 `review_status`/核验状态字段，无入库校验器（必填、枚举、来源可达性、重复、时效、可信度分级）；`docs\research\*` 的 7 条入库前检查仍是清单 |

## 8. 结论

**可直接复用**：medical 的 9 个 Schema（尤其 `canonical-experience-v2`、`bullet-claim-v2`、`career`、`medical_profile`）+ `RESEARCH_METHOD.md` 来源分级 + `DATA_POLICY.md` + `DOMAIN_MODEL_V2.md` 实体清单 + 4 个医学 Role Pack + 5 张职业卡 + 4 个事实门禁模块；ajs 的 `job_portal` 适配器契约 + `job_evaluation` 五维评分与中文分词 + 6 门户采集 CLI + 采集合规纪律。

**必须从零建**：① 字段级数据字典；② 代码表/受控词表与别名映射；③ Schema 版本化与迁移；④ 实体关系与主数据去重键；⑤ 结构化存储与检索层（另需 PII 分级与中国渠道采集）。
