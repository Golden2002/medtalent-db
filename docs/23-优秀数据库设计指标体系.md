# 23 · 优秀数据库设计指标体系（本标准为本项目的验收依据）

> **一句话**：本标准把"数据库好不好"从评价性说法变成 **34 条可测量指标**，
> 每条都有「定义 / 测法 / 目标 / 判定」。测量工具是 `ops/health.py`（一条命令出记分卡）。
>
> 立这个标准的原因不是形式主义，而是本项目已经吃过两次亏（见 §1）。

---

## 0. 为什么必须先把标准立起来

### 教训一：写在文档里的能力，和真实具备的能力，是两件事

`docs/06` 与 README 早就写了完整的数据分级模型：`access_policy` 表里有 10 条真实策略
（字段 × 动作 × 最低等级，`X` 表示禁止）、`access_log` 表建好了、`field_catalog.access_tier`
对 176 个字段标了 T0–T3。看起来"权限体系已完成"。

实测（2026-10 本轮）：

| 声称具备 | 实测 |
|---|---|
| 字段分级 | `field_catalog.access_tier` 分布 T0=53 / T1=105 / T2=13 / T3=5 —— **标了** |
| 访问策略 | `access_policy` 10 条 —— **有** |
| 访问被限制 | RLS 启用表 **0 张**；列级授权 **0 条** —— **没有拦截** |
| 访问被记录 | `access_log` **0 行** —— **从未记录过任何一次访问** |

也就是说，**指标本身必须是"实测值"，不能是"设计值"**。这是本标准第一条方法论。

### 教训二：静态合规与真实性质是两件事

16 套回归 514 项断言全绿的同时，`/quality` 页（自称「可核的数字，不是形容词」）
给出的一段"可核 SQL"用的是 **`pg_class.reltuples` 估算** —— 而项目设计纪律第 6 条明令禁止它，
同一文件里另外 3 处提到 `reltuples` 也全是在说"不要用它"。
**测试通过 ≠ 性质成立**：当时的断言只检查页面"写着"什么，不检查页面"做"什么。

所以本标准要求每条指标**给出可执行的测法**，且判定依据是那个测法的返回值。

## 1. 本标准的依据（权威框架）—— 以及**引用纪律**

标准不是凭偏好定的，但**引用必须可核查**。`docs/22` 的调研逐条去打开来源，
结果是：有些框架的正文**打不开**（403 / 需购买 / 站点不可达）。那些
**一律不作为本标准的依据**，也不在本文里提条款号。

| 维度 | 依据（均为本轮实际读到正文的来源） |
|---|---|
| 正确性与完整性 | 关系模型约束理论（主键/外键/CHECK）、PostgreSQL 16 官方文档（`ddl-constraints`、`sql-createindex`、`using-explain`） |
| 数据质量 | 数据质量六维（完整性/准确性/一致性/及时性/唯一性/有效性）；ISO/IEC 25012 中**已核实**的 Accuracy / Completeness / Consistency 三条定义 |
| 性能 | PostgreSQL 16 官方文档（`planner-stats`、`routine-vacuuming`、`monitoring-stats`）；USE 方法（utilization/saturation/errors） |
| 安全与隐私 | PostgreSQL 16 官方文档（`ddl-priv`、`ddl-rowsecurity`、`sql-grant`、`sql-createfunction`）；**PIPL 官方全文**（中国人大网，已逐条读到）；OWASP Top 10 项目页 |
| 可维护与可演进 | Fowler 的 Parallel Change（expand→migrate→contract，已读原文）；PostgreSQL `sql-altertable` / `ddl-alter`（锁级别与是否重写） |
| 可观测性 | 审计六要素（谁/何时/对什么/做了什么/结果/多少行）；PostgreSQL `monitoring-stats` |
| 成本与资源 | PostgreSQL `routine-vacuuming`、`pg_stats`、`app-vacuumdb` |
| 互操作与可复用 | codebook 发布纪律（本项目 `dataset_release` 的 CHECK 约束）；标准词表与版本化 crosswalk |

**明确不作为依据的**（`docs/22` 标为"未能核实"，本文因此不引用）：

| 框架 | 原因 |
|---|---|
| ISO 8000 | ISO 官网 **HTTP 403**，正文未取到 —— 不引用其 Part 号与特性名 |
| CMMI DMM / EDM Council DCAM | 电子书/演示 PDF 不可取；且它们是**面向组织的成熟度评估**，评估单元是"数据管理项目组"，本项目为单机便携、一人维护，**够不到评估单元** |
| Google SRE 的 SLO/误差预算/黄金信号 | `sre.google` 全站 4 个 URL 均 fetch failed —— 本文只用 USE 方法，不引 SLO 条款 |
| Codd 12 条准则 | 判定对象错配（它判的是"DBMS 产品是否完全关系型"），且条目未核实 |
| CAP / PACELC | 单机单实例、无副本，**没有测量对象** —— 本文不讨论 |
| FAIR 完整合规 | 需要持久标识符与公共仓库登记，本项目无此基础设施；硬套只会产出"缺失 12/15 项"这类打击士气的指标 |
| 一切成熟度等级评分 | 成熟度是**对组织的判断**，需独立评估方；无独立评估方时任何打分都是自评，**不具备验收效力** |

> 方法论：**只把能读到正文的框架当依据；读不到就写"未核实"并放弃引用。**
> 这比"引用一个听起来权威的标准名"诚实，也让本标准经得起追问。

## 2. 指标怎么设计（三档判定，避免"全是红灯等于没有红灯"）

| 档位 | 含义 | 未达标时的动作 |
|---|---|---|
| **MUST** | 违反就是缺陷。`ops/health.py` 返回非零，可接进回归当门禁 | 必须修；修复前不得声称该能力已具备 |
| **SHOULD** | 应当达到，但可以有条件地不达 | 必须在文档里写清理由与计划，不能沉默 |
| **INFO** | 只记录数值与趋势，不判定 | 无（例如体积、增长率、规模类数字） |

每条指标必须同时具备三样：

1. **定义** —— 它衡量什么性质（不是"我们做了什么"）；
2. **测法** —— 一条可执行查询或一次真实测量，且**打印在结果里供复核**；
3. **目标与判定** —— 达标线，以及未达标属于哪一档。

不允许出现"由某脚本保证"这类**只登记契约、不实现测量**的指标 ——
本标准第一版就这么写过一条，结果它显示成绿色的 `0/0（由 ... 保证）`，实际什么都没测。

## 3. 指标总表（2026-10-09 实测）

测量命令：`python ops/health.py`。下表的"实测"是脚本输出，"测法"是脚本里登记的那一条。

### D1 正确性与完整性 —— 数据是不是"说得通"

| 编号 | 指标 | 实测 | 目标 | 档 | 测法 |
|---|---|---|---|---|---|
| I1.1 | 指向 person 的孤儿行数 | **0** | 0 | MUST | 动态发现 **29** 张外键子表，逐表 `LEFT JOIN` 反查 |
| I1.2 | 未归入任何业务域的基础表数 | **0** | 0 | MUST | `information_schema.tables` 对比门户 `DOMAIN_TABLES`（82 张表） |
| I1.3 | 无主键的基础表数 | **0** | 0 | MUST | `table_constraints` 里没有 PRIMARY KEY 的表 |
| I1.4 | 外键约束总数 | 96 | ≥90 | INFO | `pg_constraint contype='f'` |
| I1.5 | 断链外键数 | **0** | 0 | MUST | `confrelid = 0`（引用了不存在的表） |
| I1.6 | 启用中的业务触发器数 | 88 | ≥10 | INFO | `pg_trigger` 非内部触发器 |
| I1.7 | "存码不存标签"违例数 | **0** | 0 | MUST | 码列里不允许出现中日韩字符（把纪律变成机器可检形式） |

前三条说明本项目在"引用完整性"上有真东西：**29 张子表逐个反查、0 孤儿行**。
`field_value.subject_id` 是例外（它**根本没有指向 person 的外键**，被另一个调研实测确认：
直接 `DELETE FROM person` 会成功而 `field_value` 里的值原样留下）—— 这条已单独记入
`docs/21-注册与增删验证调研.md` 的孤儿检测方案。

### D2 数据质量 —— 不只是"多少行"，而是"多少行真的有值"

| 编号 | 指标 | 实测 | 目标 | 档 | 测法 |
|---|---|---|---|---|---|
| I2.1 | 采样空值率≈100% 的列数 | 87 | — | INFO | `pg_stats.null_frac >= 0.999`（**采样值，不是精确值**，仅提示嫌疑） |
| I2.2 | 物理列被字段字典覆盖的比例 | **8.3%** | ≥70% | SHOULD | 列名与 `field_catalog.field_id` 去前缀后按约定比对 |
| I2.3 | 同时存在 NULL 与空串的文本列数 | 53 | — | INFO | `pg_stats` 里 `0 < null_frac < 1` 的文本列（"空"的歧义要显式说明） |
| I2.4 | 变更流水行数 | 565,402 | — | INFO | `count(*) FROM change_log` |

**I2.2 = 8.3% 是本次体检最重要的坏消息之一**：字段字典（176 个字段）覆盖不到一成的物理列。
换言之，"数据字典"目前更像**画像维度的注册表**，而不是**全库列的字典**。
这与访问控制那条指标（I4.3 = 8.1%）是同一个根因，见 §5 的处理计划。

`pg_stats` 是 **ANALYZE 之后的采样统计**，所以 I2.1 只作提示；
要精确值必须逐列 `count(*) FILTER (WHERE col IS NULL)` —— 那是目录页要物化的东西
（见 `docs/20-数据目录与字段剖析调研.md`：`change_log` 单列 `count(DISTINCT)` 实测 1,319 ms，
328 列实时剖析会直接拖垮回归）。

### D3 性能 —— 不看感觉，看三条可复现的测量

| 编号 | 指标 | 实测 | 目标 | 档 | 测法 |
|---|---|---|---|---|---|
| I3.1 | 最大表 `count(*)` 耗时 | **114 ms** | ≤2000 ms | SHOULD | 对 565,402 行的 `change_log` 实测一次精确计数 |
| I3.2 | 最大表 3 列浓度剖析耗时 | 见脚本 | ≤3000 ms | SHOULD | `count(*)` + 两个 `count(列)`，需扫全表 |
| I3.3 | 顺序扫描 / 索引扫描 次数比 | 见脚本 | — | INFO | `pg_stat_user_tables` 累计值 |
| I3.4 | 从未被扫描过的索引数 | 见脚本 | — | INFO | `pg_stat_user_indexes.idx_scan = 0` |
| I3.5 | 索引数 / 表数 | 见脚本 | — | INFO | `pg_indexes` 与 `pg_class` 计数 |

### D4 安全与隐私 —— 本维度全部用实测，不接受"写在文档里"

| 编号 | 指标 | 实测 | 目标 | 档 | 测法 |
|---|---|---|---|---|---|
| I4.1 | 服务入口仍用超级用户连接的文件数 | **7** | 0 | **MUST** | 只扫 10 个服务入口；命中 9 个，其中已登记例外 2 个（见下） |
| I4.1b | 门户请求路径使用受限角色 | **是** | 是 | **MUST** | 解析 `PORTAL_DSN` 的 `user=` 必须非 postgres，且请求路径确实用 `psycopg.connect(PORTAL_DSN)` |
| I4.2 | 列级策略覆盖的列数 / 全部列数 | 1048 / 1048 | — | INFO | `column_policy` 对比 `information_schema.columns` |
| I4.3 | 列级策略里有字典/人工依据的比例 | **8.1%** | ≥30% | SHOULD | `v_column_policy_coverage`：字典 82 + 人工 1 / 共 1048 |
| I4.4 | 动作级 `X` 禁令数 / 列级 `X` 数 | **5 / 0** | — | INFO | 两套策略尚未汇合 ⇒ **导出禁令目前没有强制点** |
| I4.5 | `access_log` 行数 | **198** | >0 | SHOULD | 已有真实访问记录（此前长期为 0） |
| I4.6 | 属主是超级用户的视图数 | 20 | — | INFO | 视图默认以**属主**权限执行 ⇒ 对 T0–T2 **一律不授视图**（迁移 023），只授 T3 |
| I4.7 | 启用了 RLS 的表数 | 0 | — | INFO | 行级隔离目前靠外键与角色分层，RLS 未启用 |
| I4.8 | `person_pii` 行数（加密存储） | 0 | — | INFO | 列名 `*_enc` 表示密文 |

**I4.1 的两次修正，本身就是"指标要精确"的教训。** 它第一版 grep 全仓的
`user=postgres`，于是门户接线完成后仍报 **9** —— 因为 `admin_db()`（进程级元数据缓存）
与 `ops/backup/backup.py`（备份）里确实还有那个串，而那是**有理由的例外**。
第二版改成全仓扫描，报 **34**（把临时探针脚本也算进来了）。第三版才收敛到
**10 个真正的服务入口**，得到 **7**：
**一个把"有理由的例外"和"缺陷"混在一起报红的指标，会训练人忽略它。**

已登记的例外（每一项都必须写明理由，且可被独立验证）：

| 文件 | 理由 |
|---|---|
| `code/demo/portal.py` | `admin_db()` 只用于**进程级元数据缓存**（系统目录 + 每张表行数；行数按需求是公开信息）与 `--check` 构建期自检。**用户请求一律走 `PORTAL_DSN`（mt_portal）**，由 I4.1b 独立验证 |
| `ops/backup/backup.py` | 备份**必须**用超级用户：非超级用户 `pg_dump` 会报 RLS 错误，而 `--enable-row-security` 会**静默丢行**（实测）——宁要超级用户，也不要一份悄悄少了几行的备份 |

**I4.5 = 198 行访问日志**：这条长期是 0（"设计上会记"），本轮接线后首次有真实数据。
审计记录里 `actor_role` 取自 `current_setting('role')`（数据库认定的调用者角色，不可伪造），
`actor` 取自应用声明的会话身份（应用理论上可以说谎）——两者都记，不一致时一眼可见。

**I4.1 = 9 是当前唯一未达标的 MUST。** 它不是"忘了改配置"，而是架构缺口：
数据库层已经把拦截造好了（列级 `GRANT` 实测能让 `SELECT *` 被**直接拒绝**、
未设等级就**读不到任何数据**），但**应用层还没走上去** ——
`code/demo/portal.py`、`portal_dev.py`、`app.py`、`code/db.py`、`code/bridge/*.py`
仍然以超级用户连接。**超级用户绕过一切，连 `FORCE ROW LEVEL SECURITY` 都拦不住（实测）**，
所以在此之前，I4.2 的 1029 条列级授权对任何运行中的服务都没有约束力。

> 例外：`ops/backup/backup.py` **应当保持 `postgres`**。实测：非超级用户 `pg_dump`
> 会报 `query would be affected by row-level security policy`，而加 `--enable-row-security`
> 则会**静默丢行** —— 备份宁可要超级用户，也不能要一份悄悄少了几行的备份。
> 所以 I4.1 的目标应表述为"**对外提供服务的进程**用 0 个超级用户"，备份/迁移工具除外。

### D5 可维护性与可演进 —— 改一次结构要付多少代价

| 编号 | 指标 | 实测 | 目标 | 档 | 测法 |
|---|---|---|---|---|---|
| I5.1 | 迁移文件数 / 台账条数 | 21 / 21 | 相等 | SHOULD | `schema/sql/*.sql` 对比 `schema_migration` |
| I5.2 | 字典校验错误数 / 警告数 | **0 / 0** | 0 | MUST | 真跑 `validate_catalog.py` 并解析输出 |
| I5.3 | 已登记字段数 / 统一值表行数 | 176 / 0 | — | INFO | 零 DDL 扩展机制的证据 |
| I5.4 | 画像维度数 / 声明两侧落点 / **实测两侧可评** | 50 / 50 / **14** | — | INFO | 三个数字语义不同，混起来会高估匹配能力 |

**I5.4 的两个 50 与一个 14 必须分开看**：`v_dimension_two_sided` 数的是

把前者当后者，会把匹配能力高估 3.5 倍。本标准第一版就把这条写成"50/50"，已改正。

## 4. 四条需求 → 指标映射（这就是"翻译成专业能力"的具体形态）

用户提的 4 条需求，翻译成专业能力后各自对应到本标准的具体指标：

| 需求（原话） | 专业能力 | 对应指标 | 当前状态 |
|---|---|---|---|
| ① 记录访问用户 + 每个字段权限不同 | 访问审计 + 列级授权（RBAC/列级安全） | I4.1 I4.2 I4.3 I4.4 I4.5 I4.6 I6.2 | 数据库层**已建成并实测有效**；应用层未接线（I4.1 = 9） |
| ② Cloudflare 免费域名挂到公网 | 反向隧道 + 边缘身份验证 + 纵深防御 | 新增一组（见 §6 待纳入） | 方案已调研（`docs/19`），未实施 |
| ③ 看到字段名/数量/分类统计/检索 | 数据目录 + 列级剖析 + 元数据检索 | I2.1 I2.2 I2.3 I3.1 I3.2 | 目录页未建；已确认**必须物化**（实时剖析代价过高） |
| ④ mock 窗口测试真实增删 | E2E 写路径 + 幂等 + 墓碑 + 清理覆盖面 | I1.1（孤儿行）+ 新增一套增删判据 | 方案已调研（`docs/21`），未实施 |

**"编号、年龄可以公开，其他字段限权"这句需求翻译过来是两条不同的能力**：

- **编号类**（`person_id`/`subject_code`）→ 列级策略 T0，**并且**实测确认
  `count(*)` 不引用任何列时**仍可执行** —— 所以"数量公开、字段受限"能同时成立；
- **年龄**（`birth_year`）→ 这里有一个**必须由你决策的口径冲突**（见 §5 第 2 条）：
  "年龄可以公开"与"出生年月是个人信息"是两件事，专业做法是公开**年龄段**、不公开**出生年**。

### 5.1 本轮新发现的**权限提升漏洞**（已修，单列）

这一类问题 `ops/health.py` **抓不到** —— 抓到它的是端到端探针与新增的断言。

**PostgreSQL 的 `CREATE FUNCTION` 默认把 `EXECUTE` 授予 `PUBLIC`。**
迁移 022 里我只记得对 `web_user_add` 做了 `REVOKE ... FROM PUBLIC`，
漏了 `web_session_new` —— 而它是 `SECURITY DEFINER`，且**等级是参数**：

```sql
SELECT mt.web_session_new('attacker', 'T3');   -- 返回一个合法的新会话 id
```

任何能执行它的角色都能给自己造一个 **T3 会话**，把 id 放进 cookie 就拿到全部列的读权限。
**这不是"读了不该读的"，而是"自己给自己发权限"** —— 比前者严重。

- **修法**：迁移 026 做了 `REVOKE ... FROM PUBLIC, mt_portal, mt_t0..mt_t3`，
  并把这条约束写进 `apply_role_baseline()`（否则下次 `apply_column_grants()` 会把它授回来）。
- **026 的硬断言当场拦住了第一版修复**：我当时只 REVOKE 了 PUBLIC，忘了 022 里
  显式授给过 `mt_portal`，于是断言报「角色 mt_portal 仍能执行 web_session_new」并**拒绝登记迁移**。
  这正是"把约束写成断言"的价值 —— 它不依赖我记性好不好。
- **断言**：`access_test.py` 的 **A8**（6 个角色 × 会话函数 + 会话表四个权限 + 口令哈希不可读）
  与 **A9**（审计表 append-only：无 UPDATE/DELETE/TRUNCATE）。
- **教训**：**"我没授权"不等于"没人能用"** —— 凡是 `SECURITY DEFINER` 且参数含身份/权限级别的函数，
  必须显式 `REVOKE`。

### 5.2 门户接线的三处真实设计错误（都由实测暴露）

| 错误 | 症状 | 正确做法 |
|---|---|---|
| 认证操作也切到等级角色 | 登录请求先 `SET LOCAL ROLE mt_t0`，再调只授给 `mt_portal` 的 `web_login()` → **连登录都登不进去** | "能登录"与"能用哪个等级读数据"是两件事：`db(session, as_role=False)` 专用于认证路径 |
| 整页因权限不足而失败 | 匿名访客打开首页被 `concept_relation` 拒绝 → 403 | ① 本体结构属公开字典（迁移 025 修规则漏项）；② 匿名首页给**公开落地页**（T0 概览 + 登录入口），而不是一堵 403 墙 |
| 首页要读 T1 数据 | `job_competency_weight` | 面板级**优雅降级**：读得到的显示、读不到的说"需要登录"，且**绝不当成 0**（那会把权限不足显示成数据缺失） |

## 6. 本标准尚未覆盖的指标（诚实列出）

一个只写"已覆盖什么"的标准是不可信的。以下是**目前没有纳入**的指标及原因：

| 未纳入 | 原因 | 何时补 |
|---|---|---|
| 并发下的性能（吞吐/延迟分位） | 本项目只有 2–3 个并发用户，测出来的 P99 没有意义 | 需求②上线后（公网会有真实并发），届时用 `pg_stat_statements` + 应用侧计时 |
| 故障恢复的 RTO/RPO **实测** | 备份套件已验证"恢复到新库并逐表核对"（32 项断言），但恢复耗时未作为指标登记 | 下一次全量回归时记录耗时，纳入 D6 |
| 表/索引膨胀率 | 数据量还小（163 MB），膨胀不显著；测量需要 `pgstattuple` 扩展（**未确认可装**） | 数据量翻 10 倍后 |
| 连接池与排队 | 当前连接数 6/50，远未触限 | 公网部署后 |
| 计划的稳定性（plan regression） | 无统计基线历史 | 配合一次 `ANALYZE` 建立基线 |
| 端到端可用性（uptime） | 单机开发环境，"可用性"没有意义 | 公网部署后 |

## 7. 标准怎么被强制执行（否则它也会变成"写在文档里的能力"）

1. **一条命令出记分卡**：`python ops/health.py`；有 MUST 未达标则退出码非零。
2. **接进回归**：作为新的套件登记进 `ops/tests/run_all.py`，
   与另外 17 套一起跑 —— 这样"指标退化"会像"测试失败"一样立刻被发现。
3. **每条指标自带测法**：脚本会打印每条指标的测量方式，任何人可以手工复核。
4. **例外必须显式**：例如 `backup.py` 保持超级用户，这一条例外写进指标说明里，
   而不是让指标默默只统计一半进程。
5. **不许"只登记契约"**：未达标的 MUST 项修复前，不得在任何文档或页面上声称该能力已具备。
