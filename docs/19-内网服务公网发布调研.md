# 19 · 内网服务公网发布调研

> 主题：**把本机上跑的服务安全地发布到公网（用 Cloudflare 免费方案）**，并给出针对本机限制的可执行 runbook。
> 调研日期：2026-10-09（Asia/Shanghai）。当时 `cloudflared` 最新版本：**2026.10.0**（发布 2026-10-05）。

---

## 0. 方法与可核查性声明

**做法**
- 所有关键结论都来自**实际打开官方文档/官方博客/官方仓库**，并在下文给出可点击 URL 与英文原文引用。
- 无法核实的内容一律写明「**未能核实**」，不猜数字、不猜条款。
- 本机侧的能力（网络可达性、代理行为、下载 URL 有效性、二进制签名）是**在本机实测**的，不是抄文档。

**本机约束（据用户提供，且已被我的实测部分印证）**
- Windows，**无管理员权限**（不能装服务、不能改防火墙入站规则、`schtasks /Create` 被拒）。
- 无 winget / choco / docker；不能用 `curl.exe`（`SEC_E_NO_CREDENTIALS`）和 `Invoke-WebRequest`。
- 下载只能用 **Python urllib**；用户提供代理 `http://127.0.0.1:7892`（7890 已不通）。
- 便携版 PostgreSQL 在 `127.0.0.1:55432`；三个 Python 服务：`:8082` 只读门户、`:8083` 可写开发者模式、`:8081` 业务控制台；**全部只监听 127.0.0.1**。

**本机实测结论（与 runbook 直接相关，重要）**
1. **代理 7892 目前是坏的**：端口在监听，SOCKS5 握手有响应（`05 00`），HTTP `CONNECT example.com:443` 曾返回 `200 Connection established`，但随后**对所有目标**（example.com / github.com / api.github.com / developers.cloudflare.com / tailscale.com / ngrok.com / registry.npmjs.org）的 TLS 一律 `ConnectionResetError` 或 `SSLEOFError`。
2. **直连反而可用**：不加代理时 Python urllib 可以正常 HTTPS 访问 `example.com`(200)、`api.github.com`(200)、`github.com` 以及 `raw.githubusercontent.com`。
   → 因此 runbook 的下载步骤设计为**先直连，代理 7892 仅作备选**，并在失败时如实提示换网络/热点。
3. **到 Cloudflare 隧道边缘的出站连通性正常**（TCP 实测，2026-10-09）：

   | 目标 | 端口 | 实测 |
   |---|---|---|
   | `region1.v2.argotunnel.com` | 7844 | **TCP-OK**（198.41.192.37） |
   | `region2.v2.argotunnel.com` | 7844 | **TCP-OK**（198.41.200.63） |
   | `api.cloudflare.com` | 443 | TCP-OK |
   | `update.argotunnel.com` | 443 | TCP-OK |
   | `dash.cloudflare.com` / `one.dash.cloudflare.com` | 443 | TCP-OK |

   `cloudflared` 默认走 QUIC(UDP 7844)、失败回退 http2(TCP 7844)（官方 Run parameters 文档），所以 TCP 7844 通是必要条件；UDP 是否可用我**未能核实**（UDP 无连接，无法用同样的方法断定）。

**我做不到的事（因此必须由你在浏览器里手动完成）**
- 我不能注册/登录 Cloudflare、不能创建 Zero Trust 组织、不能加域名、不能点面板按钮、不能复制 Tunnel token。
- 因此 §4 中所有「面板步骤」都是**文档所述路径**，**未在本机实操验证**；只有命令行部分是我基于已核实文档 + 本机实测写成的。

## 1. Cloudflare 免费方案的种类与真实限制（带官方 URL）

### 1.1 Quick Tunnel（`*.trycloudflare.com`）

官方文档：<https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/>（页面标注 Last updated **Sep 30, 2026**）

```bash
cloudflared tunnel --url http://localhost:8080
```

**已核实的限制**（官方 Limitations 列表原文）：
- `Quick Tunnels have no uptime guarantee.`
- `Each Quick Tunnel supports up to 200 in-flight requests. Additional requests return a 429 response.`
- `Quick Tunnels do not support Server-Sent Events (SSE).`
- `Email authentication requires an interactive browser session. It does not support non-interactive clients.`
- **`The hostname changes each time you create a Quick Tunnel.`**
  → **「每次重启换域名」属实**。
- 官方定性：`Quick Tunnels are for testing and development. For production, create a Cloudflare Tunnel.`
- 停止进程即失效：`The URL stops working when you stop the cloudflared process.`

**新变化（很重要，很多旧资料已过时）**：Quick Tunnel 现在支持**邮箱白名单 + 一次性验证码**：

```bash
cloudflared tunnel --url http://localhost:8080 --allowed-mail alice@example.com
cloudflared tunnel --url http://localhost:8080 --allowed-mail 'alice@example.com,bob@example.com'
cloudflared tunnel --url http://localhost:8080 --allowed-mail '*@example.com'
```

官方博客（2026 年，标题 *Protected Quick Tunnels: simple accountless authentication for your next dev project*）：<https://blog.cloudflare.com/protected-quick-tunnels/>
博客原文要点：
- 访客走的是 **Cloudflare Access 登录页**，用 **one-time PIN** 证明邮箱归属；
- 但**授权清单留在本机**：`your guest list never leaves your machine. Cloudflare learns that a tunnel requires email authentication. It doesn't learn who you invited.`
- 会话有效期：`up to four hours`；`Access ends for everyone the moment the process exits.`
- 改名单的办法是**停掉隧道再开一个新的**（于是域名也变）。

**关键问题：Quick Tunnel 能不能挂 Cloudflare Access 策略？——不能（这点已由官方来源确认）**

三条互相印证的官方证据：
1. 博客明确说他们**一开始想给每个 Quick Tunnel 挂 Access 应用，但做不到**：`Our first idea was to put a Cloudflare Access application in front of every Quick Tunnel hostname... But hundreds of thousands of Quick Tunnels can be running at once... With no account to own them, we would have had to invent a new namespace...`，并给出根本原因：`Every Cloudflare product that enforces access rules keeps the authorization half in the same place: your Cloudflare account. A Quick Tunnel doesn't ha[ve]...`
2. Access 自托管应用的**前提是域名必须属于你账号里的 active zone**：`Domains must belong to an active zone in your Cloudflare account.`（<https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/>）。`trycloudflare.com` 不属于你。
3. Quick Tunnel 文档给出的保护手段**只有** `--allowed-mail`，Limitations 里没有任何「可加 Access 策略」的说法。

> 结论（可直接采用）：**Quick Tunnel 只能靠 `--allowed-mail` 做「演示级」门禁，不能使用 Cloudflare Access 的策略/白名单/服务令牌体系**——所以它**不适合承载真实个人信息库**。

**未能核实**：`--allowed-mail` 所需的**最低 cloudflared 版本号**（Quick Tunnel 文档 2026-09-30 更新，我已核实当前最新版 2026.10.0 的下载可用，但没有版本号明文）。

### 1.2 Named Tunnel + 自有域名（推荐的生产路径）

官方文档：
- <https://developers.cloudflare.com/tunnel/>（Overview）
- <https://developers.cloudflare.com/tunnel/get-started/>
- 本地管理：<https://developers.cloudflare.com/tunnel/features/locally-managed-tunnels/create-local-tunnel/>
- 面板/远端管理：<https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/get-started/create-remote-tunnel/>
- Run 参数（`--token` / `--token-file`）：<https://developers.cloudflare.com/tunnel/reference/run-parameters/>

**免费版能否满足？——能满足，但有明确边界**

| 维度 | 已核实结论 | 依据 |
|---|---|---|
| 是否免费 | **Cloudflare Tunnel「Available on all plans」**，含 Free | Overview 页原文 `Available on all plans`；`no public IPs required` |
| 是否需要自有域名 | **需要**（要发布到公网主机名，必须先把域名加入 Cloudflare）。且文档明确要求先 `Add a website to Cloudflare`，并（本地管理模式）把 NS 改到 Cloudflare | create-local-tunnel 前置条件；create-remote-tunnel 的 Prerequisites |
| 子域名数量 | Tunnel 数：**每账号 1000 条隧道**；DNS 记录：**2024-09-01 之后新建的 Free zone 上限 200 条**（该日期之前建的 Free zone 为 1000 条）；Pro/Business/Enterprise 3500 条 | Account limits 页（`cloudflared` tunnels per account = 1,000）；DNS 文档源文件原文 `Free zones crated on or after 2024-09-01 ... limit of 200 DNS records` |
| 带宽 / 请求限制 | **官方没有公布 Named Tunnel 的带宽或请求计量上限**（与 ngrok 那种「1GB/月」完全不同）。但有一条**兜底的「非常规用途」条款**，见 §1.4 | 未找到任何官方计量表；ToS 有保留限制权条款 |
| SLA | **没有 SLA**。协议原文：`We will have no liability for any harm or damage arising out of or in connection with any Free Services.`，且服务按 `"AS IS" AND "AS AVAILABLE"` 提供 | <https://www.cloudflare.com/terms/>（Self-Serve Subscription Agreement） |
| 免费版日志能力 | **逐请求日志（HTTP 明细、Logpush）属 Enterprise**；免费版只有 24 小时的 Access/HTTP/DNS/Network 日志与 18 个月的 Admin 日志 | Zero Trust Logs 页的 Log retention 表（见 §3.5） |
| 加密 | 出站、**后量子加密（post-quantum encrypted）**长连接；`No open inbound ports. No public IPs.` | Overview 页原文 |

**两种建法（都很重要，因为它决定你要不要 `cert.pem`）**

- **远端管理（Remote-managed，推荐给本机）**：面板里建隧道 → 拿 **token** → 本机只需
  `cloudflared tunnel run --token <TOKEN>`（文档有该参数的正式条目；`--token-file <PATH>` 需要 **2025.4.0+**）。
  刷新 token / 轮换也在面板做（`Rotate token`）。**不需要 `cert.pem`、不需要 `config.yml`。**
- **本地管理（Locally-managed）**：`tunnel login` → 生成 `cert.pem`；`tunnel create` → 生成凭据 JSON；写 `config.yml`；`tunnel route dns`；`tunnel run`。
  默认目录：Windows = **`%USERPROFILE%\.cloudflared`**（官方 Useful terms 页）；`cert.pem` 有效期 **至少 10 年**，凭据文件「等同 token」。

**Windows 上的一个硬约束（决定了 runbook 的形态）**：官方「Run as a service / Windows」文档明确写着 **`Open CMD as an administrator`**，并且要改 `HKLM\SYSTEM\CurrentControlSet\Services\Cloudflared` 的 `ImagePath`。
→ **本机无管理员权限，不能装服务**。替代方案见 §4 Step 4（启动文件夹）。
→ 另外文档明确：**Windows 上 `cloudflared` 不会自动更新**（`Instances of cloudflared do not automatically update on Windows.`），必须手动更新。

### 1.3 Cloudflare Access（Zero Trust）

官方文档：
- 计划/席位：<https://developers.cloudflare.com/cloudflare-one/team-and-resources/users/seat-management/>
- 策略与选择器：<https://developers.cloudflare.com/cloudflare-one/access-controls/policies/>
- 发布自托管应用：<https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/>
- 账号上限：<https://developers.cloudflare.com/cloudflare-one/account-limits/>
- 上手：<https://developers.cloudflare.com/cloudflare-one/setup/>

**免费版最多多少个用户？**
- 官方 Zero Trust 定价数据里的计划描述原文（我从官方页面数据 `https://www.cloudflare.com/page-data/plans/zero-trust-services/page-data.json` 中读出）：
  - 计划名：**`Zero Trust Q4 - Free Plan`**
  - 描述：**`Best for teams under 50 users or enterprise proof-of-concept tests.`**
  - 对照的付费档描述：`Best for teams over 50 users solving narrow SSE use cases...`
- → **结论：免费档面向 50 用户以内（上限 50 个席位）。**
- **如实标注**：`https://www.cloudflare.com/plans/zero-trust-services/` 是 JS 渲染的，我**没有**在该页面正文里读到 `up to 50 users` 这个字面句子；上面的 50 来自**官方站点自身的计划描述数据**。这是我能拿到的最权威表述。
- 机制（官方 Seat management 页）：
  - 「用户执行一次认证事件就消耗一个席位」；同一用户访问多个应用仍只算一个席位；席位用满后其他用户**登录会被拦**。
  - 用户不会自动过期，除非开启 **seat expiration**（可设 1 个月~1 年）。
  - **Bypass 策略不消耗席位**（也不产生日志，官方明确警告）；**Service token 不消耗席位**（适合机器对机器/非交互客户端）。
- **创建 Zero Trust 组织时要选计划并填付款信息**，官方原文：`Complete your onboarding by selecting a subscription plan and entering your payment details. If you chose the Zero Trust Free plan, this step is still needed but you will not be charged.`
  → **这一步只能你手动做（要填卡，但不扣费）。**

**支持哪些身份源？**
- 建组织时会**自动加 Cloudflare IdP**（`your users can sign in with their Cloudflare account credentials right away`）；
- 可加 **One-time PIN**，以及第三方 IdP；账号上限页给出 **Identity providers = 50**。
- 官方 Access 选择器（selectors）里与身份相关的包括：`Emails`、`Emails ending in`、`Login Methods`、`Authentication Method`(MFA)、`Identity provider group`、`SAML Group`、`OIDC Claim`、`External Evaluation` 等。

**能否只允许特定邮箱访问？——能。**
- 官方示例策略：`Allow | Include | Emails ending in | @example.com`（这正是我们要的）。
- 也支持 `Require`（AND）与 `Exclude`（NOT）；`Allow` 可叠加 Require/Exclude。
- **Access 默认拒绝**：`All Access applications are deny by default -- a user must match an Allow policy before they are granted access.`
- **官方点名的两种致命误配置**（会造成「任何人都能进」）：
  1. `Include | Everyone | Everyone`
  2. `Include | Login Methods | One-time PIN`
  → 配置时务必核对是 `Emails` / `Emails ending in`，不是 `Login Methods`。

**能否对 `*.trycloudflare.com` 生效？——不能**（理由见 §1.1）。

**其他与本次相关的官方上限**：Access 应用 500 个、每账号 IdP 50 个、Service tokens 50 个、每条规则邮箱地址 1000 个、每应用规则 1000 条。

### 1.4 免费版条款：「非常规用途」与被保留的限制权

**(A) CDN 条款（免费/Pro/Business）** — <https://www.cloudflare.com/service-specific-terms-application-services/>
标题：*Content Delivery Network (Free, Pro, or Business)*。原文：

> Cloudflare's content delivery network (the "CDN") Service can be used to cache and serve web pages and websites. Unless you are an Enterprise customer, Cloudflare offers specific Paid Services (e.g., the Developer Platform, Images, and Stream) that you must use in order to serve video and other large files via the CDN. **Cloudflare reserves the right to disable or limit your access to or use of the CDN, or to limit your End Users' access to certain of your resources through the CDN, if you use or are suspected of using the CDN without such Paid Services to serve video or a disproportionate percentage of pictures, audio files, or other large files.** We will use reasonable efforts to provide you with notice of such action.

→ 解读：**「把大量数据/文件下载当 CDN 用」确实有被限制/禁用的风险**，且这是 Cloudflare 单方保留的权利。**没有公布具体的带宽数字阈值**——只有 `disproportionate percentage` 这种兜底表述（所以「免费版带宽软限制是多少」的准确答案是：**未有官方公开数字，只有这条兜底条款**；文档中**未能核实**任何具体 GB 数）。

**(B) Self-Serve Subscription Agreement §2.2.1 Restrictions** — <https://www.cloudflare.com/terms/>
原文节选（与「把连数据库的应用挂公网」直接相关）：
- `(b) interfere with, disrupt, alter, or modify the Services ... or create an undue burden on the Services`
- `(c) access or use the Services in a manner that violates or is intended to circumvent Service-specific usage limits, quotas, or other restrictions`
- **`(h) process or collect personal or business credit card information on any web property that is receiving Free Services`**
- **`(i) use the Services to store or transmit any "protected health information" ... without Cloudflare's written consent`**
- `(j) use the Services to provide a virtual private network or other similar proxy services`
- 免费服务免责：`We will have no liability for any harm or damage arising out of or in connection with any Free Services.`

→ 对我们意味着：**不要把支付卡信息、健康信息放进免费档挂出去**；也不要把它当 VPN/代理给第三方用。

## 2. 替代方案对照

「免管理员」= 在本机（Windows、无管理员）能不能落地；「本机可行性」是结合本机约束的判断。

| 方案 | 免费额度（已核实） | 需自有域名 | 免管理员 | 安全性 | 适用场景 | 本机可行性 |
|---|---|---|---|---|---|---|
| **Cloudflare Quick Tunnel + `--allowed-mail`** | 完全免费、无需账号；无 uptime 保证；200 并发（超限 429）；不支持 SSE；会话≤4h | 否 | **是** | 中低：邮箱 OTP 门禁，但域名每次变、**不能挂 Access 策略**、改名单要换域名 | 临时演示、给一个人看几分钟 | **可行**（需 7844 出站，已实测通） |
| **Cloudflare Named Tunnel + Access**（推荐） | Cloudflare Tunnel 全计划可用；Access 免费档 ≤50 用户；DNS 记录免费 zone 200 条 | **是**（域名托管 CF） | **是**（不装服务，用启动文件夹） | **高**：边缘 TLS + 身份认证 + 白名单邮箱 + 可做源站 JWT 校验 + 边缘 WAF/限流 | 长期、小范围、含个人数据的管理后台 | **可行** |
| **Tailscale Funnel** | 官方原文：`Tailscale Funnel is available for all plans.`（**目前处于 beta**）；免费 **Personal**：`Free forever`、`Unlimited user devices`、`Up to 6 users` | 否（用 `tailnet-name.ts.net`） | **否**（要装 Tailscale 客户端；Windows 版要装系统级组件——**官方文档未见明文「需要管理员」，此点为推断，标注未能核实**） | 中：TLS + 只暴露指定端口；**Funnel 本身公开给整个互联网，无内置身份认证**（文档：`Available on the internet: https://...`，需应用自带登录） | 个人设备互访、临时分享（本机不适合） | **不可行**（安装依赖管理员/系统组件） |
| **ngrok 免费版** | 官方 *Free Plan Limits* 明文：Data transfer out **1 GB/月**、HTTP requests **20,000/月**、TCP connections **5,000/月**、Logs **10,000/月**、Webhook verifications 500/月、Traffic identities(OAuth/OIDC MAU) **3/月**；**在线 endpoint ≤3**、agents 3、Users 1、**Development domains 1**、Traffic policy rules 5/条、**TLS endpoints 不可用**；限速 HTTP 4,000/min、TCP 100/min；endpoint 无空闲超时；免费档浏览器访问有 **interstitial 提示页** | 否（但免费只有 1 个 `*.ngrok-free.app` 开发域，**自定义域要付费**） | **是**（单文件二进制，解压即用） | 中：自动 TLS；无边缘身份层（白名单/OAuth 需付费档以上能力，免费仅 3 个 MAU） | 快速演示、Webhook 调试 | 可行但**不适合**：1 GB/月 + 单一开发域 + 提示页 |
| **frp + 自己的小服务器** | 开源免费；但**必须自备公网服务器**（VPS 要花钱）；最新 release **v0.71.0（2026-08-14）** | 可选（用 IP+端口则不需要） | 客户端**是**；服务端需要 root | 中高：支持 token/TLS/STCP 等，可自控 | 有 VPS 时的自建长期方案 | 可行（成本>0；本机无需管理员） |
| **localtunnel** | npm 包，公共服务器 `localtunnel.me`；`--subdomain` 可请求名字但 README 注明 `**Note** You may not actually receive this name depending on availability.` | 否 | **是**（需 Node） | 低：默认随机子域、**无内置认证**；README 定位为测试 | 快速本地预览 | 需 Node（本机是否有 Node **未能核实**） |
| **Serveo** | SSH 反向隧道（`ssh -R`），无需装客户端；**免费额度/稳定性未能核实**（取 `serveo.net` 正文为空） | 否（`*.serveo.net`） | **是**（用系统 ssh） | 低-中：无内置认证；底层实现 sish 已开源（最新 **v2.24.1，2026-10-09**，支持认证密钥/SNI 路由） | 临时演示 | 可能可行，但**免费服务的可用性未能核实**，不建议承载私有数据 |
| **bore** | Rust 单二进制；公共服务器 `bore.pub`，**端口随机分配**；最新 **v0.6.0（2025-06-09）** | 否 | **是** | 低：官方定位 `That's all it does: no more, and no less.`——**纯 TCP 转发，无 TLS 终止、无认证** | 端口转发（如自建服务调试） | 可行但**不适合直接暴露 Web/PII** |
| **zrok** | 基于 OpenZiti 的零信任覆盖网络，可自托管或用官方免费 `zrok.io`（需 `zrok invite` 注册）；最新 **v2.0.8（2026-10-08）**；支持 HTTP/HTTPS/TCP/UDP/文件共享，**免费额度数字未能核实**（未取到官方定价页） | 否 | 是（客户端二进制） | 中高：零信任覆盖网络，有 share 模式与访问控制 | 需要更强网络层身份时 | 可能可行（需注册；额度未能核实） |
| **直接端口转发 + DDNS** | — | 通常需要（或记 IP） | **否** | 低 | — | **不可行**，原因见下 |

**为什么「直接端口转发 + DDNS」在本机不可行**
1. **无管理员权限**：改不了路由器/系统防火墙的入站规则（本机连 `schtasks` 都被拒，更不可能改 NAT）。
2. **多半没有公网 IPv4**：家宽/校园网普遍 CGNAT，外部无法直连。
3. **运营商普遍封禁入站 80/443**（即便有公网 IP）。
4. **直接暴露真实 IP**：把攻击面从 CDN 边缘挪到自家网络，DDoS/扫描直接打到本机。
5. 而且本机服务被有意绑定在 `127.0.0.1`——这是**既有的信任边界**，反向隧道（outbound-only）恰好不需要破坏它。

## 3. 安全清单（暴露面 / 身份验证 / TLS / 限流 / 日志 / 合规 / 紧急下线）

> 本节是全文最重要的部分。前提：这是一个**连着真实数据库的本地 Web 应用**，要挂到公网。

### 3.1 哪些端口绝对不能暴露（只放 `:8082`）

| 端口 | 内容 | 结论 | 为什么 |
|---|---|---|---|
| `:8082` | 只读门户（纯服务端渲染） | **唯一发布对象** | 只读、无写接口，风险面最小 |
| `:8083` | **可写**开发者模式 | **绝不发布** | 写权限 + 公网 = 数据被改/被删/被注入；开发者模式通常校验更松 |
| `:8081` | 业务控制台 | **绝不发布** | 控制台天然是高权限入口，且可能带调试/管理功能 |
| `:55432` | 便携版 PostgreSQL | **绝不发布** | 数据库线协议直接暴露＝把暴力破解、弱口令、PostgreSQL CVE 扫描仪请进门；隧道没有 SQL 层防护 |

**怎么做（具体到命令/配置）**
- 本地管理模式的 `config.yml`（唯一一条 hostname，末尾必须兜底 404）：
  ```yaml
  tunnel: <UUID>
  credentials-file: C:\Users\<你>\.cloudflared\<UUID>.json
  ingress:
    - hostname: portal.example.com
      service: http://127.0.0.1:8082
    - service: http_status:404
  ```
  校验：`cloudflared tunnel ingress validate`、`cloudflared tunnel ingress rule http://127.0.0.1:8082/`。
- 远端管理模式：**只加一条** Published application route → `http://127.0.0.1:8082`。**不要**建任何 CIDR 路由（`Tunnel CIDR`）指向 `127.0.0.1`/`::1` 或数据库端口。
- 本机侧自检（应全部是 `127.0.0.1`，不能是 `0.0.0.0`）：
  ```powershell
  Get-NetTCPConnection -State Listen |
    Where-Object { $_.LocalPort -in 8081,8082,8083,55432 } |
    Select-Object LocalAddress,LocalPort,OwningProcess
  ```
- **永远不要**为了「方便」把服务绑到 `0.0.0.0`：那等于同时暴露给局域网/校园网，且破坏既有信任边界。

### 3.2 身份验证：Cloudflare Access vs 应用内登录（两者关系 + 纵深防御怎么摆）

**关系（一句话）**：Access 解决「**谁能进来**」（网络边缘的认证+授权），应用内登录解决「**进来的是谁、能做什么**」（业务授权、细粒度权限、审计）。二者**不能互相替代**。

**推荐的纵深防御（三层）**
1. **第 1 层 — Cloudflare Access（边缘门禁）**：只允许指定邮箱，一次性 PIN 或 Google 登录。挡住 99% 的扫描器/爬虫/陌生人，且不需要你写代码。
2. **第 2 层 — 应用自身鉴权**：`:8082` 现在是**只读门户**；如果它本身**没有登录**，那么 Access 就是唯一门禁，风险集中在一个配置上（一旦策略写错＝裸奔）。建议至少加一个应用层口令/会话，或明确接受「只读 + Access 白名单」的风险。
3. **第 3 层 — 源站校验 Access JWT（关键，最容易被忽略）**：Cloudflare 官方明确要求：
   > `To secure your origin, you must validate the application token issued by Cloudflare Access. Token validation ensures that any requests which bypass Cloudflare Access (for example, due to a network misconfiguration) are rejected.`
   两种做法：在 Tunnel 设置里开 **`Protect with Access`**（由 `cloudflared` 代校验），或自建反向代理校验 `Cf-Access-Jwt-Assertion`。
   来源：<https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/self-hosted-public-app/>

**面板步骤（必须你手动做）**
1. `dash.cloudflare.com` → **Zero Trust** → 选 **Free** 计划（要填付款信息，不扣费）→ 建团队名。
2. **Zero Trust > Access controls > Applications > Create new application > Self-hosted and private**。
3. **Add public hostname** → Domain 选你的子域（域名必须已在 CF 账号内）。
4. **Access policies** → 新建：`Action=Allow`，`Include` → `Emails`（或 `Emails ending in`）填入你的邮箱/公司域。
   ⚠️ **绝对不要**用 `Include Everyone` 或 `Include Login Methods = One-time PIN`（官方点名的两种「谁都放进来」误配置）。
5. 身份源勾选 **One-time PIN**（最省事）或 Google。
6. **Session Duration** 选短一些（如 8h / 24h）——因为本方案下 Access 会话是你唯一的强门禁。
7. **Create**。
8. ⚠️ **顺序**：官方警告——**先建 Access 应用，再建隧道路由**；否则发布出来的应用会对全互联网开放：
   > `We recommend creating an Access application before setting up the tunnel route. If you do not have an Access application in place, the published application will be available to anyone on the Internet.`
9. 回到 **Networking > Tunnels**，为隧道 **Add route → Published application**，指向 `http://127.0.0.1:8082`。

**席位提醒**：免费档上限 **50 个用户席位**；每次认证事件消耗 1 个；被 Bypass 或 Service token 访问不消耗。给同事开权限前先想清楚席位数。

### 3.3 HTTPS 终点在哪？能不能只靠 Cloudflare 终止 TLS？

- **可以只靠 Cloudflare 终止 TLS**，本机不需要证书：
  - 访客 ↔ Cloudflare 边缘：HTTPS（CF 自动签发/续期，免费）。
  - Cloudflare ↔ `cloudflared`：**outbound-only、post-quantum encrypted** 长连接（官方 Overview 原文）。
  - `cloudflared` ↔ `127.0.0.1:8082`：**明文 HTTP，但只走回环接口**——这就是为什么 3.1 的「必须绑 127.0.0.1」是硬要求。
- 加固建议：zone 里开启 **Always Use HTTPS**；HSTS 视情况（开错会把自己锁死，谨慎）。
- 不要用自签证书折腾源站（会有 `noTLSVerify` 之类的坑，官方专门有 *Troubleshoot HTTPS origins* 文档）。

### 3.4 速率限制 / 爬虫 / 暴力破解（免费手段「有哪些、有多弱」）

**免费版速率限制的真实能力（已核实，别高估）** — <https://developers.cloudflare.com/waf/rate-limiting-rules/>
官方 Availability 表：Free 档
- **规则数：1 条**（Pro 2、Business 5、Enterprise 100）
- 表达式可用字段：**仅 Path 和 Verified Bot**
- 计数特征：**仅 IP**；不支持自定义计数表达式
- 计数周期：**固定 10 s**；缓解时长：**固定 10 s**

**面板步骤**（<https://developers.cloudflare.com/waf/rate-limiting-rules/create-zone-dashboard/>）
1. Dashboard → **Security rules**（`dash.cloudflare.com/?to=/:account/:zone/security/security-rules`）
2. **Create rule > Rate limiting rules**
3. Rule name：`portal-burst`
4. Field = `Path`，Operator = `equals`，Value = `/`（免费档只能用 Path）
5. **With the same characteristics** = `IP`
6. **When rate exceeds** = 例如 `20` requests / `10` seconds
7. **Then take action** = `Block`；Duration = `10 seconds`
8. **Deploy**

**其他免费缓解手段**
- **Bot Fight Mode**（免费）与 **Security Level**（必要时临时开 *I'm Under Attack*）。
- **WAF 托管规则**：免费档有 Cloudflare Free Managed Ruleset（对已知 CVE 的通用防护）。
- **缩短 Access 会话时长**（比限流有效得多）。
- **应用侧**：给 `:8082` 的查询加行数上限与超时，避免一次请求把便携版 PostgreSQL 拖死（免费版限流只有 10 秒窗口，挡不住慢速爬取）。
- **不要依赖「URL 保密」**：`trycloudflare.com` 子域会被扫描；Named Tunnel 的子域也会被证书透明度日志暴露。

|---|---|---|---|---|---|
| Admin logs | 18 个月 | 18 个月 | 18 个月 | 18 个月 | 18 个月 |
| **Access logs** | **24 小时** | 30 天 | 30 天 | 24 小时 | 180 天 |
| DNS logs | 24 小时 | 30 天 | 24 小时 | 30 天 | 180 天 |

**能看到的**（免费）：Zero Trust → **Insights > Logs > Access authentication logs**：谁、何时、用哪个邮箱、从哪个 IP/国家、`Allow=true/false`、Ray ID。字段清单见 <https://developers.cloudflare.com/cloudflare-one/insights/logs/dashboard-logs/access-authentication-logs/>。

**⚠️ 对合规的直接影响**：**免费版 Access 日志只留 24 小时**。任何「谁在什么时候访问了哪些个人数据」的事后审计，**不能依赖免费档**，必须：
- 自行用 API 定期导出（`GET /accounts/{account_id}/access/logs/access_requests`，需 `Access: Audit Logs Read` 权限），或
- 在应用/本机侧自己记审计日志。
- 本机 `cloudflared` 侧可选日志：`--log-directory <PATH>`（写入 `cloudflared.log`，**1 MB 轮转，保留 5 个备份**）或 `--logfile <PATH>`（不轮转）；`--loglevel debug` 会记录完整请求头，**可能泄露敏感信息**，生产别开。
- 注意日志本身也是个人数据（邮箱/IP）：导出后要有访问控制与保留期限。

### 3.6 数据合规要点（**仅为要点提示，不构成法律意见**）

把**含个人信息的数据库**挂到公网（哪怕加了登录），至少涉以下几件事：

1. **处理者/受托方链条变长**：Cloudflare（Tunnel + Access + CDN/WAF）成为链路上的**受托处理方/处理者之一**，会接触连接元数据与 Access 日志（邮箱、IP、国家、时间）。需要查 Cloudflare 的 **DPA / GDPR 条款 / 子处理者清单**；**Customer Metadata Boundary（把数据存储限定在特定地理区域）属于 Data Localization Suite，是付费能力**（官方 Logs 页提到）。
2. **《个人信息保护法》(PIPL)**：
   - **跨境提供**（第 38 条）：向境外提供个人信息需走安全评估、标准合同或认证之一，并履行告知—单独同意；即使只是「境外节点承载境内个人信息」也要评估。**需要做个人信息保护影响评估（PIPIA）并留存记录（第 55、56 条）**。
   - **最小必要与安全措施义务（第 51 条）**：加密、去标识化、访问控制、审计日志、应急预案、定期合规审计。**免费档 24 小时日志 + 无 SLA** 与「可审计」要求存在明显张力。
   - 委托处理（第 21 条）需约定处理目的、期限、方式、保护措施与双方权责。
3. **GDPR**（若涉及欧盟数据主体）：你通常是 **controller**、Cloudflare 通常是 **processor** → 需要 Art.28 处理者协议、Art.30 处理活动记录、Art.32 技术与组织措施、以及跨境传输机制（SCC / 充分性决定）。Access 日志中的邮箱与 IP 是个人数据；**24 小时保留**既降低了暴露面，也可能不满足你自己的问责（accountability）举证需要。
4. **Cloudflare 自己的条款红线**（§1.4 已核实）：**Free Services 上不得处理/收集支付卡信息**（ToS 2.2.1(h)）；**PHI（受保护健康信息）需书面同意**（(i)）；不得提供 VPN/代理服务（(j)）。→ **人才库/简历类个人数据可以，但支付卡与健康信息不要走这一层。**
5. **落地建议**：真实个人信息库优先做到「**具体少数人 + 强身份 + 有审计**」：Access 白名单（实名邮箱）+ 应用层鉴权 + 源站 JWT 校验 + 自建审计日志；如果合规压力大，**干脆不挂公网**，改用内网方案（Tailscale/ZeroTier 等）；对外只发布**脱敏/聚合**的只读视图。

> ⚠️ 以上是工程视角的要点提示，**不是法律意见**。涉及真实个人信息出境/委托处理前，请让法务/合规同学确认。

### 3.7 出事了怎么紧急下线（一条命令 / 一个按钮）

**最快（本机一条命令，秒级生效）**
```powershell
# PowerShell：杀掉 cloudflared → 隧道连接断开 → 公网立刻不可达
Get-Process cloudflared -ErrorAction SilentlyContinue | Stop-Process -Force
```
```bat
:: CMD 等价写法
taskkill /IM cloudflared.exe /F
```
- 若是 Quick Tunnel：杀进程即彻底失效（URL 不可恢复）。
- 若由启动文件夹里的 `.cmd` 拉起：**关掉那个控制台窗口**同样有效；这也提醒你——**把它做成一个看得见、关得掉的窗口**，而不是隐藏后台进程，便于「一关就断」。

**彻底（面板，1 分钟）**
1. **Networking > Tunnels** → 选中隧道 → **Delete**（删除隧道后连接立即失效）。
2. 删除对应 DNS 记录（指向 `<UUID>.cfargotunnel.com` 的 CNAME），否则域名会指向黑洞。
3. 远端管理模式若怀疑 token 泄露：**Rotate token**（注意：官方说明**已存在的连接在重启前仍然有效**，所以要配合「删连接」或直接删隧道）。
4. 本地管理模式（有 `cert.pem` 时）：
   ```powershell
   cloudflared tunnel cleanup <NAME>     # 清理僵死连接
   cloudflared tunnel delete -f <NAME>   # 强制删除隧道
   ```
   （`-f` 是官方文档给出的「无条件删除」标志。）

**Zone 级熔断（还想保住域名/其它服务时）**
- **Security > Settings > Under Attack Mode**（I'm Under Attack）——一键对所有访问加挑战。
- 或临时把该子域 DNS 记录改为 **DNS only / 删除**。

**建议**：把 §3.7 的命令抄成一张纸贴在显示器旁；并预先确认「我知道哪个窗口/哪个进程是隧道」。

## 4. 本机 runbook（逐步命令 + 必须人工完成的步骤）

> 约定：`$cf = "$env:USERPROFILE\cloudflared"`，`$exe = "$cf\cloudflared.exe"`。
> 所有命令**均不需要管理员权限**。涉及面板的步骤用 **【人工】** 标注。

### Step 0 — 建工作目录（不需要管理员）

```powershell
$cf  = "$env:USERPROFILE\cloudflared"
$exe = "$cf\cloudflared.exe"
New-Item -ItemType Directory -Force -Path $cf | Out-Null
New-Item -ItemType Directory -Force -Path "$cf\logs" | Out-Null
```
不要用 `C:\Program Files`（无管理员写不进去）。

### Step 1 — 用 Python urllib 下载 `cloudflared.exe`

**确切下载 URL（已在官方 Downloads 页核实，并已实测可下载）**
- 64 位（本机应选这个）：<https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-amd64.exe>
- 32 位：<https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-386.exe>
- 来源：<https://developers.cloudflare.com/tunnel/downloads/>（Windows 表格）

**我的实测证据（2026-10-09）**
- `GET` 该 URL 带 `Range: bytes=0-63` → **HTTP 206**，`Content-Range: bytes 0-63/55365048`，`Content-Type: application/octet-stream`，`Last-Modified: Mon, 05 Oct 2026 17:44:20 GMT`，前两字节 `MZ`（有效 PE 可执行文件）。
- GitHub API `releases/latest` → `tag_name = 2026.10.0`，`published_at = 2026-10-05T17:43:45Z`；资产 `cloudflared-windows-amd64.exe` 大小 **55,365,048** 字节（与 Content-Range 一致）。

**下载命令（先直连；本机实测直连可用）**
```powershell
$env:HTTP_PROXY  = ""
$env:HTTPS_PROXY = ""
@'
import urllib.request, os, hashlib
dst = os.path.join(os.environ["USERPROFILE"], "cloudflared", "cloudflared.exe")
url = "https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-windows-amd64.exe"
print("GET", url)
req = urllib.request.Request(url, headers={"User-Agent": "Mozilla/5.0"})
h = hashlib.sha256(); n = 0
with urllib.request.urlopen(req, timeout=300) as r, open(dst, "wb") as f:
    while True:
        b = r.read(1 << 20)
        if not b:
            break
        f.write(b); h.update(b); n += len(b)
print("saved :", dst)
print("bytes :", n)
print("sha256:", h.hexdigest())
'@ | python -
```
- 期望 `bytes` = **55365048**（如果你下载时官方已发新版本，这个数字会变——**这很正常**；不要把它当成校验失败的判据，用 Step 2 的签名校验）。
- **若直连失败**（超时 / TLS 报错 / 被重置），再试代理（注意：**本机 7892 实测对所有 HTTPS CONNECT 返回 RST 或 SSL EOF，多半也不通**）：
  ```powershell
  $env:HTTPS_PROXY = "http://127.0.0.1:7892"
  $env:HTTP_PROXY  = "http://127.0.0.1:7892"
  ```
  仍失败就只能换网络（手机热点）或从另一台能上网的机器下载后拷贝过来。
- **关于镜像**：Cloudflare 官方 Downloads 页对 Windows **只给出 GitHub 链接**，`pkg.cloudflare.com` 是 Linux 的 deb/rpm 仓库。→ **没有官方非 GitHub 镜像**（这点我核实过）。
- **不要下 MSI**：MSI 安装会写 `Program Files` 并装服务，**需要管理员**，与本机约束冲突。用裸 `.exe`。

### Step 2 — 校验完整性（**没有官方 SHA256 文件，用 Authenticode 签名**）

**已核实的事实**：
- 该 release 的资产清单里**只有** `cloudflared-windows-386.exe` / `cloudflared-windows-amd64.exe` / `cloudflared-windows-386.msi` / `cloudflared-windows-amd64.msi` —— **没有** `.sha256`、`.sha256sum`、`SHA256SUMS`、`sha256sums.txt`、`checksums.txt`、`.sig`。我逐个探测了这些候选 URL，全部失败。
  → **Cloudflare 不为 Windows 二进制提供官方 SHA256 文件**（至少这个 release 没有）。
- 官方提供的是 **Windows 代码签名**。我把 exe 下载到内存后解析了 PE 的 `IMAGE_DIRECTORY_ENTRY_SECURITY`：
  - 存在 Authenticode 签名表（**11,912 字节**，`WIN_CERTIFICATE` revision `0x200`、type `0x2`）；
  - 签名者 CN：**`Cloudflare, Inc.`**；
  - 证书链：**`DigiCert Trusted G4 Code Signing RSA4096 SHA384 2021 CA1`** → DigiCert 根；
  - 含 **DigiCert 时间戳**（`DigiCert Trusted G4 TimeStamping RSA4096 SHA256 2025 CA1`）。

**验证命令**
```powershell
$sig = Get-AuthenticodeSignature $exe
$sig.Status                        # 期望：Valid
$sig.SignerCertificate.Subject     # 期望：包含 CN=Cloudflare, Inc.
$sig.TimeStamperCertificate.Subject # 期望：DigiCert 时间戳
Get-FileHash $exe -Algorithm SHA256 # 记录下哈希，便于将来比对/上报
```
- 注意：`Get-AuthenticodeSignature` 需要联网做吊销检查；本机代理异常时可能返回 `UnknownError`。此时**至少**确认 `Subject` 含 `CN=Cloudflare, Inc.`，并记录哈希；网络恢复后再复核。
- 也顺手确认文件是 PE 而不是 HTML 错误页：
  ```powershell
  (Get-Item $exe).Length
  [System.Text.Encoding]::ASCII.GetString((Get-Content $exe -Encoding Byte -TotalCount 2))
  ```
  （期望长度 ≈55 MB，头两字节 `MZ`。）

### Step 3a — Quick Tunnel 试跑（**仅供短期演示**，含邮箱白名单）

```powershell
& $exe tunnel --url http://127.0.0.1:8082 --allowed-mail you@example.com
```
- 输出里会打印 `https://<随机串>.trycloudflare.com`。
- **已核实的限制**：每次重启换域名；200 并发上限（超出 429）；不支持 SSE；邮箱认证需浏览器交互；无 uptime 保证；进程退出访问即结束；会话最长约 4 小时。
- **不能**给它加 Cloudflare Access 策略（§1.1）；改白名单＝停掉重开＝**换域名**。
- 这个模式**只适合**「给某个人看几分钟」，不适合承载真实个人信息。

### Step 3b — Named Tunnel（推荐路径）

#### 路径 A：远端管理（最省事，**不需要 `cert.pem` / `config.yml`**）

**【人工】1. 建账号与组织**：注册 `dash.cloudflare.com` → 开 2FA → **Zero Trust** → 选 **Free** 计划（要填付款信息，不扣费）→ 建团队名。

**【人工】2. 先建 Access 应用**（顺序很重要，见 §3.2）：Zero Trust > Access controls > Applications > Create new application > Self-hosted and private → Add public hostname（选你的子域）→ 策略 `Allow / Include / Emails` → 勾 One-time PIN → 设 Session Duration → Create。
（此时还没有隧道，hostname 暂时打不开，这是正常的。）

**【人工】3. 建隧道并取 token**：**Networking > Tunnels > Create a tunnel** → 类型选 Cloudflared → 命名（如 `medtalent-portal`）→ 保存 → 复制 **token**（`eyJ...` 长串；文档说明 token 就在安装命令里）。

**【人工】4. 加路由**：同一隧道 → **Routes > Add route > Published application** → 子域 + 域名 → Service URL = **`http://127.0.0.1:8082`** → Add route。
（**只加这一条**；不要加 CIDR 路由。）

**5. 本机运行（无需管理员）**——把 token 存文件，避免进命令行历史：
```powershell
# 把 token 写进文件（粘贴后回车；用 ascii 无换行，避免 --token-file 解析问题）
Set-Content -Path "$cf\tunnel-token.txt" -Value (Read-Host "粘贴 Tunnel Token") -NoNewline -Encoding ascii

# 收紧权限（无需管理员，只要你是文件属主）
icacls "$cf\tunnel-token.txt" /inheritance:r /grant:r "$env:USERNAME:F"
icacls $cf /inheritance:r /grant:r "$env:USERNAME:(OI)(CI)F"

# 运行
& $exe tunnel --no-autoupdate --log-directory "$cf\logs" run --token-file "$cf\tunnel-token.txt"
```
- `--token-file` 需要 `cloudflared >= 2025.4.0`（官方 Run parameters 页标注）；当前 **2026.10.0** 满足。若报错，退回 `--token <TOKEN>`。
- Windows 上**不会自动更新**（官方明确），`--no-autoupdate` 只是把意图写清楚；请定期手动 `cloudflared --version` 并重新下载。

#### 路径 B：本地管理（CLI 全流程）

```powershell
# 1) 登录：会打开浏览器，选你的域名授权 → 生成 %USERPROFILE%\.cloudflared\cert.pem
& $exe tunnel login

# 2) 建隧道：生成凭据文件 %USERPROFILE%\.cloudflared\<UUID>.json
& $exe tunnel create medtalent-portal
& $exe tunnel list

# 3) 建 DNS 路由（生成指向 <UUID>.cfargotunnel.com 的 CNAME）
& $exe tunnel route dns medtalent-portal portal.example.com

# 4) 写 config.yml（见 §3.1 的 ingress；只放 :8082）
notepad "$env:USERPROFILE\.cloudflared\config.yml"

# 5) 校验并运行
& $exe tunnel ingress validate
& $exe tunnel run medtalent-portal
```
- **默认目录**：`%USERPROFILE%\.cloudflared`（官方 Useful terms 页）。
- **`cert.pem` 有效期至少 10 年**（官方原文），且**能创建/删除隧道、改 DNS**；凭据 JSON 文件「functions as a token authenticating the tunnel」。
  → 两者都必须保护：
  ```powershell
  icacls "$env:USERPROFILE\.cloudflared" /inheritance:r /grant:r "$env:USERNAME:(OI)(CI)F"
  ```
  （不需要管理员，因为目录在你自己的 profile 下。）
- 如果后来想改成远端管理模式，两套凭据不要同时散落：把不用的 `cert.pem` / 凭据 JSON / token 文件清理掉（官方文档：token 泄露时用 `Rotate token`；`cert.pem` 里的服务令牌「valid until revoked」）。

### Step 4 — 做成「登录自启」（**不能用 `schtasks`**）

本机已知 `schtasks /Create` 被拒；官方 Windows 服务方案又明确要求 **管理员 CMD** + 改 `HKLM` 注册表 → **都不可用**。用启动文件夹：

```powershell
# 打开启动文件夹（等价于 Win+R 输入 shell:startup）
explorer "$env:APPDATA\Microsoft\Windows\Start Menu\Programs\Startup"
```

在该目录新建 **`medtalent-tunnel.cmd`**：
```bat
@echo off
title medtalent-tunnel  (close this window to take the site offline)
set HTTP_PROXY=
set HTTPS_PROXY=
"%USERPROFILE%\cloudflared\cloudflared.exe" tunnel --no-autoupdate --log-directory "%USERPROFILE%\cloudflared\logs" run --token-file "%USERPROFILE%\cloudflared\tunnel-token.txt"
pause
```
- 本地管理模式把最后一行换成：`... tunnel --config "%USERPROFILE%\.cloudflared\config.yml" run medtalent-portal`
- **注意**：启动文件夹只在**用户登录后**触发；机器重启后要登录一次才会上线。真正无人值守需要管理员权限装服务（本机做不到）。
- `title` 里写明「关掉窗口＝下线」，配合 §3.7 的紧急下线。
- 如果你更希望先手动验证再自启，可以先放一个 `.cmd` 在桌面手动双击，跑通后再复制进启动文件夹。

### Step 5 — 验证「公网真的能打开，且只有被允许的人能打开」

1. **隧道健康**（本机）：
   ```powershell
   & $exe tunnel info medtalent-portal      # 本地管理
   ```
   远端管理模式看面板 **Networking > Tunnels** 是否为 `Healthy`。
2. **公网可达性——必须用另一条网络**：手机 **关 Wi-Fi、用 4G/5G** 打开你的 URL。
   > 为什么强调：同一 Wi-Fi 下能打开，不能证明公网能开（可能命中了本地 DNS/缓存/回环）。这是最容易自欺的一步。
3. **门禁验证（三连测）**：
   - **未登录**：应看到 **Cloudflare Access 登录页**，**不是**你的门户页面。
   - **非白名单邮箱**：输入一个不在名单里的邮箱 → 应被拒（官方博客：访客只得到不透露名单信息的通用响应）。
   - **白名单邮箱**：收到一次性 PIN → 能打开门户 → 去 **Zero Trust > Insights > Logs > Access authentication logs** 应看到本次登录记录（`Allow=true`）。
     ⚠️ 记住**只有 24 小时**（§3.5），别指望明天还能翻到。
4. **反证测试（证明没多开端口）**：
   ```powershell
   Get-NetTCPConnection -State Listen |
     Where-Object { $_.LocalPort -in 8081,8082,8083,55432 } |
     Select-Object LocalAddress,LocalPort
   # 期望：LocalAddress 全部为 127.0.0.1（不能出现 0.0.0.0 / ::）
   ```
5. **未授权直连测试**（用 Python，不依赖 curl）：
   ```powershell
   @'
   import urllib.request, urllib.error
   u = "https://portal.example.com/"   # 换成你的真实地址
   try:
       r = urllib.request.urlopen(urllib.request.Request(u, headers={"User-Agent": "Mozilla/5.0"}), timeout=30)
       print("status:", r.status, "url:", r.geturl())   # 期望：被 Access 拦到登录页，或 403
       print("body[:200]:", r.read(200))
   except urllib.error.HTTPError as e:
       print("HTTPError:", e.code, e.headers.get("location"))  # 期望 302/403
   '@ | python -
   ```
   期望：**看不到门户内容**（302 到 `*.cloudflareaccess.com` 或 403），而不是 200 + 你的页面 HTML。
6. **确认只有被允许的人**：临时把白名单里的邮箱删掉/改掉，用一个"以前的"邮箱再测一次 → 应被拒。这一步能证明策略真的在起作用，而不是「其实谁都能进」。

### Step 6 — 可选加固（做完再上线更稳）

- Access **Session Duration** 调短（8h 或更短）。
- 若身份源支持，开启 **独立 MFA**（Access 的 `Authentication Method` / independent MFA）。
- 配 1 条免费速率限制规则（§3.4）。
- 若 `:8082` 本身没有登录：**优先补一个应用层口令**（第 2 层防御），或明确记录"仅靠 Access"的残余风险。
- 开启 Tunnel 的 **`Protect with Access`**（源站校验 Access token），或用反向代理校验 JWT（第 3 层防御）。
- 建一个「审计日志导出」的小脚本（每 <24h 拉一次 Access logs），因为免费档只留 24 小时。
- 记录版本与哈希：`cloudflared --version`、`Get-FileHash $exe`。

## 5. 明确不推荐的方案（以及理由）

1. **把数据库端口 `:55432` 暴露出去**（无论做成 TCP 路由还是 CIDR 路由）。理由：数据库线协议直接面对公网＝把暴力破解、弱口令、已知 CVE 扫描全部请进门；隧道不提供 SQL 层任何保护；一旦被拖库，损失不可逆。
2. **暴露 `:8083`（可写开发者模式）或 `:8081`（业务控制台）**。理由：写权限 + 无强认证 = 数据被篡改/删除；开发者模式通常校验最松、调试接口最多。
3. **用 Quick Tunnel 长期承载真实个人信息**。理由（全部已核实）：域名每次重启都变（无法稳定白名单/无法做审计）；无 uptime 保证；200 并发上限；不支持 SSE；**不能挂 Cloudflare Access 策略**；`--allowed-mail` 只是演示级门禁（授权清单在本机、进程退出即失效、改名单要换域名）。
4. **「我在应用里自己写个登录就算安全了」**。理由：单层认证；没有边缘限流/DDoS 防护/统一审计，口令一旦泄露无第二道门。正确姿势是 **Access（谁进来）+ 应用鉴权（进来干什么）+ 源站 JWT 校验（防绕过）** 三层。
5. **把 `127.0.0.1` 改成 `0.0.0.0`「图方便」**。理由：直接把服务暴露到局域网/校园网，绕过一切公网侧防护，并破坏项目既有的信任边界。
6. **用免费版当文件/视频 CDN 分发**。理由：Service-Specific Terms 的 CDN 条款明确保留「对 video / disproportionate percentage of pictures, audio files, or other large files 禁用或限流」的权利，且没有公布阈值——随时可能被掐。
7. **在 Free Services 上处理支付卡信息或健康信息（PHI）**。理由：ToS 2.2.1 **(h)** 明确禁止在 Free Services 的 web property 上 `process or collect personal or business credit card information`；**(i)** 要求 PHI 需 Cloudflare 书面同意。
8. **依赖「URL 保密」当安全措施（security by obscurity）**。理由：`trycloudflare.com` 子域会被扫描；自有子域会出现在证书透明度日志；而免费版 Access 日志只留 24 小时，出了事根本追溯不了。
9. **用 Tailscale Funnel 作为本机方案**。理由：Windows 上需要安装 Tailscale 客户端（系统级组件/服务，实际需要管理员权限——**官方文档未见明文，此点为推断，标注未能核实**）；且 Funnel 只在 **443 / 8443 / 10000** 监听、只能用 `*.ts.net` 域名、**本身公开给整个互联网且无内置身份认证**、还有 `non-configurable bandwidth limits`。
10. **直接端口转发 + DDNS**。理由：无管理员不能改入站规则；家宽/校园网多半无公网 IPv4（CGNAT）；运营商普遍封 80/443；且会把真实 IP 暴露给攻击者。
11. **在同一台机器上再开一个「公网版」服务、把数据复制一份出去**。理由（工程角度）：数据副本会脱离现有访问控制与审计；如果非要对外，优先只发布**脱敏/聚合**视图，只读、且限定字段。**注意这是建议，不是合规结论。**
